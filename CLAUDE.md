# Canopy Web

Collaborative web workspace for the canopy agent ecosystem — first-class AI agents, demo-driven development (DDD), walkthroughs, and shareouts.

> **How to write this file.** It is loaded into every session, so it holds only the current state an agent needs before it knows what it is working on: how to run, test and ship, and the invariants nothing may break — each as a rule plus a pointer. Subject detail goes in `docs/architecture/<topic>.md` (index below). History — what something replaced, what broke, when, who decided — goes in the PR description, not here or in the topic docs. `tests/test_claude_md_budget.py` fails above 60k characters or on a date or PR reference.

## Architecture

- **Backend:** Django 6 ASGI + uvicorn, Django Ninja 1.x + Pydantic v2, PostgreSQL (shared labs RDS, `canopy_web` DB). OpenAPI 3.1 at `/api/openapi.json` (Scalar at `/api/docs/`, Redoc at `/api/redoc/`). Errors are RFC 7807 `application/problem+json`. Frontend types are generated from the schema into `frontend/src/api/generated.ts` and consumed via `openapi-fetch`.
- **Frontend:** React 19 + Vite + Tailwind CSS 4 + shadcn/ui; shared kit in `frontend/packages/canopy-ui`.
- **AI:** canopy-web makes **no model calls of its own**. Every agent turn, chat reply and review runs on a **runner**, in an agent CLI (Claude Code or Codex, `apps/harness/clis.py`) under that box's login for it (`/supervisor` → Runners).
- **MCP:** `apps/mcp/` (FastMCP, Streamable HTTP, mounted at `/api/mcp/` in `config/asgi.py`) exposes every REST route as a tool, run in-process as the caller (OAuth or PAT) → `docs/architecture/mcp-surface.md`. Every project's toolbox is served through one fixed set of tools at `/api/mcp/projects/` (`apps/mcp/project_gateway.py`); never wire a project's own server into an agent's plugin → `docs/architecture/work.md`.
- **Framework/product boundary:** framework apps never import product apps; product imports framework freely. Every app's tier is in `ARCHITECTURE.md` and in `FRAMEWORK`/`PRODUCT` in `tests/test_architecture_boundary.py` — a new app must be tiered in both. Inside the framework, apps are layered (kit → core → features) and an import points only down; today's upward imports are a shrink-only ratchet in `tests/test_layered_app_imports.py` → `ARCHITECTURE.md` § Layers inside the framework.
- **Deployment:** one container (Django serves SPA + API + MCP) on AWS ECS Fargate in the shared labs account, at `https://canopy.dimagi.com/`. Merging does NOT deploy: `gh workflow run "Deploy to Labs (AWS)" --ref main` (main only; migrations run automatically; CloudFormation owns the task def + service — never `ecs update-service` by hand).
- The old address `labs.connect.dimagi.com/canopy/` still serves machine traffic (API, WS, OAuth, health) in place and 302s browser pages to canopy.dimagi.com — don't turn machine paths into redirects; docs must name the new address (`tests/test_old_address_in_docs.py`).
- **IAM:** canopy-web's deploy role must trust the IMMUTABLE OIDC subject `repo:dimagi-internal@272902307/canopy-web@1193139337:ref:refs/heads/main` (name-based silently fails); never attach `SecretsManagerReadWrite` to the shared task-execution role. → `docs/architecture/deploy.md`

## Development

Backend uses [`uv`](https://docs.astral.sh/uv/) (`uv.lock` is committed).

```bash
cp .env.example .env
uv sync --extra dev
uv run python manage.py migrate
uv run python manage.py runserver
cd frontend && npm install && npm run dev      # frontend
uv run honcho start -f Procfile.dev            # both
docker compose up                              # backend + frontend + Postgres

gh workflow run "Deploy to Labs (AWS)" --ref main                          # deploy (migrations run automatically)
gh workflow run "Deploy to Labs (AWS)" --ref main -f skip_migrations=true  # EMERGENCY ONLY
```

**Migrations:** write them the obvious way. Drops, renames and type changes need no expand/contract split; a brief window of errors during a deploy is accepted. One exception, because it fails the deploy rather than erroring briefly: a `RunPython` that **deletes or updates rows other tables reference** goes in its own migration, ahead of any schema change to those tables. PostgreSQL queues deferred FK trigger events for those rows and then refuses the ALTER in the same transaction ("pending trigger events"); SQLite and CI's empty Postgres test DB never see it, because there are no rows to touch.

**A data migration's test lives until its migration deploys.** One that walks the graph back (`MigrationExecutor.migrate(BEFORE)`, marked `needs_migrations`) costs more with every later migration, and once the migration has run in production it guards nothing; delete it in a later PR once a deploy includes it. `tests/test_migrations_apply.py` stays: it proves the whole graph applies to an empty DB.

## Testing and shipping

```bash
uv run pytest                                    # all backend tests
uv run pytest tests/test_agents.py -v            # one file
cd frontend && npm run build                     # frontend type check + build
cd frontend && npm run gen:api                   # regenerate TS types (backend on :8000), or gen:api:local
```

- **Changed an `apps/**/schemas.py` or `api.py` — including a route docstring, which is published as the OpenAPI description — regenerate `generated.ts` and commit it.** The required `Backend tests` check fails on a stale one. Put maintainer rationale in `#` comments, not docstrings.
- **Every PR: `gh pr merge <n> --auto`, with NO strategy flag** (`--squash` leaves auto-merge unarmed — the merge queue owns the strategy). Confirm with `gh pr view <n> --json autoMergeRequest`.
- **A queue failure ejects the PR and disarms auto-merge** (your checks green, `autoMergeRequest: null`): check `gh run view <queue-run> --log-failed`, then re-arm with `gh pr merge <n> --auto`.
- **Confirm what deployed** — deploys aren't ordered by commit: `gh run list --workflow="Deploy to Labs (AWS)" --limit 3 --json headSha,conclusion`, then check the feature is live (e.g. `/api/openapi.json`). Ruleset/queue settings → `docs/architecture/deploy.md`
- **Bump the version when you change published package source.** Changing `frontend/packages/{canopy-ui,canopy-client}/src` or `sdk/python/src` without a version bump fails a required CI check, and merging the bump publishes the release. Never scope the npm names (`@canopy` belongs to someone else). → `docs/architecture/embedding-internals.md`

## Key URLs

Every page, what it is for and how it behaves: **`docs/architecture/pages.md`**. Routes: `frontend/src/router.tsx` (SPA), `config/urls.py` (server).

- **Tenant data lives under `/w/:workspace/`**; root holds personal/global pages, pre-tenant pages (invite, first run), redirects and the public site. Any route outside `/w/` carries its reason (`flat` on its descriptor, or `NOT_PAGES` for a redirect), checked by `frontend/src/routeTenancy.test.ts`.
- **One URL per artifact, nothing forwarded** — except `/w/<ws>/review/<id>`, which forwards a narrative review to its storyboard (`apps/reviews/views.py`, `docs/architecture/pages.md`). Flat `/walkthrough/`, `/review/`, `/share/`, `/storyboard/`, `/narrative/`, `/ddd-release/` are a plain 404 (`config/views.py::flat_artifact_gone`). Build links with `scoped_path` / `useScopedPath` — no flat fallback.
- **One registry of pages: `frontend/src/guide/surfaces.ts`.** A new page needs a descriptor there (the `/guide` coverage test fails without one), saying where it lives (`home`/`group`/`flat`); the guide, the workspace switcher and the tenancy test read it → `docs/architecture/pages.md`.

**The shape of the app** (the full list, with what each page is for, is `docs/architecture/pages.md`; the registry is `frontend/src/guide/surfaces.ts`):
- `/w/:workspace/…` is the tenant shell: agents (`agents/:slug`), projects (`projects/:handle` is a project's ONE page; an idea is a task with `kind: "idea"`), tasks and triage, sessions and huddles, schedules, activity, health, analytics, runners and vaults (one page each, `components/objectPage/`), workspace apps, views, MCP servers, mail, approvals, sign-offs, and `settings/<section>`. `marketplace.json` and `plugins/…` under a workspace are retired (410).
- Public with a token (the only `/w/` pages anonymous visitors reach, `apps/common/middleware.py::_SCOPED_VIEWER`): `walkthrough/:id` (+ `/content`), `review/:id`, `share/:token`, `storyboard/:slug`, `narrative/:slug?b=`, `ddd-release/:narrative/:runId`.
- Root: `/` is the public product site (Astro, `site/`, `config/public_site.py`); `/app` is the way into the app (`LOGIN_REDIRECT_URL`); `/home` is what waits on you across workspaces (`/api/me/attention/`); `/supervisor` and `/ide` are the cross-fleet and desktop-IDE views; `/settings/<section>` is your account; `/plugins/marketplace.json` is your agents as ONE Claude Code catalog (`docs/architecture/plugin-marketplace.md`); personal approval pages (`/pair/:code`, `/act-as/:requestId`, `/confirm/page-permission/:grantId`), `/invite/:token` and `/new-workspace` are pre-tenant or personal.
- `/api/` is REST (`/api/docs/`), plus `/admin/` and `/health/`.

## API

Every route with its behaviour: **`docs/architecture/api-surface.md`**; machine-readable: `/api/openapi.json`.

- All routes are Django Ninja on the single `NinjaAPI` in `apps/api/api.py`; request/response models live in `apps/<app>/schemas.py`, routes in `apps/<app>/api.py`.
- The canonical tenant URL is `/api/w/{ws}/…` (`apps/api/tenancy.py::WorkspaceResolveMiddleware` gates membership, strips the prefix, reroutes to the flat mount); a flat `/api/…` list spans the caller's workspaces only within one tenant tree (else 422 `workspace-required`) → `docs/architecture/roles.md` § A read that names no workspace stays inside one organisation.
- **A page about the person, not one workspace (Home, Supervisor, `/ide`), reads a user-level view `/api/me/<list>/`**: the list run once per organisation (`wsvc.each_organisation`), never a client loop over pins → `docs/architecture/roles.md` § A user-level view.
- Bare Django views (session/cookie/redirect work, Range streaming) are matched in `config/urls.py` before the Ninja catch-all: `/api/csrf/`, `/api/debug/mint-session/`, the retired `/api/agents/<slug>/interface…` (410), `/auth/cli/authorize/`, `/health/`, `/runner-app/` (the runner desktop window's home, `apps/harness/views.py`), and `/w/<ws>/walkthrough/<id>/content` (`apps/walkthroughs/streaming.py`, the only Range-streaming view); OAuth/HCP/Slack/embed endpoints are bare views too (`/oauth/…`, `/api/hcp/oauth/…`, `/api/slack/…`, `/embed/…`).

## Invariants

Each is enforced or load-bearing across the codebase; the pointer says where.

**Tenancy and identity**
- **Never a NULL-means-allow tenant.** `Agent.workspace` is NOT NULL; don't re-nullable it or write `if row.workspace_id and <check>` anywhere — a row with no workspace is visible to nobody. → `docs/architecture/tenancy.md`
- **One workspace authorizer.** Only `apps/workspaces/services.py` decides membership (`member_role`/`is_member`/`membership`); a `WorkspaceMembership` read filtered by workspace AND user elsewhere fails CI (`# authz-exempt: why` for questions about a target). → `tests/test_workspace_authorizer_is_sole_gate.py`
- **Only `services._grant`, `ensure_member` and workspace creation may create a `WorkspaceMembership`** — never as a side effect of a read or a write. → `apps/workspaces/tests/test_access_requests.py`, `tests/test_no_implicit_enrolment.py`
- **A write names its workspace.** Creates resolve via `wsvc.creation_workspace` (pinned, else sole membership, else 422 `creation_refusal`) then still check `CONTENT_WRITE`; links via `links.scoped_url`, never `build_absolute_uri`. → `tests/test_nothing_outside_a_workspace.py`
- **Two principals, two types.** A contact (`ContactToken`) is anonymous to Django and reaches only `/api/contact/`; recording a contact grants nothing; no shared-secret-plus-email route — a site speaks for someone only by signed assertion. → `tests/test_contact_surface_is_bounded.py`, `tests/test_contacts.py`
- **A sensitive conversation's words are sealed to its people, and canopy-web cannot decrypt them.** `Message.sealed` is sealed to the conversation's own key, whose private half exists only wrapped to each person's vault key (`canopy_sessions.conversation_keys`); the ciphertext goes out only through `harness.sensitivity.reads_content` / `readable` (its own people, on its chat surfaces) and their browser decrypts it. Never add a server-side decrypt; every other reader gets the metadata columns. → `docs/architecture/tenancy.md` § Sensitive conversations, `tests/test_sealed_words_have_one_gate.py`
- **`Agent.slug` is globally unique** (it is the Slack slash command); don't make it per-workspace. **Uploaded HTML is never `allow-same-origin`.** → `docs/architecture/tenancy.md`
- **Rolling sessions:** every request writes the session, so a view catching `IntegrityError` needs its own `transaction.atomic()` savepoint. → `docs/architecture/tenancy.md` § Rolling sessions

**Access**
- **Nothing outside `apps/workspaces/` names a role.** Gate on a workspace permission with `perms.can(user, ws, perms.X)` (`apps/workspaces/permissions.py`); every route declares its gate at the route, `@gate(...)` directly above its `def` (vocabulary in `apps/api/route_gates.py`). → `tests/test_roles_named_only_in_workspaces.py`, `tests/test_every_route_declares_its_gate.py`, `docs/architecture/roles.md`
- **One rule decides what a person may make an agent do: `apps/agents/turn_context.resolve_turn_context`.** Ask it; never write a second predicate. Who has which role (a role is a named bundle of the fixed permissions `read`, `write`, `agent_edit`, `use:<site>`: the built-ins read_only, read_write and editor, plus any a workspace defines as `AgentRole` rows; owner and admin are fixed in `apps/agents/roles.py` and are never lines) is the agent's access list (`apps/agents/grants.py`) plus the default lines of its workspace; nobody is let in by being in the workspace, and a connected site (a confined profile an agent offers on one site) never says who may use it — a line names a role, or that one connected site. `read_only` opens read mode on every agent. A line grants its role's ROW, so editing a role changes its holders; **never branch on a role's name (`permissions` is the contract), never let a role hold `admin`/`own`, and the rails are by permission (an address-only line can never hold a role that drives or changes the agent)** — define roles only through `roleadmin`. → `tests/test_access_matrix.py`, `tests/test_agent_roles_api.py`, `docs/architecture/access.md` § Configurable roles
- **Read mode is the default confined profile for `read`, on every agent with no setup**: canopy's profile (`interface.default_read_profile`, pinned exactly by `tests/test_default_read_profile.py`, the agent's own read mode replaces it whole; its stored name `ask` lives only in `interface_default.READ_MODE_STAMP`). **An agent's session reads inside a turn are bound to the turn's verified asker** (`canopy_sessions.access.review_grantors`; a turn with no verified asker reads nobody's). → `docs/architecture/access.md`, `tests/test_agent_session_reads_bind_to_the_asker.py`
- **A view judging many (person, workspace/agent) pairs reads the facts once** — `perms.slugs_with` (one person), `wsvc.member_roles_of` / `access.Standings` (many) — and asks the one rule with them; never `member_role`/`perms.can`/`is_admin`/the rule per pair in a loop. → `docs/architecture/roles.md` § A view that judges many pairs reads once, `tests/test_bulk_authz_parity.py`
- **An agent turn's caller token reads as its asker only as far as the agent is in it** (`access.turn_reach`, REST and MCP): its own conversation and sessions with that agent; a repo chat's token is the person's own tool. **A one-session review's chat runs in canopy's `session_review` profile for everyone, owner included** (`turn_context._review_rule`): no login, no Bash, no tool but `read_asked_session`, never published, never forked. → `docs/architecture/access-sessions-and-people.md` § Asking a coach to review one session, `tests/test_session_review_asks.py`
- **An agent acts as itself — with its own credentials or ones a person delegated to it — or as you only under an act-as-you permission you granted** (a site's host grant, or canopy-web's own act-as grant in your turn). A delegated credential (a person's GitHub token) is a vault entry marked `delegated`, sealed only to the machines that run the agent and readable by no person — never settled under the vault key, never in a member's read, only in a runner resolve's `delegated` field (`credentials/accounts.py`); an agent turn's caller token only reads; an agent's login is always the account at its own email, linked only when that account's person accepts if someone has ever signed in to it (canopy creates it when there is none); no turn inherits the box's token. → `docs/architecture/access.md` § Whose authority an agent acts with
- **A project's vault opens to the project's people, never to its agents' access lists.** `vault_members` counts a project's lead and members (`project_members`), and its member agents only get the secret in their turns; a machine still needs its owner to be a member. Only its lead, an admin on it or a workspace owner changes the list, never an agent's login. → `docs/architecture/work.md` § A project's people
- **A token from canopy's own OAuth flow (Salesforce, Google; a provider is one module in `apps/connections/providers/`, its OAuth client a per-workspace `ConnectionApp` set up in Settings → Connections) is sealed to its owner, not held**: canopy-web exchanges the code at connect and seals the refresh token to the owner's vault key at once; it stores no readable token and never refreshes or revokes one. Machines the owner's signed grant statement allows refresh under a lease, write back, re-seal and revoke; the app client secret is the only connection secret that stays server-held. Pasted secrets stay in the zero-knowledge vault. → `docs/architecture/vault.md` § OAuth connections are sealed to their owner
- **An act-as-you permission (`HostGrant`) is usable only once the person confirmed it with their passkey**, for 30 minutes from that touch; a re-mint inherits the confirmation and its end, never extends it (`host_grants.confirm`/`_inherit`). Every reader spends a grant through `host_grants.live`/`lookup` or `host_gateway.context_for_grant`, which refuse an unconfirmed one. A contact has no passkey, so never holds one. → `docs/architecture/embedding-internals.md` § Act-as-you permissions, `tests/test_act_as_you_needs_a_passkey.py`
- **On canopy-web itself, an agent acts as you only under an `ActAsGrant`**: asked by its turn's own login for that turn's verified human asker (never one it names), approved with a passkey assertion made for that request in their browser, `read` or `write`, 30 minutes from the touch and never extended, dead when its turn and conversation (chat or laptop session) are over or someone else speaks there; the `cact_` token is returned once and reaches nothing in `act_as.EXCLUDED_*` — one list, asked by REST and MCP alike (`act_as.route_refusal`). → `docs/architecture/access-confinement-and-act-as.md` § Acting as the person on canopy-web, `tests/test_act_as_you_on_canopy.py`
- **One chat-session ACL.** Every entry point (REST, socket, MCP, Slack, push…) asks `apps/canopy_sessions/access.py`; opening a chat is never a grant. → `tests/test_session_acl.py`
- **A browser action that reveals or changes a secret needs a passkey step-up**: call `apps.passkeys.stepup.require_recent_step_up(request)` (403 `step_up_required`, which the SPA's API client answers with Touch ID and a retry — no per-page code), and declare it: `@gate(..., step_up=True)`, or `step_up="<why not>"` on a route carrying a secret (CI checks both ways). A token never steps up; decide per route whether it is refused or allowed. → `docs/architecture/api-surface.md` § Passkeys
- **A personal project is read only by its lead and its agents' logins**: `agents.services.project_read_q` / `may_read_project`, ANDed with the tenant scope; no role bypasses it, and an unreadable handle is a 404. A query over `AgentProject` or board `AgentTask` asks the rule or says why not. → `docs/architecture/work.md` § Personal projects, `tests/test_personal_project_never_leaks.py`
- **MCP is the REST API.** A new route is a tool automatically; secure it in the route, never by excluding it from MCP. → `docs/architecture/mcp-surface.md`
- **Every analytics fact goes through `apps.events.activity.emit`**; analytics reads only `Activity` + `SessionUsage` (tokens as each box reports them), never tables retention purges. → `docs/architecture/analytics.md`
- **Every settings change is audited by one plumbing.** Each write route's `@gate` says whether it is a setting (`setting=True`, recorded as a `SettingChange` in the same transaction, from every entry point) or not (`kind=` a `WRITE_KINDS` kind); never write a per-route audit, report before/after with `audit.note_change`. → `tests/test_every_route_declares_its_gate.py`, `docs/architecture/settings-audit.md`

**Runners**
- **Canopy is opt-in per repo, on the person's account (`ProjectOptIn`).** A box's repos are `Runner.project_names()` (what it holds ∩ what its owner opted into); file mirrored sessions and scope usage through it, never `capabilities["projects"]` directly; an agent's repo uses `observed_projects()`. **Repo work also asks which workspace:** `Runner.offers_project_in(repo, workspace)`, where the owner assigned each repo (`ProjectOptIn.workspaces`; unassigned means the box's home workspace), so enrolling a box in a tree carries no repo there. → `docs/architecture/runners.md` § Opted-in projects
- **A turn's agent CLI (`claude-code`/`codex`) is decided by `apps/harness/clis.py`** — its conversation, turn or schedule may choose one the agent is set up for (`refusal`), else the agent's default; the claim, coverage and `turn_reach` all ask `choose`, above the pin; a caller's turn runs only on a CLI the box confines, a conversation never changes CLI. → `docs/architecture/runner-routing.md` § Which CLI runs a turn
- **A runner serves its OWNER's workspaces, never `Runner.workspace`.** The tenant gate is `routing.runner_tenant_slugs` (owner's `agent.work` ∩ `RunnerEnrollment` coverage), shared by claim and schedules; a NULL owner fails closed → `tests/test_claim_schedule_parity.py`, `docs/architecture/runners.md`
- **A cloud runner serves one workspace tree, or one agent.** It enrolls in one root only (laptops may span); an agent's runner runs only its agent, and that agent runs on no other runner of its `machine_id` — `routing.serves_refusal`, asked above the pin and by the vault → `tests/test_runners_on_one_machine.py`, `docs/architecture/runners.md` § Several runners on one machine
- **A box runs an agent only if its owner is one of the agent's admins** (`agents.services.runner_may_hold_agent`) — claim, credential resolve, GitHub token, pins and routing writes all ask it. **No box holds a GitHub token**: a turn gets its agent owner's delegation, per turn, with no shared fallback (409 when absent; never for a confined turn). The one use outside a turn is the runner's own `git fetch`/`pull` of the agent's clone (`cloud_runner._clone_refresh_env`): that single git process, only while this box's fresh resolve still lists the delegation, never on a sensitive-data box, never in any turn's env, a file or a log. → `docs/architecture/runners.md` § Which agents a box may hold, `docs/architecture/runner-credentials.md` § The GitHub identity a turn gets
- **A runner signs in as itself, never with a person's PAT.** Its approved device key buys an hour-long `RunnerAccessToken` (`POST /api/runner-sessions/`) that opens the runner protocol only (`apps/harness/runner_auth.py`); a laptop pairs with a PAT; a cloud box pairs by invitation (`apps/harness/api_runner_invitations.py`: only the invitation's creator approves it, from a browser behind a passkey; no token can). Don't widen `runner_auth` to non-runner routes or hand the box credential to an agent turn. → `tests/test_keyless_runner_auth.py`, `docs/architecture/runner-credentials.md` § How a runner signs in
- **A WS control frame is a doorbell, never a mechanism.** Anything a runner must do (answer a menu, stop or close a session) gets a durable row it drains on its poll tick (`RunnerBinding.pending_answer`/`pending_interrupt`/`close_requested`) — a frame to a dead channel vanishes while the runner still reads ONLINE. → `docs/architecture/blocked-agent-menus.md`

**Chat**
- **Turn status is derived once, server-side** (`apps/harness/turn_status.py`); every channel renders it, never invents its own. A new socket frame needs an explicit passthrough in `apps/canopy_sessions/agui.py` or it is dropped silently. → `docs/architecture/chat-sessions.md`
- **Every session transition is one `session.*` event** (`apps/canopy_sessions/lifecycle.py`): a `save()` of a session's status, workspace or metadata and every `SessionParticipant` row are observed for free; a queryset `update()` of those columns calls `lifecycle.record_many` beside it. Ids only, never content. → `docs/architecture/chat-sessions.md` § A session's lifecycle is in the event log
- **A session's deleted words stay deleted.** `Session.content_deleted_at` is a tombstone every writer of a session's words honours (`transcript_ingest.refuses_ship` for what a runner ships), or the next ship restores what its person deleted; only that person, as themselves, may delete (`access.owns_words`). A new table holding what was said is placed in `tests/test_session_content_deletion.py`. → `docs/architecture/tenancy.md` § Deleting your own session's content
- **An agent chat's worktree project is `Session.emdash_project`, not `Session.project`** (blank for agent chats); send the bare `project` to a runner and it silently skips the session. → `docs/architecture/chat-sessions.md`

**Frontend**
- **Design tokens are the single source of truth: no raw Tailwind palette literals (`stone-*`, `red-*`, …) and no `dark:` variants** — use the semantic tokens (`bg-card`, `text-foreground`, `text-muted-foreground`, `success`/`warning`/`destructive`…). Token list + the one exception → `docs/architecture/frontend.md`
- APP UI: dense, readable, tables not cards.
