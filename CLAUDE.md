# Canopy Web

Collaborative web workspace for the canopy agent ecosystem — portfolio insights,
first-class AI agents, demo-driven development (DDD), walkthroughs, and shareouts.

## Architecture

- **Backend:** Django 5 ASGI + uvicorn, Django Ninja 1.x + Pydantic v2, PostgreSQL.
  OpenAPI 3.1 schema auto-generated at `/api/openapi.json`; Scalar UI at
  `/api/docs/`; Redoc at `/api/redoc/`. All errors return RFC 7807
  `application/problem+json`. Frontend TypeScript types are generated from the
  schema (`frontend/src/api/generated.ts`) and consumed via `openapi-fetch`.
- **Frontend:** React 19 + Vite + Tailwind CSS 4 + shadcn/ui
- **AI:** Anthropic Claude API via SSE streaming. Dual backend — direct API key (`AI_BACKEND=api`) or Claude Code CLI subscription (`AI_BACKEND=cli`), switchable at runtime via `/api/ai/switch/`.
- **MCP server:** `apps/mcp/` is a FastMCP 3.x Streamable-HTTP server mounted into the ASGI app at `/api/mcp/` (wired in `config/asgi.py`). Tools run **as the authenticated user** via per-user PAT (`CanopyPATVerifier`) and reuse the same service functions as the REST views, so the two surfaces can't drift. See `docs/architecture/mcp-surface.md`.
- **Deployment:** AWS ECS Fargate on the shared labs platform (account `858923557655`, `us-east-1`), served at `https://labs.connect.dimagi.com/canopy/` behind the shared ALB. One container (Django serves the built SPA + API + MCP). Deploys run from GitHub via the **Deploy to Labs (AWS)** workflow (`.github/workflows/deploy-labs.yml`): build → push to ECR (`labs-jj-canopy-web`) → migrate on a throwaway task def (idempotent; skippable only via `skip_migrations`) → create a change set (`aws cloudformation deploy --no-execute-changeset`) → deploy preflight (`deploy/aws/preflight.py`) asks IAM whether the deploying role may perform the actions this change set will call, naming the missing action instead of a 403 five minutes into a rollout → `aws cloudformation execute-change-set` registers the real task definition and rolls the ECS service (CFN owns both — see Design Decisions). The preflight gate **enforces** (since 2026-09-09): the deploy role now has `iam:SimulatePrincipalPolicy` and `cloudformation:ListChangeSets`, so it actually runs and blocks. It still degrades safely — a preflight that *cannot* run (exit 2) logs a warning and lets the deploy proceed, because a gate that cannot evaluate must not become an outage. The one thing that hard-fails is a failed `ListChangeSets`: mistaking it for "no changes" would produce a green deploy that shipped nothing. Those two grants are HAND-MADE on the shared role and tracked nowhere — moving them into a bootstrap stack is the outstanding work (`docs/superpowers/specs/2026-09-09-labs-iac-status.md`). **Since 2026-09-13 each deployment has its OWN deploy role** (`github-actions-{canopy-web,ace-web,connect-labs}-deploy`), generated by `deploy/aws/deploy_roles.py` and trusting exactly one repo, scoped to its own stack / secrets prefix / ECR repo / target group / log groups. The old shared `github-actions-labs-deploy` was assumable by six OIDC subjects (two of them personal-account repos) and held the union of all three deployments' permissions — connect-labs' CI could modify canopy-web's stack. It still exists but grants nothing, so a stray consumer fails with a named AccessDenied rather than a missing role. **canopy-web's role must trust the IMMUTABLE OIDC subject** (`repo:dimagi-internal@272902307/canopy-web@1193139337:*`) — the name-based form silently fails `AssumeRoleWithWebIdentity`; ace-web and connect-labs use the name-based form. Check with `gh api repos/dimagi-internal/<repo>/actions/oidc/customization/sub`. **The shared ECS task-execution role was scoped the same day**: `labs-jj-ecs-task-execution-role` had the AWS-managed `SecretsManagerReadWrite` attached, so every container's startup role could read, overwrite or DELETE every secret in the account (plus `lambda:CreateFunction`, `s3:GetObject`, `cloudformation:CreateChangeSet`). It now reads only via scoped inline policies covering the four prefixes the live task definitions actually reference — `labs-jj-*`, `canopy-web/*`, `ace-web/*`, `labs/*` (`labs/SENTRY_DSN` is the one `labs-jj-*` does not match, so detaching without it would have broken connect-labs' Sentry). Renaming the 34 unprefixed secrets is NOT needed and was rejected: there is no rename API, the 34 span four apps (12 are ace-web's, 3 umami's, 1 ace-mobile's), and neither ace-web nor connect-labs declares secrets in CFN — they reference pre-existing ARNs — so no deploy role needs a grant for them. Infra is provisioned by `deploy/aws/canopy-web.cfn.yaml` (CloudFormation). Runtime settings in `config/settings/connectlabs.py` (extends `production.py`; `FORCE_SCRIPT_NAME=/canopy`, shared RDS `canopy_web` DB).
- **Framework/product boundary (the one invariant):** apps split into **framework** (generic, agent-agnostic substrate — `agents`, `agent_runs`, `workspaces`, `api`, `common`, `timeline`, `tokens`, `session_sharing`, `issues`, `mcp`, `system`, `realtime` (Channels WS transport), `canopy_sessions` (multiplayer chat sessions), `events` (the fleet log of actions and errors), `inbound` (the push doorbell), `slack` (the Slack front door)) and **product** (canopy's own features — `projects`, `walkthroughs`, `reviews`, `shareouts`, `runs`). **Framework code must never import product code; product freely imports framework.** This keeps the blend cuttable (the framework apps could lift onto a standalone host without dragging canopy's product). It's a *direction, not a wall* — we don't move apps into `framework/`/`product/` folders. Enforced by `tests/test_architecture_boundary.py` (fails CI on a framework→product import, or on a new app left untiered). Full rationale, the per-app tier table, and the accepted carve-outs (the `api` composition root, the `mcp` insights tool): **`ARCHITECTURE.md`**. The framework apps are being harvested as the generic layer out of ACE — see `docs/superpowers/specs/2026-06-24-canopy-framework-harvest-design.md`.

## Development

Backend uses [`uv`](https://docs.astral.sh/uv/) for dependency management (uv.lock is committed). Install uv first if you don't have it: `curl -LsSf https://astral.sh/uv/install.sh | sh`.

```bash
# Backend
cp .env.example .env  # Set AI_BACKEND=api + ANTHROPIC_API_KEY, or AI_BACKEND=cli
uv sync --extra dev
uv run python manage.py migrate
uv run python manage.py seed_projects   # optional: seed the initial 13 portfolio projects
uv run python manage.py runserver

# Frontend
cd frontend && npm install && npm run dev

# Both (via honcho)
uv run honcho start -f Procfile.dev

# Docker (backend + frontend + Postgres)
docker compose up

# Deploy to AWS labs (https://labs.connect.dimagi.com/canopy/). Deploys run from
# GitHub only — trigger the "Deploy to Labs (AWS)" workflow from the Actions tab
# (workflow_dispatch), or:
gh workflow run "Deploy to Labs (AWS)" --ref main                          # migrations run automatically
gh workflow run "Deploy to Labs (AWS)" --ref main -f skip_migrations=true  # EMERGENCY ONLY: skip migrations
# Production ships from `main` ONLY — the workflow hard-fails on any other ref.
# It builds+pushes the image to ECR, migrates on a throwaway task def (the live
# one with only the image swapped) before cutover, then `aws cloudformation deploy`
# rolls the real task definition + service (CFN owns both — see Design Decisions).
# See .github/workflows/deploy-labs.yml + deploy/aws/canopy-web.cfn.yaml.
#
# MIGRATIONS: write the migration the obvious way. Destructive ones are fine —
# drops, renames, and column type changes do not need to be split into
# expand/contract phases, and a brief window of errors during a deploy is
# accepted. Migrating BEFORE cutover is just the cheaper order (old code against
# the new schema beats new code against the old one), not a contract you have to
# design around. Do NOT turn a one-line migration into a multi-PR dance to avoid
# a blip: the cost of that ceremony is real and the blip is not.
```

When `AI_BACKEND=cli`, the `claude` binary must be on PATH and authenticated. In Docker, use the headless auth flow at `/settings` (drives `claude setup-token` via PTY; token persists in `CLAUDE_CODE_OAUTH_TOKEN`).

## Testing

```bash
uv run pytest                                    # All backend tests
uv run pytest tests/test_agents.py -v            # Specific
cd frontend && npm run build                     # Frontend type check + build
cd frontend && npm run gen:api                   # Regenerate TypeScript types from OpenAPI schema
```

**Always open PRs with auto-merge armed: `gh pr merge <n> --auto`.** Many agents ship in
parallel here, so `main` moves constantly and a PR goes stale within minutes of being
opened. Without auto-merge you will hand-rebase the same PR several times (observed:
three times in one afternoon).

**Do not pass `--squash` (or any strategy flag).** The merge queue owns the strategy now,
and `gh` answers a strategy flag with `! The merge strategy for main is set by the merge
queue` — which reads like a warning but leaves auto-merge UNARMED. Check it took:
`gh pr view <n> --json autoMergeRequest`.

**The merge queue is ENABLED** (ruleset `main protection`, 2026-07-28). It needed an
ORGANISATION-owned repo — the blocker while this was `jjackson/canopy-web`, where a
`merge_queue` rule returned `422 Invalid rule 'merge_queue':` with no field named (the
rule TYPE was rejected, not any parameter; established 2026-07-26 across three parameter
shapes, don't re-spend that twenty minutes). The repo moved to
`dimagi-internal/canopy-web` and the rule went in. Current parameters: `SQUASH`,
`ALLGREEN` grouping, up to 5 entries, and a **5-minute minimum wait** — so a merged PR
does not land instantly even with everything green.

**A queue failure ejects your PR AND disarms auto-merge.** The queue builds your branch
merged with `main` and runs CI on THAT, so it fails on things your PR alone never shows —
including someone else's flaky test (observed 2026-07-28: a `ChatSessionsPanel` flake
ejected an unrelated PR). Symptom: all your own checks green, `mergeStateStatus: CLEAN`,
PR still open, `autoMergeRequest: null`. Fix: confirm the failure isn't yours
(`gh run view <queue-run> --log-failed`; the queue's branch is
`gh-readonly-queue/main/pr-<n>-<sha>`), then re-arm with `gh pr merge <n> --auto`.

**`strict` is now OFF** (`strict_required_status_checks_policy: false`), deliberately: it
was load-bearing only because nothing else re-tested a stale branch, and the queue does
that properly by testing the merged result. Don't turn it back on to "be safe" — with a
queue it just makes every PR wait on a branch update it no longer needs.

Branch protection lives in ONE place: the `main protection` **ruleset** (requires a PR,
both CI checks, the merge queue, and blocks deletion/force-push). There is deliberately
no classic branch protection — having both meant two contradictory `strict` settings
where the stricter silently won.

**Deploys are not ordered by commit.** Several agents each trigger "Deploy to Labs"; the
workflow's concurrency group serializes execution but a NEWER pending deploy CANCELS an
older pending one, and an in-flight deploy of an OLDER sha can finish last. Observed
2026-07-28. So after merging, confirm what actually shipped rather than assuming your run
landed: `gh run list --workflow="Deploy to Labs (AWS)" --limit 3 --json headSha,conclusion`,
and check the feature is really live (e.g. a new endpoint appears in
`/api/openapi.json`).

CI (`.github/workflows/ci.yml`) runs both on every PR and on push to main. Deploys are a **separate** workflow (`deploy-labs.yml`, `workflow_dispatch`) — trigger from the Actions tab. Walkthrough QA spec at `docs/walkthroughs/project-workbench.yaml` (run via `/walkthrough project-workbench`).

## Key URLs

The app is **workspace-tenant-scoped** (PR #183). Every surface that owns tenant
data lives under `/w/:workspace/`; personal/global surfaces and public viewers
stay at root. A header workspace switcher appears when you belong to >1 workspace.
Bare `/` redirects to the active workspace's workbench, and the legacy flat paths
(`/timeline`, `/shareouts`, `/walkthroughs`, `/agents/*`, `/ddd/*`) redirect into
the active workspace. `/ddd-plans` and `/reviews` now redirect to `/`.

**Tenant-scoped (under `/w/:workspace/`):**
- `/w/:workspace` — Project workbench. Tile grid dashboard with a "Today's top 3" insight hero, freshness chip, inline insights triage, and self-prioritizing tile order by insight count.
- `/w/:workspace/timeline` — Team activity timeline (cross-app activity feed; link-out only)
- `/w/:workspace/activity` — Fleet turn log scoped to that workspace (see `/activity` below)
- `/w/:workspace/shareouts` (+ `/shareouts/:period`) — Dated, teammate-facing work briefings (what shipped, why, how to leverage) posted by `/canopy:shareout`; `:period` is a copy-linkable permalink to one briefing
- `/w/:workspace/walkthroughs` — Sharable demos uploaded from `/canopy:walkthrough`
- `/w/:workspace/storyboards` — Index of the workspace's storyboards (the shared arcs): title, layout (review / reel), act count, and the token-bearing share link to copy. Under the Demos menu. The board itself opens at `/storyboard/:slug`
- `/w/:workspace/ddd` (+ `/ddd/:narrative`, `/ddd/:narrative/:runId`) — Demo-driven-development (DDD) views: narrative → version → run → package (video + deck + narrative + links)
- `/w/:workspace/agents` — First-class AI agents list (e.g. "Echo")
- `/w/:workspace/settings` — **The workspace's settings: one page, four sections** (`/settings/{members,slack,inbound,connected-apps}`), each its own URL so a deep link still names a place. **Members** + invites admin surface (owner-only actions): list members, remove a member, invite by email, list/revoke pending invites — canopy sends no email, so invite by copying the generated `/invite/:token` link and sending it yourself. **Slack** — the workspace's Slack connection (one Slack may serve several canopy workspaces; each owner connects their own, and a message's tenant is decided by the thread or agent it is about — `docs/superpowers/specs/2026-09-22-slack-multi-tenant-design.md`), the app configuration token that lets canopy manage the `/<agent>` slash commands, and the one-way "declare the app an agent" action (confirmed, owner-only, and Slack cannot undo it). **Inbound email** — the Gmail push doorbell. **Connected sites** — which websites may host one of this workspace's agents. They were four sibling top-level routes (`/w/:ws/{members,inbound,slack,connected-apps}`), which is why "where do I change something about this workspace" had four answers and one of them (connected sites) was in no menu at all; those paths now redirect, carrying query and hash. The sections are tabs rather than one scrolling page because each fetches its own data, and because a one-way action belongs on a section you opened on purpose. Distinct from the global `/settings`, which is your own account.
- `/w/:workspace/agents/:slug` — Agent workspace: a full-bleed rail + scrolling main built on `canopy-ui`. Sub-routes (rail): **Inbox** (the default landing — the agent's OPEN `Item`s, ranked review→question, decidable in place; legacy `needs-you` path 302s here), Overview, Tasks (the "who has the ball" board), **Items** (the full item ledger incl. decided/dismissed; `?batch=<key>` renders one sitting, e.g. a fleet audit), Turns (packaged units of work + optional transcript), Schedules, Syncs, Work products, Skills, **History** (how each skill changed, from the agent repo's git history, read with the owner's GitHub grant; the in-app assistant sees the selected skill/commit/date)
- `/w/:workspace/schedules` — Weekly calendar of that workspace's recurring schedules
- `/w/:workspace/chat` — Session-centric chat home: a findable list of your chat sessions to continue from any device + "New chat with `<agent>`". Reusable `ChatSessionsPanel` (cross-workspace); supervisor's Sessions tab embeds it (with the grouped-by-project `OpenSessions` view). "Chats" nav entry.
- `/w/:workspace/chat/:id` — Live multiplayer chat with an agent, built on the **`canopy-ui/chat`** kit (ported from ace-web; `ChatPanel` + `useSessionSocket` over `ws/canopy-sessions/{id}/`, co-edited draft + presence + streamed reply). A send enqueues a session `Turn`; a session-capable runner drives the agent's emdash session and bridges the reply back live. See `docs/superpowers/specs/2026-07-22-reusable-chat-kit-design.md`.

**Root / personal / global:**
- `/system` — Capability catalog + Workflows view (how canopy's plugin capabilities compose; read live from the canopy plugin)
- `/insights` — Cross-portfolio AI insights feed (user-scoped; deliberately not tenant-scoped)
- `/supervisor` — Cross-fleet "waiting on you" inbox, agent KPI cards, and runner status. Loaded by three consumers (phone PWA, the menubar's WKWebView, desktop browser); deliberately root, not `/w/:workspace/` — the fleet spans workspaces, like `/insights`. Installable as an Android PWA (manifest + service worker) and pushes a notification when any owned agent's `waiting_count` increases — see Push below
- `/schedules` — Personal weekly calendar of every recurring schedule across all workspaces you belong to (client-filterable by workspace/agent); the per-workspace view is `/w/:workspace/schedules`. Same component (`ScheduleCalendar`) mounts both routes and reuses the per-agent rail's `ScheduleEditor` for edits
- `/activity` — Read-only fleet turn log (in the header nav): recent harness turns — time, agent, origin, runner, status — with client-side filters and an inline event-ledger drill-down. The "what DID fire" sibling of `/schedules` ("what WILL fire"); tenant twin at `/w/:workspace/activity`
- `/sessions` — My shared Claude Code sessions (transcripts uploaded via `/canopy:share-session`)
- `/settings` — AI backend status, switch backends, headless Claude CLI auth, theme toggle, and debug-session minting (consolidated under the user menu)
- `/walkthrough/:id` — Single walkthrough viewer (HTML iframe or video player). Reclaimed from `/w/:id` when `/w/` became the tenant prefix; a legacy `/w/<uuid>/content` link 302-redirects here
- `/review/:id` — Editable narrative review surface for DDD (approve / redraft a story before build); public (link-visibility) reviews are readable by anyone with the URL, but submitting a decision requires a Dimagi login
- `/invite/:token` — Accept-invite page (deliberately outside `/w/:workspace/`: an invitee has no membership yet, so there's no tenant to scope into). Pre-auth, previews the invite (masked email, workspace name, role) via `GET /api/workspaces/invites/{token}/preview`; accepting requires a Dimagi (or invite-admitted) login
- `/share/:token` — Public, chrome-less read-only viewer for a shared session (no login; mounted outside the app shell)
- `/storyboard/:slug` — **The shared arc**: several DDD narratives, as ONE link. The reader sees **narratives, never "acts"** — storage still groups entries under an `Act` (that is where the curated title + connective prose live, and it orders the arc) but an act holding a single narrative is not a second thing to a reader, and naming it one produced two composers on the same narrative that differed in nothing the page showed. One composer per narrative. Public via `?t=<share_token>`, chrome-less (`PublicLayout`), no login. The page *follows* each narrative's current release rather than freezing a run id, so an emailed link never goes stale. Acts are numbered because act order carries meaning; a narrative with nothing published yet renders as "Being built" rather than vanishing (a storyboard is usually authored before its narratives are filmed)
- `/narrative/:slug?b=<storyboard>` — **The reviewer surface**: one narrative scene by scene. Reads **clean by default** — what changed since the last version is a question you ask, via the toggle beside the version pill, not the first thing you are shown (most readers of a shared link are meeting the story for the first time, and struck-through wording makes a finished narrative look unfinished). With it on, a before/after appears on the scenes that changed and cut scenes reappear; with it off they are not on the page, because they are not in this narrative. Commenting is a blank box; **editing opens the scene's own text** so a reviewer mutates the words directly rather than describing the change in prose. A signed-in editor is not asked who they are (`useAuth`). Gated by the storyboard's token (`b=` names the board). Shows the story and nothing else — no gates, features, provenance, actionability or findings. This is now the front door for narrative review; the operator console (`/w/:ws/ddd/:narrative`) keeps the machinery and sits behind a link (canopy-web#290: *"something only I understand"*)
- `/ddd-release/:narrative/:runId` — Public, chrome-less release page for one DDD run (`PublicLayout`, `?t=<share_token>`, no login) — the clean shareable read; backed by `GET /api/ddd/release/{run_id}/`. Carries the same Canopy bar (`PublicHeader`) as `/storyboard` + `/narrative`
- `/api/` — REST API
- `/admin/` — Django admin
- `/health/` — Health check

## Design Decisions

- **API is Pydantic-first via Django Ninja**: every request/response is a Pydantic v2 model declared in `apps/<app>/schemas.py`. Routes live in `apps/<app>/api.py`, registered on the single `NinjaAPI` instance in `apps/api/api.py`. Errors are RFC 7807 `application/problem+json`. Frontend types are generated from the OpenAPI 3.1 schema by `openapi-typescript` into `frontend/src/api/generated.ts` and consumed via `openapi-fetch`. **When you change an `apps/**/schemas.py` or `api.py`, regenerate the types and commit them: `cd frontend && npm run gen:api` (backend up on :8000) or `npm run gen:api:local` (against a dumped `openapi.json`).** A step in the **`Backend tests`** job (a required check) VERIFIES they're fresh on EVERY PR and fails if `generated.ts` is stale — it does NOT commit for you (an auto-commit pushed with `GITHUB_TOKEN` can't trigger the required CI checks, which used to leave the PR head unchecked and block the merge). It is deliberately unconditional rather than path-scoped: the old filter was a guess about what can move the schema and missed real cases (a `Literal` fed by an enum in `models.py`, a router registered elsewhere, or `generated.ts` mangled by a bad merge with no backend change at all). **A route's docstring is published API documentation** — put maintainer rationale in `#` comments instead, or it ships to every consumer via the schema and `generated.ts`.
- **Streaming endpoints stay on Django**: `GET /walkthrough/<uuid>/content` (the walkthrough viewer) is a bare Django view at `apps/walkthroughs/streaming.py` — HTTP Range support (for `<video>` scrubbing) doesn't fit the Ninja contract. It is the only `StreamingHttpResponse` left now that the co-authoring workspace SSE engine has been retired. (Reclaimed from `/w/<uuid>/content` by the tenancy migration; the legacy path 302-redirects.)
- **Bare Django views**: `/api/csrf/`, `/api/debug/mint-session/`, `/auth/cli/authorize/`, and `/health/` (the last is also Ninja-mountable via `public_router`) — they manipulate sessions/cookies/redirects directly. Matched in `config/urls.py` BEFORE the Ninja `/api/` catch-all so they don't get shadowed.
- **MCP is in-process FastMCP, not OpenAPI-derived**: `apps/mcp/` mounts a FastMCP 4.x Streamable-HTTP server at `/api/mcp/` whose tools are explicit Python functions calling the same service layer as the REST views (no HTTP self-loopback). Auth is per-user PAT inside the server (fail-closed), every call is audited, and writes are rate-limited. **`openapi_extra={"x-mcp-expose": True}` was deleted from 55 routes across 7 apps on 2026-09-18** — nothing had ever read it. It was the marker of the OpenAPI-derived design this bullet rejects, and left in place it said "these 55 routes are on MCP" while twelve hand-written tools actually existed. That is the `page_tools.py` failure (a declared intent with no mechanism) at 55x the scale, and it misleads exactly the person extending the surface. **Adding a tool means writing it in `apps/mcp/tools/` and asserting against the MOUNTED server** — a decorator on a REST route does nothing.
- **"Where does my ask stand" is derived ONCE, server-side, and every channel renders it.** `apps/harness/turn_status.py` turns a `Turn` plus `turn_reach` into eleven states; `apps/slack/status.py` renders them to mrkdwn and a Run-on-cloud button, `apps/canopy_sessions/status_feed.py` pushes them onto the session socket where `canopy-ui/chat/turnStatus.ts` draws them, and the embedded widget gets it free because it mounts the same `ChatPanel`. - **Directed runner routing (`RunnerAssignment` is the routing authority):** per-agent turns no longer route by a runner's self-declared `capabilities.agents` or an agent's kind-level `runner_preference` — both are superseded by `RunnerAssignment`, an explicit per-agent **ordered** runner list (`GET|PUT /api/agents/{slug}/runners`) that only that agent's owner edits, in place on the Runners tab (no separate routing tab). Routing is an availability cascade (highest ranked online+ready+**enabled** runner claims; lower ranks take over on unavailability, disablement, or after a 60s grace) rather than a static preference, because the operating loop is "shift the fleet to the next account/box when the current one runs out of tokens" and the system needs to degrade automatically, not silently deadlock. `enabled` (default `true`) replaced removal as the row-level control (an operator-requested follow-up): hitting the toggle greys a runner out instead of dropping it from the list, so the rank is preserved and re-enabling doesn't require re-adding it; a disabled row stays fully drillable. `Turn.pinned_runner` and session-turn stickiness (bound to a `RunnerBinding`, no auto-failover — the user is asked) sit on top of the cascade for the cases where availability-by-rank is wrong (drills, an in-flight chat's live context, an explicit "run on X"). **Source-aware routing (spec 2026-07-27) layers onto this rather than replacing it:** a row with a non-empty `source` is that source's single priority runner, composed into the same ordered list the same cascade walks — because the real operating question is not "which box runs Echo" but "which box runs *this kind of* Echo work" (ace-web execution belongs on the cloud runner; mail belongs where the mailbox credentials are). A rule is one runner plus a strict toggle, NOT a second ordered list: ordering already exists once, in the default list. See `docs/superpowers/specs/2026-07-24-directed-runner-routing-design.md` and `2026-07-27-source-aware-runner-routing-design.md`.
- **Scheduled turns are runner-fired, server-configured, and self-superseding:** `AgentSchedule` (`apps/harness`) holds cron config server-side so it is visible/editable in the Agent UI, but the runner evaluates the cron and POSTs a due slot — the scheduler is a *producer of turns*, not a second execution engine (no celery, no beat, no new deploy surface). `ScheduleOut.fire_after` (`= last_slot or created_at`) is the anchor the runner must pass to `due_slot(after=...)`, not `last_slot` directly — `last_slot` is NULL until the first fire, and looking backward with no lower bound would fire a fresh schedule for a slot that predates it. Both macOS-account runners may fire the same slot safely: the slot-derived `idempotency_key` collapses the race inside `enqueue_turn`. There is deliberately **no occurrence table** — the `Turn` is the occurrence (`latest_occurrence_turn` selects by `origin_ref__schedule_id`, scheduled or manual, regardless of status). Unattended occurrences are released as `MISSED` after `grace_minutes`, because an abandoned session otherwise wedges the agent forever via `one_executing_turn_per_agent` (the runner's heartbeat keeps renewing its lease, so the lease sweep never rescues it) — release is scoped to `EXECUTING` turns and anchored on `claimed_at` (not `created_at`, which measures *owed* time, not *held* time), and it runs lazily on the runner's **claim** tick (`claim_next_turn` → `release_stale_occurrence_turns_all()`), not the fire tick, since a weekly schedule's fire tick is too far apart to ever honor a short grace window. A grace-released occurrence raises a real `review` **`Item`** (`services._raise_schedule_nag`, honoring the schedule's `notify` channels) whose `implement` re-runs the schedule's prompt — the generic Item action replaces the old bespoke "Run now" button; `finish_turn` on a later `DONE` occurrence dismisses it (`resolve_schedule_nags`). So the nag reaches the **Inbox** rail as an ordinary item, with no scheduling-specific UI. See `docs/superpowers/specs/2026-07-15-agent-scheduled-turns-design.md` and `2026-07-21-supervisor-inbox-items-only-design.md`.
- **PWA navigate-fallback is fail-safe (allowlist SPA routes, not denylist server routes):** the service worker **handles** a navigation **only** when its path matches a known SPA route prefix; every other navigation goes to the network and reaches Django. "Handles" means **network-first with the precached `index.html` as the OFFLINE fallback** — it is emphatically *not* "serve the precached shell", which is the bug described in the next bullet. This inverts the old "shell for everything minus a denylist" default, which silently swallowed any server route nobody remembered to denylist — a `<iframe src="/walkthrough/<id>/content">` (an iframe load **is** a navigation) rendered the whole SPA again inside itself (issue #345). The rule now fails safe: a **new server route** is excluded by construction (unknown ⇒ network); a **forgotten SPA route** only loses *offline* shell fallback (online it still resolves via the `spa_view` catch-all). The two regex lists (`NAVIGATE_FALLBACK_ALLOWLIST` / `NAVIGATE_FALLBACK_DENYLIST`) live in — and are unit-tested in — `frontend/src/pwa/navigation-fallback.ts`, and `vite.config.ts` imports them. Server-content streams that sit *under* an allowlisted SPA prefix (`/walkthrough/<id>/content`, legacy `/w/<uuid>/content`) are carved back out on the denylist (workbox: denylist wins), and those carve-outs end in `(?:\?.*)?$` because workbox matches `pathname + search` and the DDD console now embeds artifacts with a `?t=<share_token>`. See `docs/superpowers/specs/2026-07-23-pwa-navigation-fallback-fail-safe-design.md`.
- **The app shell is never served stale — that is what "do I have to hard-refresh?" comes down to.** `index.html` is the only file naming a build's content-hashed assets, so a stale copy renders a stale app; two independent layers were serving one, and each was sufficient alone. (1) The SW answered every navigation from its **precache**, a copy frozen at build time — so a fresh visit rendered the *previous* deploy and only a hard refresh (which bypasses the SW) reached the new one. Two defaults had to be turned off, not one: `navigateFallback` must be set to `undefined` **explicitly** (vite-plugin-pwa re-adds `'index.html'` when the key is absent), and `directoryIndex: null` (workbox otherwise resolves a bare `/` to the precached `index.html`, ahead of any runtimeCaching route — so `/`, the entry point, stayed broken after the first fix). A **build-time guard in `vite.config.ts` reads the emitted `sw.js` and fails the build** on either, because both are silent defaults a dependency bump can restore and neither shows up in a type error or a test. (2) WhiteNoise's default `max-age=60` on everything kept a 60-second stale window even after the SW was fixed, and `spa_view` (which serves every deep link) sent no `Cache-Control` at all. Policy now: **content-hashed name ⇒ `immutable` for a year, everything else ⇒ `no-cache`** (`config/static_cache.py`), a total rule so an unconsidered file costs a 304 rather than serving something stale — it deliberately leaves WhiteNoise's own `immutable` verdict on hashed `/static/` files alone. A third door stays open by nature: a **tab already open** across a deploy asks for `lazy()` chunks that no longer exist, so `lazyRoute` (`frontend/src/pwa/staleChunk.ts`) reloads once on a chunk-load failure — guarded on `navigator.onLine` and one reload per 10s, since a looping reload is worse than the bug. Adopting a new SW promptly (`registerPwa.ts`) is consequently no longer urgent: a waiting SW now only means a stale *offline* precache. Note the residual, inherent to service workers: a browser holding the previous SW gets its shell from that worker one more time.
- **A chat is recorded the same way whatever surface it started on (`transcript_sourced`).** Where a conversation ORIGINATED says nothing about where its record belongs, but it used to decide it: a phone-created session took its durable rows from projecting a `Turn`'s events, so it captured only what happened INSIDE a turn — text typed straight into emdash never appeared, and neither did text an agent wrote after handing the floor back (a background job finishing). A session discovered in emdash had none of this; spec 2026-07-24 already made its transcript the sole durable source, ordinal-keyed. That split was an unfinished migration held in place by three `if origin == ORIGIN_RUNNER` branches. `services.transcript_sourced(session)` replaces them with the question that matters — is a real runner driving this, so does a transcript exist? — and phone chats inherit the working path: **sends author no second copy** of the user's line (it becomes durable as the transcript record the agent actually read; until then it lives in `Turn.prompt` + the client's optimistic echo), streamed transcript rows persist for any transcript-sourced session, and the ledger projection survives ONLY where there is no transcript (the dev stub). `origin` is back to meaning only "how this started". Sessions predating the flag stay ledger-sourced until reset — their dense counter (0,1,2…) would collide with transcript ordinals in the same `turn_index` column. **Recoverability ≠ listing:** a backfill resolves the transcript by worktree PATH under `~/.claude/projects` and never asks emdash, and Claude Code never deletes those files, so a task emdash deleted months ago still ships its full history (verified 2026-07-26: tasks absent from emdash's DB entirely, transcripts resolved, 545 and 607 records). Falling off the session report ends a session's listing, not its recoverability — conflating the two is what made reset look dangerous. See `POST /api/canopy-sessions/reset` above.
- **Session liveness is polled; the runner FK is identity, not a flag.** `RunnerBinding` carries two things that were once conflated into one column: **`runner`** = which box this session lives on (durable — a report never nulls it), and **`live_seen_at`** = when the runner last reported it (the liveness clock, read against `SESSION_LIVE_WINDOW` = 3 min). Using the FK for both meant every closed task stripped its session of its identity, and the *only* durable retirement path was a closing signal that never fires — emdash **deletes** a closed task instead of setting `archived_at`, so `list_recently_archived_tasks` returns `[]` forever. Labs ended up with 71 "active" sessions: 14 real, 10 bound to a retired box, and **47 that could not say which runner they came from**. Polling is what makes this self-healing — the runner re-reports its whole open-task set on a guaranteed 10s heartbeat and skips the report entirely if it cannot read emdash, so absence is an observation (and a returning runner un-retires its own sessions with no repair step). Deliberately **not** extended to claim routing: a stale binding still pins its session to its holder rather than failing over, because continuing elsewhere means a fresh emdash session with none of the conversation's context — that stays the user's call via the placement banner (spec 2026-07-24). The stuck-send that motivated revisiting it was never routing but the banner failing **open**: `isBoundRunnerOffline` treated "not in the fleet list" as *unknown* when `GET /runners/` omits retired runners, so exactly the sessions that needed placement never offered it. See `apps/canopy_sessions/staleness.py` + `frontend/src/components/chat/runnerEligibility.ts`.
- **ACP is the wire shape; emdash stays the laptop's executor.** `@agentclientprotocol/claude-agent-acp` (public npm, what emdash itself runs) already specifies what canopy invented: `tool_call`/`tool_call_update` with a status, `agent_message_chunk`, `agent_thought_chunk`, `plan`, `usage_update`, agent-authored tool titles, and — uniquely — subscription **rate-limit metadata** (`_claude/rateLimit`, `five_hour`), the only *predictive* signal the runner cascade could use instead of failing over reactively. The **cloud** runner can execute over it (`runner/canopy_acp`, `RUNNER_EXECUTOR=acp`, default off until it has run on a real box); the **laptop cannot and should not** — a canopy-spawned ACP session would be invisible to emdash, costing the jump-in that makes the laptop worth running. So the laptop keeps CDP+emdash and gains only the SHAPE. Two rules follow: `tool_call_update` is a **sparse patch** (merge by `toolCallId`; rendering one as a row ships half-empty tool calls), and `session/load` **replays the whole conversation** as updates, so a resumed turn must suppress them or it re-appends its own history to the ledger.
- **A blocked agent's menu comes from three places and one payload.** A hook can say an agent is BLOCKED (`Notification`) but never *what* it is asking — no options, no command, no way to reply. On the **cloud**, ACP's `session/request_permission` carries all of it. On the **laptop** a permission dialog exists only on emdash's terminal, so the runner reads the rendered screen over CDP and parses it (`canopy_runner/menu.py`); `canopy_acp/menus.py` maps the ACP request onto the SAME dict, and a test asserts they're interchangeable — so the client never learns which produced it, and the parser is deletable the day emdash exposes its own ACP stream. Read the **DOM, not the PTY**: Claude Code draws spaces as `ESC[nC`, so stripping ANSI from the raw stream welds words together. Fail closed — numbered lines are the most common shape in an agent's own output, so a dialog needs a footer offering a way out; and re-read before pressing anything, because a stale number typed at a session with no dialog lands in its PROMPT, where the agent reads it as an instruction.
- **The blocked-agent dialog: the hook is the primary producer, not the transcript.** Claude Code writes the `AskUserQuestion` `tool_use` record only once the ask is ANSWERED (measured: 39 records across 60 transcripts, zero pending, while two dialogs were on screen), so `pending_question` reports dialogs that are over and never one that is waiting — and it fails silently, because `None` also means "nothing is blocked". `PreToolUse` carries the same `tool_input` at the moment the ask starts, so `canopy_transcript.menu_from_hook` is the primary path; the transcript reader is consulted SECOND (it wins where hooks were never installed) and the screen read covers what neither can see (permission prompts, trust gates). All three emit the identical dict; `source` says which, and every one stamps `observed_at` so staleness is visible rather than discovered by tapping. A `Notification` counts only MID-TURN — it also fires for an idle prompt, which is every idle session on the box. Full chain and evidence: `docs/superpowers/specs/2026-08-01-clicking-does-nothing-incident.md`.
- **The screen parser fails closed, twice over.** `menu.find_menu` needs consecutively-numbered options plus either a footer offering a way out OR the TUI's selection cursor (`❯`) on an option with the dialog running to the bottom of the frame — because a tall dialog overflows a short emdash pane and the footer is the line that falls off. Both halves matter: prose does not draw `❯` at the head of a numbered line, and a live dialog is always the last thing on screen, so a menu an agent merely *quoted* is still rejected. A grid-wrapped question is rejoined only on the wrap signature, since a dialog's SUBJECT sits directly above its question. See `docs/superpowers/specs/2026-08-01-clicking-does-nothing-incident.md`.
- **A dialog canopy cannot read still reaches the phone, as words without buttons.** `AskUserQuestion` arrives whole because it is a tool call; a permission prompt or trust gate is drawn with no tool call behind it, so it exists only on the rendered terminal — and reading that means CDP, which clicks the task and steals focus (#510). Those dialogs therefore reached a phone only if somebody happened to be watching when they appeared. The `Notification` hook needs neither: it says a human is wanted and its `message` says roughly why, so `canopy_transcript.marker_from_hook` records an **option-less** menu carrying that message verbatim. Deliberately not parsed to work out which kind of dialog it is — guessing at the wording is how a signal starts lying, and the human reading it can tell. **A `Notification` counts only MID-TURN.** It fires both when an agent stops to ask and when a prompt merely sits idle after a turn ends, and the second is every idle session on the box — counting those put four of them on the fleet's "waiting on you" list within minutes of shipping this (labs, 2026-08-01), and a badge that counts every idle session is a badge nobody reads. The discriminator is turn STATE (`UserPromptSubmit` seen, `Stop` not yet), never the message wording, which Claude Code is free to change. It fails closed: a runner that restarted mid-turn misses a real prompt rather than raising a false one — silence costs a menu, noise costs the signal. Precedence is one-way: a notification never overwrites a real menu (buttons that work must not become words that do not), while a real menu always replaces a notification. **Escape stays real on one of these** — the runner re-reads the actual screen before pressing anything and a permission prompt parses there, so the refuse button is an action, not a placeholder.
- **`send-keys` selects the Claude tab before refusing.** A task can hold several terminals (the Claude pane plus shells a human opened) and only the selected one is rendered, so with a shell tab selected every answer died on `NOT_A_CLAUDE_PANE` — correctly, since pressing "3" then Enter in a shell RUNS something. The human asked for this keystroke, so switching the tab for them is the on-demand case that may move emdash's UI. Two rules make it safe to do blind: the tab is matched by `title` starting `Claude (` — never by position, and never by an `aria-label` starting `Close`, which is the button that KILLS the session and sits inside that very tab — and it is dispatched as a direct `.click()` rather than a real mouse click, so no overlay can intercept it by sitting on the coordinates. Ambiguity (zero or several visible matches) is not actionable and falls through. The positive identification still has the final say: if the pane is still not a Claude session, it refuses exactly as before, and now says the switch was tried.
- **One authority, and a tap reconciles every copy to it.** The dialog is drawn on a terminal; `HookListener._pending_menus`, `~/.canopy/pending-menus.json`, `RunnerBinding.pending_question` and the client's `menu` are all COPIES. At the tap: **could we read the screen? the screen wins** — clear if it showed nothing, REPLACE if it showed a different dialog, never keep a cache the authority just contradicted; **could we not? keep the cache and say why** (`wrong_pane` / `unreachable` / `no_session`). So `answer_error` only ever rides a menu we are KEEPING, and tapping an already-answered dialog removes it rather than leaving dead buttons. Some refusals are irreducible — the dialog is on a laptop and you are on a phone — and re-reading before pressing is what stops a stale number landing in a prompt, where a bare "2" reads as an instruction. See `docs/superpowers/specs/2026-08-01-clicking-does-nothing-incident.md`.

- **Two principals reach canopy, and they are two TYPES, not one shape with a flag.** A `DelegatedToken` resolves to a `User` and every surface applies that user's ACL. A **contact** has no membership, so one arriving through the same lookup would not be a smaller permission but an *unspecified* one — which is the `Agent.workspace` failure exactly, where six predicates each grew a "no tenant ⇒ allow" leg because a row without one met code written for rows with one. So `ContactToken` is its own model: it sets `request.contact` and deliberately leaves the request ANONYMOUS, which means `LoginRequiredMiddleware` refuses everything outside the one prefix opened to it. **`/api/contact/` is the entire surface a contact can reach** — a tuple entry in `apps/common/middleware.py`, not a decision distributed across views — and the trailing slash is load-bearing, since `/api/contacts/` is the tenant-admin list and must not match. `visible_session_q` and `contact_session_q` are disjoint predicates, so neither has to know the other exists. A host vouches for a contact with a **signed assertion** (`apps/tokens/assertions.py`: asymmetric algorithms only, `aud` enforced, `exp` capped at 120s, single-use `jti` failing closed), never a shared secret — canopy holds only a public key, so compromising canopy's database yields nothing that can impersonate. Guarded by `tests/test_contact_surface_is_bounded.py`, the sibling of `test_workspace_authorizer_is_sole_gate.py` at the other principal.
- **Live end-to-end check: `scripts/e2e_session_chat.py`.** Everything in `tests/*_e2e.py` runs in-process with both ends faked, which is the right shape for seams and is exactly what passed while the live chain was broken — on 2026-08-01 six production bugs shipped green and were each found only by driving the real thing. Eight steps against the real deployment, pinned to one agent (`hal`) and to one runner (this machine by default, from `~/.canopy/runner.json`) so the keystroke has a known destination you can watch in emdash: `check_runner · create_session · send_and_reply · answer_from_the_web · load_full_history · scroll_back · rebuild_from_transcript · close_session`. `--steps check_runner` is the free connectivity check; `--keep` leaves the session for inspection. **`answer_from_the_web` is the point of the file**: it asserts the agent ACTED on the answer, not merely that a menu appeared or a tap returned `ok:true` — every check run during the incident stopped one clause short of that, which is how a dead button looked like a working one for 45 minutes. Deliberately NOT covered: a dialog answered at the KEYBOARD while the phone still shows it — that race is real (the report is ~10s) but reproducing it means fabricating state the system cannot produce on its own, and the recovery is pinned by unit tests instead.
- **Live end-to-end check: `scripts/e2e_embed_widget.py`.** The same argument at the embedded-widget seam, and this feature made it the hard way: between 2026-09-13 and 2026-09-15 the widget shipped with a full green suite and about a dozen silent failures in it — a CSRF cookie read under the wrong name, an API base missing the `/canopy` prefix, sessions created against the wrong tenant, an MCP provider no module imported, a session cookie that hid the frame's own bearer token, and a session created on every page load. None could have been caught by a test that constructs both ends. Walks the chain a browser walks — loader, `/api/embed/self`, the framable shell and its `frame-ancestors`, a minted token, and the SAME token listing agents (the 403 that was live) — then checks the empty-session count did not move, which is the create-on-load bug asserted against the real deployment. Read-only by default; `--send "text"` starts a real conversation and costs real tokens.
- **A session's WORKTREE project is not its `project`.** `Session.project` is set only for an agentless repo chat; an agent chat leaves it blank. But an agent chat's worktree still lives under a project — the agent's own repo (`~/emdash/worktrees/hal/emdash/hal-canopy-web-chat-…`) — and the runner resolves a transcript by `(project, task)`. Both descriptors that tell it what to ship (`/runners/{id}/streams`, `/runners/{id}/backfills`) sent the bare `project`, so an agent session sent `""`, `resolve_transcript` returned None, and both consumers hit `continue` — silently, every tick, forever. **Agent chats were therefore never streamed and never backfilled**, which is precisely the "983 of 6119 rows (16%), 8 sessions at exactly zero" `list_streams` records: the fix for the 16% could not reach the sessions that needed it most. `Session.emdash_project` (`project or agent.slug`) is the one place that question is answered. Found 2026-08-01 by an e2e step that waited 420s for "load full session" to produce a single durable row and got none.
- **A control frame is a doorbell, never a mechanism.** `answer-menu` and `close_session` published a WS frame and returned success — and a frame published while the control channel is down lands in a Channels group with no consumer and is discarded, while the runner keeps heartbeating over REST and still reads `ONLINE`. Nothing runs, so there is no keystroke AND no refusal, because no code executed to produce one. Measured 2026-08-01: channel reconnected at 10:16 and 10:58, an answer sent at 10:50 produced no keystroke, no refusal, no log line. So anything that must happen gets a durable record the runner drains on its poll tick — `RunnerBinding.pending_answer` (`streams.drain_menu_answers`) and `close_requested` (`streams.drain_closes`), beside `/streams` and `/backfills`. A dropped channel costs one tick, not the action; the same shape as inbound mail and runner updates. `pending_answer` carries an `id` the runner echoes back, because applying an answer twice is a second keystroke into a session that has moved on. See `docs/superpowers/specs/2026-08-01-clicking-does-nothing-incident.md`.
- **A runner must not be exiled by one bad turn.** A failed turn writes `~/.canopy/not-ready`; `mark_ok` runs only after a turn EXECUTES and `claim_next_turn` will not give a not-ready runner a turn — so one transient failure removed a box from the fleet permanently, escapable only by deleting a file by hand, with no signal (it keeps heartbeating and reads `ONLINE`). Observed when a laptop was shut down mid-turn and came back on a DNS error. The marker now expires after `readiness.MARKER_TTL_SECONDS` (15 min) — exile becomes retry-with-backoff — while the CDP probe still gates independently, so expiry cannot mask emdash being down.
- **A tap's outcome is a value, not a log line.** The API returns `sent` the instant it relays; only the runner knows whether the key landed. Refusals (`answered` / `no_dialog` / `not_on_menu` / `wrong_pane` / `unreachable` / `no_session`) ride the next session report back inside the menu itself (`answer_error` + a human sentence in `answer_note`; no migration — the column is JSON), and the report is forced (`sessions.request_report_now`) because a blocked session writes nothing to trigger the change-driven tick. `wrong_pane` stays a refusal on purpose: `send-keys` first tries to select the Claude tab (matched by `title` starting `Claude (`, never by an `aria-label` starting `Close` — that button KILLS the session and sits inside the tab), and if it still is not a Claude pane it refuses rather than guessing, because the cost of guessing is a digit executed in your shell. See `docs/superpowers/specs/2026-08-01-clicking-does-nothing-incident.md`.
- **A pending menu is persisted, and pruned from both ends.** `~/.canopy/pending-menus.json` (`menu_store.py`) — the hook fires once, so without it a restart does not merely forget a live dialog, it makes the next report ship `question: null` and RETIRE it, with nothing able to rediscover it. A notification marker is NOT restored (it claims a turn was in flight, and turn state is deliberately not persisted). Persisting then creates the opposite failure — a menu outliving its session — so both ends prune on the wholesale report: the runner drops menus whose task is not in the open set (`hooks.prune_menus`), and `replace_reported_sessions` clears `pending_question` for that runner's bindings absent from `now_keys`. The server half is load-bearing: the runner cannot say anything about a session it can no longer see. See `docs/superpowers/specs/2026-08-01-clicking-does-nothing-incident.md`.
- **A blocked turn is not a wedged one.** The chat bridge's 15-minute idle backstop exists for a writer that never stamps a `stop_reason`; an agent waiting on a human is silent by exactly the same signature. `LiveBridge.step(..., blocked=)` suppresses the idle finish (and only that — `MAX_TICKS` still bounds it) while a dialog is up on that session. Measured cost of not knowing: a turn finished `done` after 15 minutes carrying 936 characters of preamble while its dialog was still on screen, so the phone showed a completed chat whose answer never came (labs, 2026-08-01).
- **A menu must survive being looked at later.** `RunnerBinding.pending_question` holds it; `session_state_dto` (the WS connect snapshot) and `GET /api/canopy-sessions/{id}` both serve it through one reader (`serializers.pending_menu`), the list carries `waiting_on_you`, and `session.menu` pushes the EDGES to an open chat. Before this, a menu existed only as a view-only `session.activity` frame (`index=-1`), so it reached a client **only if that client was already connected when the agent asked** — which is exactly the case that fails, because you go and look BECAUSE the session stopped. Consequences: a bare `blocked` activity frame no longer retracts the menu (the hook path deliberately sends none, #510), only a non-blocked state does; and the composer refuses to send while a **parsed dialog** is up, because the TUI draws the menu where the composer would be and the send would bounce as `COMPOSER_NOT_VISIBLE`. **An option-less `Notification` marker does NOT lock it** (`menuBlocksComposer`): nothing was parsed to produce one, so "a dialog is up" is a guess, and when the guess is wrong the lock has no way out. It was wrong on 2026-08-17 — an API 500 ends a turn but fires **no `Stop`** hook, so `_in_turn` never cleared, the next idle notification was recorded as a mid-turn block, and `ace`'s `spark` showed a "Waiting on you" with no options over a composer that refused to send. Both halves are fixed: `turn_ended_in_api_error` reads the transcript tail on a `Notification` and clears the turn state, and a marker no longer blocks the composer. A marker that IS real still costs nothing — the send bounces loudly and the runner ships back the dialog it actually found. Cost of getting this wrong, measured: `ace`'s `spark` sat blocked for **52 minutes** on 2026-07-31 showing a phone nothing at all.
- **In the fleet, permission dialogs basically never appear.** Sessions run `⏵⏵ bypass permissions on`, and the cloud runner passes `--dangerously-skip-permissions`. The menu you actually meet is **AskUserQuestion** — part of the conversation, independent of permission mode, and shaped differently (a description line under each option, a box rule *between* options, no `?` in the question, plus two options Claude Code appends itself). Test against that, not against a permission prompt.
- **CloudFormation owns the task definition and service; the pipeline only passes an image tag.** The deploy workflow builds, registers a THROWAWAY task def to migrate on, then runs `aws cloudformation deploy --parameter-overrides ImageTag=<sha>` — CFN registers the real task definition and rolls the service. One writer per resource, so the stack can never drift from what is running.
  **This replaced a two-writer setup** where CFN *declared* `TaskDefinition` + `Service` while the workflow registered revisions and called `update-service` behind its back. The stack's `ImageTag` froze at the last apply — observed 2026-07-26 at **ten days and 118 revisions** — so a plain `aws cloudformation deploy` would re-register from the stale parameter and silently roll prod back, reported as success. `deploy/aws/apply-stack.sh` existed to pin around that and is now deleted, as is `render_taskdef.py`: it read the template OUTSIDE CloudFormation and silently dropped any env value that was an intrinsic (`!Ref` → gone, no error). CFN resolves intrinsics natively, so that bug class cannot recur.
  **The migration seam.** CFN's `Service` references its `TaskDefinition`, so an apply rolls both atomically and leaves nowhere to migrate. Hence the throwaway task def: built from the LIVE one with only the image swapped (no YAML parsing), migrations run on new code against the current schema, then CFN does the real roll. Its env is one deploy stale — only a problem if a deploy changes an env var AND a migration in that same deploy reads it. Migrations operate on schema and essentially never read settings; if it ever happens, deploy twice.
  **Cost, measured 2026-07-26:** CFN's own overhead is ~10s (TaskDefinition 6s); the remaining ~6min is the ECS rollout that `update-service` waited for anyway. Deploys are already serialized by the workflow's `concurrency` group, so CFN adds latency, not contention.
- **Rolling sessions (`SESSION_SAVE_EVERY_REQUEST = True`):** Django's default sets the 2-week session expiry AT LOGIN and never extends it, so an installed PWA would log you out every fortnight no matter how often you opened it. Fix costs a session write on **every request**, on every surface, for every user — and changes a failure mode: any view with `except IntegrityError` now needs its own `transaction.atomic()` savepoint, or the session write `SessionMiddleware` makes on the way out hits a poisoned outer transaction instead of the intended 409/handled error. Worked example: `apps/projects/api.py::create_project`; pre-existing precedent: `apps/harness/services.py`.
- PostgreSQL on the shared labs RDS (`canopy_web` DB on `labs-jj-postgres`)
- Dual AI backend lets users run either against an API key or their own Claude Code subscription
