# Access: direct use, admission rules and the caller envelope

How a person who is not the agent's owner uses an agent directly, what a caller's turn tells the owner, the admission rules a workspace's admins write to refuse or let turns run `auto`, and the caller envelope an agent receives with a caller's turn. The words and the one rule (`apps/agents/turn_context.resolve_turn_context`) are defined in [access.md](access.md).

**See also:** [access.md](access.md) (glossary, roles, access list, decision table), [access-confinement-and-act-as.md](access-confinement-and-act-as.md), [access-sessions-and-people.md](access-sessions-and-people.md), [roles.md](roles.md).

## Direct use of an agent

A person may run an agent in their **own** Claude Code, with the agent's plugin and skills, and canopy keeps the record (`apps/harness/local_turns.py`, whose module docstring is the orientation). Prose and screens say **direct**; the stored and wire names stay `local` (`Turn.origin = local`, `LocalTurnIn`, `/api/harness/local-turns/`): do not rename them.

* **Private runner** (`PrivateRunner`): a person's machine, plain Claude Code with the canopy plugin, registered once with the person's own token; it belongs to the PERSON and never claims a turn. When the machine also runs the runner app, `PrivateRunner.runner` links the two and the runner is marked `private` (owner only: `api_runners_settings.py::set_runner_private`). A private runner takes no fleet work, only what its owner pins or binds to it plus the direct sessions on it (`Runner.directed_only`). A machine without the runner app gets a `computer` runner (`local_turns.ensure_computer_runner`) so it can enrol a device key; the computer appears in no fleet runner list.
* **No PAT on a private runner or computer.** The owner's direct sessions sign in with the box's device key, whose token reaches only the owner's direct turns and license reads, never the runner protocol (`runner_auth._PRIVATE_RULES`, `_COMPUTER_RULES`); a shared runner's token opens no direct session. The initiator assurance is `private-runner-key` (verified, like a PAT). Only the owner registers or approves a device key on a private runner, because that box signs in AS the owner; its runner admins still see and may revoke keys (`runners.may_trust_device_keys`).
* **A direct turn** is one session with one agent, opened by the plugin's SessionStart hook. It is a real turn: the person is its initiator (verified, `via=local`), it is RUNNING from the start, never queued or claimed, carries the same caller envelope, and never holds the agent (it neither waits behind the agent's runner turns nor delays them). Only its initiator may renew, finish or append to it; a session that dies is swept `lost` (`local_turns.LOCAL_LEASE`, `may_report`).
* **Who may**: exactly whom the rule gives the WHOLE agent (owner, agent admin, anyone whose lines give `write`). A read_only or host-site line, or a contact, is refused (403) and keeps the confined path through canopy (`local_turns.authorize`).
* **Mode**: `manual`, always, except an agent admin who asks for `auto` (`local_turns.mode_for`). An editor gets no routing ladder here, because nothing about a session on their own machine is an entry point the owner set a posture for.
* **License** (`AgentLicense`, `agents/credentials/licenses.py`, whose module docstring has the three rules): person x agent, the record that someone uses the agent directly. The access list decides who MAY; the license is who DOES. A revoked license is never re-issued automatically, and `approve` re-asks the rule, so it cannot license someone the access list does not give the whole agent. `licenses.active` re-asks the rule on every use, so a demotion takes effect at once.
* **Credentials.** `/credentials/resolve` has a third principal, `license`, beside `runner` and `admin` (`apps/agents/credentials/credential_resolve.py::credential_access`, whose docstring is the definition): an ACTIVE license AND one of the caller's OWN live turns on that agent named in `X-Canopy-Turn-Id`. No turn, no secrets. A request naming that turn is a `license` read even from an agent admin or a runner owner. What it is handed is `authority`'s direct column: never the agent's canopy login (graded `system`, past an editor line's `manual_only` cap), the owner's GitHub delegation, or lent or shared credentials. Secrets read this way reach the person's machine; nothing brokers each call through canopy-web.
* **Acting as a lower role.** `acts_as` is a property of ONE turn or of one client's requests, never a setting left on a machine; it only lowers, so it needs no proof. Mechanism and every reader that honours it: `apps/workspaces/role_cap.py` (module docstring). A capped owner or agent admin is neither (`Agent.is_admin`, `caller_context.relationship_for_user`), and the server stamps `origin_ref.acts_as`; a client's own `origin_ref` cannot.

## What a caller's turn tells the owner

A confined turn can act on nothing, so a caller's procedure ends its final message with one line, `For <Agent>'s owner: <the ask>`, and tells the caller the request is noted where the owner reviews it. The runner lifts the line out and sends it as an `owner_ask` turn event; canopy-web re-parses it and appends it to `result_note` for a confined turn only, once per line (`apps/harness/owner_ask.py`). The note is what every view of the turn shows the people who may read it; the transcript stays the record.

## Admission rules

Some combinations can never complete, and canopy refuses them before any session starts instead of spending one (`apps/admission`). The worked example: an email from a **confined** caller, in **manual** mode, claimed by a **cloud** runner: the read-mode procedure drafts a reply and waits for a human yes, which a cloud session that ends cannot receive. Start at `admission/evaluate.py` (module docstring: where rules are evaluated and precedence), `apps/admission/models.py::AdmissionRule` (conditions and the `clean` refusals), `admission/notices.py` and `admission/runner_notices.py` (module docstrings: the notices).

* **A rule** is a row on a workspace edited by its workspace admins (`admission.manage`); only the agent's own workspace's rules apply, to agent turns (a project turn has no agent and is never evaluated). A blank condition means any; a rule needs at least one. A rule's `principal` condition is who asked in the rule's own words (`member`, `contact`, `agent`, `system`), not an agent role.
* **Precedence** (`evaluate.decide`): an enabled `allow` that matches exempts the turn from every `reject`. A disabled rule matches nothing, so a disabled agent-narrowed copy of a reject does NOT exempt anyone. At enqueue, a condition not yet known counts as matching for an `allow` and as not matching for a `reject`, so the claim decides. Among matching rejects the most specific wins, then the oldest. Both claim channels pass through `evaluate.at_claim`.
* **`auto` raises only the standing posture** (`evaluate.auto_rule`, `turn_mode.Resolved.raisable`): never an editor's cap, a dispatch that asked for manual, or auto withheld from an unverified message. A session that started manual is raised only when nothing about THIS turn holds it back (`turn_mode._carried`: its own rungs resolve to the standing posture, the message is verified, the caller is not confined); otherwise a thread first answered manually on a laptop would run manual on the cloud, where nobody can approve its reply. It cannot be about refused or unclaimed turns (`AdmissionRule.clean`).
* **A rejection** closes the turn **CANCELLED**, not FAILED, so no debugger turn starts, and no runner ever holds it (`evaluate.reject`; `REJECTED_PREFIX` is what `harness.turn_status` reads to tell it from a person pressing stop).
* **Notices are fixed text, never model-written, and safe by construction.** The sender's automatic reply goes on their email thread from the agent's mailbox, never to a machine (Auto-Submitted, Precedence, list mail, a no-reply address), the agent's own mailbox, a system sender or another agent, and at most once per thread per 24 hours (`notices._why_not_reply`, `SENDER_WINDOW`). It is **off** in each workspace until one of its admins turns it on (`AdmissionSettings`); while off it is recorded as `held`. canopy-web never sends from an agent's Gmail (it holds no mailbox token it can open): the notice is left `pending` and the agent's runner leases and sends it (`runner_notices.claim`, `LEASE`, `EXPIRES`); a runner failure leaves it pending, one no runner sends within `EXPIRES` ends `failed` saying why, and a send that may have gone out (a timeout) is never retried, so the sender is never answered twice. The owner's notice is separate from the thread and owner-only.
* **Defaults** are ordinary rows seeded per workspace (`apps/admission/defaults.py::DEFAULTS`; a deleted default is not re-seeded). Do not read the list from here.
* **Refusals as rules.** canopy refuses two kinds of turn on its own, before any rule: mail from a blocked contact (`channels.email.refused_email_turn`) and a person the agent offers nothing (`_apply_capability`, `access: none`). Those are access decisions and stand whatever the rules say: no `allow` can cover them (`AdmissionRule.clean`) and disabling their rule does not let them run. A rule only decides what the refusal records and who is told (`evaluate.at_refusal`), and the seeded refusal rules ship with every notice off.
* **Reach rules: no runner will take it** (`reach: paused | offline`, `evaluate.reach_facts`, `recheck_stranded`, `sweep_unrunnable`). A pause WITH a resume time matches neither: the turn waits (`waiting_runner`, `parked`, `held_until`). A claim never matches a reach rule, and a reach rule cannot be an `allow` or name a runner kind or mode. Disabling the seeded reach rules leaves such turns queued.

## The caller envelope

What the runner hands the agent beside each turn: `apps/harness/caller_context.py::build`, where each field carries its meaning in a comment (additive fields need no `VERSION` bump; a change of meaning does). The envelope **informs, it does not enforce**: nothing in it is a grant. `verified` is about THIS message, never the contact's best-ever grade. The non-obvious contracts:

* **`role` / `source` / `permissions` / `manual_only`** come from the one decision (`published_profiles.grant_facts`, `turn_context.TurnContext.held_permissions`). `permissions` is closed under the dependency rule, and **`write` is in `permissions` exactly when `profile` is `full`**, so a reader may trust either (`tests/test_caller_envelope.py`). A confined turn holds only `read` and `use:<name>` for the host site the turn runs in, even for an owner a sensitive conversation confined; `[]` when refused or for a turn with no agent.
* **`agent_edit` in `permissions` is the agent's cue that THIS asker may change the agent itself** (skills, persona, the code in its own repo; `access.may_edit_agent` says the same on canopy-web). An agent whose asker lacks it does the work asked and does not push or merge to its own repo; the canopy plugin's runner-side rail enforces that, canopy-web only reports it.
* **`granted_by`** is a legacy one-word summary of the same decision for older readers; new readers use `permissions` and `access`, never match its strings. `relationship` is likewise coarser (how canopy knows the asker, not what they may do); read `role`. `trigger.matched_classes` is always `[]`.
* **`access`** (`full` | `confined` | `refused`) is the Turn Context's word; `profile` says `full` on a turn refused before it ran and stays for runners and plugins that read it. `access_help` explains a confined turn in roles only, never people or other callers' data.
* **`agent_repo`** is the agent's own repo as `owner/repo`, on every turn, so the plugin's own-repo rail holds in a session outside the agent's clone. `""` means no repo set (a turn whose asker lacks `agent_edit` then cannot make repo writes from a session where the hook finds none either); `null` means no agent; an envelope without the field means neither. **`own_box_turn`** is true only for a verified person's unconfined no-agent turn on a box that person owns (`relationship: owner` cannot say this); an agent's own login is never one (`caller_context._own_box_turn`). **`ship_grant`** pre-approves push / PR / merge in this agent's OWN repo, even in `manual`, when another agent's verified login that is its owner or an agent admin dispatched the turn; nothing else is pre-approved (`caller_context._ship_grant` lists every condition and `SHIP_NOT_GRANTED`).
* **`unproven_member`** and **`sender_trust`** grant nothing and change no other field. `unproven_member` tells the agent an email sender stayed a `contact` although the address belongs to exactly one member of the agent's workspace and THIS message was not aligned ("your own member, whose mail authentication needs fixing", not "a stranger"); canopy also logs it on the turn's ledger (`UNPROVEN_MEMBER_EVENT`), and a runner cannot post that kind. `sender_trust` is set when a temporary `SenderTrust` an agent admin set for that address tied the sender to a member although the message is not aligned (`verified` stays false).
* **`person`** is what canopy knows about the human asking, null only when the asker is not a human; see "What agents know about a person" in [access-sessions-and-people.md](access-sessions-and-people.md). **`trigger.agent_trigger`** and **`conversation.slack`**: see "Triggers" in [access.md](access.md) and "Agents and their own conversation" in `api-channels.md`; building the envelope never calls Slack (`apps/slack/location.py`).

Readers accept both spellings of the older words: `relationship: caller` means `contact`, `profile: restricted` means `confined` (`normalize_relationship`, `normalize_profile`; the runners and the plugin's hooks do the same). A runner gets confined turns only if it reports `envelope` and `profiles` at or above `apps/harness/routing_orders.py::ENVELOPE_VERSION` / `PROFILES_VERSION` on every heartbeat (`harness/clis.py`).
