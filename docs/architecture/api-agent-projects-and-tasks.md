# API: projects and tasks

The rules the project, task, knowledge-base and proposal routes enforce that their schemas do not show. Part of the [api surface](api-surface.md) topic; the index there lists every part. Methods, paths, filters, fields and status codes are in `/api/openapi.json` (the route docstrings are its descriptions); the model is in [`work.md`](work.md).

## Where to read
- Two addresses reach the same rows. By workspace (`/api/workspace-projects/{workspace}/{handle}/…`, `/api/tasks/{key}/…`): `apps/agents/api_fleet.py` (lists, create, patch, members, shares, KB publish), `api_tasks.py` (task by key, bulk, relations, triage, labels, views, task settings, milestones, updates, services). Through an agent (`/api/agents/{slug}/projects|tasks/…`): `api_board.py` (shared helpers `apply_project_patch`, `apply_task_patch`, `act_and_record`), `api_proposals.py` (propose, backings), `api_contributors.py` (team, ideas, contributor pages), `api_kb.py` (KB versions, steward store, sources). Gates: `apps/agents/gates.py`.
- Project rules (`services/projects.py`, `ProjectScopeError`), task actions (`services/task_actions.py`), proposals (`proposals.py`), KB (`kb_store.py`, `kb_versions.py`, `packages/canopy_kb`), project MCP servers (`apps/mcp/projects.py`, `apps/mcp/project_gateway.py`).
- Sharing, a project's people, personal projects, what a project serves: [`work.md`](work.md).

## Reading and visibility
- A project is readable by members of its workspace, of its lead agent's workspace, and of a workspace it is shared with (and the ones below it); a MEMBER agent's workspace is not enough (`gates.py::project_in_reach`). A project nobody may read, or that does not exist, is the same 404 (`project_ws_or_404`). A personal project is also gated by `services.may_read_project`: a workspace admin does not read it.
- Task reads go through `services.task_read_q`, applied FIRST: `waiting=me` adds unrouted open asks from whatever queryset it is handed, so an unscoped query would leak other tenants' asks (`api_fleet.py::task_query`).
- Filtering an agent's task list by `?project=` returns EVERY task in that project that the agent leads or works on and the caller may read, not just the agent's share (`api_board.py::list_tasks`).

## Who may change a project
- `may_edit_project` (`gates.py`): an editor (`agent.work`) of its workspace or of its lead agent's, a person on it (its lead or `project_members`), or the login of an agent leading or working on it. Milestones, updates, services and KB publish use this gate.
- Creating (`create_workspace_project`) needs an editor of the target workspace, and of the lead agent's too when they differ (`require_workspace_editor`, a non-member gets 404). A project made through an agent's route lives in that agent's workspace and carries its next `P<N>` alias.
- `apply_project_patch` (`api_board.py`): `handle`/`workspace` re-address (409 taken, 422 malformed); `steward` must belong to the project's workspace or one above and the caller must be able to write that agent; a proposed project cannot be started by changing its status (409, `services/projects.py::patch_project`: approve its decision card); a personal project's lead, agents, workspace and visibility are its lead's alone (403). Deleting the lead agent leaves the project unled (`SET_NULL`); moving an agent that leads a project of another workspace is refused (`apps/agents/move.py`). Moving a project to another workspace turns `lead_agent_may_publish` off.
- People (`add_project_member`, `remove_project_member`): the project's lead, an admin on it, or a workspace owner; never an agent's login; joining adds them to every vault attached to the project, so removal does not revoke a key copy they already hold (rotate the vault). A browser needs a passkey step-up, a token does not.
- Shares (`add_project_share`, `remove_project_share`): an editor of the project's OWN workspace (its lead or a working agent's login is not enough); only workspaces of the same organisation, never the project's own or one above it (422). Unsharing removes member agents that qualified only through that share; the lead agent is never removed.

## Updates and who publishes
`apps/agents/api_tasks.py`. A person's update is published unless `draft`; an agent's own login always writes a DRAFT. Publishing: a person who may change the project, or an agent's login only as the project's lead agent, for its own draft, with `lead_agent_may_publish` on (then `published_by_agent`); refusals 403. `set_project_update_settings` (gate `projects.decide`) is a person's decision, never an agent's login; turning it on with no lead agent is 422; every change is audited with the lead agent it covers. Drafts are listed only to those who may edit the project.

## Knowledge base (`apps/agents/api_fleet.py`, `api_kb.py`, `kb_store.py`, `kb_versions.py`)
- canopy-web never builds an index (a build inside the web task would run it out of memory): the steward builds `kb.sqlite` on its own machine and publishes the whole file. The bytes go by a presigned PUT, never through canopy; a key outside the project's prefix or an object that never arrived is 422, no bucket is 503.
- `publish_kb` records a FULL version made from `base`: 409 when another version landed since, so one refresh wins. Rollback serves an earlier version as a new ROLLBACK version; only the newest `KEEP_FILES` versions keep their file (`can_roll_back`). Originals are stored by sha256 and never deleted. Step results are immutable by key.
- Two write gates: upload/originals/publish use `require_project_edit`; the curation routes in `api_kb.py` (results, objects, rollback, settings, source writes) use `_steward`: the project must have a lead agent (409 otherwise) and the caller must be able to work that agent. Reads (`versions`, `file`, `sources`) are the project's readers.
- A project that serves a KB gets its own MCP server at `mcp_path`, and `/api/mcp/projects/` is ONE fixed-tool server for every project (`projects`, `open_project`, `project_skill`, the `kb_*` tools); both use the same sign-in as `/api/mcp/` and check project access on every call, so a non-reader sees no tools and the same answer as a project that does not exist. canopy serves what it holds; it does not proxy a shared remote MCP server. `services` rules: a KB is not removed through the services route (422). Search involves no embeddings: vectors are DORMANT unless `KB_VECTORS` is on (`kb_vectors.py`).

## Proposals and backings (`api_proposals.py`, `proposals.py`)
- `propose_project`: the agent itself or an editor. Creates a `proposed` project, its plan steps, ONE decision card and a linked suggested task on each partner's board; an open proposal of the same name is revised in place (backings go stale, no second card); a name a person declined is 409 unless `new_evidence`. Partners must be agents the caller can see (422).
- Starting or declining is the decision card's approve/decline (the ordinary task action): only `projects.decide` or the project's `owner_user` may decide (403 `MayNotDecide`). Nobody deciding within `proposals.EXPIRES_AFTER` archives it "not taken up".
- Backing is a signal and starts nothing. A person backs as themself, any member, never an agent's login (422); an agent's stance is written by its own login, the project's agent, or the leader of a huddle it took part in (403 otherwise).

## Tasks and actions
- Creating: a workspace editor or the agent's own login, because a task may carry `on_approve` (work that runs the moment a viewer approves it); `POST /api/tasks/` refuses `on_approve` (422). Each task gets a `T<N>` alias; an `idempotency_key` replays, an explicit duplicate `ext_id` without one is 409. A reference naming nothing usable (person, project, turn) is 422.
- Editing a task: an editor of its workspace, its assignee person, or the login of its agent or of the agent that filed it. Giving a task to an agent is the editor's, or that agent claiming it under its own login.
- Actions (`api_board.py::act_and_record`, `services/task_actions.py`): only `nudge` and `done` need an editor; every other action (approve, decline, reply, accept, backlog, snooze, duplicate) is the member tier, because they answer what is already on the board. Exceptions to `done`: the person whose words an idea task carries, and a task's assignee. A task assigned to a person starts no turn. 409 when the action does not apply to the task's state (`ClosedAskError`); 422 changes nothing (empty reply, `on_approve` that cannot run). A reply to an open question wakes the agent whoever writes it, never the agent itself.
- `POST /api/tasks/bulk`: each key is gated and committed on its own, so one task the caller may not change does not undo the rest (per-key `ok`/`error`).
- Marking an action applied (`mark_task_action_applied`) is the agent's own login or the editor tier, never a viewer.
- Task settings: the key prefix is frozen once a task carries it; changes are audited settings (`work.py` rejects a prefix change once tasks carry it; route `api_tasks.py::set_task_settings`).

## Ideas, team and contributor pages (`api_contributors.py`)
Ideas are top-level `kind: "idea"` tasks; a `work` task never shows. `POST …/ideas/` is any member with their own words as `human_why`; an agent's login is 422 (record a person's words through `POST …/tasks/` with `kind: "idea"`). A contributor page holds quotes with `source_url`. An agent reads a page's content only for people who let agents use what they learned, and writes one only while the person's record switch is on and they granted that agent, or by the person themself (403 otherwise, `contributors.py::may_write_summary`); the page read is logged (`PersonAccess`). Delete: the person, the agent's admins, or the writing agent.
