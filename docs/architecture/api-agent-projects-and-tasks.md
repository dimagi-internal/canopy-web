# API: projects and tasks

Routes for projects and tasks by address, knowledge-base versions, proposals, backings, contributors and the workspace task list. Part of the [api surface](api-surface.md) topic; the index there lists every part.

- **Projects (an agent's view):** `GET|POST /api/agents/{slug}/projects/` (`?status=`, a comma list) — the projects it leads or works on; a create through this route lives in the agent's workspace, is led by it and carries its next `P<N>` alias (never reused). Rows carry `handle`, `address`, `url`, `member_agents`, `status` (proposed/planned/active/paused/done/canceled/archived) and `category`, `priority`, `start_date`/`target_date`, `health`, `update_missing`, and the task counts. `GET|PATCH …/projects/{ref}/` (ref: alias, handle or address) — fields, tasks (live first), `participants`, recent turns, `progress`, `milestones`, `latest_update` and (for those who may change it) `draft_updates`, `may_edit`. A PATCH from `proposed` to a started status is 409: the decision card starts it.
- **Every project, by address** (`apps/agents/api_fleet.py`, `api_tasks.py`). `GET /api/workspace-projects/` (member; `?status=`) lists them; `POST /api/workspace-projects/` `{name, handle?, steward?, workspace?, member_agents?, …}` creates one (an editor of the workspace; the handle is free from the name when omitted). `GET|PATCH /api/workspace-projects/{workspace}/{handle}/` — the detail and patch (an editor of its workspace or its lead agent's, its lead `owner_email`, or a working agent's login; non-members 404): `steward` sets the lead agent (`""` none; it must belong to the workspace or one above it, else 422), `member_agents` replaces its agents, `handle`/`workspace` re-address it (409 taken, 422 malformed; tasks moving workspace take new keys; its knowledge base's stored objects stay where they are, keyed by the project rather than its address, `kb_store.root`). Readable by its workspace's members, by its lead agent's, and by a workspace it is shared with and the ones below it. `…/shares/` — `GET` (member) the workspaces it is shared with and the member agents that joined through each, `POST {workspace}` and `DELETE …/shares/{workspace}/` (an editor of the project's own workspace; 422 a workspace outside its tree or its own or above it; the delete returns the `removed_agents` that no longer qualify): `docs/architecture/work.md` § Sharing a project across its workspace tree. `…/members/` — `GET` (member) the people on it, `POST {email, role}` and `DELETE …/members/{user_id}/` (its lead, an admin on it or a workspace owner; never an agent's login; a browser steps up): `docs/architecture/work.md` § A project's people. Deleting its lead agent leaves it led by nobody; moving an agent that leads a project of ANOTHER workspace out of that tree is 409. `…/milestones/` (GET member; POST/PATCH/DELETE `…/milestones/{id}` its editors) — each with `done`/`total`. `…/updates/` (GET: newest first, drafts only for its editors; POST `{health: on_track|at_risk|off_track, body, draft?, checkin_run?}` — an agent's own login always writes a DRAFT) · `POST …/updates/{id}/publish {health?, body?}` (a person who may change it; an agent login only as the project's lead agent, its own draft, with `lead_agent_may_publish` on — then `published_by_agent`; 403 otherwise) records what changed since the last update in `diff`. `PATCH …/update-settings {lead_agent_may_publish}` (a PERSON who is an admin of the project's workspace, `projects.decide` — an agent's login is 403; 422 turning it on with no lead agent; a setting, audited with the lead agent it covers; handing the lead seat on or moving the project to another workspace turns it off) — the detail carries `lead_agent_may_publish` and `may_decide`. **Its own MCP server** (`apps/mcp/projects.py`, `apps/agents/kb_store.py`, `packages/canopy_kb`): the steward's curator `POST …/{workspace}/{handle}/kb/upload` (a presigned S3 PUT, the bytes never pass through canopy; the steward's write gate) then `POST …/kb/publish {key, sha256}` (422 a key outside the project's prefix or an object that never arrived; 503 no bucket). Before publishing, `POST …/kb/originals {files: [{sha256, bytes, content_type}]}` (≤1000; the steward's write gate) answers a presigned PUT for each original file the project's store lacks, under `originals/<sha256>` with S3 checking the sha256 (`x-amz-checksum-sha256`); originals are never deleted, so a KB's superseded versions stay downloadable. The project then has `mcp_kind: "kb"` and `mcp_path` `/api/mcp/projects/{workspace}/{handle}/` — a Streamable-HTTP MCP server carrying ONLY that KB's tools (`canopy_kb.tools`: kb_info, search, entity, doc, read, grep, sql, get, whats_new, one per table…, and `original` — a 15-minute signed download of the file a document was read from, under its file name — when the KB keeps originals), answered from a per-instance copy cached by sha256. Same sign-in as `/api/mcp/` (personal token or OAuth; the `/api/mcp/` protected resource covers it as a path prefix); readable by members of the project's workspace or its steward's, and anyone else sees no tools. The project page shows the one-line install (`claude mcp add --transport http <handle> <url>`) and the connector URL. **The directory** — `GET /api/mcp-servers/` (member; the `list_mcp_servers` tool), page `/w/<ws>/mcp` (Work ▸ Shared MCP servers): every published, unarchived project knowledge-base server in the pinned workspace and the ones below it the caller belongs to (`read_scope`), and every remote MCP server a project there shares (`kind: mcp`), each with its title, description, lead agent, date, URL and add command. **What a project serves** (`ProjectService`, `docs/architecture/work.md`): `GET|POST /api/workspace-projects/{ws}/{handle}/services/` (GET member; POST `{kind: mcp|skill|plugin, name, url, description, instructions}` by those who may change the project — a server or plugin needs its `url`, a skill its `instructions` or the `url` they live at; 422 a taken name, a non-web URL, a malformed name, or instructions on anything but a skill) · `PATCH|DELETE …/services/{id}` (a knowledge base is not removed there, 422). The project detail carries `services`. **The projects connection** (`apps/mcp/project_gateway.py`): `/api/mcp/projects/` itself is ONE MCP server for every project, with a fixed tool list — `projects {query?}` (what the caller may open that carries something), `open_project {project}` (the project's card: its knowledge base's `kb_info`, its skills, its shared servers and plugins with their add lines), `project_skill {project, skill}` (a skill's instructions), and the knowledge-base tools `kb_info`, `kb_search`, `kb_entity`, `kb_doc`, `kb_read`, `kb_grep`, `kb_sql`, `kb_get`, `kb_list_items`, `kb_whats_new`, `kb_table`, `kb_original`, each with a required `project`. Same sign-in and the same per-call access check as a project's own server; no session state. A board turn on a task whose project carries something is told to open it (`dispatch._task_context`). Every row is one the caller can call (the list spans owner and steward workspaces the same way the server's read check does). **Search** (`canopy_kb.research`, `apps/agents/kb_rerank.py`): research tools for an agent — `kb_info`, `search` (passages matching the words, all then any, plus documents whose catalog card matches; with `KB_RERANK_MODEL` set, a Vertex AI ranking API model orders the pool, the word order standing whenever it fails), `entity`, `doc`, `read`, `grep`, `sql`. No embeddings are involved. **Vectors are dormant** (`apps/agents/kb_vectors.py`, `canopy_kb.vectors`, `KbPassage`): with `KB_VECTORS` off (the default and production) search passes none, a publish starts no sync and `manage.py kb_embed` refuses. Kept so a corpus that needs search by meaning can have it back with one setting: when on, a publish syncs passage vectors (gemini-embedding-001, `halfvec(3072)`, HNSW, at most `KB_SYNC_MAX_EMBED` per publish; `kb_embed <ws>/<handle>` for the rest) and `search` adds the nearest passages to the pool the reranker orders.
- **Knowledge-base versions and sources** (`apps/agents/api_kb.py`, `kb_versions.py`; engine `canopy_kb.curate`). A KB is a version log of whole files (`KbVersion`: full | rollback; `delta` survives only on versions from the earlier in-process build). canopy-web never builds an index: the steward builds kb.sqlite on its own machine (`canopy_kb.curate`, `canopy kb push`) and publishes it whole (a build inside the web task would run it out of memory). Each version carries the curation state it was built from (`curation_sha`, a root in the steward's results store), and a refresh starts from the head version's: it decides on its own that nothing changed (nothing built, sent or saved), else applies the difference to the served file (`GET …/kb/file`), builds, and publishes the whole file, `…/kb/upload` then `…/kb/publish {key, sha256, base, curation, changes?}`, which records a FULL version made from version `base` (409 when another landed since: one refresh wins; `changes` counts content changes for the log). `GET …/kb/versions` (member) is the log; `POST …/kb/versions/{n}/rollback` serves version n's file and state again as a new ROLLBACK version (only the newest `KEEP_FILES` versions keep their file: `can_roll_back`). `GET …/kb/file` (member) is a 15-minute download of the served file (`canopy kb pull`). The `whats_new` tool reads the file's own history (`changes`: its builder records only documents whose content changed). Step results (`…/kb/results`, `…/kb/objects/have|links`, steward only) are immutable, by key. `PUT …/kb/settings {drive_replica}` (setting): off by default; on, each new version's kb.sqlite.gz is also written into the project's Drive folder with canopy-web's service account. **Sources** (`KbSource`): `GET …/kb/sources` (member), `POST …/kb/sources {kind, name, config}` (the steward; setting): `web`, a curator's crawler, is the only kind (anything else 422). Readable by the same members as the project, like every KB. Page: `/w/<ws>/projects/<handle>/kb`.
- **Proposed projects** (`apps/agents/proposals.py`, `api_proposals.py`; spec `docs/superpowers/specs/2026-10-16-work-group-huddles-design.md` layer 1). `status=proposed`, `source_url` = the page that proposed it. `POST /api/agents/{slug}/projects/propose/` `{name, outcome, why, plan[], partners[], source_url, owner_email?, new_evidence?, group?}` (the agent's login or an editor) → 201 `{created, project}`: the project, its plan steps (`suggested`), ONE decision card (review ask "Start this project?", `origin_ref.kind=project_decision`) and a linked `suggested` task on each partner's board (`origin_ref.kind=project_partner`, `source_url` = the project page); 200 when an open proposed project of that name (any case) is revised in place — backings go `stale`, no second card; 409 for a name a person declined unless `new_evidence`. The card's **approve** (only `projects.decide` or the project's `owner_user`, else 403) makes the project `active`, starts the lead's turn and moves partners' tasks to `in_progress`; **decline** archives it with `Declined: <reason>` in `notes`; **reply** (any member) is the comment thread. Unstarted for 14 days (from `proposed_at`) → archived "not taken up" by the agents app's periodic job (`agents.pat_rotation` on `apps/common/ticks.py`). `GET …/projects/{ref}/` carries `proposal` (the card both the project and huddle pages render).
- `GET …/projects/{ref}/backings/` (member) · `PUT|DELETE …/backings/me/` (any member as themself, never an agent login; makes them a `backing` participant) · `PUT …/backings/agents/{agent}/` (that agent's login, or the project's agent's) — `{stance: backs|backs_with_changes|passes, line ≤280 (required unless backs), huddle_id?}`; one row per person and per agent, rewriting clears `stale`. A signal: backing starts nothing.
- `GET /api/agents/{slug}/projects/{ref}/contributors/` (`apps/agents/api_contributors.py`) — the project's ideas: its top-level `kind: "idea"` tasks (a `work` task never shows); `stage` (suggested → proposed, in_progress → started, done → shipped, declined); `came_from` per person, strongest evidence first (`human_why`, the raising human, pages that claim it).
- `GET /api/agents/{slug}/projects/{ref}/team/` — the team view's one read: outcome, links, owner, ideas shipped / in progress, the decisions waiting on people, every idea with its status and whose it is, and the people tallied over them; `may_edit` = may use the work board. `POST …/projects/{ref}/ideas/` `{quote, title?}` (any member) → 201 `{idea, notified}`: your own idea, as a `kind: "idea"` task with your words as its `human_why`; tells the agent (one turn) and the project's owner. An agent's own login is 422 (record a person's words via `POST …/tasks/` with `kind: "idea"`).
- `GET /api/agents/{slug}/projects/{ref}/contributors/{person}/` — one contributor page (`person` = id or email, must be `known_in` the workspace; read logged in `PersonAccess`): goal in their words, quotes with `source_url`, ideas by stage, uncovered wants (`open`); `may_write`/`why_not`. `PUT …/summary/` stores an agent's page (`ideas[].task` must be a project task) — for an agent only while the person's **record** switch is on and they granted it, or by the person; `DELETE …/summary/` by the person, the agent's admins, or the writing agent. Without the person's **use** switch + grant an agent gets `summary_state: withheld`. Procedure: canopy's `contributor-page` skill.
- **Tasks (an agent's view):** `GET /api/agents/{slug}/tasks/` — the tasks it is assigned, plus those it filed that no agent is assigned — or, filtered `?project=` to ONE project it leads or works on that the caller may read (the ref resolves as the agent's other routes do, its own alias first), every task in that project (a person's, an unassigned one, another agent's); filters `project` (alias, handle, address or `none`), `status` (comma list), `waiting=me`, `ask=open|closed`, `batch`, `parent`. `POST …/tasks/` — a list; the agent files them, is their assignee unless `assignee` says otherwise, and each gets its `T<N>` alias (explicit or next); a per-task `idempotency_key` replays; a workspace editor or the agent's own login (a task can carry `on_approve`). `GET|PATCH …/tasks/{ref}/` (ref: a key, or this agent's alias) — one task with action history / patch fields (`project: ""` unfiles; omitted leaves it). Every task carries `key`, `url`, `agent_slug` (assignee agent), `assignee_email`, `category`, `priority`, `labels`, `milestone`, `snoozed_until`, `rank`; `ext_id` is its alias, else its key.
- `POST /api/agents/{slug}/tasks/{ref}/actions` — `{action, comment?}`: `approve` → in progress and the agent starts now (`on_approve` turns, or one turn written from the card via `apps.harness.dispatch.enqueue_task_turn`); `decline` → declined (comment = reason); `reply` → on an open question the answer (closes the ask, runs `on_approve` or starts a turn carrying the answer, unless the agent answers itself); otherwise a note (an editor's starts a turn, a viewer's waits for the next turn); `nudge` (editor, `in_progress` only) → starts a turn, status unchanged; `done` → done; `accept` → todo and `backlog` → backlog (both close a review ask and start nothing); `snooze` (comment: a date, default a week) → out of Triage until then or until anything happens on it; `duplicate` (comment: the key it duplicates) → declined, with a `duplicate` relation. A task assigned to a person starts no turn: approve moves it to in progress. Viewers may approve/decline/reply. A board turn reuses a not-yet-started turn of the same task; `turn_ids` names turns started. 409 when the action does not apply to the task's state; 422 (nothing changed) on an empty reply or an `on_approve` that cannot run.
- `GET /api/agents/{slug}/actions/` — action queue (`?status=pending`; `limit` default 200, cap 500; unfiltered: pending first). `POST …/actions/{action_id}/applied` — `{result_note?}`, the agent marks one carried out.
- `GET /api/agent-roster/` — one row per visible agent for the Agents table: open tasks and those waiting on a person, active projects, skills, schedules (`health._counts`), and its turns through `visible_turns_qs` — last turn and status, turns and failed/lost in 7 days.
- `GET /api/tasks/` — the workspace task list across every workspace you may list: the agent-view filters plus `agent` (that agent's board), `assignee`/`created_by` (`me`, an email, `agent:<slug>`, `none`), `category` (triage/backlog/unstarted/started/completed/canceled), `label`, `priority`, `milestone`, `kind`, `due_before`/`due_after`, `q`, `snoozed=hide|only`, `sort` (rank, created, updated, priority, due, status, title; default reviews → questions → rest, oldest first), `limit` ≤ 500. `GET /api/tasks/count/` — the same filters as one number (badges). `POST /api/tasks/` — one task in `workspace` (editor), assigned as `assignee` says. `GET|PATCH /api/tasks/{key}/` — one task by key: fields, `events` (its whole history: created, every tracked field change, every action with its comment, relations), `relations`, `subtasks`, `parent`, `turn` (the assignee agent's latest turn on it and its `turn_status` state), `blocked`, `may_edit`, `status_names`; PATCH as on the agent route plus `assignee`, `labels` (replaces), `milestone`, `priority`, `snoozed_until`, `before`/`after` (keys: the tasks just above and below where a drag lands it). Editing: an editor, the task's assignee person, or the login of its agent or of the agent that filed it; giving it to an agent is the editor's (or that agent's own login). `POST /api/tasks/{key}/actions` — the actions above. `POST /api/tasks/bulk {keys, patch?, action?}` — each key under its own gate and transaction; per-key `ok`/`error`. `POST /api/tasks/{key}/relations/ {kind: blocks|blocked_by|related|duplicate, other}` · `DELETE …/relations/{kind}/{other}`. `GET /api/triage/` (`?workspace=`, `?project=`) — suggested tasks and ideas (unsnoozed) and proposed projects, oldest first, with backers. `/api/labels/` (GET member; POST/PATCH/DELETE editor; colours are semantic token names). `/api/views/` — saved task views: yours and the shared ones (a member saves their own; sharing is an editor's). `GET|PATCH /api/task-settings/?workspace=` — key prefix (frozen once a task carries it), status names per category, update cadence (audited setting). `GET /api/projects/` — every project you may list (`?status=` comma list or `open`, default active; `?repo_slug=`; `?scope=` is accepted and ignored).
