# Stored agents

A **stored agent** is an agent whose definition is a git repository **canopy-web hosts** instead of GitHub (`Agent.source == "stored"`, `repo_url` empty). canopy is its only writer and its publish gate; people and runners read it with ordinary git over HTTPS (`definition.git_url`), so everything downstream of "a git clone of the agent" works unchanged. A repo agent's definition is its GitHub repository (`apps/agents/definition.py`). Start reading at `apps/agent_definitions/services.py` (module docstring) and `apps/agent_definitions/api.py`; the git layer is `apps/agents/definition_git.py`, the smart HTTP endpoint `apps/agent_definitions/git_http.py`, the models `apps/agents/models/definition.py`.

## The repository

- **One bare repository per agent, in the database.** Its objects are `AgentGitObject` rows (zlib'd raw content, keyed per agent by git's SHA-1) and its refs `AgentGitRef` rows; dulwich reads and writes them through `definition_git.AgentObjectStore`. A Fargate task's disk does not last, so no git binary or working tree holds any state. Objects are scoped to their agent, so who may read a repository is a question about one agent. The hashing is git's, so the repository is byte-compatible with GitHub.
- **Refs.** `refs/heads/main` is the live published definition; `refs/heads/draft` the one draft; `refs/tags/r<N>` published revision N; `refs/heads/imported` the history a convert brought from GitHub, never moved again.
- **A revision is a commit.** `AgentDefinitionRevision` is the metadata and approval layer over it: `commit`, `number`, `status`, `approval`, the author and publisher. Its `tree` (`{path: {sha256, size, executable}}`) and `root_sha256` (`canopy_sdk.agent_definition.manifest_root`, which older CLIs check an archive against) are read from the commit's files when it is written, and kept so the API answers without reading every file.
- **Commits.** The author is the person, or `<slug> <agent@canopy.dimagi.com>` for an agent's own draft (`definition_git.agent_author`); the committer is always `canopy <agents@canopy.dimagi.com>`; the message is the revision's; the parent is the commit the draft was made on.
- **Publishing writes the commit `main` points to.** The generated files are rendered again for the revision going live (its number is the plugin version) into a commit on the live one, with the draft's author and message; `main` and `r<N>` move to it and `draft` goes (`services.publish`, `_publish_now`). A rollback is a new commit on `main` with an old revision's editable files. Nothing deletes or rewrites history: revisions are append-only, a discarded draft keeps its commit, and numbers are never reused.

## The file policy

`canopy_sdk.agent_definition.check_tree` is the policy, in the SDK so the CLI can ask it before uploading; `services._full_tree` enforces it on the tree of **every commit canopy writes to `draft` or `main`**. A tree holds only the editable paths (`EDITABLE_GLOBS`: the top-level docs, `skills/<name>/…` text files, three `config/` files, `tests/` and `docs/` data files) plus the files canopy generates. Refused: traversal, absolute paths, backslashes, NUL, `.git/`, hooks, symlinks, any executable but `bin/<slug>-email`, more than 200 files, 256 KB a file or 2 MB in all, non-UTF-8 content, and secret-shaped strings (`SECRET_SHAPES`, kept in step with `apps/common/redact.py` by a test). A refused write changes nothing — its objects and ref are undone with its transaction — and answers 422 with every `problems` entry. Imported history is not held to the policy; only convert's secret scan covers it.

**Generated files** (`definition_store.generated_files`) are written by canopy on every revision and again at publish, never taken from an upload: `.claude-plugin/plugin.json` (name, version `0.<N>.0`, description; never `hooks` or `mcpServers`), `.claude-plugin/marketplace.json` (`source: "./"`), `.claude/settings.json` (only `CANOPY_AGENT`), `bin/<slug>-email` from the agent factory, and `.gitignore`. A stored agent therefore runs only its skills, under canopy's own plugin.

## Who changes it

Changing a definition changes what runs with the agent's vault and credentials, so:

- **Drafting** is `agent_edit` on the agent (`agent_for_edit`), which its own login holds. Changes apply to the live revision named as `base` (409 `stale_base` otherwise) and replace any earlier draft.
- **An agent's draft asks a person.** A draft written by an agent (its own login, or any token a turn holds: `harness.acting_person.refusal`) records `by_agent` and the turn it came from, and files an `agent.definition.publish` approval (`apps/agent_definitions/publish_kind.py`) naming the draft by number and root sha256. Its approvers are the agent's admins who are people, from the request's page with a passkey (`Kind.step_up`); a draft replaced or discarded withdraws it, and one left open cannot publish anything else.
- **Publishing, rolling back, converting, exporting and detaching** are the agent's owner or an admin acting as themselves (`api._require_person`): refused to an agent's login, a turn's login, a caller or act-as token, and any request naming a turn.
- **Creating** one (`POST /api/agents/stored`) is the same gate as registering an agent: the factory's scaffold, less what only a repo needs (workflows, scripts, Python), becomes revision 1, published (`services.create_stored_agent`).
- **Nobody pushes.** The repository is served read-only; every change is a draft through the API (`canopy agent definition edit`).

## Moving between GitHub and canopy

- **Convert** (`…/definition/convert`) takes a repo agent's tracked files as revision 1; any file outside the policy refuses the whole conversion, and uploaded generated files are ignored. With `bundle_b64` (a `git bundle` of its branch) the history comes too: every object goes under `refs/heads/imported` and revision 1 is a commit on its tip (`definition_git.read_bundle`). Every blob in the bundle, in every commit, is scanned for secret shapes first; one hit refuses the convert with its path and commit, and nothing is kept. A bundle with prerequisites (a partial history) is refused. Files and history together are held to what one request carries (`services.MAX_CONVERT_BYTES`): more is 413, and the answer is a files-only convert.
- **Export** (`…/definition/export {repo, ref?, github_token}`) pushes `main` — every commit and every `r<N>` tag — to an **empty** GitHub repository, then sets `source=repo`, `repo_url`, `repo_ref` and no live revision (`services.export`). A repository with any ref is 409 `not_empty`; one that cannot be reached (including one that does not exist: creating it is the person's job) is 502. The push uses a token of the person exporting, for that request only: canopy-web cannot open the agent's delegated GitHub token, which is sealed to the machines that run the agent (`apps/agents/credentials/delegations.py`). The token is never kept, logged or echoed (`services._redacted` on any error).
- **Detach** (`…/definition/detach {repo_url, ref?}`) is the same switch with nothing pushed, for a person who cloned the definition and pushed it themselves.
- **After either**, canopy's repository is a read-only archive (`Agent.definition_exported_to`): it is still served, and every draft, publish, discard, rollback, convert, export or detach answers 409 `exported`. Runners see `source: "repo"` and clone it from GitHub.

## Reading over git

The repository is at `<base>/git/<workspace>/<slug>.git`, git's two smart HTTP reads (`info/refs?service=git-upload-pack`, then a POST to `git-upload-pack`) served by `git_http.serve`, a bare view in `config/urls.py`. It authenticates itself — `/git/` is in `apps/common/middleware.py::PUBLIC_PATH_PREFIXES`, it is CSRF-exempt because it writes nothing, and the old address serves it in place (`legacy_prefix.MACHINE_PREFIXES`):

- **The credential** is a canopy token as the password of HTTP Basic (any username) or as `Authorization: Bearer`. Only a PAT and a runner's own token are taken (`principal.resolve_bearer` with those two kinds); a contact's token, a conversation's caller token (all a confined turn holds), a site's delegated token, an act-as token and a browser session are refused as if absent: 401 with `WWW-Authenticate: Basic realm="canopy"`, so git asks.
- **Who reads what.** A person reads an agent in a workspace they are a member of; an agent's login (its own, or a turn's) reads its own agent only; a runner reads an agent its box may hold (`holding.runner_may_hold_agent`) and a `computer` runner nothing (`apps/harness/runner_auth.py` admits the two git routes for a runner token). Anything else is 404, as for a missing repository. A runner is served `main` and the tags; a person and the agent's login also `draft` and `imported`.
- **No push, ever.** `git-receive-pack` is answered for everyone, before any credential is read, with git's `ERR` line naming `canopy agent definition edit`. The dumb protocol is not served.
- **Streaming.** The repository is read into memory (`AgentObjectStore.preload`), dulwich's upload-pack runs on a worker thread, and the response yields each write as it happens — an async iterator under ASGI, so Django never collects the pack first.
- **The token is never logged**, and the CLI passes it with `-c http.extraHeader` on each command, never in `.git/config` or the remote URL.

`definition.git_url` (`<CANOPY_PUBLIC_BASE_URL>/git/<workspace>/<slug>.git`, `definition_store.git_url`) is on the agent detail, `/runtime`, the credential resolve and `GET …/definition`, with `commit`; an exported agent keeps its archive's `git_url`.

**Older CLIs** still work: `GET …/definition/archive` is a gzip'd tar of one revision (regular files, 0644 or 0755, fixed times and owners) with `X-Canopy-Revision`, `X-Canopy-Root-Sha256`, `X-Canopy-Published-At` and `X-Canopy-Workspace`, read from the revision's commit, and every revision still carries `tree` and `root_sha256`. A runner's token reaches the archive for an agent its box may hold, published revisions only. Neither the archive nor the git endpoint is an MCP tool; an agent reads a file with `get_agent_definition_file`.

## What a stored agent does not have

- **No GitHub repository.** `repo_url` stays empty: `set_repository` and the upsert refuse to give it one (409 `stored_agent`, `apps/agents/api.py::_refuse_repo_on_stored`), since that repo's code would run instead of what a person published; moving to GitHub is an export. Where it comes from instead is `definition: {source, revision, root_sha256, commit, git_url}` (`definition_store.source_of`) on the agent detail, `/runtime` and the credential resolve a box's `canopy agent prepare` reads.
- **No GitHub identity or repo step** in its setup checklist (`setup.setup_steps`), **no plugin-catalog entry** (`apps/plugins/services.py::member_agents`), and **no repo-internal ship grant** in its caller envelope (`harness/caller_context.py::_ship_grant`): it changes itself only by drafts.
- **No `canopy agent-publish` of skills** (`PUT …/skills/` is 409): its catalog is read from the live revision at each publish, and its skill history from its published revisions (`skill_history._sync_stored`). Its definition key is `canopy:<workspace>/<slug>` (`definition.agent_definition_key`), shared with no other instance.
