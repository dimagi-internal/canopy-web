# Vaults: OAuth connections sealed to their owner

How a person's OAuth connection is sealed to them, the connection audit and calls from screens. Part of the [vault](vault.md) topic; the index there lists every part.

Start reading at `apps/connections/__init__.py` (the contract and where each piece lives); each module's docstring is the contract for its part. The normative wire format is `docs/vault/zk-v1/connections_v1_reference.py` with vectors in `connections_v1_vectors.json` (the CLI and the frontend test against the same files). Routes: [`api-connections-and-tokens.md`](api-connections-and-tokens.md) § Connections. The KMS key and `CONNECTIONS_SERVER_STATEMENTS` are set in `config/settings/base.py` ([`deploy.md`](deploy.md)); the minimum CLI for cloud boxes is `runner/ec2/cloud_runner.py::CONNECTIONS_ZK_MIN_CLI`. A new provider is one module in `apps/connections/providers/` (the recipe is that package's docstring, `providers/base.py`) plus a module in the canopy CLI for refresh and revoke.

## OAuth connections are sealed to their owner

A token canopy gets from **its own OAuth flow** (Settings → Connections: Salesforce, Google) is kept like a vault secret: canopy-web finishes the sign-in and seals the refresh token to the owner's vault key at once. Machines the owner allows refresh it. Unless the owner switched on "canopy-web can use this" for that connection, canopy-web keeps nothing it can open. Other things canopy-web holds (Slack tokens and so on) are outside this section.

**The guarantee, and its limits.**

- **With the switch off, a connection made before canopy-web is compromised is safe.** canopy-web stores no readable refresh or access token, never refreshes and never revokes a stored token; an attacker who takes the server gets ciphertext.
- **With the switch on, canopy-web can open it.** The switch is `Connection.server_use` (a new row's default is the provider's `server_use_default`; the owner may change it). On, the tokens are also sealed to canopy-web's own `ECC_NIST_P256` KMS key (`server_key.py::KEY_SPEC`) that only the task role may use to derive, so canopy-web can open, refresh and revoke without a runner or a person present (`server_key.py`, `server_tokens.py`).

  | If someone gets… | Switch off | Switch on |
  |---|---|---|
  | A database dump or backup | Nothing | Nothing: the key never leaves KMS |
  | Control of the running server | Can trigger runs, can't take the token | Can have KMS open the token and keep using it after being evicted, until the owner disconnects |

  KMS logs every use, and removing the task role's grant from the key's policy cuts canopy-web off at once. Turning the switch off stops future use by an honest server; it does not retract a copy already stolen, which takes a disconnect. A hacked server cannot turn the switch on for an off connection: it is not a recipient, and machines reseal only as the owner's signed statement allows.
- A connection made while canopy-web is compromised is exposed: canopy-web does the code exchange, so it sees that one refresh token in passing, and could substitute the owner key the token is sealed to.
- Browser code is served by canopy-web, so an owner who opens the share screen or Settings while it is compromised can be handed hostile JavaScript. This is the limit of every canopy zero-knowledge vault.
- A box with no pin for a connection (its first read) can be handed a self-consistent forged set. That gives it a substitute token, never the real one, and the box pins the forger's owner key, so the real set is refused there until the pin entry is removed or the box replaced.
- A device carrying an old endorsement by the owner or a listed endorser, for an agent still in the statement, can be re-listed by a hacked server. Removing it from the statement or revoking its device key does not retire it; to retire one that may be compromised, disconnect and connect again.
- A hacked server can force a revoke (mark a connection `revoking`). That is an outage, not theft.
- **The switch in the protocol.** canopy-web is a `device` recipient whose target is the key's thumbprint. The signed statement carries an optional `canopy_web: <thumbprint>`, present only while the switch is on, so a statement with the switch off is byte-identical to one without the feature. `recipients.py` adds canopy-web when `server_use` is true and, on an `active` row, only when the statement names the current thumbprint; machines accept an envelope canopy-web wrote only under a statement naming it. `sharing.py` accepts `canopy_web` only if it equals the current thumbprint, the signer is the owner, and `CONNECTIONS_SERVER_STATEMENTS` is on; the statement then sets `server_use`. Turning it off with no statement yet is `sharing.turn_off_server_use` (no passkey; canopy-web prunes itself from both envelopes); every other change goes through Share and a signed statement. Reconnecting keeps the owner's choice, unless the reconnect names limits, which turns it off and seals to the owner alone. With the key unset every connection behaves as switched off, except that an unshared or active row already naming canopy-web is kept rather than stripped, so a bad deploy cannot take away access only the owner can restore. To roll back, roll back the image, not the KMS key setting: with the key unset, a machine's rotated write-back drops canopy-web from that envelope until the owner's next share.
- **How canopy-web gets a token** (`server_tokens.access_token`): an in-process cache keyed by connection and envelope digest; else it opens the access envelope through the key; else it takes the same refresh lease machines take (holder `canopy-web`), refreshes, and writes back under the same compare-and-swap, sealed to everyone `recipients` names with the plaintext's contract fields unchanged. A rotated token is retried for a bounded time (`ROTATED_WRITE_SECONDS`). `invalid_grant` marks `needs_reconnect`. Disconnecting a row canopy-web can open revokes it at once.
- A person the statement names in `endorsers` who replaces their vault key leaves the machines only they vouched for unprovable: those machines stop until the owner shares again, or reconnects if such a machine wrote the envelope. The owner's own replaced key does not do this: the row keeps their key and signatures (`owner_public_jwk`, `owner_endorsements`), which readers verify against the sealed `owner_key`. Until the row is disconnected, new tokens stay readable by that old key (`ConnectionOut.owner_key_replaced`).
- The app's client secret stays server-held (`ConnectionApp.client_secret_enc`, Fernet, never returned: only `has_secret`). Alone it is worth little: it needs a refresh token, and token endpoints come from the provider's fixed rules, so a lying server cannot send a refresh token to itself. It leaves canopy-web only in a material response to an authenticated machine.

Rules:

- **App.** A provider's OAuth client is a `ConnectionApp`, one per (workspace, provider), set up by a workspace admin. Every `Connection` belongs to one app, so a connection through workspace A's app is a different row from the same account through B's. A person can use a connection only while a member of its app's workspace; an agent connects with its own workspace's app, and its connection (with every grant of it) works only while the agent is still in that workspace. `client_id` and the provider's `locked_options` cannot change while connections exist (409 `app_locked`). Removing an app sets `removed_at`, hides it and marks each of its connections `revoking`; the sweep deletes the app once they are gone. A callback is bound to the workspace and client its start parked (`bad_state` otherwise); a provider's `check_owner` can refuse an account after sign-in (`wrong_account`).
- **Owner.** A `Connection` belongs to exactly one person or one agent; there is no fallback between owners. An agent's turn uses the agent's own connection or one lent to it, never the person who started the turn. A row's `owner_key` (the thumbprint of the owner's member vault key, sealed inside the envelope) never changes. The key and its holder's user id are kept on the row at connect (`owner_public_jwk`, `owner_user_id`), so a signer who replaced their key or was deleted leaves a connection machines can still read and revoke; a reader trusts that key only because its thumbprint is the sealed `owner_key`. Connecting the same account again with a different vault key is refused as 409 `owner_changed`, the new grant discarded and the row untouched: disconnect first, a holder revokes, then connect (a new row, so a new pin on every box). Only the connector, the person or the admin who connected an agent's connection, can change who uses it; any other admin of the agent can see and disconnect it.
- **Scopes.** A connection stores what the provider GRANTED. A grant missing a provider's `required_scopes` is refused at connect (`insufficient_scope`).
- **Connect and seal.** Connecting needs the owner's vault key (the person's, or the connecting admin's for an agent): without one, start refuses with 409 `no_vault_key`. At the callback canopy-web exchanges the code with the app's secret, looks up the identity, applies every policy check, then seals the `refresh` plaintext to the owner's member key (plus canopy-web's key when the switch is on), drops the access token and records `connected`. The row is `unshared`. A Salesforce grant refused after the exchange is revoked at the provider before it is dropped; a Google grant refused after the exchange is discarded without revoking, because revoking at Google ends every token of that account on that OAuth client. Salesforce hosts are checked (`providers/salesforce.py::LOGIN_HOSTS`, `MY_DOMAIN_SUFFIX`; https only) when the app's `login_url` is set and again at connect, and every machine applies the check to what it opens. Refresh and revoke endpoints are derived from these and never taken from canopy-web or from the envelope as given. Connecting the same account again for the same owner through the same app replaces that row's envelope, sets it `unshared` and keeps its grants.
- **Sharing and the signed statement** (`sharing.py`). The owner's browser opens the envelope and signs a **grant statement** (ECDSA P-256 by the owner's member key), re-signed on every lend, withdrawal or change of "Use on my computers". `agents` are the agents it is lent to (for an agent's connection it must list the agent itself); `my_computers` are the owner's own enrolled machines (a person's connection only); `endorsers` are person keys, besides the owner, whose endorsement of a machine counts; `version` only goes forward. canopy-web checks what it can: the signer holds `owner_key`, the signature, the version, that every agent added is one the signer administers in the app's workspace, that the computers are the signer's own, and that the new envelope is sealed to nobody the statement and `recipients` do not allow. It never signs and never opens the envelope. A machine vouched for only by someone this browser has not trusted is offered there for the owner to trust; accepting pins them as elsewhere (`vault/trust.ts`) and names them in `endorsers`. An owner who closes the tab leaves the connection `unshared`: sealed to the owner only, handed to no machine. An agent's connection is part of the connect, so it is not listed until the first signed share (`Connection.objects.unfinished`), and the sweep disconnects it after `keeper.UNFINISHED_AFTER`. A passkey can't be asked before the sign-in: the statement names an account only the sign-in reveals, and the envelope's MAC needs the unlocked key once the token exists.
- **Envelope authentication.** Every envelope a machine or the owner's browser writes carries, per recipient, a MAC keyed by ECDH between the writer's key and that recipient's key, bound to the digest it replaces (`expect`). A reader accepts an envelope only if its writer is a device the statement allows or the owner's member key; anyone can build a `zks1` from public keys, so an unauthenticated envelope is refused by every machine. The one exception is the owner's own browser accepting canopy-web's first seal (which carries no MAC) while the connection is `unshared`. Both envelopes (`refresh` and `access`) carry `owner_key` and `statement_floor`: a reader refuses a statement whose `version` is below the floor in either envelope, so an old validly signed statement cannot re-admit a device the owner removed. A machine that has validated a read pins `(owner key, version)` for that connection and refuses a rollback or a changed owner.
- **Recipients** (`recipients.py`, the one rule behind every seal, re-seal and write-back). A machine never trusts canopy-web's list over the signed statement: the list can only narrow it. Who may open: the owner's member key; a device whose ECDH key is in the statement's `my_computers`; a device carrying a valid endorsement of its exact ECDH key for an agent the statement lists, signed by the owner or a listed endorser. There is no first-sight pinning for connections: an endorsement counts only when the owner or a listed endorser signed it. A grant counts only while it is in force today: the agent is still in the app's workspace and, for a person's connection, the person still administers it. An agent-owned connection's grants do not lapse on its signer's admin standing as such, but its machines can: an endorsement counts only while its endorser is in the agent's vault (`zk_endorse.endorsements`), so when the connecting admin leaves, machines only they vouched for stop being recipients and the connection reaches nothing for that agent until someone connects it again. A lent agent no machine can receive it for is listed in `ConnectionOut.unreachable`. Recipients that stop qualifying are pruned from the envelopes without decrypting, except one cloud box kept so that a revoke can still happen.
- **Getting a token (lease and write-back)** (`tokens.py`). A machine reads the material (both envelopes, the statement, the owner's key, endorsements, recipients and the app's client id and secret, never a token) and opens the envelopes itself. A live access token is used as it is. Otherwise it reads twice around the one **refresh lease** (single holder, `LEASE_SECONDS`, answered with `ttl_seconds` so a skewed box clock cannot matter): material, lease, material again with full validation; if a newer access token landed meanwhile it releases the lease and uses that, else it refreshes from the second read, so it can never refresh with a token already rotated away. It then writes back a new `access` envelope and, when the refresh token rotated, a new `refresh` envelope, against the digest it read; only then is the token staged. A rotated token gets a time budget, not a retry count. If the box dies, the lease expires, the next refresher gets `invalid_grant` and the connection is marked `needs_reconnect` (recorded `lease_expired_unwritten`). A refresh the provider refuses ends the lease at once. A laptop that refreshes seals the write-back to the envelope's current holders narrowed by what the statement allows, never to machines still waiting; a laptop never adds recipients and never revokes. A write-back onto a `revoking` row is 409 `revoking` and stores nothing. The client id sealed in the envelope must equal the app's, or the refresher refuses.
- **Re-sealing for new machines** (`keeper.py`). The cloud box's keeper (`canopy vault zk keep`) asks for connection work and re-seals the same plaintext to machines the statement allows that are still waiting for a copy (`expect` = the stored digest), so lending a connection to a new agent needs no action from the owner when any holder is online. With no holder the grant shows as waiting, and the owner can give waiting machines a copy from the share screen.
- **Lending for an hour (not sealed)** (`temporary.py`). A person's connect with `temporary=1` and `for_agent=<slug>` (Google only) asks the provider for no refresh token, needs no vault key or passkey, and has no share screen. The access token is the one thing here canopy-web CAN read: it is encrypted with canopy-web's own key (`TemporaryAccess`) and handed in the clear over the runner's authenticated route to the runner holding a turn the lender started. So a hacked canopy-web could use or redirect a token while it lives, for at most an hour, and cannot renew it or mint another: nothing renewable is ever held, and a provider that answers with a refresh token anyway is refused. Ending it revokes it at the provider (at Google, that ends every token of the account on that client) and takes no passkey; a token that ran out is swept.
- **Lending for a while.** A person's connect can name limits (`lend_minutes`, `owner_turns_only`; `Connection.limited`). `expires_at`: from then on no machine is handed it, on a turn or the owner's own computer, and the sweep disconnects it. `owner_turns_only`: it is staged only on a turn its owner started (signed in or on their own token, or canopy's follow-up to their agent task), never on anyone else's turn of that agent, which also keeps two people's lends to one agent from being `ambiguous`. A connection with either limit is never canopy-web's own to use: a new row starts with the switch off, a limited reconnect turns an on row off, and a statement naming canopy-web is refused (422 `bad_canopy_web`). Both limits are canopy-web's to enforce, outside the signed statement: a hacked canopy-web could lift them, though it still cannot read the token. Neither reaches a turn already holding the staged file, and the file is one per agent on a box, so another turn of that agent running beside the owner's on the same box could read it.
- **Revoking.** Disconnecting marks the row `revoking`: gone from every list at once and never handed out again. The first cloud box that holds it opens it, revokes at the provider (Google: only when no other connection of that account through that app remains) and confirms, and the row is deleted. A dead token counts as revoked. A provider outage confirms nothing: the box tries again on a later pass. A connection no cloud box heard from within `recipients.REVOKER_GONE_AFTER`, or whose envelope no holder could accept, is deleted at once (or by the next sweep if already `revoking`); one still unconfirmed after `keeper.REVOKE_GRACE` is deleted by the sweep; all are recorded `revoke_unconfirmed`, and the provider's own idle expiry finishes the job. The disconnect route says which happened (`outcome`), so nobody is told a machine will revoke what none will. Only cloud boxes keep or revoke.
- **On a box** (`runner/ec2/cloud_runner.py`, the connections staging). The cloud runner asks which providers a turn's agent has and, for each, runs `canopy cred connection-token <provider> --runner` to write `~/.canopy/connections/<slug>/<provider>.json` (0600, a sensitive path), re-staged on the lease heartbeat and removed when the turn ends. CLI exit 3 means nothing to stage (not connected, or being revoked); exit 4 means waiting, no copy has reached this box yet: the turn keeps its hold and the heartbeat tries again. A person's own CLI needs the laptop **enrolled** (`canopy vault device --enroll`) and **Use on my computers** turned on for that connection; a PAT alone gets no token. Neither the material nor the lease routes are MCP tools (`apps/mcp/api_tools.EXCLUDED`).
- **In a plain job.** A job (`runner-flags-and-schedules.md` § Plain jobs) holds its own 0600 copy of the access token of each connection its agent can use, in `$CANOPY_JOB_TOKENS/<provider>.json`, for its run only. It is an ACCESS token (never the refresh token), but whoever wrote the job, the repo's authors who can merge to `main`, can read it and print it or send it anywhere on the public internet. The runner scrubs the exact token value from what it streams back, which stops accidents and nothing more. Setting a job needs agent admin, as lending the agent's connections does; the connection used is the agent's by the usual rule (its own, else one lent to it).

### Connection audit

Every record goes through one function, `apps/connections/services.record`, in one vocabulary; the verbs that are the owner's history are `services.AUDITED` (listed with the rest in the `apps/connections/__init__.py` docstring). An audited verb about an **agent's** connection is an Event (`source=connections`) in the owning agent's workspace; about a **person's** it is a log line on `apps.connections.services`. Other verbs are operational log lines for every owner. Never a token, code, state, verifier or client secret (`tests/test_connections_audit.py` scans every log record and Event of a full run for each one). A log line is always one line (`connections.<kind> key=value …`); `services.parse_log_line` recovers the exact values. The cloud runner logs the same vocabulary for what happens on the box (`connections.stage_failed`, `connections.waiting`, `connections.not_for_this_box`; `runner/ec2/cloud_runner.py`).

## Calls from screens

A dynamic view or a workspace app page can call Salesforce through canopy-web (`apps/connections/calls.py`, `call_service.py`; route in [`api-connections-and-tokens.md`](api-connections-and-tokens.md)). This is the trade: for a connection whose `server_use` switch is on, canopy-web opens the token itself, so the zero-knowledge promise (canopy-web never holds a readable token) is given up for that connection, in exchange for screens that work without a computer of the owner's being online. The switch stays per connection, and a limited lend never has it on.

- **Whose account.** Always one from the screen's own workspace. `as: viewer` (default) is the signed-in person's own; `as: shared` is an agent's, which its admin approved for that project or app (`ConnectionSurfaceShare`, approval needs a fresh passkey from a browser: `api.py` `step_up=True`). Anyone who can open an approved screen acts as that agent in Salesforce, within the lines approved; a screen that later declares more stops until approved again.
- **What may be called.** Only what the screen declared (`connections` on the view or app manifest) and the Salesforce allowlist (`calls.py::SALESFORCE_RULES`) both allow; identity, permission and code objects are never writable from a screen (`GUARDED_OBJECTS`). The server checks the revision the page drew.
- **The click's limits.** A write needs a click, which the page around the frame decides from its own `navigator.userActivation`, and an operation lease (`call_service.py::OPERATION_SECONDS`, `OPERATION_HARD_LIMIT_SECONDS`, `OPERATION_MAX_WRITES`) for this person, this screen and revision. canopy-web cannot verify a click, and a screen can trick a person into one it wants. What bounds the damage is the declaration and the window, not the click. A view declaring `as: viewer` reads each viewer's data with no click, and its author can get at what it shows.
- **A page queues.** The page around the frames queues its calls (`frontend/src/dynamicViews/connectionCalls.ts::MAX_IN_FLIGHT`, `QUEUE_WAIT_MS`); the server's own per-person limit is `call_service.py::MAX_IN_FLIGHT_PER_PERSON`.
- **Not here.** A PAT or OAuth token (session only), Google, public app pages, composite calls, redirects; size and rate limits are `call_service.py` (`MAX_REQUEST_BYTES`, `MAX_RESPONSE_BYTES`, `CALLS_PER_MINUTE`). No token reaches an event, log or response.
