# Runners: flags, host requirements and scheduled turns

Host-required runner flags (sensitive-data runners), why a turn on a site's page withholds the agent's own login there, scheduled turns and plain jobs.

**See also:** [runners.md](runners.md), [runner-routing.md](runner-routing.md), [runner-credentials.md](runner-credentials.md), [runner-fleets.md](runner-fleets.md).

## Runner flags and host requirements (sensitive-data runners)

A **sensitive-data runner** (flag `sensitive_data`) is a box set up for a host's sensitive data. It is not "zero data retention" itself: it runs Claude only on a ZDR API key, runs every turn under a locked harness, limits egress to an allowlist, keeps nothing after a turn, and holds only agents that handle sensitive data. The box side (locked profile, what is deleted, what a kept conversation is, standing one up) is `runner/ec2/README.md` § Sensitive-data mode and § Egress lock, guarded by `runner/ec2/tests/test_sensitive_data_box.py`.

- **The declaration and the report never come from the same hand.** The box runs with `RUNNER_DATA_MODE=sensitive_data` and reports it on every heartbeat; any other non-empty value takes no turn. The report is believed only from a cloud runner's beat signed in with its own device key (`runner_protocol.data_mode_trusted`); a laptop's, or any beat sent with a person's token, is recorded as no data mode. A runner admin declares the flag (`RunnerFlag`, `PUT /api/harness/runners/{id}/flags`, audited with `declared_by`); canopy cannot verify a flag, it records who vouched, and nothing a runner reports can set one. `tests/test_data_mode_trust.py`.
- **Nothing of a sensitive-data box's transcripts reaches canopy-web except a confined turn's sealed turn-end rows.** Its usage report keeps no title, a session canopy has no record of is neither kept nor listed as missing (`events.usage`), and sending one up, asking a backfill (`transcript_read.backfill_refused`), resetting one, filing a reported session (`session_sync.session_home`) or posting `session-backfill` is refused, with 409 on the routes. `tests/test_sensitive_box_uploads.py`.
- **A caller's words never reach a confined prompt with a live `@`.** Claude Code expands `@/path` into the file's contents before the model runs, with no tool call: only deny rules stop it, not the allow list or `profile_guard`. Every confined turn, cloud and laptop, turns each `@` that could start a mention into `＠` (`caller.neutralise_mentions`, cloud `_neutralise_mentions`); an email address keeps its `@`, and server-side attribution folds `＠` back (`transcript_ingest._squash`).
- **Per-turn read scope is by pattern, never a snapshot:** every other session's directory and every other turn's caller envelope are denied by `native_permissions.complement_globs`, and the settings are rewritten as each session starts so a fork never reads its source's (`sensitive_data_settings`).
- **A host requires flags of its visitors' conversations** with `CANOPY_HOST["RUNNER_REQUIREMENTS"] = ["sensitive_data"]` (SDK `dimagi-canopy`); the SDK signs them into the visitor assertion (`canopy_runner_requirements`) and canopy stamps them on the session's `metadata["runner_requirements"]`: server-owned, union-only, never lifted by a later token that omits them. A host grant carries its own (`runner_requirements.requirements_of_grant`).
- `apps/harness/runner_requirements.py` is the one reader. The claim, placement, the unclaimable report, turn status (`requires`) and the `site_call` gateway (`apps/host_grants/host_gateway.py`) all refuse a runner missing a flag, above pins and with no fallback: a requirement is a floor applied to the composed list after strict truncation, so a turn nothing can serve says so and waits. Guarded by `tests/test_sdk_round_trip.py` and `tests/test_runner_requirements*.py`.

## A turn on a site's page withholds the agent's own login there

A turn whose conversation is held on a host site's page that its agent serves carries `page_site: {site, withheld}` in its claim (`published_profiles.page_turn`; the names come from the host site's `own_login`). There the agent reaches the site only through canopy's gateway, as the person who sent (`access-confinement-and-act-as.md` § Acting as the person on a host site), so:

- **Cloud runner** (`runner/ec2/cloud_runner.py`): the withheld names are dropped from the turn's environment (`_agent_env`) and its per-turn env file (`write_turn_env`, `CANOPY_AGENT_ENV_FILE`), and `CANOPY_PAGE_SITE=<site>` is set, confined turns too. The box still holds the values for the agent's other turns (the in-memory resolve is per agent), so the boundary is the turn's own process.
- **Laptop runner** (`runner/canopy_runner/canopy_runner/page_site.py`): emdash, not the runner, starts the session, so it writes `~/.canopy/page/task/<task>.json` for the agent's MCP headers helper. The agent's own `.env` stays on that disk: on a laptop the helper and the caller envelope's `site` block are the boundary, not the environment.
- Keep the site login in the agent's Canopy vault for the withholding to bind: a value kept anywhere else is outside it.

## Scheduled turns

The scheduler is a producer of turns, not an execution engine. `AgentSchedule` (`apps/harness/models/schedule.py`) holds the cron server-side and **canopy-web fires it itself**: `schedule_clock.run` on the off-request clock evaluates every enabled schedule and calls `schedule_turns.fire_schedule` for each due slot, so a workspace whose agents run only on cloud boxes still fires. A laptop runner evaluates them too (`runner/canopy_runner/canopy_runner/schedules.py`, `POST …/schedules/{id}/fire`); both reach the same slot key, so whichever fires second collapses onto the first's turn. Firing only queues a turn; which box runs it is decided on the claim. The module docstrings of `schedule_clock.py` and `schedule_turns.py` are the overview.

A schedule is an agent **trigger** of kind `cron` (`access.md` § Triggers); the server clock, the runner's sync and fire, and the week calendar read `kind=cron` only. Its turn is accountable to whoever set it up: a slot whose creator has lost the right to it (`triggers.refusal`) is not fired but consumed (`last_slot`), logged (`harness.triggers` / `trigger.refused`), answered 409 to a runner, and the `trigger_stopped` alert stays open until it is fixed. An occurrence runs as `system` with the creator as the accountable person (`turn_mode._accountable_cap`).

- **Anchor on `fire_after`, never `last_slot`.** `schedule_turns.fire_after_of` is what the server clock and the runner pass to `due_slot(after=...)`; `last_slot` is NULL until the first fire, and an unbounded backward look fires a slot that predates the schedule.
- **Concurrent fires are safe:** the slot-derived `idempotency_key` (`sched:<id>:<slot>`) collapses duplicates inside `enqueue_turn`. Firing a new slot supersedes the schedule's still-open occurrences as MISSED: you only owe the newest.
- **No occurrence table:** the `Turn` is the occurrence; `latest_occurrence_turn` selects by `origin_ref__schedule_id`, scheduled or "Run now", any status.
- **One-offs** (`run_once_at`) fire only their instant and disable themselves in the same transaction (`OneOffSlotMismatch` otherwise).
- **Grace release:** an EXECUTING occurrence held past `grace_minutes` (anchored on `claimed_at`, held time) is finished MISSED, because an abandoned session would occupy a runner forever (its heartbeat keeps renewing the lease). It runs on the queue sweeps (`harness.queue_sweeps`), not the fire tick, since a weekly fire tick could never honour a short grace.
- **Late slots:** a queued slot turn not started within `LATE_SLOT_WINDOW_MINUTES` of its slot is skipped as MISSED with no nag (`skip_late_scheduled_turns`); `always_run` and one-offs are exempt, manual runs untouched.
- **Nag:** a grace-released occurrence raises a `review` ask on a task (`_raise_schedule_nag`, only when the schedule's `notify` includes `inbox`); approving re-runs the prompt, and a later DONE occurrence closes open nags (`resolve_schedule_nags`).
- **A schedule can be a job** (`job`, `job_repo`); its fire is the same, its claim, run and nag are not (§ Plain jobs).

## Plain jobs

A schedule can run a **job** instead of a prompt: a command from a repo's `main`, on a cloud machine, with no model, using the agent's connections. Only an admin of the agent can set or change one; the schedule runs on `routing = cloud_only` and `grace_minutes` is at least `schedule_services.JOB_MIN_GRACE_MINUTES` so a long job is not released as missed while it runs. Field rules: `schedule_services.py`; the HTTP shape: the Schedules entry of `api-turns-and-routing.md`.

- **The file.** canopy-web says only the job's name, the agent and the repo's bare name; the box builds the address from its own `REPO_URL_TEMPLATE`, so it reaches only the org's repos, and **the command always comes from that repo's `main`**. A failed fetch fails the job: it never runs stale code. The file's shape and its refusals are `cloud_runner._job_spec` (`.canopy/jobs.yaml`: `run` is an argv list, no shell).
- **The job gets only its six environment variables and no model key, MCP token or runner token.** The list, the sandbox and what a job cannot reach are `runner/ec2/README.md` § Plain jobs. A connection's access token (never the refresh token) is copied to `$CANOPY_JOB_TOKENS/<provider>.json`; an agent with no such connection has no file, and a job should say so and exit non-zero. What that exposes: the plain-job entry of `vault-connections.md`.
- **Output and ending.** Output streams to the turn as `status` events (`{source: "job", text}`), shown as a plain log with the exit and last lines (`result_note`); there is no chat and no transcript. Output is scrubbed of the exact token values (an accident guard, not a boundary). A non-zero exit is `FAILED` and is **never retried** (a job may have written); so is a timeout. A failed, lost or missed job raises a review task on Waiting on you; none starts a debugger turn. It has no Start now (that would start a model turn): the task offers Run now, and a later good run closes it.
- **Dependencies are the job's to install** into its own `HOME` or vendor in the repo; the box carries Python and the usual system tools, download time counts against `timeout_minutes`, and nothing persists between runs.
- **One job per machine at a time:** jobs share one Unix user, so canopy-web compares machines (`routing_orders.holds_a_job`, by `machine_id`; each fleet member is its own, a runner with none answers for itself). The box backs it up with a lock, so in a race the second job fails and touches nothing.
- **How long a job waits:** a slot waits for a box that takes jobs up to `LATE_SLOT_WINDOW_MINUTES`, then is skipped as `MISSED` with `JOB_NOT_TAKEN_NOTE`, which its row shows and a review task repeats (one open review per schedule). An `always_run` schedule does not skip, and a one-off or Run now waits until a box takes it. Run now while the job runs is refused (409); a new SLOT in that time is recorded `MISSED` with no review.
- **Boxes that don't take jobs** (`routing_orders.runs_jobs`, `job_refusal`): not a cloud box reporting `capabilities.jobs` exactly True, a sensitive-data runner, a box with any egress-locked runner (so a job never fails on its first network call), or a box without the `canopy-job` user and broker (`--setup-runners` makes them). A runner re-asks every few minutes. If no box can take a job, the turn is listed as unclaimable with that reason.
