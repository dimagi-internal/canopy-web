# API: runners and capabilities

Routes for the runner registry: gates, device keys, machine and laptop pairing, releases, the runners list and capability leases. Part of the [api surface](api-surface.md) topic; the index there lists every part.

## Harness (`apps/harness`, mounted at `/api/harness`) — runner registry + turn lifecycle
The agent-execution control plane: paired `Runner`s (laptop emdash daemons, cloud boxes) heartbeat and claim queued `Turn`s; a `Turn` is one unit of agent work with an append-only `TurnEvent` ledger. How a turn reaches a box — tenant gate, which agents a box may hold, the claim, `RunnerAssignment` lists and rules, the workspace default order, flags, schedules, the per-turn GitHub identity — is owned by [`runners.md`](runners.md); runner roles by [`access.md`](access.md) → "Runner roles". Spec: `docs/superpowers/specs/2026-07-05-agent-execution-control-plane-design.md`.

**Gates (three tiers, all 404 rather than 403).** *See* (`_runner_read_q`): runners homed in, or serving (`runner_tenant_slugs`, the claim gate), the caller's tenants, regardless of who paired them — so a turn can be pinned to any box claim would give it; a runner with no workspace is visible only to its owner. *Act as* (`_runner_or_404`): the runner's owner — everything that speaks FOR the box (heartbeat, claim, reports, its own credential fetch, its half of a mint). *Administer* (`_runner_admin_or_404`): the owner or a `RunnerAdmin` — credentials, browser sign-in, enrollments, flags, engine, refresh, starting drills. `RunnerOut.can_manage` / `can_administer` tell each caller which listed rows it may act on / administer. Retired runners 404 everywhere except `unretire`.

**Runner device keys** (Canopy Vault; `apps/harness/api_device_keys.py`, `apps/harness/device_key_out.py`, `apps/harness/device_keys.py`) — all runner-admin (owner or `RunnerAdmin`), 404 otherwise.
- `POST /api/runner-device-keys/` `{runner, public_jwk, kind: secure-enclave|tpm|software, label}` → `{id, jkt, status: "pending", approve_url}` (201; the same RFC 7638 `jkt` again → 200 with the existing row, whatever its status; a `jkt` on another runner → 409; a non-P-256 or private JWK → 422).
- An EC2 cloud runner registers its instance ROLE instead: `POST /api/runner-device-keys/` `{runner, kind: "aws-iam", role_arn, proof, label}` — `proof` is an `X-Canopy-Aws-Proof` value (below) whose htu is this URL; STS must answer with `role_arn` (422 otherwise). Stored as the canonical, path-free `arn:aws:iam::<acct>:role/<name>`, `jkt` = sha256 hex of it, `public_jwk` empty; approved and revoked like any key.
- `POST /api/runner-sessions/` `{runner}` — a box signs in as itself (`apps/harness/api_runner_sessions.py`, `auth=None`): an `X-Canopy-Aws-Proof` or `DPoP` proof for this URL from an ACTIVE device key of that runner → 201 `{access_token, expires_at, runner}`. The token (`crt_…`, `RunnerAccessToken`) lasts an hour, authenticates as the runner's owner, and opens only the runner protocol (`apps/harness/runner_auth.py`: its own `/api/harness/runners/<id>/…`, the owner's runner list, `/api/harness/turns…`, schedule list + fire, agent roster/detail/resolve reads, its agents' mailboxes (`/api/inbound/runner-mailboxes`, `POST /api/inbound/watch`), `/api/workspaces` GET, `/api/runner-device-keys`, `GET /api/harness/runner-releases/current`, `POST /api/events`, its own `ws/runner/<id>/`) — 403 elsewhere. It dies at once when the key is revoked, the runner retired or the owner deactivated. Every refusal is the same 401.
- `GET /api/runner-device-keys/?runner=<id>` — keys with status (no `runner` = every runner the caller administers); rows carry `role_arn` for `aws-iam`.
- `POST /api/runner-device-key-requests/` — `auth=None`: a runner whose token was revoked (within 30 days) proves a token of the runner's owner and the key being registered → a PENDING key and its `approve_url`; the owner is emailed and pushed the link. Every refusal is the same 401.
- `POST /api/runner-device-keys/{id}/approve` — `pending` → `active`; **browser session only** (a token is 403), behind a passkey step-up; a revoked key → 409.
- `POST /api/harness/runner-invitations/` `{name, workspace, role_arn, ecdh_public_jwk?}` — invite one new cloud box (what `runner/ec2/up.sh` calls). Non-member → 404, no `agent.work` there → 403, a name that is not a runner name or an ARN that is not an IAM role → 422. → 201 `{id, name, workspace, role_arn, status: "pending", approve_url, expires_at, runner_id: null, …}`; an hour long; your own live one for the same role and name is replaced (and anyone's expired one), but someone else's live one → 409, naming nobody (concurrent creates → 409 too). The creator is mailed and pushed `approve_url` (`/w/<ws>/runner-invitations/<id>`). Recorded as `runner.invited` activity.
- `GET /api/harness/runner-invitations/check?workspace=<slug>` — the create's gates without creating anything (404 not a member, 403 no `agent.work`) → `{workspace}`; `up.sh` asks it before any AWS write.
- `GET /api/harness/runner-invitations/{id}` — the creator only (else 404): `status` is `pending|approved|consumed|expired`, and `runner_id` once consumed.
- `POST /api/harness/runner-invitations/{id}/approve` — the creator only, **browser session + passkey step-up** (a token is 403); expired or used → 409; again → no-op. Recorded as `runner.invitation.approved`.
- `POST /api/harness/runners/pair-by-role` `{name, kind: "cloud", capabilities, host, proof, ecdh_public_jwk?, ecdh_store?}` — `auth=None`, public in `apps/common/middleware.py`: `proof` is an `X-Canopy-Aws-Proof` value for this URL. 201 `{status: "paired", runner_id}` (an approved invitation for that role and name: a new runner owned by its creator, in its workspace, with an ACTIVE aws-iam key); 200 `{status: "reattached", runner_id}` (that role's existing runner of that name); 202 `{status: "waiting"}` (not approved yet); every other case the same 401. Recorded as `runner.paired`. A role that is a **fleet's** joins instead (`fleets.join`): 201 `paired` for an instance EC2 says is pending/running in the fleet's group, named `<fleet>-<instance id>`, under an ACTIVE fleet; 200 `reattached` for that instance again; 202 `waiting` before the fleet's approval.
- **A machine running several runners** (`apps/harness/machine_pairing.py`): the invitation takes `runners: [{name, workspace, kind: "tree"|"agent", slug?, ecdh_public_jwk?}]` (each workspace passes the same gates; an agent's runner names an agent of its workspace; a name twice → 422) and returns them, each with its `runner_id` once paired. `pair-by-role` with `runners: [{name, public_jwk, ecdh_public_jwk?, ecdh_store?, capabilities, host}]` (`name` is then the box's): one runner per entry with an ACTIVE software key, in one transaction, under one approval → 201 `{status: "paired", runners: {name: runner_id}, device_keys: {name: key_id}}`; every entry already a live runner on this machine → 200 `reattached`, each key replaced in place (runner ids, bindings and wraps kept); a runner the invitation does not list, an invited runner the box did not bring, a creator without `agent.work` in any runner's workspace, a revoked runner key, a name live on another machine → the same 401, nothing made.
- **Laptop pairing by browser** (`apps/harness/api_runner_pairings.py`) — what a downloaded Canopy Runner does; no PAT at any point:
  - `POST /api/harness/runner-pairings/` `{public_jwk, kind: secure-enclave|tpm|software, ecdh_public_jwk?, ecdh_store?, hostname, account, platform: macos|windows|linux, has_emdash, emdash_cdp_live?, redirect_port: 1024–65535}` — `auth=None` (public in `apps/common/middleware.py`, POST only), with a `DPoP` proof for this URL by the key in `public_jwk`. → 201 `{id, user_code: "ABCD-EFGH", verify_url: "<CANOPY_PUBLIC_BASE_URL>/pair/<code>", expires_at (15 min), interval: 3}`; a key that is an ACTIVE key of a non-retired runner → 200 `{status: "reattached", runner_id, name, workspace, device_key_id}`, nothing made. One live pairing per key (a new one replaces it). A proof by another key, or a key canopy knows in any other state (pending, revoked, a retired runner's) → the same 401. A malformed body → 422.
  - `GET /api/harness/runner-pairings/{user_code}` — any signed-in person with the code (case and dash insensitive; unknown → 404): `{user_code, hostname, account, platform, kind, has_emdash, status: pending|approved|consumed|declined|expired, expires_at, suggested_name, workspaces: [{slug, name}], runner_id?}` — `workspaces` are the caller's with `agent.work`; `runner_id` only to the approver.
  - `POST /api/harness/runner-pairings/{user_code}/approve` `{workspace, name}` — **browser session + passkey step-up** (a token is 403); an agent's login → 403; not a member → 404, no `agent.work` there → 403; a name that is not a runner name → 422; a name the caller's own non-retired runner has → 409; used, declined or expired → 409. → `{status: "approved", redirect_url: "http://127.0.0.1:<port>/paired?pairing=<id>&secret=<raw>"}`. The secret is stored only as its sha256; approving again before the claim issues a new one. The first approval extends `expires_at` by 10 minutes. Recorded as `runner.pairing.approved`.
  - `POST /api/harness/runner-pairings/{user_code}/decline` — signed in → `{status: "declined"}`; used or expired → 409.
  - `POST /api/harness/runner-pairings/{id}/claim` `{secret?}` — `auth=None` (public, POST only), with a `DPoP` proof for this URL by the pairing's key. Pending → 202 `{status: "waiting"}`; approved, unexpired, with the right secret and an approver who is still active with `agent.work` in the chosen workspace → 201 `{status: "paired", runner_id, name, workspace, device_key_id}`: a `Runner(kind=emdash, engine=emdash if has_emdash (on windows: and emdash_cdp_live) else claude-cli, capabilities={"sessions": true}, host=hostname, platform)` owned by the approver in that workspace, its device key ACTIVE (its ECDH key approved with it). Everything else the same 401. Recorded as `runner.paired`. The box then signs in at `POST /api/runner-sessions/`.
- **Runner releases** (`apps/harness/runner_releases.py`, `api_runner_releases.py`) — CI uploads each runner version's artifacts and `manifest.json` under `s3://<CANOPY_RUNNER_RELEASES_BUCKET>/<RUNNER_RELEASES_PREFIX><sha>/` (bucket defaults to the attachments bucket, prefix `runner-releases/`); current is the deployed `RUNNER_CODE_SHA`. The manifest is cached 60 s (a miss 15 s).
  - `GET /api/harness/runner-releases/current?platform=macos-arm64|macos-x86_64|windows-x86_64` — a person, or a runner's own token (`runner_auth`) → `{sha, platform, file, url (presigned, 15 min), sha256, size, signed, notarized}` for the platform's update artifact; nothing deployed or built → 404; unknown platform → 422; no bucket → 503.
  - `GET /api/harness/runner-releases/downloads` — a person (a runner token is 403) → `{sha, downloads: [{platform, label, file, size, signed, notarized, href: "/download/runner/<platform>"}]}`; empty when none is built.
- `DELETE /api/runner-device-keys/{id}` — revoke, immediately; idempotent.
- Per agent: resolve needs a DPoP proof (ES256, `htm`, `htu` without query, `iat` ±120 s, single-use `jti` in the cache) from an ACTIVE key on a runner the agent routes to or its owner owns, else 401 problem+json with members `{error: "device_proof_required", reason: "not_routed"|"no_valid_proof"}` and `WWW-Authenticate: DPoP`. `GET /api/agents/{slug}/device-keys` (agent admin) lists the keys that would count; `GET /api/agents/{slug}/credentials/{name}/reads` (agent admin) is the read log; `credentials/status` rows carry `last_read_at` + `read_count`. `GET /api/agents/{slug}/credentials/shared-vaults` (agent admin) lists the workspace vaults its turns also read, the names in each and why; `GET /api/vaults/{id}/log` (vault owner/admin) is a workspace vault's log, merging its `SettingChange` rows with agent and machine reads. UI: agent Settings → Security (Access: People, Agents, Machines; per-secret read history; Log) and `/settings#device-keys` (where `approve_url` lands).

**Runners**
- `POST /api/harness/runners/` — Pair a runner; `owner` = the caller. Refused (403) for an agent's login — a runner is owned by a person (grant the agent admin instead). `workspace` optional: a non-member gets 404; omitted with zero or several memberships → 422 naming the fix. The box is enrolled only in the workspace it paired into. `profiles`/`envelope`/`midturn`/`claude_model` in `capabilities` are dropped (they are reported, never declared).
- `GET /api/harness/runners/` — The fleet the caller can see (newest heartbeat first, max 50), each row stamped `can_manage`/`can_administer`. A host site acting for a visitor sees only runners serving its own agents.
- `GET|POST /api/harness/runners/{runner_id}/workspaces` · `DELETE …/workspaces/{workspace}` — Which workspaces the box serves (`RunnerEnrollment`). It claims a workspace's work (agent turns, repo turns, unbound chats, schedules) only where it is enrolled — there or in any workspace above it, including divisions created later — AND its owner holds `agent.work` there; separate roots stay separate (`routing.runner_tenant_slugs`, see runners.md). Row: `serving` (both hold), `covers` (served workspaces below it). Administer tier. POST is idempotent; 422 when the box's OWNER is not an editor there, or when a cloud runner would span two roots (a cloud runner serves one tree); 404 when the CALLER is not a member. An administrator lists only workspaces they are themselves in. DELETE does nothing effective while a workspace above is still enrolled; a held turn runs to completion. Joining a workspace never enrolls existing boxes; leaving one drops their enrollments. Session discovery (`POST …/sessions`) is not routed by enrollment.
- `GET|POST /api/harness/runners/{runner_id}/admins` · `DELETE …/admins/{user_id}` — Runner administrators. GET: administer tier. Grant/revoke: owner only (grantees cannot mint more admins); 404 for an unknown email, 422 when the grantee is not a member of the runner's workspace.
- `POST /api/harness/runners/{runner_id}/heartbeat` — Act-as. Status, `active_turn_ids`, `degraded`/`note`, `ready`/`ready_note`, `host`, code provenance (`code_branch`, `code_version`, `code_sha`, `code_committed_at`), and reported capabilities: `projects` (the repos the box can drive — emdash's `projects` table on a laptop, `RUNNER_PROJECTS` on a cloud box), `profiles`/`envelope`/`midturn` (versions of confinement, caller-envelope and mid-turn support), `clis` (per agent CLI: `signed_in`, `profiles`, `envelope`, `version` — a level, absent = Claude Code alone), `claude_model` (the model setting its sessions start on, e.g. `opus[1m]`, served on a bound session as `runner_model` for the context meter), `mailboxes_readable`, and an optional `health` block (`{checks: [{name, status: ok|warn|fail, detail}], checked_at, bootstrapped_at, canopy_version}`). **Absent ≠ empty:** an omitted `projects` or `health` leaves the stored value alone; `projects: []` means "none". A runner that cannot read emdash must omit `projects`. Provenance fields are assigned unconditionally (an omitted one clears), so each runner builds its payload in one place. Served back on `RunnerOut` as `health_checks` (map keyed by check name; `null` = never reported, i.e. unknown), `health_received_at`, `health_bootstrapped_at`, `refresh_pending`, `expected_code_sha`, `expected_canopy_version`. The WS heartbeat carries the same block; its `heartbeat.ack` returns `refresh_pending` and `expected_canopy_version`.
- `PATCH /api/harness/runners/{runner_id}` — Replace `capabilities` (act-as). 422 on `projects`, `profiles`, `envelope`, `midturn` or `claude_model` (reported by the runner); those are preserved across a write that omits them. `capabilities` is a routing hint, never a boundary.
- `POST /api/harness/runners/{runner_id}/refresh` — Administer tier. Asks the box to re-run its bootstrap (canopy plugin + CLI, Claude Code, each agent's provisioning) and restart at its next idle moment. Durable (`Runner.refresh_requested_at`), read by the box off its heartbeat reply as `refresh_pending`; discharged only when the box reports a `bootstrapped_at` newer than the request. `refresh_pending` is also true, with no request, when the box reports a canopy CLI strictly behind the canopy release (`apps/harness/canopy_release.py`: canopy main's plugin.json, read anonymously and cached; unknown asks nothing) and has not bootstrapped since canopy-web first saw that release. The cloud runner also refreshes itself when its last bootstrap is over 24h old, and never restarts itself twice within 30 minutes. A laptop runner has no bootstrap: it updates its plugin marketplaces, this account's plugins and the canopy CLI in place, without restarting, and reports one `refresh` health check (`runner/canopy_runner/canopy_runner/refresh.py`, at most once per 30 minutes). A request already pending is left as it is. `RunnerOut.refresh` is the request as a person reads it (`apps/harness/runner_refresh.py`): `state` `none|pending|done`, who asked and when; pending: `waiting_on` (`offline`, `busy` with `in_flight`, `floor` with `eligible_at` — the box's `health.refresh_floor_until`); done: `finished_at`, `took_seconds`, `changes` (runner code, Claude Code, canopy CLI before → after, against a snapshot taken at request time) and `problems` (its refresh checks not `ok`). The asker is emailed and pushed once when it finishes; one still pending after 30 min is the `runner_refresh` alert, handed to them. The cloud runner also refreshes itself when its last bootstrap is over 24h old, and never restarts itself twice within 30 minutes. A laptop runner has no bootstrap: it updates its plugin marketplaces, this account's plugins and the canopy CLI in place, without restarting, and reports one `refresh` health check (`runner/canopy_runner/canopy_runner/refresh.py`, at most once per 30 minutes).
- `GET /api/harness/runners/{runner_id}/projects` (anyone who can see the runner) · `POST …/projects {agent | repo_url, name?}` (Administer tier, laptops only; 201) · `DELETE …/projects/{request_id}` (Administer; withdraw or clear) · `POST …/projects/{request_id}/result {ok, detail}` (Act-as: the box's report). Add a repo to a laptop as an emdash project (`RunnerProjectRequest`, `apps/harness/runner_projects.py`): the GET lists the box's reported projects, every ask with `pending`/`added`/`failed` and the box's reason, and `can_add`. Pending asks ride the heartbeat reply as `RunnerOut.add_projects`; an ask is `added` once the project is in the box's report. A failure marks only that ask, never the runner. `GET /api/agents/{slug}/default-order` names the laptops lacking the repo by id too (`missing_repo_ids`). → [runners.md § Adding a repo to a laptop](runners.md#adding-a-repo-to-a-laptop-runnerprojectrequest)
- `PUT /api/harness/runners/{runner_id}/name` — Administer tier. Rename a runner: the name people see. Routing, pins and the vault follow its id; the box keeps the name it paired as (`paired_as`), which pairing also matches on so a replaced instance re-attaches. Audited as a setting. 422 on a blank or over-100-character name.
- `PUT /api/harness/runners/{runner_id}/flags` — Administer tier. Replace the attestations the owner vouches for (today `sensitive_data`: a sensitive-data runner — a ZDR API key for Claude, a locked harness, egress limited to an allowlist, nothing kept after a turn); each records who declared it and changes are logged as events. Unverifiable by canopy; checked against a host's `canopy_runner_requirements` at claim, placement and `site_call`. 422 on an unknown flag. See runner-flags-and-schedules.md → "Runner flags and host requirements" and `docs/superpowers/specs/2026-09-30-zdr-runners-design.md`.
- `PUT /api/harness/runners/{runner_id}/egress` `{locked, allow}` — Administer tier, an audited setting. The runner's egress lock (`apps/harness/egress.py`): locked, its runners reach the network only through the box's proxy, to canopy-web, the model, GitHub and `allow` (hostnames; `.example.com` = every subdomain; 422 otherwise). A sensitive-data box (`runner_requirements.is_sensitive_data_box`) cannot be unlocked (422), and adding a host to one needs a browser passkey step-up (a token gets 403); anything else from any client, MCP included. `RunnerOut` carries `egress_locked`, `egress_allow`, `egress_forced`. See `runner/ec2/README.md` § Egress lock.
- `POST /api/harness/runner-fleets/` `{name, workspace, role_arn, ecdh_public_jwk, region, group_name, min_members, max_members, member_turns, credential_set?}` — `agent.work` in the workspace (404 for a non-member), as for a box's invitation. Makes a PENDING `RunnerFleet` and its credential set (or reads `credential_set`, one of the caller's, else 404), and returns the `RunnerInvitationOut` (with `fleet`) its creator approves on the usual approve page with a passkey; a token cannot. 422 for a role that is already a box's or another fleet's. `GET /api/harness/runner-fleets/` and `/{id}` (owner only, else 404) list fleets and their members; `PUT …/{id}/size` `{min_members, max_members}` is an audited setting; `POST …/{id}/retire` stops joins and scaling. Members join at `pair-by-role` (below). `RunnerOut` carries `fleet_name`, `instance_id` and `power` (`on|draining|stopped|waking`). → [`runner-fleets.md`](runner-fleets.md) § Runner fleets
- `GET /api/harness/runner-credential-sets/` (the caller's sets: runners, and each workspace tree's vault with the entries it has no value for); `POST /api/harness/runner-credential-sets/` `{runner, name}` shares a cloud runner's own list as a new set (its owner; browser + step-up; 409 while the list holds a login); `PUT /api/harness/runner-credential-sets/runners/{id}` `{credential_set: id|null}` chooses the set a runner reads (its owner, and the set's; browser + step-up; 409 for a fleet member or a runner with entries of its own; 422 `vault_crosses_isolation`). Both writes are audited settings and answer the runner's `RunnerCredentialStatusOut`, which carries `credential_set` when it reads one. → [`runner-fleets.md`](runner-fleets.md) § Credential sets
- `POST /api/harness/runners/box-egress` `{proof}` — `auth=None`: root on a cloud box proves its instance role (`aws_iam_proof`, bound to this URL) and reads every live runner on that machine (`Runner.machine_id`) with its effective lock (`locked` is true for a sensitive-data box whatever is set) and `allow`. One uniform 401 for a bad proof (`apps/harness/api_box_egress.py`).
- `PUT /api/harness/runners/{runner_id}/engine` — Administer tier. The runtime a LAPTOP runner opens new sessions in (`emdash` | `claude-desktop` | `claude-cli`); read off the next heartbeat, running sessions stay put. 422 for an unknown runtime or a cloud runner.
- `POST /api/harness/runners/{runner_id}/pause` · `/unpause` — Act-as, idempotent. Park a box without decommissioning it; `pause` takes `note` and optional `until` (a scheduled unpause — what a runner sends on a Claude usage cap; a past `until` is a no-op, it never shortens a scheduled unpause nor attaches one to an open-ended operator pause, and a pause without `until` cancels any scheduled unpause). `Runner.paused` mirrors the box's local `~/.canopy/PAUSED` sentinel (reported as an edge). Enforced server-side (`live_status` = `PAUSED`), so it binds any runner binary; outranks a pin; stops STARTING work, never finishing it. Records who paused (`paused_by_email` on `RunnerOut`); an open-ended pause puts the queued turns only that box could take to the workspace's reach admission rules (`access.md`). Unpause clears the flag and `paused_by` only — liveness comes from the next heartbeat. UI: `/supervisor` → Runners → `RunnerDetail`.
- `POST /api/harness/runners/{runner_id}/retire` — Act-as. Decommission: status `RETIRED`, and the runner is removed from every `RunnerAssignment` and every `WorkspaceRunnerOrder` (each logged as `runner.route_dropped`). Returns `{runner, dropped_routes}`. Prefer `pause` to park a box.
- `POST /api/harness/runners/{runner_id}/unretire` — Bring a retired runner back keeping its id (bindings, sessions, credentials survive); restores `DISCONNECTED`, never `ONLINE`. Does NOT restore the routes `retire` dropped — re-add them. The only route that reaches a retired runner. Idempotent.
- `GET /api/harness/fleet-hold` · `POST /api/harness/fleet-hold` (`{note}`) · `POST /api/harness/fleet-hold/release` — The fleet-wide sibling of pause (`FleetHold`): while held no runner starts anything; turns keep enqueuing and wait QUEUED; running turns finish. GET: anyone signed in (`can_hold`, `can_release`, `queued`). Hold: a superuser or a named holder (`CANOPY_FLEET_HOLDERS`), idempotent (refreshes the note). Release: superuser only; wakes every workspace's runners. 403 otherwise.
- `GET /api/agents/{slug}/hold` · `POST /api/agents/{slug}/hold` (`{note}`) · `POST /api/agents/{slug}/hold/release` — The per-agent sibling of the fleet hold (`Agent.held`): while held no runner starts that agent's turns — its own or a chat with it, pins included — and every other agent runs as usual; its turns keep enqueuing and wait QUEUED (`unclaimable` names it `agent_hold`, a chat shows it unrouted); running turns finish. GET: any member (`queued`). Hold and release: `agent.work` (an editor or above), audited; hold is idempotent (refreshes the note); release wakes the workspace's runners.

## Capabilities (`apps/capabilities`) — machines an agent leases
Framework tier. Bodies, lease states, long-poll, exec, slot data and every refusal: [`capabilities.md`](capabilities.md) §1, §3, §4, §6. "Own login" = the agent's own login; lease routes take editor+ of the agent's workspace or its own login.
- `GET /api/agents/{slug}/capabilities` — declared capabilities + grant, limits, live leases, `retired` (member).
- `PUT /api/agents/{slug}/capabilities` — publish the whole list (agent owner/admins, or own login). A setting.
- `POST /api/agents/{slug}/capabilities/{name}/refresh` — re-read the stack's Outputs (agent admins, or own login).
- `POST /api/agents/{slug}/capabilities/{name}/terminate-orphans` — the sweep's machine pass, now (`integrations`, or the agent's admins).
- `GET /api/agents/{slug}/capabilities/{name}/slots` — a pool's slots, masked (member).
- `PUT|DELETE /api/agents/{slug}/capabilities/{name}/slots/{slot}` — set / remove a pool slot's data (`integrations`, or own login). A setting (audited with key names only). Setting it from a browser needs a passkey step-up; a token does not.
- `GET /api/capabilities/grants?agent=` — grants in your workspaces.
- `PUT /api/capabilities/grants` · `DELETE /api/capabilities/grants/{id}` — grant / revoke (`integrations`). Settings.
- `POST /api/capabilities/leases` — acquire (editor+, or own login).
- `GET /api/capabilities/leases` — list, a read with no heartbeat (member, or own login).
- `GET /api/capabilities/spend` — machine-seconds per agent and capability.
- `GET|DELETE /api/capabilities/leases/{id}` — read + heartbeat (`?wait_s=` long-poll) / release.
- `POST /api/capabilities/leases/{id}/force-release` — end it and terminate its machine, even if already ended (`integrations`, or the agent's admins).
- `POST /api/capabilities/leases/{id}/exec` · `GET …/exec/{exec_id}` — run an allow-listed command / read it back.
- `POST /api/capabilities/leases/{id}/uploads` · `GET …/artifacts?prefix=` — presigned PUTs into `in/` / GETs from `out/`.
