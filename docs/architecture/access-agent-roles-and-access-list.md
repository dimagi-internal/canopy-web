# Access: agent roles, the access list, read mode and host sites

What a person may make one agent do: agent roles and configurable roles, the access list and workspace defaults, read mode and host sites. Part of the [access](access.md) topic; the index there lists every part. Start reading at `apps/agents/roles.py` (the vocabulary), `apps/agents/grants.py` (the lines), `apps/agents/turn_context.py` (the one rule that reads them).

## Agent roles

A **permission** is one thing a person may do with ONE agent; a **role** is a named bundle of them. The permissions, the built-in roles and their bundles are `apps/agents/roles.py` (`SEED`, `_FIXED`, `_IMPLIES`); do not copy them here.

* **The dependency rule** (`roles.py::_IMPLIES`, closed by `apps/common/rolesets.py::RoleSet`, tested in `tests/test_agent_access_list.py`): a role never holds a permission without the ones it depends on. `write` (drive the whole agent) opens read mode and every host site; `agent_edit` implies `write`; `admin` implies everything except `own`. The mechanism is shared with the workspace's roles (`apps/workspaces/permissions.py`); the vocabularies are not.
* **`system` is not a person's role** (`roles.py::SYSTEM`): it is canopy itself, the agent's own login and an approved dispatch, and may do what an admin may. Another agent's login is graded like any person (`caller_context.relationship_for_user`), or agent A could steer all of agent B.
* **What the rule reads.** `grants.resolve` unions the permissions of every matching line and asks one question: do they hold `write` (`roles.holds`)? Then they get the whole agent. Otherwise they get one confined profile, chosen by what their lines open (`roles.can_use`, `published_profiles.opens`: `read` opens read mode, `use:<site>` opens that host site). The branch is `turn_context._base_stage`.
* **`agent_edit` is the permission to change the agent itself.** `access.may_edit_agent` is the one predicate (never write a second); `gates.agent_for_edit` asks it. The owner, an agent admin and the agent's own login always may; anyone else only through a line whose role holds `agent_edit`. Being an editor of the agent's workspace gives nothing by itself. An agent acting for its asker is judged as the asker (`turn_asker.of`), so a `read_write` asker cannot make the agent edit itself. Every change to an agent falls in one of three classes:
  * **agent_edit**: the agent's own definition (skills and skill history, name, description, persona, email, avatar, runner-kind preference; `apps/agents/api.py::SELF_FIELDS`, checked with `may_edit_agent`) and the code in its own repo. The envelope's `permissions` is the agent's cue; the runner-side rail in the canopy plugin refuses a push or merge from a turn whose asker lacks `agent_edit` (canopy-web only reports it).
  * **admin** (`@gate("agent-admin")`): everything that decides who reaches what or what runs with the agent's credentials: where the repo points and what boxes install (`api.py::set_repository`; whoever names the repo writes code that runs with the agent's credentials), the access list, read mode and host sites including `sensitive`, machine capabilities (`apps/capabilities/api.py::put_agent_capabilities`), credentials, vaults, licenses, canopy login and token, GitHub identity, mailbox, runner pins, routing, Slack switch.
  * **own**: transfer, delete, naming admins (`Agent.owner` or a workspace owner).
  * Work (`agent.work` or `write`: schedules, triggers, tasks, turns, hold, turn mode) is none of these: it changes what the agent DOES, never what it IS.
* **Where each role comes from.** The owner (`Agent.owner`), agent admins (a workspace owner, or an `AgentAdmin` grant) and canopy itself hold their role with no line; the access list shows them as implicit lines it does not let you edit (`api_access_list.py::_implicit`). Every other role is a line. A line cannot give `admin` or `owner`.
* **An owner or agent admin who has left the workspace is neither** (`Agent.is_admin`, `caller_context.relationship_for_user`): both need current membership, so an owner removed from the tenant is an outsider.
* **Safety rails are stated by permission, not by role name** (`grants.grants_write`, `roles.drives`): a `domain` or `contact` line can never give a role that holds `write`; a workspace default whose role holds `write` is the workspace owner's call.

### Configurable roles

The roles a line can give are rows (`AgentRole`) a workspace's people define (`roleadmin.py`, `rolecatalog.py`, `api_roles.py`; the Roles page).

* A role is a key (immutable, stored on its lines and sent in the envelope), a label, a sentence and a permission set stored **closed**. A custom role can **never** hold `admin` or `own`: those come from who the agent belongs to (`roles.validate_permissions`).
* A role is defined on a workspace and usable by it and every workspace below; its key means one thing everywhere it is visible (a clash along a chain is refused), so nothing is overridden. The built-ins are seeded on every root workspace (`rolecatalog.ensure_seeded`).
* A line holds its role's **row** (`AgentGrant.role_def`), so **editing a role changes everyone holding it from the next request**, and a role in use cannot be deleted (`PROTECT`; the API names the lines or moves them with `reassign_to`). Nothing branches on a role's name: the envelope's `permissions` is the contract, `role` is for display.
* **Who may** (`api_roles.py::_need_rights`, `_machine_may_not`): a workspace admin defines roles that cannot drive or change an agent; anything that does (`write`, which `agent_edit` carries), before or after an edit, is the workspace owner's. Every write is a settings change and takes a passkey step-up from a browser; a token may write a role that only reads or opens host sites, never one that drives or changes the agent.
* **The rails follow the role's contents**: an edit that would make a role drive is refused while a `domain` or `contact` line holds it (`roleadmin`, `grants.lock_role_for` re-asks the rail inside the saving transaction). Moving an agent into another tree re-points its lines to the destination's identical role, or refuses (`move.py::_carry_roles`).
* `manage.py check_agent_roles` proves every role line is linked to the row of its own tree and grants what the code table gave it.

## The access list

An agent's **access list** (`AgentGrant`, `apps/agents/grants.py`) is the one place that says who has what on it. A line is `(who, what)` with a `manual_only` flag and a note. `what` is ONE role or, rarely, ONE host site (`AgentGrant.capability`, the scoped permission `use:<site>`, which opens that one site and nothing else, not `read`, not read mode). `who` is one of four kinds; how each matches an asker is `grants.matches`, and the gotchas are:

* A `workspace` line matches by the asker's effective role in that workspace (a parent workspace's owners and admins count); with `include_below` a role in any workspace of the line's own subtree meets the floor too, never another organisation's and never upward. It never matches a contact, nor a guest (`access.md` § Guests), whatever its floor.
* A `person` line may name a workspace **guest** only when it opens one entry (`use:<key>`), never a role (`grants._person`): that is how a guest reaches an agent's app entry ([host-sites.md](host-sites.md) § App entries).
* A `domain` or `contact` line identifies people only by an address a message can claim. A `verified` line also needs THIS message to prove the address.
* **A person's permissions are the union of their matching lines** (`grants.resolve`). The line that gives `write` (or opens the profile the turn runs in) is the Turn Context's `Standing.source`, `list:<subject key>`.
* **`manual_only`** makes every turn the line lets someone start run `manual`, so an agent admin approves what goes out (`turn_mode.editor_cap`). It matters only for lines that give `write`. A person is manual only when EVERY line that gives them `write` says so: one line without the flag frees them.
* **Which lines you can write** (`grants.check_line`, `check_role`): exactly one of a role and a host site; a `domain` or `contact` line can give `read_only` or a host site but **never a role that holds `write`**, because an address is something a message can claim and driving the whole agent takes a named person or a workspace's people; `include_below` is for a workspace line only; one line per subject per list and per host site (409 on a repeat). Naming a host site the agent does not have is allowed with a warning (`api_access_list.py::_host_site_warning`): the line opens nothing until it does.
* **Who may read and change it.** Any member of the agent's workspace reads the list; an **agent admin** changes it and turns inheritance on or off (`api_access_list.py`). Every change is a settings change (`access-list:<slug>`, [settings-audit.md](settings-audit.md)).
* **A line can only open what exists**, and read mode exists on every agent: a `read_only` line is live the moment it is added. `manage.py read_mode_gate` lists agents with such a line and no read mode of their own; `manage.py answering_snapshot` prints how every agent answers, so a change to read mode, host sites or the rule can be diffed.
* **Default: nobody.** A new agent has no lines of its own; only its owner and agent admins reach it unless lines name others. Nobody gets in by being in the workspace (`turn_context._no_list_stage` then `_base_stage`).

### Workspace defaults

A line can sit on a **workspace** (`AgentGrant.workspace`, no agent). Every agent in that workspace and below inherits it (`grants.lines_for`) unless the agent sets `inherit_workspace_defaults` false (an agent admin's switch; use it for an agent holding credentials people should be named for). Defaults are changed on the workspace by a **workspace admin** (`members.manage`), except that a default whose role holds `write` is the **workspace owner's** call, decided by that permission, not the role's name (`api_access_list.py::_require_default_rights`). A default shows on each agent's list as `scope: workspace` and is removed only at the workspace.

A line cannot give `admin` or `owner`, and a workspace editor is not an agent editor: the workspace role gates the routes that reshape an agent, while whether a person's own turn runs the whole agent is the access list. A stored document carrying `role:`, `full:`, `editors:` or `callers:` is refused (422) with a pointer to the access list (`published_profiles.parse`).

## Read mode and host sites

(The whole path for a site, from the workspace's registration to the gateway, is [host-sites.md](host-sites.md).)

The two settings admins edit for **what** a confined turn may do (`apps/agents/profile_settings.py`, routes in `api_answering.py`). Who may use them is the access list, never these settings. Saving is for the agent's owner or an agent admin, browser or token; `dry_run` checks a draft with the server's own parser without saving; every save is a settings change.

* **Read mode** is the default confined profile for someone who holds `read` and not `write`, **on every agent with no setup**. With no setting it is canopy's default (`read_mode.default_read_profile`, a pure function of the agent, pinned exactly by `tests/test_default_read_profile.py` so a change that widens every agent at once cannot pass unnoticed; `READ_PROFILE_VERSION` rides the envelope as `default_profile_version`). An admin's first change starts from that default as it stands for this agent and saves it as the agent's own, which then replaces the default whole; reset returns to the default (`profile_settings.set_read_mode`, `reset_read_mode`). A read-mode turn's envelope lists only `read` in `permissions`. A sensitive conversation never gets read mode: read mode cannot be marked sensitive (`profile_settings.document_problems`) and a sensitive conversation anywhere but its sensitive entry is refused (`turn_context._sensitive_rule`).
* **A host site** is one row per registered site: a confined profile plus an optional **site tool limit** (stored and sent as `ceiling`, narrowing what the host's grant already allows, on the owner's word; one that matches every tool is refused, `profile_settings._limits_nothing`), `own_login` (the agent's credentials at that site) and **Handles sensitive data**. A conversation held on that site selects it, and its profile gains canopy's gateway tools and the page's own actions (`published_profiles.profile`) → [access-confinement-and-act-as.md](access-confinement-and-act-as.md). Removing a row gives a turn already stamped with it the `deny_all` profile (`turn_context.stamped_profile`), and a line naming it opens nothing. **Handles sensitive data** is per site, not per agent: it confines a conversation on that site for everyone, while the owner's ordinary chat with the same agent is still the whole agent (`turn_context._sensitive_rule`). Such a site may hold only the gateway's tools, read-only local tools and no shell or writes, else 422 (`sensitive_data.structural_refusals`).

**Storage and the names that stay.** Both settings are views of one document, `Agent.interface`, live state on canopy-web (never a repo file), written only by `profile_settings.store`. Its entries live under a `capabilities` key; a host site's row is an entry naming that one site, and the entry's name (`profile_settings.key_for`, never renamed) is what a turn is stamped with and what an access line names. Read mode is stored as `read` (canopy's default) or `ask` (an agent's own; `read_mode.READ_MODE_STAMP`), and `read_mode.is_read_mode` is the one place that treats the two as the same. `Turn.capability`, `AgentGrant.capability`, `AdmissionRule.capability`, `use:<name>` in stored role permissions, the envelope's `capability` and `granted_by` are stored or wire names: renaming any would split live conversations (`runner/canopy_runner/canopy_runner/session_naming.py::restricted_key`, `runner/ec2/cloud_runner.py::_kept_identity`).

**One entry per site; what a document may hold.** An entry names exactly one site and no site is named by two entries; the writer refuses a document that breaks either, and an unknown key (`profile_settings.document_problems`, `published_profiles.parse`; `manage.py answering_snapshot` reports it as `shape`). A page's declared resource selects nothing: an entry carrying `pages:` is refused. The default document is `{capabilities: {}}` (`read_mode.default_interface`).
