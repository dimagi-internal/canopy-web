# Access: confinement and acting on someone's behalf

How a confined turn is enforced (what a caller's turn can and cannot reach), how an agent acts on behalf of the person who asked, and the two act-as-you permissions: canopy-web's own `ActAsGrant` in the agent's turn, and the passkey-confirmed host grants on a host site. The words and the one rule are defined in [access.md](access.md).

**See also:** [access.md](access.md) (glossary, "Whose authority an agent acts with"), [access-direct-use-and-admission.md](access-direct-use-and-admission.md), [embedding-internals.md](embedding-internals.md) (host grants).

## How confinement is enforced

Who asked is recorded on every turn (`initiator_*`), and the caller envelope ([access-direct-use-and-admission.md](access-direct-use-and-admission.md) "The caller envelope") reaches the agent three ways: the claim response (the runner writes `~/.canopy/caller/<turn_id>.json`), the `who_is_asking` MCP tool, and a summary the canopy plugin's `caller_context` UserPromptSubmit hook adds beside every delivered prompt.

* **Default deny.** An agent with no `read` or `write` line and no host site is reached only by its owner and agent admins; every contact or unidentified caller no line names, and every line that opens nothing the agent has, is refused. Read mode and host sites are live state on canopy-web (`Agent.interface`), never a file in the agent's repo. They confine callers who reach the agent through canopy (web chat, Slack, email, embedded sites). canopy's MCP server offers NO per-agent tools: someone who wants to use an agent installs its plugin and runs it in their own Claude Code, as themselves.
* **An agent's own login is the agent.** `Agent.user` grades as `system`; another agent's login grades like any person, or agent A could steer all of B (`Agent.is_own_login`, `caller_context.relationship_for_user`).
* **Three layers, each failing closed.** (1) canopy stamps the profile's name on `Turn.capability` at enqueue (`apps/harness/services.py::_apply_capability`) and again at claim (`turn_context.at_claim`, which asks the rule afresh and rewrites the stamp), or refuses the turn; (2) only a runner reporting `profiles` and `envelope` at or above `apps/harness/routing_orders.py::PROFILES_VERSION` / `ENVELOPE_VERSION` may claim such a turn, and it runs it in its own `cx-` session with the profile written to `~/.canopy/profiles/<task>.json` first; (3) the canopy plugin's `profile_guard` PreToolUse hook refuses anything the profile does not list: Bash argument-for-argument, `{thread_id}`-pinned, paths realpath'd.
* **Native deny rules under the guard** (`runner/canopy_runner/canopy_runner/native_permissions.py`, module docstring): the runner also writes the profile as Claude Code's own DENY rules, because fleet sessions skip permission prompts and only deny rules take effect natively. They remove whole tools, MCP servers and high-risk programs the profile never grants; exact-argument scoping stays the hook's job.
* **Confined sessions have `Read`; a cloud runner's Claude Code has no `Grep` or `Glob`.** A profile that lists them grants nothing there, so `read_mode.default_read_profile` does not (its comments say why, including `ToolSearch` and the two scratch folders). File search in a confined session needs an explicit bash pattern in the profile. The default carries no network tool.
* **An app entry's turn** holds canopy's fixed app tools and nothing else canopy serves, `Read`/`Write` only in its scratch folder, and no Bash but read mode's thread-pinned email lines (`app_entries.profile`); the runner renders it like any profile (`native_permissions.settings_for`).
* **A confined session never holds the runner owner's PAT.** It reaches canopy's MCP with a **caller token** (`apps/harness/caller_tokens.py`, issued by `apps/harness/claim_payload.py::issue_credentials`), minted per confined turn and bound to its conversation. It resolves to the conversation's CURRENT turn: tools run as that turn's caller (no canopy user at all for an outside contact), and only the tools the profile lists exist (`apps/mcp/turn_scope.py`). Expired, long-finished, or a conversation whose current turn is not confined authenticates nothing (`caller_tokens.resolve`); `who_is_asking` answers only about its own conversation. A sensitive turn's token reaches at most `sensitive_data.SENSITIVE_CANOPY_TOOLS`, re-asked on every call.
* **A confined turn holds no credentials it does not need.** canopy refuses it the GitHub token delegated to the agent (`apps/agents/credentials/delegations.py::github_refusal`). The cloud runner builds its env from an allowlist (`runner/ec2/cloud_runner.py::_confined_env`), with no canopy token, agent `.env`, vault key or chat key.
* **A colleague's FULL turn reads as the colleague.** A full-profile turn not asked by the agent's owner, an agent admin or canopy (`caller_tokens.is_caller_scoped`) gets a **scoped** caller token (`CallerToken.scoped`): every READ tool exists, plus driving the asker's open page and the site gateway (`PAGE_DRIVE_TOOLS`, `SITE_GATEWAY_TOOLS`); a write is refused, because the asker granted no act-as-you permission. Each tool runs as the conversation's current asker, so `turn_access.can_read_turn_content` and the session ACL decide what `harness_list_turns` / `read_turn_messages` / `read_turn_transcript` return. The runner leaves the token where only that session finds it (`cloud_runner.py::_scoped_token_env`; `runner/canopy_runner/canopy_runner/scoped_token.py`, which clears it for a later turn with none), the plugin's headers helper never falls back to a PAT once it has one, and a write failure refuses the turn. A scoped token does not serve a confined turn's conversation, and a confined token does not serve a full turn's.
  **Reads stop where the agent's part in them stops** (`apps/canopy_sessions/access.py::turn_reach`, REST and MCP alike): an agent turn's caller token reads the asker's sessions only if the session is its own conversation or is with that agent. Their laptop sessions and chats with other agents take an act-as-you grant. A repo chat's token has no agent and is not limited. The reach covers a turn's content too (`apps/harness/turn_access.py::can_read_turn_log`, `apps/canopy_sessions/access.py::turn_in_reach`).
  **REST takes a scoped token too, but only where MCP would** (`apps/tokens/middleware.py::_authenticate_caller_token`): re-resolved on every request, it signs in as the asker on a route MCP serves as a tool (`apps/mcp/api_tools.py::is_tool_route`) and is refused (403) on every other one, and an agent turn's token is refused every write but driving the page. A confined token is refused on REST (401): its tool list is an MCP filter REST cannot apply. A repo chat's token keeps its writes.
* **Projects run as the person who asked.** A project turn or project chat (a repo, no agent) has no agent to act as, so it acts as its verified, active human asker with a scoped token (`caller_tokens._project_asker`): exactly that person's access, never the box's (the cloud runner strips its own canopy token). Unlike an agent's caller token it may write: a repo chat is the person's own tool. The token follows the conversation's current asker and voids when a later turn has none verified; a turn with no person behind it (a schedule, a drill) gets no token. GitHub is the one thing a project borrows from an agent, its repo's `RepoIdentity` agent (`delegations.turn_agent`; [runner-credentials.md](runner-credentials.md)).
* **Known limit.** On a laptop every session is the same OS user and emdash spawns it, so the runner cannot strip its environment; on any box, credential FILES (agent `.env`s, gog's keyring, ace's Drive key) stay readable to an escaped session. The guard and the native deny layer are what keep a confined session off them.

## App entries: a confined turn writes as its asker, within one app

The one narrow exception to "an agent turn's caller token never writes" (`apps/mcp/tools/app.py`, module docstring). A turn confined to an app entry ([host-sites.md](host-sites.md) § App entries) may run `app_act` / `app_tasks_act`, which change the app's records and its declared project's tasks AS the person who asked:

* **Only those two tools, only that app.** The app is read from the turn's own entry (`Turn.capability`), never an argument; a turn in read mode, a host site, the whole agent or a scoped token is refused (`tools/app.py::resolve`).
* **Only a verified, active human asker**: the turn's initiator user, proven by this message (`caller_context.is_verified`), not an agent's login, not a contact; an unproven sender reaches nothing in the app even when a line names their address.
* **Only what they could do themselves**: the app's DECLARED actions under their own app role (a guest's scoped role included; `apps/workspace_apps/agent_host.py`), on the live app; task actions never start a turn (`workspace_apps/tasks.py`). No act-as-you approval: it is exactly what they could tap on the app's page.
* **Recorded "<agent> for <person>"** in the record's and the task's history (`services.act(acting_agent=)`, `tasks.act_task(on_behalf_by_agent=)`), and one MCP audit row per call naming the turn and the app.

## Acting on behalf of the person who asked

An agent's turn does the work of the person who started it, and canopy-web carries that person without being told (`apps/harness/turn_asker.py`, whose module docstring is the definition). The person is found only from the per-turn login (`TurnAgentToken`), never a stored PAT (which anything holding it could use to name any turn), and only while that turn is executing, unconfined, for this agent, and was started by a verified, active human or on such a person's behalf (`turn_asker._serving`, `_principal`). The request must not have lowered itself (`acts_as`); anything else is the agent acting for itself. `X-Canopy-On-Behalf-Of` is accepted only as an assertion naming that same person; any mismatch, and any other credential sending it, is a 403 saying why (`turn_asker.declare`).

Decisions judged as that person (`turn_asker.of` / `note`):

| Decision | Where | Their access needed |
|---|---|---|
| Pin a turn, or place a chat, on a runner | `access.may_pin_runner` | the target agent admin, or the runner's administrator |
| Ask for `turn_mode: auto` | `turn_gates.check_requested_turn_mode`; the claim re-checks `requested_turn_mode_by` | the target agent admin |

Reads are unchanged: a turn already reads as its asker where that matters (scoped tokens, above). Each decision is recorded as an `agent.on_behalf.decided` event. Every turn the agent starts from there carries `origin_ref.on_behalf_of`, stamped by `services.enqueue_turn` alone (a client's own is dropped); the turn's initiator stays the agent. The receiving agent's envelope says so in `who.on_behalf_of` (`initiator.py::_on_behalf_of`); `null` means the agent acted on its own.

## Acting as the person on canopy-web (act-as-you, in your own turn)

An agent working in a turn you started can ask to act **as you** on canopy-web itself, for 30 minutes, and does so only once you approve with your passkey (`apps/harness/act_as.py`, `harness.models.ActAsGrant`; rules pinned by `tests/test_act_as_you_on_canopy.py`):

* **Asked by the turn, for the turn's own person.** The request is made with the login canopy-web issued for the turn, and the person is worked out exactly as in "Acting on behalf" (`turn_asker.check`); nothing the agent sends names the person, so it can never ask to act as anyone else. A stored token, a confined turn, a contact's, canopy's own or an unverified asker's turn asks no one (403 saying why); so does a person with no passkey (`act_as.ask`).
* **It belongs to the conversation, not the one turn.** In a chat the reply carrying the approve link reaches the person only when the asking turn ends, and each later message is a new turn with a new login. So the request and the permission live while the turn runs **or**, when asked in a conversation, while that conversation is active and its newest turn is still the person's (`act_as.held`). Any turn login of the same agent in that conversation working for the same person may read the status, collect the token (once) and stop it (`act_as.agent_may`). A colleague's message, or the conversation closing, ends it.
* **Approved with a fresh passkey touch, for that request, in your browser.** A session cookie, a step-up window or any token is not enough, and approve/decline refuse every token (`act_as.approve`, `harness/api_act_as.py`).
* **Write is refused to an unattended `auto` turn** (`act_as.unreviewed_write_refusal`: 403 at the request, 422 at the approval). An `auto` turn is unreviewed, and write authority as you with no human in it is the one combination refused. A `manual` turn is unaffected. An `auto` turn **you are attending** may ask for write; the conditions are `act_as.attended_by` (your message typed in the canopy-web chat, that very person, verified, not confined, and present in that chat when it asks). Presence is checked when the agent asks; the permission still dies with the conversation.
* **Read or write, 30 minutes, dies with the turn.** `read` reaches GET routes and read-only tools only; `write` reaches every route canopy's MCP serves as a tool except the lists in `act_as.EXCLUDED_PREFIXES` / `EXCLUDED_PATTERNS` / `EXCLUDED_TOOLS` (tokens, passkeys, vaults, keys and secrets, act-as and host-grant approvals, the runner protocol). 30 minutes from the touch, never extended; a new approval needs a new request. Every request re-checks it (`act_as.dead_reason`).
* **The token is returned once** (`cact_…`, only its hash is kept; `act_as.collect_token`). It signs in as you on REST (`apps/tokens/middleware.py::_authenticate_act_as_token`) and MCP (`mcp/act_as_scope.py`), never mints, never steps up, and is refused where only you may act (`kinds.speaks_for_a_turn`). A turn it starts is not a verified asker's, so it never chains into another permission.
* **Attributed "<agent> as <person>"**: every request is a row in the MCP call log with the acting agent and the grant (`MCPAuditLog.acting_agent`, `act_as_grant`); `act_as.*` events (never the reason) are in the workspace's event log for its admins.
* **You see and stop it** (Settings → Agents acting for you, the approval page); the agent may stop it too.

## Acting as the person on a host site (act-as-you permissions)

The **act-as-you permission** is the person's word for a **host grant** (`apps/tokens/models.py::HostGrant`): a time-limited permission that lets an agent call a host site's tools as that person, within their own access on that site, for the page they are on. It is the only way an agent acts as a person *on a host*:

* **Given by acting, never by loading, and only with the person's passkey.** The panel asks the site for one only when the person sends from it; nothing can use it until they confirm it with their passkey in the panel, which is asked only when the agent's turn first calls the site, never at the send. The wording shown is the site's own `site.json` (`host_grants/site_needs.py`), descriptive only, never enforced. 30 minutes from the passkey (`host_grants.CONFIRM_SECONDS`); token renewals carry the same end, never extend it.
* **Never a contact's.** Only a canopy user has a passkey, so a contact is never given one, and an agent that serves the site on pages is not offered to a contact there at all.
* **Read by one lookup, with no fallback** (`host_grants.lookup`): a turn (gateway) or a View in a conversation reads only the grant of the page that last acted in that conversation as the person; expired, stopped or unconfirmed is a refusal, never another page's grant or the agent's own credential.
* **A chat on a page reaches its site only as the person, under their act-as-you permission, owners included.** The gateway (`site_tools` / `site_call` / `site_read`) serves every turn in a conversation held on a site's page whose agent lists that site (`published_profiles.page_site_of`), whatever the turn's profile; every call uses the SENDER's grant for that page. A full-profile turn is narrowed by the host site's tool limit (`published_profiles.site_ceiling`).
* **The agent's own login at that site is withheld from such a turn** (`published_profiles.own_login_of`, `page_turn`): the claim carries `page_site: {site, withheld}`; a cloud runner leaves those credential names out of the turn's environment; a laptop runner cannot set an emdash session's environment, so it leaves a by-task marker for the agent's MCP headers helper, and there the boundary is the helper and the instructions (the agent's `.env` is still on that disk). The envelope's `site` block tells the agent it has no account of its own there in this conversation.
* **The person sees and stops theirs** (Settings → Agents acting for you; Stop in the panel). Stop takes effect on the next call.
