# API: runner credentials and sign-in

Routes for how a cloud runner signs in and gets its credentials, and the credential sets several runners read. Part of the [api surface](api-surface.md) topic; the index there lists every part.

**Runner credentials and sign-in** (cloud boxes; laptops use ambient auth)
- `GET /api/harness/runners/{runner_id}/credential/status` — Administer tier. The box's Claude `credentials`, one ordered list of logins, tokens and API keys (key, kind, name, account, signed_in, has_value, in_vault — never a value), the `vaults` that hold its values, plus the fixed-slot view older callers read. A true read: it never bumps `updated_at`/`updated_by`.
- `GET /api/harness/runners/{runner_id}/credential/resolve` — the box's OWN runner token only (403 `runner_only`), with a device proof of an active key on that runner (401 `device_proof_required`): each vault serving the runner as ciphertext, this device's copy of its key, and the values its list names; each logged (`RunnerCredentialRead`). Not an MCP tool. `POST /api/harness/runners/{runner_id}/vault` — Administer tier (browser + step-up): the runner's own vault, made and attached (`docs/architecture/vault.md` § A runner's own vault). `PUT …/vault/values` — the box only, as resolve: `zk1:` values it sealed, for names on its list; each drops the stored copy. `POST …/vault/entries` — Administer tier: a token or API key whose value the browser seals into the vault (`{key, secret_name, vault_id, kv}`; 422 with no vault key).
- `PATCH /api/harness/runners/{runner_id}/credentials/{key}` (`{name}`; anything else, a `value` above all, is 422) · `DELETE …/credentials/{key}` · `PUT …/credentials/order` (`{keys}`) — Administer tier, settings. Rename one, remove any entry (422 for the last token or API key), or set the order (every key exactly once, else 422). A token or API key is added by signing it in or sealing it into the vault (`…/vault/entries`), never pasted here. The box uses the first that works; stepping onto an API key raises a coalesced `warn` event. Each returns the masked status. See `runner-credentials.md` § A cloud runner's Claude credentials.
- `POST /api/harness/runners/{runner_id}/logins` — Administer tier, settings. Add a full Claude login at the end of the list and start its sign-in. `DELETE …/logins/{key}` and `PUT …/logins/order` are the older names for the `credentials` routes.
- `GET /api/harness/runners/{runner_id}/credential` — Act-as. The list the box uses, with no value: `cascade` (every entry in order, a token's or key's `vault_secret` once a vault serving the runner holds it), `logins`, `vault_open`. No route takes a plaintext token or API key.
- `POST /api/harness/runners/{runner_id}/credential/swap` — Administer tier. Exchanges the first two tokens' places.
- `POST …/logins/report` (`{logins: [{key, signed_in, account}], adopt_default}`) — Act-as (the runner's half). Which listed logins the box holds and as whom; `adopt_default` adds a pre-existing default login at the front.
- `POST /api/harness/runners/{runner_id}/mint` (`{slot: box|token, login_key}`) · `GET …/mint` — Administer tier. Start (superseding any unfinished attempt) / read a browser sign-in: `box` signs in one of the box's logins (`login_key` "" = the default one), `token` makes a setup-token (`login_key` names the token to replace, "" adds one); 404 for an unknown key; `null` when none was ever started. canopy-web only relays — it never holds the PKCE verifier.
- `GET …/mint/claim` · `POST …/mint/url` · `POST …/mint/entry` · `POST …/mint/result` — Act-as (the runner's half). `claim` is polled and returns work only when the runner owes it; reading a code consumes it. `url` posts the URL a human must open. A `token` sign-in names its entry (`entry {vault_key}`), seals the token into the runner's vault, then reports `result {vault_key}` — done only if the vault holds it; with a `detail` it failed, and an entry made for it goes again. A token itself is never accepted (one sent fails the sign-in, unstored). A `box` sign-in reports `logged_in` + `account`, which marks that login signed in. 409 when no sign-in is in progress.
- `POST …/mint/code` — Administer tier. The human submits the single-use authorization code; 409 unless the runner is waiting for one, 422 if empty.
- `POST /api/harness/runners/{runner_id}/sign-in-request` — Act-as. The box started a device-code sign-in (AWS SSO) and pushes the approval link to the runner's owner. `reason` required (422). Returns `{sent, id}`: `sent` = devices reached (0 → fall back to another channel); `id` = the stored `SignInRequest`, kept until its code expires (~10 min) and shown on the owner's supervisor feed.
- `POST /api/harness/runners/{runner_id}/sign-in-requests/{request_id}/result` — Act-as. The box reports `outcome` (`approved` | `failed` | `expired`); clears the URL and takes it off the feed. First report wins.
- `GET /api/harness/sign-in-requests/mine` — Self. The caller's own open sign-in requests (runner, who, why, URL, expiry); expired rows are closed on read.
- `POST /api/harness/runners/{runner_id}/turns/{turn_id}/github-token` — Act-as, for a turn this runner is executing (else 404). The git identity of the GitHub token delegated to the turn's agent, and where it is: `delegated: "github-token"` and `agent` — the box opens it from its own resolve; no token (`token` is always empty now; older runners still read it). 409 with the reason when none is delegated, its person is no longer an admin, or the turn is a caller's (confined) turn — no shared fallback. Re-checks that the box may still hold the agent. Each issue logged. See runner-credentials.md → "The GitHub identity a turn gets".
- `POST /api/harness/runners/{runner_id}/turns/{turn_id}/agent-token` — A canopy login as the turn's agent (`Agent.user`), for a turn this runner is executing (else 404); only with this runner's own runner token (a PAT, even its owner's, is 403). 409 with the reason for a direct turn, a confined (caller) turn, or an agent with no active login. Expires within 12 h; revoked when the turn stops executing on the runner. Each issue logged as a credential read. See runner-credentials.md → "The canopy login a turn gets".
- `GET /api/harness/runners/{runner_id}/turns/{turn_id}/attachments/{attachment_id}/content` — Act-as, for a turn this runner is executing. The bytes of any attachment already SENT in that turn's chat (earlier messages included; never another chat's, never an unsent draft), with the browser route's headers. Authorized by holding the turn, not by the box owner reading the chat — a teammate's chat is often invisible to the box's owner. Re-checks that the box may still hold the agent; every refusal is the same 404. In a sensitive conversation only a file THIS turn claimed, once: the bytes are deleted as they are served (`private_attachments.take_for_runner`), the name rides only in `Content-Disposition`, `Cache-Control: no-store`.
- `GET /api/harness/runners/{runner_id}/github-readiness` — Act-as. Per agent this runner serves: can it open a PR (by what the machines that open the delegated token last reported). Called at boot so a bad token is a red health check, not a mid-turn 403.
- `POST /api/harness/runners/{runner_id}/delegated-checks` — Runner. `{agent, name, checks, provider_expires_at, error}`: what this box found probing a credential delegated to an agent it runs (canopy-web cannot open one). A failed probe tells its person to replace it.
- `GET /api/harness/runners/{runner_id}/vault-keeper/slot-secrets` — Runner (a keeper). Pool-slot secrets sealed to one of this box's machines that a reader of the agent (a machine approved since, or a vault member) waits for, in the shape of `delegated`. `PUT …/vault-keeper/{slug}/slot-secrets/{capability}/{slot}/{key}` (`{value_zk, expect}`) stores the re-seal, refused for a recipient that is not one of the agent's readers, for dropping one that holds it, for a box with no copy, and when stale. capabilities.md §6.
- `PUT /api/harness/runners/{runner_id}/vault-keeper/{slug}/delegated/{name}` — Runner (a keeper). `{value_zk, expect}`: a delegated credential this box holds, re-sealed for a machine that was waiting (listed in `GET …/vault-keeper` → `delegated`). Refused for any recipient that is not a machine that runs the agent or its person, for dropping one that holds it, and when stale.
- `GET /api/harness/runners/{runner_id}/agents` — Act-as. The slugs of the agents this runner runs (`routing.agents_routed_to`: the claim's own static gates — enabled routing, enrollment, the hold check). The box's credential refresh prepares only these.
