# API: walkthroughs, reviews, DDD runs, shareouts, storyboards and dynamic views

Routes for the demo and review surfaces: walkthroughs, narrative reviews, DDD runs, shareouts, storyboards, dynamic views and issues. Part of the [api surface](api-surface.md) topic; the index there lists every part.

## Issues (`apps/issues`)
`canopy.origin` records — GitHub issue provenance / evidence capture (the issues ACE files as it runs).
- `POST /api/issues/` upsert · `GET /api/issues/` list (paginated) · `GET|DELETE /api/issues/{repo_slug}/{number}/`.

## Walkthroughs (`apps/walkthroughs`)
- `GET /api/walkthroughs/` — list, scoped to the pinned workspace or all the caller's. Filters: `project` (repo `project_slug`), `agent_project` (`hal/P5`, `hal:P5` or id), `kind=html|video`, `mine=true`, `session`, `turn`.
- `POST /api/walkthroughs/` — upload (multipart): `file`, `kind`, optional `title`, `description`, `project_slug`, `visibility` (`private` | `link`; `link` mints a share token), `links`, `run_id`, `narrative_slug`, `role`, `narrative_review_id`, `session_id`, `turn_id`, `agent_project`. Optional `duration_sec` (the measured length; a malformed value is ignored). A video pinned to a narrative version (`narrative_review_id`) may name its **cut** (`cut_id` = the recipe's `cuts[].id`, `cut_scene_ids` = comma-separated narration ids): a `style: recorded` narrative holds one video per cut, latest upload per cut wins; a cut without a version is 422. Over `WALKTHROUGH_MAX_UPLOAD_BYTES` → 413.
- `GET /api/walkthroughs/{wid}/` — `auth=None`. A `link` walkthrough needs `?t=<share_token>` for anonymous read; a missing/wrong token 404s like private. `is_owner` drives the toolbar; owners also get `share_url` (`…/w/<workspace>/walkthrough/<uuid>?t=<token>`).
- `PATCH /api/walkthroughs/{wid}/` (uploader or workspace owner) — title/description/project_slug/visibility. To `link` mints a token if none; to `private` keeps it (re-publishing revives the same link).
- `DELETE /api/walkthroughs/{wid}/` (uploader or workspace owner) — deletes the Drive file and the row.
- `POST /api/walkthroughs/{wid}/rotate-token` (uploader or workspace owner) — re-mints the token, killing shared links.
- `GET /w/<workspace>/walkthrough/<id>/content` — bare streaming view (`apps/walkthroughs/streaming.py`), Range-aware. Session auth OR (`link` AND correct `?t=`). Another workspace's walkthrough 404s; registered `<str:wid>` so a malformed id 404s rather than hitting the SPA. Every `content_url` / `video_url` the API returns is this path.
- **No flat artifact addresses** — which prefixes 404 and why: [pages.md § Rules for every page](pages.md#rules-for-every-page). `tests/test_api_urls_are_workspace_scoped.py` fails on any artifact URL field not under `/w/<workspace>/`.
- Settings: `WALKTHROUGHS_ENABLED` (default on; off → the API and content stream 404), `CANOPY_DRIVE_SA_KEY_JSON` (empty → uploads/streams 503 `drive-not-configured`), `CANOPY_DRIVE_ROOT_FOLDER_ID` (`walkthroughs/<uuid>/` subfolders go under it), `WALKTHROUGH_MAX_UPLOAD_BYTES` (default 75 MB). Spec: `docs/superpowers/specs/2026-07-13-walkthrough-share-token-revival-design.md`.

## Reviews (`apps/reviews`) — DDD narrative review surface
- `GET /api/reviews/` list (the `/ddd` dashboard) · `POST /api/reviews/` create (DDD orchestrator) · `DELETE /api/reviews/{rid}/`.
- `GET /api/reviews/{rid}/` — `auth=None`; detail / poll for resolution. A `link` review is readable by anyone with the URL (tokenless); private 404s. Carries `version_video` + `cut_videos`, each URL playable by THIS reader (a guest gets a public cut's token URL and none for a private one).
- `request_json` is stored verbatim; beyond the DDD fields the page renders these optional demo-framing keys when present: `title` (the narrative's name — also the storyboard card heading), `audience`, `purpose`, `data_disclosure`, `storyboard_url` + `storyboard_title` (the set it belongs to), `cuts[{id, title, screen_notes, audience_note, provenance, poster_url, duration_sec}]`, `assumptions[]`, `divergences[{script, data, resolution}]`, `open_questions[]`; and per narration item, `provenance`.
- `GET /api/reviews/{rid}/destination` — `auth=None`; where a review is read: `{url}` = the narrative's storyboard entry (board token only for a caller holding the review's own valid `?t=`; a member gets it tokenless), `null` for a findings review. May create the board. 404 to anyone else.
- A narrative review's gate is ALSO a decision row on its storyboard (`apps/storyboards/review_gate.py`): ruling it, or a round closing with it ruled, resolves the review server-side with `{decisions, edited_scenes, overall_feedback, build_order, resolved_via}`; a `submit` marks the row ruled in turn.
- `POST /api/reviews/{rid}/submit/` — approve/redraft + narration edits; requires a login (403 to an anonymous reader) and CSRF.
- `POST /api/reviews/{rid}/suggest/` — `auth=None`; suggested edits that never resolve the gate, appended for the owner (who is told). Caller: an external reviewer with the share token (`?t=`, no CSRF), or a member of the review's workspace saving edits without deciding (CSRF-checked). Unreadable → 404; neither → 403.
- **Run-child gates belong to no narrative.** `RUN_CHILD_GATES` (`apps/runs/ddd.py`; `product_findings`) hang off the run: `create_review` stores `narrative_slug=None`, `version=0`, and `/w/<ws>/review/:id` renders them standalone (the one review page left) (no DDD rail). `apps/runs/aggregate.py` may attach one to an existing narrative but never creates one, since the same gate is used outside DDD runs. `_NON_NARRATIVE_GATES` is a superset: `external_release` is not a version but may create its narrative.

## DDD runs (`apps/runs`, mounted at `/api/ddd`)
- `GET /api/ddd/narratives/` — list.
- `GET /api/ddd/narratives/{slug}/` — narrative + runs grouped by version, with computed `visibility` (`public` / `private` / `mixed`). Each version has `cuts` (narration order) beside its hero `video_url`: the non-cut video, else a cut uploaded as `role=hero_video`, else the first cut (`apps/walkthroughs/pinned.py`).
- `GET /api/ddd/runs/{run_id}/` — run package (video + deck + narrative + links).
- `GET /api/ddd/release/{run_id}/` — `auth=None`; workspace member OR `?t=<share_token>`. Backs `/w/<ws>/ddd-release/…` (`ws` = the page's workspace; a run elsewhere 404s; `share_url` is the page's scoped token-bearing address).
- `PATCH /api/ddd/narratives/{slug}/visibility/` — Public/Private for a whole narrative, cascading to every walkthrough + review under the slug.
- `DELETE /api/ddd/runs/{run_id}/` (cascades walkthroughs + reviews) · `DELETE …/narratives/{slug}/versions/{version}/` · `DELETE …/narratives/{slug}/`.
- `POST /api/ddd/narratives/{slug}/move/` — `{to_workspace, dry_run=true, also: [slug…]}`. A narrative is inferred from the `ReviewRequest` + `Walkthrough` rows sharing its slug, so this moves all of them (and the storyboards referencing it) together. Dry run by default (the plan is the undo record). Requires membership of both workspaces. Same service: `manage.py move_narrative_workspace --to <ws> --slug <slug> [--apply]`.
- A narrative is identified by `narrative_slug` (independent of `run_id`); the server rejects narrative-less package artifacts.
- **Iteration sources: nothing needed to keep iterating a narrative may live only on one machine.** `POST /api/ddd/narratives/{slug}/sources/` (multipart `file`, `role`, `narrative_review_id`; editor of that version's workspace) pins a file to a narrative version. Roles are a closed set: `recipe`, `intent`, `master` (the recording cuts are re-rendered from), `capture_report`, `capture_manifest` (`NarrativeSource.ROLES`). Identical bytes on the same version and role are reused (`reused: true`); changed bytes replace the previous file. `GET …/sources/` lists them (member, newest first) and `GET …/sources/{id}/content` downloads one. Each version in the narrative detail lists its newest source per role under `sources`. Version and narrative deletes drop their sources, and a move carries them. Bytes are on Drive under `narrative-sources/<id>/`, capped by `NARRATIVE_SOURCE_MAX_UPLOAD_BYTES` (150 MB). The canopy plugin pushes them with every narrative post and video upload, and `narrative pull` restores them (`apps/runs/sources.py`, `tests/test_narrative_sources.py`).

## Shareouts (`apps/shareouts`)
- `GET /api/shareouts/` — list (teammate-facing work briefings per window).
- `POST /api/shareouts/` — batch create, idempotent per `period`+`source`; optional `project_slug` stored as given (any well-formed slug). Returns `{created, replaced}`.
- `POST /api/shareouts/clear/` — clear by source / project / date (AND-combined).

## Storyboards (`apps/storyboards`) — the shareable arc
Product tier. `Storyboard → Act → Entry`; an entry names a narrative by slug and resolves to its current release at read time (`Entry.pinned_run_id` holds a known-good run while a narrative is redrafted). `slug` is unique per workspace.
- `GET|POST /api/storyboards/` — List (member) / create (editor+).
- `GET /api/storyboards/{slug}?ws=&t=` — `auth=None`, self-enforcing: member, or a matching `?t=`. A wrong token 404s (never 403). `ws` (the workspace in `/w/<ws>/storyboard/<slug>`) 404s a board elsewhere and disambiguates a slug two workspaces share; the narrative and feedback routes take it too.
- `PATCH /api/storyboards/{slug}` — Retitle / reorder / set capability / replace `brief` (editor+). Acts are replaced wholesale.
- **A board is the one link for a SET of demos.** Optional `brief` on create / patch / YAML import (`StoryboardBrief`, unknown keys 422): `audience`, `purpose` (the point to land), `data_disclosure`, `short_version {label, note, items: [{narrative_slug, cut_id?}]}`, `assumptions[]`, `divergences[{script, data, resolution}]`, `open_questions[]`. Each read entry carries `cuts[]` — a recorded narrative's cuts in running order (`apps/storyboards/cuts.py`): the pinned cut video (`video_url` withheld when this reader cannot stream it), `duration_sec`, `word_count` (counted from the narration), `scenes`, `anchor_id` (`cut:<id>`, what a per-cut note anchors to via `/feedback`), and `screen_notes` / `audience_note` / `provenance` / `poster_url` / `optional` from the version's `request_json.cuts[]` (provenance defaults to the scenes'). A declared cut with no video reads `recorded: false`. Entries also carry the version's own `assumptions` / `divergences` / `open_questions`.
- `POST /api/storyboards/{slug}/share` · `/rotate-token` — Mint the link if missing / re-mint it (kills every link sent). The link is `/w/<ws>/storyboard/<slug>?t=…`.
- `GET /api/storyboards/{slug}/narratives/{narrative_slug}` — The reviewer surface's read (current + previous narration). Same token gate; 404 if the narrative is not on the board.
- `POST /api/storyboards/{slug}/feedback` — Anonymous, capability-gated write. One grant per board: `read` < `comment` < `suggest` (insufficient → 403). `channel`/`target_kind` are server-set; a narrative not on the board → 404. Lives here, not in `apps/feedback`, because the product app owns the token; it calls the request-free `feedback.services.ingest`.
- **Feedback rounds** (`apps/storyboards/rounds.py`; session auth): `POST /api/storyboards/{slug}/rounds` (editor+) — open one: pins every narrative's current version and adopts the notes since the last round; 422 unless the board is linked to a project in its own workspace. `GET …/rounds/{number}` (members; a token holder 404s) — the round in full. `POST …/rounds/{number}/close` `{close_note?, picks?}` (editor+) — applies staged decision edits, then creates and approves ONE task on the board's project (one agent turn); a second close or an unpicked disagreement is 409. `POST …/rounds/{number}/consume` `{run_id}` (editor+, the agent's PAT) — refuses while any note is unanswered; opens round N+1. `DELETE …/notes/{note_id}` (editor+) — remove a note from the OPEN round (409 for one in a closed round).
- `POST /api/storyboards/{slug}/decisions/{key}/edit?t=` — `auth=None`, self-enforcing like the read: confirm / change / write in / undo one decision. Inside an open round every edit is staged (a link holder needs `suggest`, else 403); outside one only a member may (409), and a review-gate row needs editor+. 422 invalid, 409 conflict.
- `GET /api/storyboards/{slug}/notes` — Notes left on the board, members only (a share token never grants it). Never returns `author_email`; refuses a real board exactly like a missing one. `StoryboardOut.is_member` tells the page whether to fetch.
- Act identity is `Act.key` (from the title, or declared `key:` in YAML), never the row id — both write paths recreate acts. One derivation: `apps/storyboards/act_keys.py`.
- Authoring: `manage.py import_storyboard storyboard.yaml --workspace <slug>` — idempotent per `(workspace, slug)`, preserves the share token.

## Dynamic views (`apps/dynamic_views`, mounted at `/api/dynamic-views`) — generated screens in a sandbox
Product tier. A view is JSX (`function View(props)`) plus declared catalog reads, on a workspace or one of its projects, drawn in an opaque-origin frame that reads canopy only through the page, as the viewer. Design and safety model: `docs/architecture/dynamic-views.md`.
- `GET /api/dynamic-views/guide/` — The render contract, the data catalog (every read a view may ask for) and a working example with its sources. Any signed-in caller. Read it before generating a view.
- `GET|POST /api/dynamic-views/` — List (member; `?project=<handle>` narrows) / create (editor of the workspace, or edit rights on the named project). Code must define `View`; every source is checked against the catalog, and every declared agent task (`agent_tasks: [{agent, name}]`) against the view's workspace and the author's own right to give that agent a task (422 names what is wrong). Slugs are unique per workspace (made from the title when omitted).
- `GET|PATCH|DELETE /api/dynamic-views/{id}` — Read with code and sources (member) / change (a new version; a patch that alters nothing is not one; `project: ""` moves it to the workspace) / delete with its history.
- `GET /api/dynamic-views/{id}/revisions/` · `POST /api/dynamic-views/{id}/rollback {version}` — Every version, newest first / restore one as a new version.
- `GET /dynamic-views/frame/` — Not an API route: the bare frame document, answered by `DynamicViewFrameMiddleware` before sessions (never sets a cookie), with its own CSP (`sandbox allow-scripts`, `connect-src 'none'`, `frame-ancestors` canopy's origins).
