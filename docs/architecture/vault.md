# Vaults: who may open an agent's secrets

Byte formats: `docs/vault/zk-v1/zk_v1_reference.py`.

## A vault and its members

A **vault** (`agents.Vault`, `apps/agents/models/vault.py`) is a named set of secrets with its own membership. Every agent has one (`kind=agent`), made when the agent is created (`apps/agents/apps.py`) and moved with it (`move._vault`). Its secrets and key copies are stored on the agent (`AgentCredential`, `AgentVaultWrap`).

Who may open a vault is `credentials.vault_members.members(vault)`, the union of:

- **direct members** (`VaultMember`): people added by name. A direct member counts only while they are in the vault's workspace (directly or inherited), until a manager removes them;
- **links** (`VaultLink`), re-read on every question:
  - `agent`: everyone with full access to the agent (`access.roster`), plus everyone with an active license to use it directly (`AgentLicense`). The agent's owner comes in as `owner`, its admins as `admin`, everyone else as the link's role;
  - `workspace_owners` / `workspace_admins`: the owners (or admins) of a workspace, inherited down the tree as those roles are.

Members are **people only**: an agent's own canopy login (`Agent.user`) is never a member by any source, and cannot be added (`member_roles.not_a_person`). They hold no vault key (except an agent login's test key, which opens no vault, below), and an agent that could change its own vault's membership could hand its key to anyone.

A vault's roles are the agent's, without contacts: `owner`, `admin`, `member` (`member_roles`; the legacy words `manage`/`use` are accepted and mapped by `role_named`). A person's role is the highest any source gives them. Owners and admins see and edit values and change membership (`member_roles.is_admin`); members open the values. Owner is never stored: it comes only from owning the linked agent, or, for a workspace vault, the workspace. Every member carries their sources, so the vault's page says why each person is in it. A new agent vault starts with one `agent` link, so giving someone the agent gives them its vault.

A change that would leave the vault with no owner or admin is refused (`vault_needs_an_admin`). Membership writes lock the vault's row, so two at once cannot together remove the last owner or admin. Setting or deleting an agent's values is a vault write like rotating its key: the caller must be an admin of the agent AND an owner or admin of its vault, and may not delete a credential a person delegated. A `zks1` value is checked on write: sealed at the vault's current kv, to recipients that may read the vault now (`api_credentials`, `vault_engine`). Membership routes are gated `vault-admin` (`apps/agents/api_vault_members.py`).

Everyone sets up a vault key of their own at sign-in, because a person can be given a vault's key only once they have one (`frontend/src/vault/VaultSetupGate.tsx`, `GET /api/vault/setup`). A failed check or a browser that cannot make a passkey lets them continue for that tab and asks again next time.

## An agent login's test vault key

An agent's own login may hold a personal vault key so a headless harness signed in as the agent can take part in its own sensitive conversations (`apps/agents/credentials/login_test_key.py`; the module docstring is the full rule). It opens nothing in any vault.

- **The switch:** `Agent.test_vault_key`, off by default, set by an agent admin (`GET|PUT /api/agents/{slug}/test-vault-key`). Turning it on needs a browser and a fresh passkey step-up (a token is refused); turning it off needs neither. Audited as a setting.
- **The key:** while on, the login makes ONE key as itself: passphrase seals only, never replaced (`login_test_key.check_keyset_write`). With the switch off, or for any other system account, a keyset write is refused (`not_a_person`).
- **What it receives:** only copies of the keys of sensitive conversations the login is itself in, and only while the switch is on (`conversation_keys._keyset`, `conversation_keys.add_wrap`).
- **What it never receives:** a copy of any vault's key or a value sealed to it, or an endorsement, whatever eligibility says (`vault_engine.parse_wraps` / `parse_values`, `zk_endorse.add`). A login that is not a person never registers a passkey or steps up (`passkeys.stepup.require_a_person`), so it approves no device key or invitation.
- **Off deletes it:** turning the switch off deletes the key and every conversation-key copy wrapped to it (`login_test_key.disable`).

## Whose account an entry is

Every entry, in an agent's vault (`AgentCredential`) or a workspace vault (`VaultSecret`), says whose account it is (`models.VaultEntryAccount`, whose docstring defines the fields), read through `credentials/accounts.py`, never the columns:

- **`agent`**: the agent's own (its own login or account). The rest of this page about the vault's key and its readers is about these.
- **`delegated`**: a standing credential from a PERSON's own account (or another agent's), given to the agent to use. Its provider status (`provider_expires_at`) is information only.

A delegated entry is sealed (`zks1`, zk-v1 §6) to the machines that run the agent (`accounts.delegated_devices`: an active device key with an approved ECDH key, on a runner that serves the agent, whose owner is one of its admins (`runner_may_hold_agent`), that runs turns, and that is a cloud box or the person's own (`accounts.may_hold_for`: a laptop's device key is in its owner's home directory, so another admin's laptop would let them open it)) and to its person's own vault key, and to nothing else. A recipient that no longer qualifies is dropped from the envelope without decrypting anything (`accounts.prune`); a machine that already opened it keeps what it saw, so its person replaces the token at the provider. It is **never under the vault key**: generic value writes refuse its name (`delegated_entry`), enable and rotate leave it out of coverage, a member's read of the vault names it and never carries its ciphertext, and a resolve's custodial and zero-knowledge `values` leave it out. It leaves canopy-web only in a resolve's `delegated` field, to a `runner` read proved by one of those machines (`accounts.resolve_payload`), while its person is still an admin of the agent (`accounts.serves`). A machine that holds it re-seals it for one that is waiting (`accounts.keeper_work`, `accounts.reseal`); a machine that opens it probes it and reports. Its person sees and withdraws it in their settings (`/api/me/delegated-credentials/`); no screen or API returns its value, even to them. Providers: `VaultEntryAccount.PROVIDERS`; GitHub is a pasted token (`delegations.set_github`), Google a runner sign-in (§ Connect your own Google account).

## Who may hold a copy of the vault's key (zero-knowledge)

- **A person** (`zk.eligible_members`): a member of the vault who has a vault key of their own.
- **A machine** (`zk.eligible_device_keys`): an active device key with an approved ECDH key, on a runner that serves the agent (`device_keys.runner_serves_agent`), **and** whose person is a member of the vault. The person is the runner's owner, else whoever approved the key (`vault_members.person_of_device`). The machine layer never grants on its own.

`pending` (`zk.pending_targets`), every wrap write and every `zks1` seal read these two functions, so nothing else decides who may hold the key (workspace vaults: the same names in `workspace_vaults.py`). A keeper's grant is checked again under the vault's lock and refused (`zk_not_pending`) for a target that already holds a copy, so two keepers make one grant. Replacing a person's vault key, or a machine's ECDH key, drops their copies in agent and workspace vaults alike.

## Removal: membership is checked on every access, never swept

Nothing deletes a copy of the vault key when someone stops being a member. Every place a copy, a value or an endorsement is used asks whether its person is a member **now**, so a leftover copy is ciphertext canopy-web never hands out:

- a machine's resolve refuses one whose person is not a member (`not_a_vault_member`), for the agent's own vault and each workspace layer (`workspace_vaults.layers_payload`);
- the browser's `GET …/vault/zk?values=true` gives the ciphertext only to a vault member, so an agent admin outside an unlinked vault cannot pair it with an old copy;
- the agent vault's zero-knowledge writes (enable, values, wraps, rotate, endorsements) need an owner or admin of the vault as well as of the agent (`vault_gates.zk_admin`, as the workspace vault's `api_vaults._vault(manage=True)`), so an agent admin outside an unlinked vault cannot rotate its key to a machine of their own;
- a box is a keeper of a vault only while it may hold that key now (`vault_keeper._held`, `workspace_vaults.device_may_hold`);
- `zk_notify.holders` and the endorsements a keeper checks (`zk_endorse.endorsements`) count current members only.

"Holds a copy" is never itself a permission. A person who comes back opens the vault again with the copy they had. Copies are deleted only by the action that makes them useless: replacing a person's vault key or a machine's ECDH key (`zk.forget_member_wraps` / `forget_device_wraps`) or changing the vault key. A revoked device key is refused at every read. A copy made for someone who has since left still shows as not current (`rotation_recommended`), because it still opens the key it was made for.

The vault key is **not** changed on removal: the server simply stops serving the vault. "Change the key" (rotate), together with rotating the outside secrets, is the response when someone may have kept a copy.

## Connect Google mailbox: the token is made on a runner

An agent's Google token (`gog-token`) is minted on one of its runners, so canopy-web never holds it (`apps/agents/credentials/google_mint.py`, `AgentGoogleMint`). The sign-in goes to an online runner that runs the agent, may hold it (`runner_may_hold_agent`), has a key that reads its vault (`zk.eligible_device_keys`) and declares `capabilities.google_mint`; with none online it is refused (`no_mint_runner`) and nothing starts: there is no server fallback. The runner makes a PKCE verifier, keeps it, and posts only the challenge; canopy-web builds the consent link around it and holds the returned code until the runner takes it (once), and without the verifier canopy-web cannot redeem it. The box exchanges code + verifier at Google, refuses no refresh token / no account / the wrong account, builds the gog token and encrypts it (`zk1` under the vault key when the box holds a copy, else `zks1` to the readers canopy-web listed). The result route takes only that ciphertext, at the current kv, sealed to no one who may not read the agent; the account it names must be `expected_account`. A restart of the box loses the verifier and the sign-in reports `interrupted`; an unfinished sign-in expires after `google_oauth.STATE_MAX_AGE`.

## Connect your own Google account: a delegated credential

A person can lend an agent their OWN Google account through the same runner sign-in (`google_mint.start_delegated`). They name the account up front and the consent must come from it; only the services they choose are asked for (`google_oauth.delegated_scopes`). It is a **delegated** entry (§ Whose account an entry is). The runner chosen must have a machine that may hold a credential of theirs (`accounts.delegated_devices`) as well as read the OAuth client from the vault; the box seals to exactly `accounts.recipients`, never under the vault key even when it holds a copy. canopy-web stores it only as `zks1` sealed to those readers, from that account, while the person is still an admin of the agent. **Only the agent's admins may start one**: a delegated entry is in force only while its person is (`accounts.serves`), so a workspace member who is not an admin of the agent is refused (`not_an_admin`) rather than given a credential that would never be used.

**Using it in a turn.** The runner opens it from its resolve's `delegated` field with its own key, holds it in memory, and stages only a short-lived ACCESS token per delegated Google account for a turn to read (`runner/ec2/cloud_runner.py::_stage_delegated_google`). The refresh token never reaches a file a turn reads; a withdrawn credential's file is removed at the next stage. A laptop of anyone but the person never holds it, so a turn that needs it must run on a cloud runner that runs the agent.

## Granting without a person

Approving a machine signs its ECDH key with the approver's own vault key (an endorsement), even when the approver holds no copy of the agent's vault key, so a **keeper** (a canopy runner that holds it, `canopy vault zk keep`) can pass the key on. `zk_notify` emails the vault's owners and admins who hold the key (a member's copy opens the vault but grants nothing) only after `zk_notify.GRACE`, for what no machine could pass on, for agent and workspace vaults alike (`ZkGrantNotice`). A notice is always about a **person**: joining for the first time, a new vault key (sent at once, since no keeper grants a changed key, asking the admin to check with them directly), or not yet reached by a rotated key. A machine is named as its person's and is not mentioned at all while its person is waiting too; nobody is ever asked to recognise a machine.

**The keepers' record.** Which key each keeper trusted for each person is kept once, in the vault itself: `Vault.keeper_pins_zk`, a `zk1` value under the vault key (name `~keeper-pins`, at `keeper_pins_kv`). canopy-web stores it and can neither read nor forge it. A keeper reads it with its work and writes it back over the version it read (`keeper_pins_stale` on a stale write). So every keeper, including a brand-new cloud box, refuses a person whose key changed and leaves them waiting for a person. Granting them is the confirmation: an owner's or admin's browser grant also records the key it granted to, so keepers trust it from then on. Someone who started over with a new key (`UserVaultKeyset.replaced_at`) is emailed to the key holders at once, with no grace period, since no keeper will grant it. A rotation leaves the record unreadable, and keepers start a new one. Every keeper grant to a person is emailed to the vault's owners and admins (`vault_keeper._announce`). Only a machine whose person is an owner or admin of the vault is a keeper (`vault_members.device_works_for_an_admin`): a member's machine reads the vault but never passes its key on.

## Workspace vaults

A workspace may keep any number of vaults (`Vault`, `kind=workspace`), always zero-knowledge, in the agent vault's formats with the vault's **binding id** (`vault:<uuid>`) where an agent's id goes in every AAD and HKDF info (`credentials/workspace_vaults.py`). Its secrets are `VaultSecret`, its key copies `VaultKeyWrap`.

**One set of rules.** Both kinds of vault are written through `credentials/vault_engine.py`: who may be handed a copy, what making or replacing the key must carry (a way back, a copy the writer can open, every value re-encrypted, every holder still eligible re-wrapped), the key-version checks, and the state a client grants and rotates from. `zk.py` and `workspace_vaults.py` only say where their rows live and who is eligible (`engine.Store`), so a rule added to one kind of vault reaches the other.

- **Members:** made with two links: the workspace's owners (`owner`) and `attached` (`member`). `attached` gives everyone with full access to an agent the vault is attached to, by itself or through a workspace, and the **people of a project** it is attached to. It never gives the full-access people of a project's member agents: using an agent does not put you on every project it works on. Direct members as for an agent vault.
- **What it serves:** `VaultAttachment` rows, each exactly one target: an agent, every agent in a workspace and below, a project, or a runner (below). Agents, workspaces and projects lie in the vault's own tree only. Attaching an agent needs the caller to administer that agent too (it then reads the vault in its turns and its people join): to anyone else it is 404. A moved agent keeps an attachment only inside that tree (`move._vault_attachments`).
- **A project** serves its CURRENT member agents (`AgentProject.member_agents`, which includes agents that joined through a `ProjectShare`), so the agents that join a project to use the skills it carries get the secret those skills need without an attachment per agent. Nothing is stored per agent: joining gives the vault, leaving (or a share ending) takes it away at the next question, and `vault_members.project_agents` is the one place that decides it. **Who may open it is the project's people** (`project_members`, `docs/architecture/work.md` § A project's people): its lead and admins as the vault's `admin`, the rest as `member`, while they belong to the vault's tree, each with the source `project:<address>`. It serves a member only when BOTH the agent and the project's workspace lie in the vault's tree; a member outside it is listed as `not_served` on the attachment and gets nothing. Attaching needs the caller to manage the vault AND to be an editor of the project's workspace (the project's lead or a working agent's login is not enough, as for sharing a project); anyone else gets 404, a project outside the vault's tree is refused (`vault_bad_attachment`). Moving a project out of the vault's tree drops the attachment (`services.promote_project`); deleting it cascades.
- **Who may hold its key:** a member with a vault key; a machine whose person is a member and which serves an agent the vault serves (a project's served members included), checked on every read as for an agent vault. So for a project's vault, the owner of each machine running a member agent must be on the project, or that machine's turns run without the secret: the project members route names them (`box_owners_missing`) to whoever may change the list.
- **What this does not stop:** a turn of a served agent holds the vault's values. Someone who can start an unconfined turn of that agent can use a secret through it, or ask to see it, without being a member. To close that, narrow who has full access to the agent, or give the project an agent of its own.
- **Reading:** credential resolve returns `vaults`, the workspace vaults layered under the agent's own values (root workspace first, then vaults attached to a project the agent is a member of, then vaults attached to the agent; a later layer wins, and the agent's own values win over all), each with this device's copy of its key, or `wrap: null` when it may not open it (`workspace_vaults.layers_payload`). The client decrypts and merges.
- Making a vault needs `own`; rotating one from its page needs the person's own recovery code, as making its key does. Routes: `apps/agents/api_vaults.py`; the keeper grants through `api_vault_keeper.py`.

## A runner's own vault

A workspace vault can also serve one **cloud runner** (`VaultAttachment.runner`): it holds that box's long-lived Claude tokens and API keys. A secret's name comes from its credential-list entry (`RunnerLogin.vault_secret_name`).

- **Making one:** a runner admin (browser + step-up) gives the runner its OWN vault, its owner a direct admin member, attached to it (`workspace_vaults.create_for_runner`). Sharing is an explicit attach, by someone who manages the vault and administers the runner.
- **Isolation boundary** (`workspace_vaults.isolation_boundary`): every runner a vault serves has the same owner, serving the same thing (the agent of a runner that runs one agent, the root of a runner that serves a tree, or, neither declared, the trees it is enrolled in) and the same sensitive-data standing. `attach` refuses another (`vault_crosses_isolation`); a box whose boundary changes after attaching stops being served (`serving_runners`, measured against the FIRST attached runner): its copy of the key is handed out to nobody until it is detached or put back. Only live cloud runners with an owner attach.
- **Who may hold its key:** an active, ECDH-approved device key on a runner the vault serves, while its person is a member: the same machine rule as for agents, checked on every read (`device_may_hold`), never swept.
- **Its key:** the runner's owner makes it on the runner's credentials page (one passkey touch): a copy for them, covered by their own recovery code, and one for each machine waiting, the box. Boxes attached later are granted from the same page.
- **Writing:** the vault is the ONLY place a runner's token or API key is kept: canopy-web holds none and takes none in plaintext. The box seals a token it signs in with its copy of the key and writes it with its own runner token plus a device proof, names on its own list only (`canopy vault runner-seal`). A pasted API key is sealed in the browser. Each write moves the bundle's stamp (`runners.store_vault_values`). Removing an entry deletes its secret unless another runner the vault serves still lists it.
- **A credential set** keeps one such vault per workspace tree its runners are in, so a list shared across trees never shares a vault across them (`runner-fleets.md` § Credential sets).
- **Reading:** the runner credential resolve takes the box's OWN runner token (`runner_only` for a person's token or session) with a device proof of a key on that runner (`device_proof_required`). It answers ciphertext in the agent resolve's layer shape, only the names the runner's list uses, and logs each as a `RunnerCredentialRead`. Routes: `api-runner-credentials.md`.
