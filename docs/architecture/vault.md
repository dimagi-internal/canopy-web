# Vaults: who may open an agent's secrets

Design: `docs/superpowers/specs/2026-10-22-vault-access-follows-canopy-access-design.md`. Byte formats: `docs/vault/zk-v1/zk_v1_reference.py`.

## A vault and its members

A **vault** (`agents.Vault`) is a named set of secrets with its own membership. Every agent has one (`kind=agent`), made when the agent is created (`apps/agents/apps.py`) and moved with it (`move._vault`). Its secrets and key copies are still stored on the agent (`AgentCredential`, `AgentVaultWrap`).

Who may open a vault is `credentials.vault_members.members(vault)`, the union of:

- **direct members** (`VaultMember`): people added by name. A direct member counts only while they are in the vault's workspace (directly or inherited), until a manager removes them;
- **links** (`VaultLink`), re-read on every question:
  - `agent`: everyone with full access to the agent (`access.roster`), plus everyone with an active license to use it directly (`AgentLicense`). The agent's owner comes in as `owner`, its admins as `admin`, everyone else as the link's role;
  - `workspace_owners` / `workspace_admins`: the owners (or admins) of a workspace, inherited down the tree as those roles are.

Members are **people only**: an agent's own canopy login (`Agent.user`) is never a member by any source, and cannot be added (`vault_members.not_a_person`). They hold no vault key — except an agent login's test key, which opens no vault (below) — and an agent that could change its own vault's membership could hand its key to anyone.

A vault's roles are the agent's, without contacts: `owner`, `admin` and `member`. A person's role is the highest any source gives them. Owners and admins see and edit values and change membership (`vault_members.is_admin`); members open the values. Owner is never stored: it comes only from owning the linked agent, or, for a workspace vault, the workspace. A direct member or a link gives `admin` or `member` (`manage` and `use`, the earlier words, are still accepted). Every member carries their sources, so the vault's page says why each person is in it. A new agent vault starts with one `agent` link, so giving someone the agent gives them its vault.

A change that would leave the vault with no owner or admin is refused (409 `vault_needs_an_admin`). Membership writes lock the vault's row, so two at once cannot together remove the last owner or admin. Setting or deleting an agent's values (`PUT|DELETE …/credentials`) is a vault write like rotating its key: the caller must be an admin of the agent AND an owner or admin of its vault, and may not delete a credential a person delegated. A `zks1` value is checked on write: sealed at the vault's current kv, to recipients that may read the vault now (422 `zk_kv_mismatch` / `zk_unknown_recipient`). Membership routes: `GET|POST /api/agents/{slug}/vault/members`, `DELETE …/members/{user_id}`, `PUT …/vault/agent-link`; writes are gated `vault-admin`.

## OAuth connections are sealed to their owner

The vault holds secrets a person pastes. A token canopy gets from **its own OAuth flow** (the connection to a third-party service: Salesforce, Google) is made differently but kept the same way: canopy-web finishes the sign-in, seals the refresh token to the owner's vault key at once and keeps nothing it can open. Machines the owner allows refresh it. This section covers Settings → Connections only; other things canopy-web holds (Slack tokens and so on) are unchanged, and the older Google mailbox and delegated-credential paths stay separate for now.

**The guarantee, and its limits.**

- A connection made before canopy-web is compromised is safe. canopy-web stores no readable refresh or access token, never refreshes and never revokes a stored token; an attacker who takes the server gets ciphertext.
- A connection made while canopy-web is compromised is exposed: canopy-web does the code exchange, so it sees that one refresh token in passing, and could substitute the owner key the token is sealed to.
- Browser code is served by canopy-web, so an owner who opens the share screen or Settings while it is compromised can be handed hostile JavaScript. This is the limit of every canopy zero-knowledge vault.
- A box with no pin for a connection (its first read) can be handed a self-consistent forged set. That gives it a substitute token, never the real one, and the box pins the forger's owner key, so the real set is refused there until the pin entry is removed or the box replaced.
- A device carrying an old endorsement by the owner or a listed endorser, for an agent still in the statement, can be re-listed by a hacked server. Removing it from the statement or revoking its device key does not retire it; the way to retire one that may be compromised is to disconnect and connect again.
- A hacked server can force a revoke (mark a connection `revoking`). That is an outage, not theft.
- A person the statement names in `endorsers` who replaces their vault key leaves the machines only they vouched for unprovable (their endorsement no longer verifies): those machines stop until the owner shares again, or reconnects if such a machine wrote the envelope. The owner's own replaced key does not do this: the row keeps their key and their signatures (`owner_public_jwk`, `owner_endorsements`), which readers verify against the sealed `owner_key`. Until the row is disconnected, new tokens stay readable by that old key, and Settings says so (`owner_key_replaced`).
- The app's client secret stays server-held (`ConnectionApp.client_secret_enc`, Fernet, pasted in Settings, never returned: only `has_secret`). Alone it is worth little: it needs a refresh token, and token endpoints come from the provider's fixed rules, so a lying server cannot send a refresh token to itself. It leaves canopy-web only in a material response to an authenticated machine.

`apps/connections/services.py` (connect and disconnect), `sharing.py` (the owner's share), `recipients.py` (who may open), `tokens.py` (material, lease, write-back), `keeper.py` (re-seal and revoke) and `wire.py` (checks on the wire format) are the code; their docstrings are the contract. The normative format is `docs/vault/zk-v1/connections_v1_reference.py` with vectors in `connections_v1_vectors.json` (the CLI and the frontend test against the same files).

Rules:

- **App.** A provider's OAuth client is a `ConnectionApp`, one per (workspace, provider), set up by a workspace admin in Settings → Connections (client id, client secret, provider options, extra scopes). Every `Connection` belongs to one app, so a person's connection through workspace A's app is a different row from the same account through B's. A person can use a connection only while a member (read) of its app's workspace; an agent connects with its own workspace's app, and its connection (with every grant of it) works only while the agent is still in that workspace. `client_id` and the provider's `locked_options` (Salesforce: `login_url`) cannot change while connections exist (409 `app_locked`). Removing an app (`DELETE …/connection-apps/{provider}`) sets `removed_at`, hides it and marks each of its connections `revoking`; the sweep deletes the app once they are gone. A workspace cannot be deleted while it has apps. A callback is bound to the workspace and client its start parked (`bad_state` otherwise); a provider's `check_owner` can refuse an account after sign-in (`wrong_account`): Google's `allowed_domains` option, and an agent's own Google account.
- **Owner.** A `Connection` belongs to exactly one person or one agent; there is no fallback between owners. An agent's turn uses the agent's own connection or one lent to it, never the person who started the turn. A row's `owner_key` (the thumbprint of the owner's member vault key, sealed inside the envelope) never changes. The key and its holder's user id are kept on the row at connect (`owner_public_jwk`, `owner_user_id`) and served from there, so a signer who replaced their key or was deleted leaves a connection machines can still read and revoke; a reader trusts that key only because its thumbprint is the sealed `owner_key`. Connecting the same account again with a different vault key (a person who replaced their key, an agent whose connecting admin left) is refused as 409 `owner_changed`, the new grant discarded and the row untouched: disconnect first, a holder revokes, then connect, which makes a new row and so a new pin on every box. Only the connector, the person or the admin who connected an agent's connection, can change who uses it; any other admin of the agent can see and disconnect it.
- **Scopes.** A connection stores what the provider GRANTED. A provider may declare `required_scopes` (Salesforce: `api`, `refresh_token`; `scope_implies`: `full` gives `api`); a grant without one is refused at connect (`insufficient_scope`).
- **Connect and seal.** Connecting needs the owner's vault key (the person's, or the connecting admin's for an agent): without one, start refuses with 409 `no_vault_key` and points at vault setup. At the callback canopy-web exchanges the code with the app's secret, looks up the identity, applies every policy check, then seals the `refresh` plaintext to the owner's member key only, drops the access token and records `connected`. The row is `unshared` and the callback lands on the share screen, `/w/<workspace>/connections/<id>/share`. A Salesforce grant refused after the exchange is revoked at the provider before it is dropped; a Google grant refused after the exchange is discarded without revoking, because revoking at Google ends every token of that account on that OAuth client. A Salesforce login host must be `login.salesforce.com`, `test.salesforce.com` or `<label>.my.salesforce.com`, the `instance_url` host must end in `.my.salesforce.com`, both https; the check runs when the app's `login_url` is set and again at connect, and every machine applies it to what it opens. Refresh and revoke endpoints are derived from these and never taken from canopy-web or from the envelope as given. Connecting the same account again for the same owner through the same app replaces that row's envelope, sets it `unshared` and keeps its grants.
- **Sharing and the signed statement.** On the share screen the owner's browser opens the envelope, shows "Connected as …", and signs a **grant statement**, which can take two passkey touches: one to unlock the vault key, and one for the route's step-up when no recent touch covers it (`PUT /api/connections/{id}/share`): `{account_id, agents, connection, endorsers, my_computers, v, version}`, ECDSA P-256 by the owner's member key, re-signed on every lend, withdrawal or change of "Use on my computers". `agents` are the agents it is lent to (for an agent's connection it must list the agent itself); `my_computers` are the owner's own enrolled machines (a person's connection only); `endorsers` are person keys, besides the owner, whose endorsement of a machine counts. `version` only goes forward. canopy-web checks what it can: the signer holds `owner_key`, the signature, the version, that every agent added is one the signer administers in the app's workspace, that the computers are the signer's own, and that the new envelope is sealed to nobody the statement and `recipients` do not allow. It never signs and never opens the envelope. A chosen machine vouched for only by someone this browser has not trusted is offered there as "Trust <name>'s vouching", with their key's fingerprint; accepting pins them as elsewhere (`vault/trust.ts`) and names them in `endorsers`. An owner who closes the tab leaves the connection `unshared`: sealed to the owner only, listed "not shared yet", handed to no machine, and finishable from Settings.
- **Envelope authentication.** Every envelope a machine or the owner's browser writes carries, per recipient, a MAC keyed by ECDH between the writer's key and that recipient's key, bound to the digest it replaces (`expect`). A reader accepts an envelope only if its writer is a device the statement allows or the owner's member key; anyone can build a `zks1` from public keys, so an unauthenticated envelope is refused by every machine. The one exception is the owner's own browser accepting canopy-web's first seal (which carries no MAC) while the connection is `unshared`. Both envelopes (`refresh` and `access`) carry `owner_key` and `statement_floor`: a reader refuses a statement whose `version` is below the floor in either envelope, so an old validly signed statement cannot re-admit a device the owner removed. A machine that has validated a read pins `(owner key, version)` for that connection and refuses a rollback or a changed owner.
- **Recipients.** `apps/connections/recipients.py` is the one rule behind every seal, re-seal and write-back, and a machine never trusts canopy-web's list over the signed statement: the list can only narrow it. Who may open: the owner's member key; a device whose ECDH key is in the statement's `my_computers`; a device carrying a valid endorsement of its exact ECDH key for an agent the statement lists, signed by the owner or a listed endorser. Whom to list as `endorsers` is the owner's choice (`vault/trust.ts`), and there is no first-sight pinning for connections: an endorsement counts only when the owner or a listed endorser signed it. A grant counts only while it is in force today: the agent is still in the app's workspace and, for a person's connection, the person still administers it. An agent-owned connection's grants do not lapse on its signer's admin standing as such, but its machines can: an endorsement counts only while its endorser is in the agent's vault (`zk_endorse.endorsements`), so when the connecting admin leaves it, machines only they vouched for stop being recipients and the connection reaches nothing for that agent, until someone connects it again (`unreachable` says so). A lent agent no machine can receive it for is listed in `ConnectionOut.unreachable` with why, and Settings says so. Recipients that stop qualifying are pruned from the envelopes without decrypting, except one cloud box kept so that a revoke can still happen.
- **Getting a token (lease and write-back).** A machine reads the material (`GET …/connections/{provider}` for a turn, `GET /api/me/connections/{provider}/material` for a person's own computer): both envelopes, the statement, the owner's key, endorsements, recipients and the app's client id and secret, never a token. It opens the envelopes itself. A live access token is used as it is. Otherwise it reads twice around the lease: material, then the one **refresh lease** (a single holder, 60 s, renewable, answered with `ttl_seconds` so a skewed box clock cannot matter), then material again with full validation; if a newer access token landed meanwhile it releases the lease and uses that, else it refreshes from the second read, so it can never refresh with a token already rotated away. It then writes back (`PUT …/sealed`) a new `access` envelope and, when the refresh token rotated, a new `refresh` envelope, against the digest it read; only then is the token staged. A rotated token gets a time budget, not a retry count: for up to 90 s the box retries the write-back with backoff, renewing the lease. If the box dies, the lease expires, the next refresher gets `invalid_grant` and the connection is marked `needs_reconnect` (recorded `lease_expired_unwritten`). A refresh the provider refuses ends the lease at once, so nobody waits on it and nobody is accused of dying. A machine waiting on another's refresh waits up to 30 s, then takes an access token that is still alive; with none alive, a cloud box exits 4 and the runner asks again on the heartbeat. A laptop that refreshes seals the write-back to the envelope's current holders narrowed by what the statement allows, never to machines still waiting; a laptop never adds recipients and never revokes. A write-back onto a `revoking` row is 409 `revoking` and stores nothing. The client id sealed in the envelope must equal the app's, or the refresher refuses.
- **Re-sealing for new machines.** The cloud box's keeper (`canopy vault zk keep`, every 120 s) also asks for connection work (`GET …/vault-keeper/connections`) and re-seals the same plaintext to machines the statement allows that are still waiting for a copy (`PUT …/vault-keeper/connections/{id}`, `expect` = the stored digest), so lending a connection to a new agent needs no action from the owner when any holder is online. With no holder the grant shows as waiting, and the owner can give waiting machines a copy from the share screen with one touch.
- **Revoking.** Disconnecting marks the row `revoking`: gone from every list at once and never handed out again. The first cloud box that holds it opens it, revokes at the provider (Google: only when no other connection of that account through that app remains) and confirms (`POST …/connections/{id}/revoked`), and the row is deleted. A dead token counts as revoked. A provider outage confirms nothing: the box tries again on a later pass. A connection no cloud box heard from in the last 15 minutes holds (`recipients.REVOKER_GONE_AFTER`, far longer than a runner's own online window, so a reboot or an outage of canopy-web loses no revoke), or whose envelope no holder could accept, is deleted at once, or by the next sweep if it was already `revoking`; one still unconfirmed after 7 days is deleted by the sweep; all are recorded `revoke_unconfirmed`, and the provider's own idle expiry finishes the job. The disconnect route says which happened (`outcome`), so nobody is told a machine will revoke what none will. Only cloud boxes keep or revoke.
- **On a box.** The cloud runner asks which providers a turn's agent has (`GET …/turns/{tid}/connections`) and, for each, runs `canopy cred connection-token <provider> --runner` (the CLI must be at least `CONNECTIONS_ZK_MIN_CLI`; an older one is logged as one `stage_failed`) to write `~/.canopy/connections/<slug>/<provider>.json` (0600, a sensitive path), re-staged on the lease heartbeat near expiry and removed when the turn ends. A stage may run 300 s. CLI exit 3 means nothing to stage (not connected, or being revoked): canopy-web listed the provider and this box got nothing, so it logs one `connections.not_for_this_box`; exit 4 means waiting, no copy has reached this box yet: the turn keeps its hold and the heartbeat tries again. A person's own CLI needs the laptop **enrolled** (`canopy vault device --enroll`) and **Use on my computers** turned on for that connection; a PAT-only laptop can no longer get a token. Neither the material nor the lease routes are MCP tools (`apps/mcp/api_tools.EXCLUDED`).

Routes: [`api-surface.md`](api-surface.md) § Connections. Configuration: none in the deployment beyond the minimum CLI version for cloud boxes ([`deploy.md`](deploy.md)); each workspace admin sets a provider up in Settings → Connections, registering the callback shown there. Adding a provider (Sage Intacct next) is one module in `apps/connections/providers/` for the connect half (`salesforce.py`, `google.py` are the examples; the recipe is that package's docstring) plus a module in the canopy CLI for refresh and revoke.

### Connection audit

Every record goes through one function, `apps/connections/services.record`, in one vocabulary. An audited verb about an **agent's** connection is an Event (`source=connections`) in the owning agent's workspace; about a **person's** connection it is a log line on `apps.connections.services`. Operational verbs are log lines for every owner. Never a token, code, state, verifier or client secret (`tests/test_connections_audit.py` scans every log record and Event of a full run for each one).

| kind | level | audited | when; keys beyond the common ones |
|---|---|---|---|
| `connections.connected` | info | yes | a sign-in completed and the token was sealed to the owner (new account or reconnect); the connection is `unshared` |
| `connections.disconnected` | info | yes | the row was marked `revoking` (deleted at once when no cloud box holds it); `by` is who disconnected it, or the admin who removed its app |
| `connections.app_configured` | info | yes | a workspace's app was created or changed (a workspace Event, no connection or owner); `workspace`, `client_id` — never the secret |
| `connections.app_removed` | info | yes | a workspace's app was removed (same shape) |
| `connections.shared` | info | yes | the owner's signed grant statement and the envelope sealed to it were stored (`sharing.share`); `version` |
| `connections.refreshed` | info | yes | a machine refreshed it and wrote back; `machine`, `rotated` (yes/no; one a day per kind) |
| `connections.resealed` | info | yes | a keeper re-sealed it to machines that were waiting; `machine`, `added` |
| `connections.revoked` | info | yes | a cloud box revoked it at the provider and confirmed; `machine`, `at_provider` |
| `connections.revoke_unconfirmed` | info, warn from the sweep | yes | the row was deleted with no confirmation: no machine held it, or none confirmed within 7 days; `reason` |
| `connections.lease_expired_unwritten` | warn | yes | a refresh lease expired before its holder wrote back, so the rotated token may be lost; `machine`, `taken_by` |
| `connections.granted` | info | yes | the statement lends it to an agent it did not before; `grantee` |
| `connections.grant_revoked` | info | yes | sharing stopped (a statement no longer lists the agent); `grantee`; `during=disconnected` when the shared connection was disconnected (or its app removed) and the grant went with it. In the owner's workspace, and also in the grantee's when that is another |
| `connections.token_issued` | info | yes | a machine read the sealed material (canopy-web hands out no token); `to` (`cli` \| `turn`), `machine` (the box or computer), and for a turn `agent`, `turn`, `runner` (one turn's re-reads coalesce into one Event) |
| `connections.reconnect_required` | warn | yes | a machine reported the provider answered `invalid_grant`; `machine`, `error`, `detail` (the provider's own words, scrubbed by the machine: Salesforce's `ip restricted` is `invalid_grant` too) |
| `connections.provider_error` | warn | no (log) | the provider refused or could not be reached; `during` (`authorize`: its `?error=` at the callback, never for `access_denied` · `connect`: the exchange or identity failed, or `no_refresh_token`, or `insufficient_scope` with `missing`, or `wrong_account` · `refresh`), `error` (the provider's code, `provider_unavailable`, or one of canopy's; an `?error=` that is not code-shaped is `unrecognised`). Before a row exists `connection` is empty and `owner` is the would-be owner |
| `connections.revoke_failed` | warn | no (log) | a holder's revoke at the provider failed (the row is deleted anyway); `machine`, `error` |

Common keys: `connection` (row id), `provider`, `owner` (`agent:<slug>` or `user:<id>`), `account_label`, `by` (the acting person's email, empty for a runner). A log line is `connections.<kind> key=value key=value …`, in that key order. A value that is empty, not printable (a newline, a control character) or contains whitespace, `=` or `"` is written as a JSON string with every non-printable character escaped as `\uXXXX` (so U+2028, U+2029 and U+0085 never split a line) and printable non-ASCII kept readable: `by=""`, `missing="api chatter_api"`. A line is always one line; `services.parse_log_line` recovers the exact values (tested with newlines, tabs, line and paragraph separators, quotes, `=` and non-ASCII). Example:

```
connections.token_issued connection=5f0c9f1e-6c1b-4f7a-9d55-2a4f7e3b8c10 provider=salesforce owner=user:7 account_label=jj@dimagi.com by=jj@dimagi.com to=cli machine=jj-laptop
```

The cloud runner logs the same vocabulary for what happens on the box: `warn: connections.stage_failed agent=<slug> provider=<p> turn=<id> reason="<why>"` when a token could not be staged (the turn still runs; `provider=*` when listing the turn's providers failed, including canopy-web being unreachable). An agent with no connection is silent, and so is a canopy-web without the listing route (404). `connections.waiting agent= provider= turn=` says once that this box has no token yet and will ask again: no copy has reached it, or it ran out of time waiting on another machine's refresh with nothing still alive; and `connections.not_for_this_box agent= provider= turn=` once that a provider the turn lists was not for this box.

## Everyone has a vault key

A person can be given a vault's key only once they have a vault key of their own, so everyone sets one up at sign-in: after Google sign-in, a person at a browser with no vault key sees one screen (`VaultSetupGate`, from `GET /api/vault/setup`) that registers a passkey and makes the key with it, or with a passphrase where the passkey cannot hold one. A failed check or a browser that cannot make a passkey lets them continue for that tab, and they are asked again next time.

## An agent login's test vault key

For testing, an agent's own login may hold a personal vault key, so a headless harness signed in as the agent can take part in its own sensitive conversations (`apps/agents/credentials/login_test_key.py`). It opens nothing in any vault.

- **The switch:** `Agent.test_vault_key`, off by default. `GET|PUT /api/agents/{slug}/test-vault-key` `{enabled}`, agent admin. Turning it on needs a browser and a fresh passkey step-up (a token is refused); turning it off needs neither. Audited as a setting.
- **The key:** while on, the login makes ONE key with `PUT /api/vault/keyset`, as itself (its token will do; no step-up, since it holds no passkey): passphrase seals only (`2skd`, optionally `recovery`; a `prf` seal is 422 `test_key_passphrase_only`), never replaced (409 `test_key_exists`). With the switch off it is 403 `not_a_person`, as for a system account always. `VaultKeysetOut.test_key` marks it.
- **What it receives:** only copies of the keys of sensitive conversations the login is itself in — their creator or a participant (`conversation_keys.add_wrap`; adding a participant writes them in before their copy). A conversation key is wrapped to it only while the switch is on (`conversation_keys._keyset`). The chat's people list and the recipient read mark it `test_key` ("agent test key").
- **What it never receives:** a copy of any vault's key or a value sealed to it — agent, workspace, shared or runner vault, by a person or a keeper (`vault_engine.parse_wraps` / `parse_values`, 403 `not_a_person`, whatever eligibility says) — or an endorsement (`zk_endorse.add`). A login that is not a person never registers a passkey or steps up (`passkeys.stepup.require_a_person`), so it approves no device key or invitation and reaches no step-up route.
- **Off deletes it:** turning the switch off deletes the key and every conversation-key copy wrapped to it (`login_test_key.disable`).

## Whose account an entry is

Every entry, in an agent's vault (`AgentCredential`) or a workspace vault (`VaultSecret`), says whose account it is (`models.VaultEntryAccount`), read through `credentials/accounts.py`, never the columns:

- **`agent`** — the agent's own (its own login or account). Everything below about the vault's key and its readers is about these.
- **`delegated`** — a standing credential from a PERSON's own account, given to the agent: `delegated_by` the person, `provider`, `identity` (the external login, never a secret), `provider_expires_at` (what the provider said: information only), and the last `checks` with who ran them (`checked_by`: "server" when it was given, else a machine's name). Shown as "GitHub · delegated by Jonathan Jackson" (`accounts.label`).

A delegated entry is sealed (`zks1`, zk-v1 §6) to the machines that run the agent — `accounts.delegated_devices`: an active device key with an approved ECDH key, on a runner that serves the agent, whose owner is one of its admins (`runner_may_hold_agent`), that runs turns, and that is a cloud box or the person's own (`accounts.may_hold_for`: a laptop's device key is in its owner's home directory, so another admin's laptop would let them open it) — and to its person's own vault key, and to nothing else. A recipient that no longer qualifies (a retired box, an owner no longer an admin) is dropped from the envelope without decrypting anything (`accounts.prune`, `manage.py prune_delegated_recipients`); a machine that already opened it keeps what it saw, so its person replaces the token at the provider. It is **never under the vault key**: every generic value write refuses its name (409 `delegated_entry`), enable and rotate leave it out of coverage, a member's read (`GET …/vault/zk`) names it in `delegated` and never carries its ciphertext, and the custodial and zero-knowledge `values` of a resolve leave it out. It leaves canopy-web only in a resolve's `delegated` field, to a `runner` read proved by one of those machines (`accounts.resolve_payload`), while its person is still an admin of the agent (`accounts.serves`). A machine that holds it re-seals it for one that is waiting (`accounts.keeper_work`, `accounts.reseal`); a machine that opens it probes it and reports (`POST /api/harness/runners/{id}/delegated-checks`). Its person sees and withdraws it at `/settings` (`GET|DELETE /api/me/delegated-credentials/`); nobody can read it, they included. Providers: `github` (a pasted token, `delegations.set_github`) and `google` (a runner sign-in, § Connect your own Google account).

## Who may hold a copy of the vault's key (zero-knowledge)

- **A person** (`zk.eligible_members`): a member of the vault who has a vault key of their own.
- **A machine** (`zk.eligible_device_keys`): an active device key with an approved ECDH key, on a runner that serves the agent (`device_keys.runner_serves_agent`), **and** whose person is a member of the vault. The person is the runner's owner, else whoever approved the key (`vault_members.person_of_device`). The machine layer never grants on its own.

`pending` (`zk.pending_targets`), every wrap write and every `zks1` seal read these two functions, so nothing else decides who may hold the key. A keeper's grant is checked again under the vault's lock and refused (409 `zk_not_pending`) for a target that already holds a copy, so two keepers make one grant. Replacing a person's vault key, or a machine's ECDH key, drops their copies in agent and workspace vaults alike.

## Removal: membership is checked on every access, never swept

Nothing deletes a copy of the vault key when someone stops being a member. Every place a copy, a value or an endorsement is used asks whether its person is a member **now**, so a leftover copy is ciphertext canopy-web never hands out:

- a machine's resolve refuses one whose person is not a member (403 `not_a_vault_member`), for the agent's own vault and each workspace layer (`workspace_vaults.layers_payload`);
- the browser's `GET …/vault/zk?values=true` gives the ciphertext only to a vault member (403 `not_a_vault_member`), so an agent admin outside an unlinked vault cannot pair it with an old copy;
- the agent vault's zero-knowledge writes (enable, values, wraps, rotate, endorsements) need an owner or admin of the vault as well as of the agent (`api_credentials._zk_admin`, as the workspace vault's `_vault(manage=True)`), so an agent admin outside an unlinked vault cannot rotate its key to a machine of their own;
- a box is a keeper of a vault only while it may hold that key now (`vault_keeper._held`, `workspace_vaults.device_may_hold`);
- `zk_notify.holders` and the endorsements a keeper checks (`zk_endorse.endorsements`) count current members only.

"Holds a copy" is never itself a permission. A person who comes back opens the vault again with the copy they had. Copies are deleted only by the action that makes them useless: replacing a person's vault key or a machine's ECDH key (`zk.forget_member_wraps` / `forget_device_wraps`) or changing the vault key. A revoked device key is refused at every read. A copy made for someone who has since left still shows as not current (`rotation_recommended`), because it still opens the key it was made for.

The vault key is **not** changed on removal: the server simply stops serving the vault. "Change the key" (rotate), together with rotating the outside secrets, is the response when someone may have kept a copy — on an agent's vault page and a workspace vault's alike.

## Connect Google mailbox: the token is made on a runner

An agent's Google token (`gog-token`) is minted on one of its runners, so canopy-web never holds it (`apps/agents/credentials/google_mint.py`, `AgentGoogleMint`). `POST /api/agents/{slug}/google/mint` (owner or admin) hands the sign-in to an online runner that runs the agent, may hold it (`runner_may_hold_agent`), has a key that reads its vault (`zk.eligible_device_keys`, one holding a copy of the vault key first) and declares `capabilities.google_mint`. With none online it is 409 `no_mint_runner` and nothing starts: there is no server fallback. The runner, on its `mint/claim` poll, makes a PKCE verifier, keeps it, and posts only the challenge (`POST /api/harness/runners/{id}/google-mint/{mint}/challenge`). canopy-web builds the consent link around it (its Web client id, `scopes_for`, the one callback, signed state naming the mint); the browser polls `GET …/google/mint/{mint}` for the link and navigates to it. Google returns the code to canopy-web's callback, which holds it until the runner takes it (once) — and without the verifier canopy-web cannot redeem it. The box runs `canopy vault google-mint`: it reads the OAuth client's secret from the agent's vault (the workspace's shared `gog-oauth-client-web`, the item boxes already refresh these tokens with), exchanges code + verifier at Google, refuses no refresh token / no account / the wrong account, builds the gog token and encrypts it — `zk1` under the vault key when the box holds a copy, else `zks1` to the readers canopy-web listed (at kv 0 that list is canopy-web's word, as for any seal before the vault has a key). `POST …/google-mint/{mint}/result` takes only that ciphertext, at the current kv, sealed to no one who may not read the agent; the account it names must be `expected_account`. A restart of the box loses the verifier and the sign-in reports `interrupted`; an unfinished sign-in expires after `STATE_MAX_AGE`.

## Connect your own Google account: a delegated credential

A person can lend an agent their OWN Google account (a personal Gmail, for an agent that helps them with it) through the same runner sign-in (`google_mint.start_delegated`, `POST /api/agents/{slug}/google/delegate {account, services}`, the page `/w/<ws>/agents/<slug>/connect/google`). They name the account up front and the consent must come from it; only the services they choose are asked for (`google_oauth.delegated_scopes`, Gmail by default). It is a **delegated** entry (§ Whose account an entry is): `google-delegated-<account>`, `provider="google"`, `identity={email}`, `scopes` as requested, `delegated_by` them. The runner chosen must have a machine that may hold a credential of theirs (`accounts.delegated_devices`: a cloud box that runs the agent, or a runner of their own) as well as read the OAuth client from the vault; its work says `delegated`, `name` and lists only `accounts.recipients` (those machines and the person's own vault key), and the box seals to exactly those — never under the vault key, even when it holds a copy — and posts `name` back. canopy-web stores it only as `zks1` sealed to those readers, under that name, from that account, while the person is still an admin of the agent. **Only the agent's admins may start one**: a delegated entry is in force only while its person is (`accounts.serves`), so a workspace member who is not an admin of the agent is refused (403 `not_an_admin`) rather than given a credential that would never be used. It is listed and withdrawn at `/settings` like a GitHub token.

**Using it in a turn.** The runner opens it from its resolve's `delegated` field with its own key, holds it in memory, and stages only a short-lived ACCESS token for each delegated Google account a turn of the agent may use: `canopy cred google-token --runner --agent <slug> --delegated <account>` (the runner's own token and device proof; it refreshes at Google with the `gog-oauth-client-web` client from the vault) writes `~/.canopy/delegated/<slug>/google/<account>.json` (0600: `access_token`, `expires_at`, `account`, `scope`), before the turn and again on the lease heartbeat while it runs; the turn's env lists the accounts in `CANOPY_DELEGATED_GOOGLE`. The turn reads it with `canopy cred google-token --delegated <account>` (prints the path) and calls Google with `gog … --access-token "$(jq -r .access_token "$(canopy cred google-token --delegated <account>)")"`. The refresh token never reaches a file a turn reads; a withdrawn credential's file is removed at the next stage. A laptop of anyone but the person never holds it, so a turn that needs it must run on a cloud runner that runs the agent.

## Granting without a person

Approving a machine signs its ECDH key with the approver's own vault key (an endorsement, `approveAndGrant`), even when the approver holds no copy of the agent's vault key, so a **keeper** (a canopy runner that holds it, `canopy vault zk keep`) can pass the key on. `zk_notify` emails the vault's owners and admins who hold the key (a member's copy opens the vault but grants nothing) only after `GRACE` (15 minutes), for what no machine could pass on, for agent vaults and workspace vaults alike (`ZkGrantNotice` names one or the other). A notice is always about a **person**, in one of three cases the subject says: joining for the first time, a new vault key (sent at once — no keeper grants a changed key — asking the admin to check with them directly), or not yet reached by a rotated key. A machine is named as its person's ("ed's machine DIM-SI-W021") and is not mentioned at all while its person is waiting too; nobody is ever asked to recognise a machine. Each vault's members list says who is waiting (`has_copy`) and who can pass the key on (`holders`: the owners and admins holding a copy, and the keeper runners), and the page says it in words (`VaultWaitingNote`), to the waiting person too.


**The keepers' record.** Which key each keeper trusted for each person is kept once, in the vault itself: `Vault.keeper_pins_zk`, a `zk1` value under the vault key (name `~keeper-pins`, at `keeper_pins_kv`). canopy-web stores it and can neither read nor forge it. A keeper reads it with its work (`pins`) and writes it back over the version it read (`PUT …/vault-keeper/{slug}/pins` or `…/vaults/{id}/pins`; 409 `keeper_pins_stale`). So every keeper, including a brand-new cloud box, refuses a person whose key changed, and leaves them waiting for a person. Granting them is the confirmation: an owner's or admin's browser grant (`grantPending`, or a workspace vault's grant on its page, `grantWorkspaceVaultPending`) also records the key it granted to in the record (`recordGranted`, `PUT …/vault/zk/pins` or `/api/vaults/{id}/zk/pins`), so keepers trust it from then on. Someone who started over with a new key (`UserVaultKeyset.replaced_at`) is emailed to the key holders at once, as a new key to check with them, with no grace period, since no keeper will grant it. A rotation leaves the record unreadable, and keepers start a new one. Every keeper grant to a person is emailed to the vault's owners and admins (`vault_keeper._announce`). Only a machine whose person is an owner or admin of the vault is a keeper (`vault_members.device_works_for_an_admin`): a member's machine reads the vault but never passes its key on.
## Workspace vaults

A workspace may keep any number of vaults (`Vault`, `kind=workspace`), always zero-knowledge, in the agent vault's formats with the vault's **binding id** (`vault:<uuid>`) where an agent's id goes in every AAD and HKDF info (`credentials/workspace_vaults.py`). Its secrets are `VaultSecret`, its key copies `VaultKeyWrap`.

**One set of rules.** Both kinds of vault are written through `credentials/vault_engine.py`: who may be handed a copy, what making or replacing the key must carry (a way back, a copy the writer can open, every value re-encrypted, every holder still eligible re-wrapped), the key-version checks, and the state a client grants and rotates from. `zk.py` and `workspace_vaults.py` only say where their rows live and who is eligible (`engine.Store`), so a rule added to one kind of vault reaches the other.

- **Members:** made with two links: the workspace's owners (`owner`) and `attached`, everyone with full access to an agent the vault serves (`member`). Direct members as for an agent vault.
- **What it serves:** `VaultAttachment` rows, each exactly one target: an agent, every agent in a workspace and below, a project, or a runner (below). Agents, workspaces and projects lie in the vault's own tree only. Attaching an agent needs the caller to administer that agent too (it then reads the vault in its turns and its people join): to anyone else it is 404. A moved agent keeps an attachment only inside that tree (`move._vault_attachments`).
- **A project** (`{project: "<workspace>/<handle>"}`) serves its CURRENT member agents (`AgentProject.member_agents`, which includes agents that joined through a `ProjectShare`), so the agents that join a project to use the skills it carries get the secret those skills need without an attachment per agent. Nothing is stored per agent: joining gives the vault, leaving (or a share ending, which removes the members it admitted) takes it away at the next question, and `vault_members.project_agents` is the one place that decides it. It serves a member only when BOTH the agent and the project's workspace lie in the vault's tree; a member outside it (a sibling workspace's agent that joined through a share, or an agent of an ancestor workspace) is listed as `not_served` on the attachment and gets nothing. Attaching needs the caller to manage the vault AND to be an editor of the project's workspace (the project's lead or a working agent's login is not enough, as for sharing a project); anyone else gets 404, a project outside the vault's tree 422 `vault_bad_attachment`. Moving a project out of the vault's tree drops the attachment (`services.promote_project`); deleting it cascades. The project's page lists its vaults by name and secret names to readers who belong to the vault's workspace.
- **Who may hold its key:** a member with a vault key; a machine whose person is a member and which serves an agent the vault serves (a project's served members included), checked on every read as for an agent vault.
- **Reading:** credential resolve returns `vaults`, the workspace vaults layered under the agent's own values (root workspace first, then vaults attached to a project the agent is a member of, then vaults attached to the agent; a later layer wins, and the agent's own values win over all), each with this device's copy of its key, or `wrap: null` when it may not open it. The client decrypts and merges.
- **Routes:** `GET|POST /api/workspaces/{slug}/vaults` (making one needs `own`), `/api/vaults/{id}` with `members`, `attachments` and `secrets/{name}`, and `/api/vaults/{id}/zk` (`enable`, `values`, `wraps`, `rotate`) in the agent vault's shapes. Rotating one from its page needs the person's own recovery code, as making its key does. The keeper grants them through `…/vault-keeper/vaults/{id}/wraps`. A machine is vouched for there by its approver's endorsement for an attached agent.

## A runner's own vault

A workspace vault can also serve one **cloud runner** (`VaultAttachment.runner`): it holds that box's long-lived Claude tokens and API keys (spec `docs/superpowers/specs/2026-10-23-runner-claude-credentials-in-the-vault-design.md`). A secret's name comes from its credential-list entry: `claude-token:<key>`, `anthropic-api-key:<key>` (`RunnerLogin.vault_secret_name`).

- **Making one:** `POST /api/harness/runners/{id}/vault` (runner admin; browser + step-up) gives the runner its OWN vault, `<runner> Claude credentials`, its owner a direct `manage` member, attached to it (`workspace_vaults.create_for_runner`). Sharing is an explicit attach: `POST /api/vaults/{id}/attachments` `{runner}`, by someone who manages the vault and administers the runner.
- **Isolation boundary** (`workspace_vaults.isolation_boundary`): every runner a vault serves has the same owner, serving the same thing (the agent of a runner that runs one agent, the root of a runner that serves a tree, or — neither declared — the trees it is enrolled in) and the same sensitive-data standing. `attach` refuses another (422 `vault_crosses_isolation`); a box whose boundary changes after attaching stops being served (`serving_runners`, measured against the FIRST attached runner): its copy of the key is handed out to nobody until it is detached or put back. Only live cloud runners with an owner attach.
- **Who may hold its key:** an active, ECDH-approved device key on a runner the vault serves, while its person is a member — the same machine rule as for agents, checked on every read (`device_may_hold`), never swept.
- **Its key:** the runner's owner makes it on the runner's credentials page (`makeWorkspaceVaultKey`, one passkey touch): a copy for them, covered by their own recovery code, and one for each machine waiting — the box. "Give … a copy" there grants boxes attached later (`grantWorkspaceVaultPending`).
- **Writing:** the vault is the ONLY place a runner's token or API key is kept — canopy-web holds none and takes none in plaintext. The box seals a token it signs in with its copy of the key (`mint/entry` names the entry, `canopy vault runner-seal` → `PUT /api/harness/runners/{id}/vault/values` — the box's own runner token with a device proof, names on its own list only — then `mint/result {vault_key}`, done only if the vault holds it). A pasted API key is sealed in the browser (`POST …/vault/entries` makes the entry with no value, then `PUT /api/vaults/{id}/zk/values`). Each write moves the bundle's stamp (`runners.store_vault_values`, `vault_values_written`). Removing an entry deletes its secret unless another runner the vault serves still lists it.
- **A credential set** keeps one such vault per workspace tree its runners are in, so a list shared across trees never shares a vault across them (`runner-fleets.md` § Credential sets).
- **Reading:** `GET /api/harness/runners/{id}/credential/resolve` — the box's OWN runner token (403 `runner_only` for a person's token or session) with a device proof of a key on that runner (401 `device_proof_required`). It answers ciphertext in the agent resolve's layer shape, only the names the runner's list uses, and logs each as a `RunnerCredentialRead` plus a `runner.credentials.resolved` event. The box opens it with `canopy vault runner-credentials`.
