# Runners: routing, the claim and turn mode

How a queued `Turn` finds a box: which agents a box runs, which CLI runs a turn, the claim, the off-request clock, an agent's runner list, the workspace default order, project chats and turn mode per rule. Start reading at the module docstrings of `apps/harness/routing.py` (it re-exports `routing_orders`, `routing_serving`, `routing_machine`, `routing_projects`), `apps/harness/claim.py` (`claim_next_turn`, `claim_reach` for the explanations) and `apps/harness/clis.py`.

**See also:** [runners.md](runners.md) (how an agent runs, the tenant gate, opt-in projects, which agents a box may hold), [runner-flags-and-schedules.md](runner-flags-and-schedules.md), [runner-credentials.md](runner-credentials.md), [runner-fleets.md](runner-fleets.md).

The claim and every "why is this waiting" reader (`claim_reach.turn_reach`, `unclaimable_queued_turns`, `blocking_turn`, the topology) ask the same predicates, so they cannot disagree. A new gate goes in the shared predicate, never in one reader.

## Which agents a box runs — one rule

`routing_serving.runner_routes_agent` answers "could this box ever claim a turn of this agent?" from the claim's static gates only: not retired, not directed-only, the agent's workspace in the box's tenant (`runner_tenant_slugs`), its owner may hold the agent (`runner_may_hold_agent`), and an ENABLED `RunnerAssignment` row or the workspace order it follows routes to it. Availability, the cascade and a turn's requirements decide WHICH box takes a turn, never whether a box runs the agent, so a box that failed to set an agent up keeps it on its roster and retries at its next bootstrap.

**A box never claims a turn of an agent it reports it cannot run** (`routing_orders.cannot_serve`): a laptop whose reported `projects` lacks the agent's slug (never-reported means unknown, not empty), any box naming the agent in `capabilities["unprepared"]`, or what it serves on its machine (`routing_machine.serves_refusal`). It is a floor on the composed list in `assignment_rows_for` (`serves=`), applied like `requires`. A pin still lands on such a box (a drill exists to find this out) unless `serves_refusal` refuses it.

Three readers share the rule and `tests/test_runner_serves_agents.py` holds them to `claim_next_turn`: the vault's device proof (`device_keys.runner_serves_agent`, which adds a few named exceptions in its docstring), the box's refresh (`GET /runners/{id}/agents`, read by `bootstrap_agents.sh`; an empty answer is final, only no answer falls back to the registry), and readiness / the fleet view (`agents_routed_to`). Do not widen a reader past the rule (counting disabled rows, skipping enrollment or the hold check, walking the whole registry): a box then asks every 30 minutes for the vault of an agent it never runs, and once that agent is zero-knowledge every refusal emails its owner. A resolve refused because an approved box does not run the agent is `reason: not_routed` (`credential_resolve.py`), recorded as `agent.credentials.refused`, with no email; a missing or unapproved proof is a `device-proof` alert.

## Which CLI runs a turn (`apps/harness/clis.py`)

A turn runs in an agent CLI (`clis.CLIS`). A CLI is not a surface: `Runner.engine` says where a laptop opens a session, and `claude-desktop` and `emdash` run Claude Code only. The module docstring of `clis.py` is the overview; the rules below are the ones that cross modules.

- **One rule picks:** `clis.choose(turn, runner)`. The claim, coverage (`claim_reach._refined_allows`) and `turn_reach` all ask it, above the pin: a pin never puts a turn on a CLI the box lacks or a caller's confined turn on one that cannot confine it (`clis.confines`).
- **A choice is refused when it is made**, never left to wait: `clis.refusal` (conversation, turn, schedule), `clis.list_refusal` (an agent's CLI list, edited by agent admins), `placement._placeable_runner` (transfers), `clis.conversation_refusal` (every send path). An agentless or repo turn runs Claude Code only; a sensitive conversation runs only on `clis.SENSITIVE_CLIS`.
- **Asked and picked are two fields.** `Turn.requested_cli` is what was asked; the claim writes `Turn.cli`; every requeue clears `Turn.cli` and keeps `requested_cli`. `Agent.cli_models` sets the model each CLI starts on; the claim sends it as `cli_model`.
- **A conversation is held to a CLI once its history is in one** (`clis.pin_conversation`, first write wins; called from `session_sync` and when a turn finishes `done`, never at the claim). It changes CLI only by a transfer that names one, a fresh start from the handoff (`chat-sessions-recording-and-transfer.md` § A transfer carries the work).
- **Sign-in is per CLI.** A box claims nothing only when no CLI is signed in. Coverage asks `choose` without the sign-in; `turn_reach` adds it. `clis.blocker` gives the most specific reason a CLI keeps a turn waiting.
- **A box reports its CLIs on every heartbeat** (`capabilities.clis`, via `clis.sanitize`; a beat without it removes it). A box that reports none is read as Claude Code alone (`clis.reported`).
- **Credentials name their CLI** (`RunnerLogin.cli`); each CLI keeps its own cascade and its own last-fallback refusal.
- **A prompt's plugin command is parsed once** in `apps/harness/invocations.py`; the claimed turn carries it as `invocation` and each executor renders it in its CLI's terms.

## The claim (`claim.claim_next_turn`)

The function is commented step by step; read it. The order matters and each gate is a hard stop:

1. **Pause outranks a pin, the fleet hold and agent/workspace holds outrank a pin, a fleet member not `on` claims nothing, a signed-out box claims nothing** (the `live_status`, `FleetHold`, `Agent.held`, `Workspace.held`, `clis.reported` checks at the top). Do not add a bypass. `services.pause` records `paused_by` and, for a pause with no `unpause_at`, sends the turns only that box could take to the admission rules (`admission.evaluate.recheck_stranded`); `turn_reach` reports a turn whose every taker is paused as `parked`.
2. **No sweeps in the claim.** Expired leases, stale occurrences, late slots and stale drills run on the off-request clock (below).
3. **Candidate filter:** pinned here, or (`runner_target_q` and routing kind); a cloud runner never takes `local_only`. A directed-only box (`Runner.directed_only`) claims just its pins and its bound chats and is dropped from every routed list (`assignment_rows_for`, the workspace order, `InheritedOrder.directed`), so it neither claims nor counts as a better rank. `profile_q` holds a confined (caller) turn to a runner reporting `PROFILES_VERSION` and `ENVELOPE_VERSION`, not bypassable by a pin. The `chat_session__isnull=False` filter in `routing_orders.busy_session_ids` is load-bearing (a NULL in the IN-list excludes every row).
4. **An agent is not a lane:** any number of one agent's turns may execute at once, each on its own worktree; only a CONVERSATION serializes (`busy_session_ids`, the `one_executing_turn_per_session` index; a follow-up may ride into the running turn, `routing.may_ride`).
5. **Per candidate, above the pin:** runner flags satisfy the turn's requirements, `job_refusal`, `runner_may_hold_agent`, `turn_serves_refusal`, `clis.choose`. Then, unless pinned here, the availability cascade over a list with `cannot_serve` boxes removed, the workspace order for repo turns, and `project_session_allows` for an unbound project chat.
6. **The Turn Context is asked again at the claim** (`turn_context.at_claim`; `access-turn-context.md` § Two moments). A refused turn is closed `cancelled`, never claimed, with `refusals.CHANGED_WHILE_QUEUED` in its note. Otherwise the new stamp is written to `Turn.capability` before the payload is built, and a box that cannot confine it passes the turn over.
7. **Turn mode is decided and stamped** (`turn_mode.for_turn`), an admission `auto` rule may raise a standing manual to auto, admission may reject (`access-direct-use-and-admission.md` § Admission rules), then a conditional update to CLAIMED inside its own `transaction.atomic()` (an `IntegrityError` means another box won that conversation). The claim event records why (`_routing_basis`: pin / actor / source / default).

**The box's own gate, before it asks.** A cloud runner skips `POST /claim` (and the WS `claim`) while one of its own limits says no, none of which the server can see: setting up, at its turn cap, below the memory floor, token refused, unknown `RUNNER_DATA_MODE`. `cloud_runner.claim_gate` is the one function both claim loops ask, and every heartbeat reports it as the `claim` health check, so a turn `turn_reach` calls LIVE that nobody claims is read off the runner page (or `get_runner`'s `health_checks.claim`), not journald. The laptop runner has no such limit: its skips reach canopy-web as the pause, a degraded heartbeat and `signed_out`.

## Periodic work: the off-request clock (`apps/common/ticks.py`)

A runner's heartbeat is liveness only and a claim does no global sweep. Everything periodic is a job registered with `ticks.register(name, fn, every_s)` from its own app's `AppConfig.ready` and run by one asyncio loop in every web process (`config/asgi.py`). The module docstring of `ticks.py` has the mechanics (fleet-wide cache key, cache-down fallback, a failing job never stops the rest); `manage.py run_ticks [--list]` runs one pass by hand. The jobs run with no runner online and through a fleet hold, except `harness.queue_sweeps`, which is skipped while `FleetHold` is on so a held slot is not closed as MISSED. The full list is the `ticks.register` calls (`grep -rn "ticks.register" apps`); the queue-related ones are in `apps/harness/sweeps.py`. Tests set `TICK_BASE_S = 0` and call a job's function directly.

## An agent's runner list (`RunnerAssignment`)

`RunnerAssignment` is the routing authority for agent turns. The box's `capabilities.agents` and `Agent.runner_preference` do not route agent turns. The ladder and its edge cases are in the docstrings of `routing_orders.assignment_rows_for`, `labelled_assignment_rows`, `load_assignment_rows` and `assignment_allows_for_agent`; the ones to remember:

- **Default order:** rows with `source=""`, `rank` 0 first. **Availability cascade:** the highest-ranked available runner (`is_available`: online and ready) claims; a lower rank claims when every better rank is unavailable or once the turn has been queued `CASCADE_GRACE_SECONDS`, so a heartbeating-but-wedged box cannot stall the queue.
- **`enabled` is a toggle, not removal:** a disabled row is filtered out in `load_assignment_rows`, so it neither claims nor blocks a lower rank. An agent whose own default rows are all disabled has still chosen a list and does NOT fall back to the workspace order (`agents_with_own_order`).
- **Rules** layer on top: actor rule, then source rule, then the default order. A non-strict rule puts its runners first; a `strict` rule truncates ("these runners or nothing": the turn waits, and the grace has nobody below to promote). A rule whose rows are all disabled disappears, its strictness with it. `source` is the `Turn.origin` vocabulary; `actor` is matched against `actors.actor_of(turn)`. `GET /api/agents/{slug}/route-preview` reads `labelled_assignment_rows`. Writes: `apps/agents/api_routing.py` (`replace_agent_runner_rules`, `set_agent_runner_rule`, `set_agent_actor_route`).
- **Above the cascade:** `Turn.pinned_runner` hard-pins one turn (drills, chat "wait"/"continue", directed starts, `runner_id` on `POST /api/harness/turns/`). It bypasses assignments and kind, never the tenant gate, flags, may-hold, `profile_q`, pause or the one-executing-turn constraints.
- **Session stickiness:** a chat bound to a `RunnerBinding` claims only on that runner. If it is gone the turn waits for the person to place it, with no automatic failover, because continuing elsewhere starts a fresh emdash session without the conversation's context. The one exception is a fleet member: members are interchangeable, so the fleet scaler moves the chat (`runner-fleets.md`).
- **Edit rights:** `agent.work` on the agent plus administering every runner the write ADDS (`api_routing._runners_for_routing`); the added runner must also be able to hold the agent. `auto` on any rule is for agent admins (`access.md` § Turn mode).
- The UI is one table, `frontend/src/components/agents/AgentRouting.tsx`, in evaluation order.

## The workspace default order (`WorkspaceRunnerOrder`)

A workspace's ordered runner list (`apps/harness/api_workspace_routing.py`; set needs `runners.route`, and every runner must serve the workspace per `runner_tenant_slugs`).

- **An agent with no default order of its own FOLLOWS it:** the nearest workspace up the tree with an enabled order, live, never copied, and after the agent's own source/actor rules (`routing_orders.inherited_orders`, folded into `defaults` by `load_assignment_rows` so every reader sees it). It drops a laptop that does not report the agent's repo, a directed-only box, and a box that may not hold the agent, and reports each (`InheritedOrder`). Replacing a cloud box is therefore one edit to the workspace order (`runner/ec2/wire.sh`). `GET /api/agents/{slug}/default-order` shows what an agent follows.
- **Repo turns** (a project dispatch: no agent, no session) route by it (`repo_order_for`, `repo_order_allows`): same cascade and grace, ranked only among listed runners that declare the repo and meet the turn's requirements. A workspace with no enabled rows: any serving runner that declares the repo.

### Project chats

A project chat (no agent, only a repo, `Session.project`) is routed while **unbound** by `routing_projects.project_session_allows`: the box offers the repo in the session's workspace (`Runner.offers_project_in`); if the workspace has an enabled order, the order decides (same cascade and grace); with no order, only a box the sender (`enqueued_by`) administers, so a turn with no person behind it needs an order. A bound session claims only on its holder, and a pin bypasses all of it. The claim asks `project_session_allows`; `_refined_allows` (so `turn_reach`, the unclaimable report and the topology) asks `project_session_covers`, the same predicates without the clock. Choosing a box for a project chat needs you to administer it (`canopy_sessions.placement.may_place`).

## Turn mode per rule

`RunnerAssignment.turn_mode` (`""` defers, `manual`, `auto`) rides the routing ladder and is decided at CLAIM, stamped on `Turn.turn_mode` / `turn_mode_basis` so a rule edited mid-turn does not flip work under way. The ladder, caps and requests are in the `apps/harness/turn_mode.py` module docstring and `access.md` § Turn mode. **An `auto` on a rule naming a person applies only to a VERIFIED message** (`turn_mode.resolve`); otherwise the turn runs manual, because a forged `From:` may pick a box but must never drive an unreviewed agent (`tests/test_turn_mode_rules.py`).
