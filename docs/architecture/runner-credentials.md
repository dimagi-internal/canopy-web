# Runners: the credentials a turn gets

What a turn is handed to act with: its GitHub identity (delegation, the per-user GitHub App), the canopy login a turn gets, a cloud runner's Claude credentials and the probe that says "ready", how a runner signs in without a key, the runner software and how the cloud runner drives a CLI.

**See also:** [runners.md](runners.md), [runner-routing.md](runner-routing.md), [runner-flags-and-schedules.md](runner-flags-and-schedules.md), [runner-fleets.md](runner-fleets.md), [vault.md](vault.md), [access.md](access.md) ("Whose authority an agent acts with").

## The GitHub identity a turn gets

**An agent acts on GitHub with a delegated credential, a token its OWNER or one of its ADMINS gave it from their own account, never a box credential.** Boxes hold no GitHub token of their own. The token is a vault entry of the agent's (`github-token`, `account: "delegated"`), sealed only to the machines that run the agent (`apps/agents/credentials/accounts.py`, `delegations.py`; tests `tests/test_agent_delegations.py`).

- **Giving one.** A fine-grained PAT pasted by an owner or admin (GitHub has no API to mint one; `delegations.create_url` pre-fills the form). Its repository selection IS the agent's scope. It is refused unless it can push and open a pull request on the agent's repo (`delegations.check_repo`, which creates nothing), and with 409 `no_machine_can_open` while no machine that runs the agent has an approved device key. canopy-web seals it to those machines and the person's own vault key and keeps nothing it can read.
- **In force** (`accounts.serves`) while its person is one of the agent's admins (`is_admin` fails closed on someone who left the workspace). Never on a date: GitHub's own expiry is shown and GitHub refuses it.
- **Per turn**, `POST /api/harness/runners/{rid}/turns/{tid}/github-token` (`api_runners_credentials.py::turn_github_token`): only for a turn that runner is executing, re-checking `runner_may_hold_agent`; the principal is resolved server-side (`delegations.turn_agent`); **409 with the reason and no shared fallback** when absent or no longer in force; always refused for a confined (caller) turn. It returns the git identity and `delegated: "github-token"` with the `agent` whose vault holds it, no token: the cloud runner opens the value from its OWN resolve of that agent (`cloud_runner._delegated_value`).
- **Checked by the boxes.** canopy-web cannot open the token, so a box probes it (`cloud_runner.probe_github_token`) and reports `POST …/delegated-checks`; a failed probe turns `github.<slug>` red. A box calls `GET …/github-readiness` at boot, so a missing or expired token is a red health check, not a mid-turn 403.
- **A new machine** gets it from one that holds it: the keeper (`canopy vault zk keep`) re-seals it after checking the newcomer's endorsement (`…/vault-keeper`).
- **Cloning a new agent.** The box-wide prepare (`bootstrap_agents.sh`) has no GitHub token, so an agent whose private repo is not on the box is cloned at its FIRST turn with that turn's token (`cloud_runner._ensure_agent_clone`) and prepared with that turn's GitHub env (`_PREPARED_WITH_GITHUB`). A clone the box-wide pass could not make is not reported unprepared (that would stop canopy-web sending the turn that clones it); a failed in-turn clone is.
- **Keeping a clone current.** A confined turn is handed no token, so the runner fetches the clone itself (`cloud_runner._fetch_clone`) with the delegation in THAT git process's environment only (`_clone_refresh_env`: credential-helper env, no file, no URL, no argument), only when this box's own recent resolve still lists `github-token`, never on a sensitive-data box, and the turn's env never receives it; git's error is redacted (`_redact_credentials`). That resolve names NO turn (`_turn_values(outside_turn=True)`): a turn id would cap the owner to the turn's `acts_as` and make the resolve a 403. Held by `runner/ec2/tests/test_clone_refresh_token_exposure.py` and `test_clone_refresh_resolve_names_no_turn.py`.
- **Agentless repo turns and project chats** run as no one on GitHub and are refused the same way, unless the repo has an `agents.RepoIdentity` row (`repo_slug` unique → agent; Django admin; `identity_for_repos` on `GET /api/agents/{slug}/github`), in which case the turn runs as that agent. Which identity a session uses is shown, not inferred: `delegations.session_identity` is the one decision `turn_agent` also takes (`agent`, `repo_default`, `none`). A workspace project (`AgentProject`) has no default agent of its own.
- **canopy-web's MCP sign-in is per turn.** Claude Code skips an MCP server that answered 401 for ~15 minutes in every session sharing `mcp-needs-auth-cache.json`; the cloud runner removes the canopy-web entry before each turn (`_clear_canopy_needs_auth`), so one session without a credential cannot take canopy's tools from the next.

### The canopy login a turn gets (turn-scoped agent token)

A runner turn acts as its agent with a login canopy-web issues for THAT turn (`PersonalToken` for `Agent.user`, `apps/harness/turn_agent_tokens.py`; tests `tests/test_turn_agent_token.py`). A client that cannot get one falls back to the agent's stored `canopy-pat` (`cloud_runner._agent_token_env`).

- `POST /api/harness/runners/{rid}/turns/{tid}/agent-token` (`api_turn_agent_token.py`): only with runner `rid`'s own runner token (a PAT is 403), for a turn it is executing, re-checking `runner_may_hold_agent`; 409 for a direct turn, a confined (caller) turn, or an agent with no active `Agent.user`. The read is logged as an `AgentCredentialRead` (`turn-agent-token`) and an `agent.canopy_token.issued` event.
- Revoked when the turn stops executing on that runner: `finish_turn`, every terminal transition (`harness.turn_close.close_turn`) and `revoke_stale` on every queue-sweep tick.
- **Session-scoped on a laptop.** An emdash turn finishes as soon as its Claude session exists and the person goes on driving it, so there the login follows the SESSION (`TurnAgentToken.session`): held while the session is active and bound to that runner, revoked by `revoke_stale` when it leaves or is archived; `?scope=session` asks for that login only. Never for a cloud or `computer` runner. Every action it takes is tied to `turn`, the turn that opened the session. Rules in the docstrings of `turn_agent_tokens.issue_for_session`.
- Delivery: a cloud runner puts it in the turn env as `CANOPY_WEB_PAT` and in `~/.canopy/agent-token/turn/<tid>.token` for the MCP headers helper; a laptop's canopy CLI asks on demand (`canopy agent session-token`).

### The per-user GitHub App (`apps/github_connect/github_app.py`)

A public GitHub App authorized per user (user-to-server flow). It is canopy-web's OWN server-side GitHub access as a person (skill history, the installation list via `access_token_for(user)`); no route hands it to a runner. Its module docstring is the spec; the invariants:

- **The refresh token rotates**, so a refresh runs under `select_for_update` with a re-read after the lock: two concurrent refreshes spending one refresh token kill the grant (`refresh_failed_at` → "reconnect").
- **No `Administration` permission**: repo creation needs it, a user token cannot be down-scoped, and it would let agents delete repos. The user creates a blank repo; canopy only pushes.
- **Authorizing is not installing**: `/login/oauth/authorize` has no repository picker, so Connect points at `install_url`; an empty installation list means access to nothing.
- `GITHUB_APP_CLIENT_ID` and `GITHUB_APP_SLUG` are public; only `GITHUB_APP_CLIENT_SECRET` is a Secrets Manager entry. Unconfigured is a real state (`is_configured`). Tests: `tests/test_github_connect.py`.

## A cloud runner's Claude credentials (one ordered list)

A cloud runner holds **one ordered list** of Claude credentials (`RunnerLogin`), any number of each kind, in the order a person sets on its credentials page. The box uses the first that works and moves down when one hits its usage cap or stops working. Kinds:

- **Login**: a full `claude auth login --claudeai`, signed in through the browser relay (`RunnerMint`, `slot: box`). It **stays on the box**: its refresh token rotates, so a copy elsewhere would break both. The only kind that carries claude.ai connectors (a setup-token lacks the `user:mcp_servers` scope).
- **Token**: a `claude setup-token` made on the box through the same relay (`slot: token`). The box reads it off a replayed screen (`render_screen`), probes it, seals it into the runner's vault (`canopy vault runner-seal`) and only then reports it, and it counts as done only if the vault holds it.
- **API key**: sealed into the runner's vault in the browser. Billed per use: stepping onto one raises the coalesced `claude_api_key_fallback` alert.

**Values live only in the runner's vault** ([vault.md](vault.md) § A runner's own vault): canopy-web keeps the list (names, kinds, order) and never a token or key. The bundle names each value's secret (`cascade[].vault_secret`); the box opens them with its own device key (`canopy vault runner-credentials`) and re-reads on `VAULT_REREAD_SECONDS`. Nothing takes a plaintext value (no paste route, no token in a sign-in result), so a runner needs a vault with a key before it can hold a token or key; a login needs none. A rename takes `name` only; a `value` is refused. Nothing copies between boxes: `wire.sh` gives a new box its own vault.

On the box, each login has its own config directory (`default` is the CLI's `~/.claude`; every other is `~/.claude-logins/<key>`, with everything but its credentials symlinked to `~/.claude`, so transcripts and plugins stay in one place). Selecting a login sets `CLAUDE_CONFIG_DIR` and clears both auth env vars; concurrent turns keep the directory they started with. The box reports which logins are signed in (`POST …/logins/report`); a default login the list has never held is reported with `adopt_default` and joins the list first.

**A token or key keeps the box alive.** A login renews itself and a renewal can fail; a box with nothing else then stops. So removing the **last** token or API key is refused (422, `runners.LAST_FALLBACK_REFUSAL`). A box with no usable credential waits in `fetch_and_stage_credential`, heartbeating online but not ready, and serves the browser sign-in from there. `claude.credentials` fails only when the list is empty; any mix is a healthy box. Tests: `runner/ec2/tests/test_box_login.py`, `tests/test_runner_logins.py`, `tests/test_runner_mint.py`, `tests/test_runner_credential.py`.

### The credential probe: "ready" means a credential answered

A stored value is not a working one, so the box asks each credential one short question with no tools (`cloud_runner._probe_credential`; its section header is the spec) with that credential's environment built as a copy, never `os.environ` (turns run concurrently). The answer is `ok`, `capped` (+ the reset), `dead`, `no_credit` or `unknown`; `CLAUDE_PROBE=0` makes every probe `unknown`.

- **Probes spend usage**: only when a credential is staged or changes, when a capped one's reset has passed (a dead one every `DEAD_REPROBE_SECONDS`, `no_credit` like dead), and when a turn's own failure is ambiguous. **Never on a plain heartbeat.** A re-probe keeps the entry's old check in the heartbeat until the new answer replaces it, because the `runner_credential` alert reads a missing check as fixed.
- **Health**: one `claude.probe.<label>` check per credential; the runner page colours its dots by it (`RunnerCredentials.tsx` `probeLabel`, pinned to the box's labels by `tests/test_probe_labels_match.py`).
- **Readiness**: `ready=False` only when every staged credential was probed and none is `ok`, `unknown`, or capped with its reset passed. A hung probe is `unknown`, so it never keeps a box from serving.
- **Self-pause**: `ready` alone does not stop claims (it feeds only `Runner.is_available`), so the box pauses itself (`POST …/pause`, note prefixed `SELF_PAUSE_PREFIX`) until the earliest reset when every credential is capped, open-ended when any is dead. It lifts only a pause carrying that prefix, once a probe answers `ok`, and **never pauses over, or lifts, a person's pause**. A beat with no usable reply leaves the pause alone.
- **A turn's failure is read from the stream, not its text** (`cloud_runner._credential_fault`): the structured error, `api_error_status: 401` or a rejected `rate_limit_event` classify it; the text matchers (`_is_usage_cap`, `_is_auth_required`, `_is_out_of_credit`) decide only when the stream named nothing. **No credit** is not a cap, since nothing resets it: the box fails over like a cap, raises `claude_credit_exhausted` at once, and when every credential is spent pauses itself. Tests: `runner/ec2/tests/test_structured_credential_errors.py`.
- **An ACP turn is read from its transcript** (`_transcript_fault`): the adapter can end a turn the API refused with a clean stop, so the runner reads the last `isApiErrorMessage` record written since the turn began. A bare ACP `authentication required` with no transcript fault is probed to tell a cap from a sign-out; the CLI's own sentences (`_AUTH_REQUIRED_MARKERS`) win without a probe. Tests: `runner/ec2/tests/test_out_of_credit_and_acp_faults.py`.

**The alerts reach a person** (`apps/harness/credential_notify.py`): the box posts `claude_auth_required`, `claude_usage_exhausted`, `claude_credit_exhausted` and `claude_api_key_fallback` to `POST /api/events/` with its runner token; each mails and pushes the runner's approvers (owner + runner admins) once per (runner, alert) per UTC day. A signed-out or out-of-credit credential on a box whose health reports a `claude.probe.<slot>` check is the `runner_credential` alert instead (`apps/harness/alerts/runner_credential.py`), resolved when the probe passes, and is not also mailed; a laptop (no probe checks) or an inconclusive probe is still mailed. Tests: `runner/ec2/tests/test_credential_probe.py`, `tests/test_credential_notify.py`, `tests/test_alerts_runner_credential.py`.

## How a runner signs in (keyless)

- A paired box signs in **as itself**: it trades a fresh proof of its APPROVED device key (an EC2 box's instance role; a laptop's Secure Enclave/TPM key) for an hour-long `RunnerAccessToken` at `POST /api/runner-sessions/`, renews it before it runs out, and uses it for REST and its `ws/runner/<id>/` socket. Nothing long-lived lives on the box, and nothing in Settings → Tokens can cut a runner off.
- **One protocol, two channels.** The socket's `heartbeat` and `finish` frames are read and applied by the same functions as the REST routes (`apps/harness/runner_protocol.py`, over `HeartbeatIn` / `TurnFinishIn`). Who may act as a runner is `runner_protocol.acting_runner_q`: its owner; a runner with no owner connects for nobody.
- The token opens the runner protocol only (`apps/harness/runner_auth.py`) and authenticates as `Runner.owner`, so every owner-scoped runner gate is unchanged. Revoking the device key (Settings → Security) stops the box at once: the socket re-checks its credential on every frame (`channels_auth.still_signed_in`).
- **A laptop installed from a download pairs in the browser and holds no PAT** (`apps/harness/api_runner_pairings.py`, `runner/canopy_runner/canopy_runner/browser_pair.py`). The box makes its device key and posts the public key with a DPoP proof; the person signs in, checks the code, picks a workspace where they hold `agent.work` and approves behind a passkey step-up (a token is refused). The approval's one-time secret comes back only as a redirect to `http://127.0.0.1:<port>/paired` on the machine whose browser approved, so an approve link sent to someone else gives the sender nothing. The box then claims with DPoP of the same key plus the secret and gets a `Runner` whose device key is already ACTIVE. A key already ACTIVE on a live runner re-attaches; any other known key, an expired, declined or used pairing, or a wrong secret or proof is one uniform 401 (`PAIRING_TTL`, one live per key).
- A developer laptop (`install-runner.sh`) pairs with its person's PAT (`CANOPY_TOKEN`), which also registers its key. A **cloud box pairs by invitation and holds no PAT**. A box paired by invitation, and every runner with its own Unix user, has **no PAT fallback**: without a token it reports itself unauthenticated; only an older cloud stack that still has `CANOPY_TOKEN` falls back while no approved key can get a token (`cloud_runner._bearer`). No turn inherits the box's credential: an agent turn acts with its own login, and an agentless repo turn reaches canopy only through its asker's read-only caller token (`cloud_runner._agent_env` strips `CANOPY_TOKEN` from both).
- **Pairing a cloud box by invitation** (`apps/harness/api_runner_invitations.py`). `runner/ec2/up.sh`, with the operator's workbench token, creates a `RunnerInvitation` (`{name, workspace, role_arn, ecdh_public_jwk}`; `INVITATION_TTL`) in a workspace where the operator has `agent.work`; one live invitation exists per (role, name), and someone else's live one is never replaced (409). **Only the creator approves it**, behind a passkey step-up (`stepup.require_recent_step_up`); a token gets 403, so neither `up.sh` nor the box can approve its own pairing. The box calls `POST /api/harness/runners/pair-by-role` with an instance-role proof bound to that URL (`aws_iam_proof.verify`): waiting → 202; approved → one transaction creates the `Runner` (owner = creator), its `aws-iam` `RunnerDeviceKey` already ACTIVE, and consumes the invitation. The creator must still have `agent.work` there at that moment. Every other answer (no invitation, expired, used, another name, another ECDH key, a bad or replayed proof) is one uniform 401 that creates nothing.
- **A replaced instance re-attaches.** The role is the box's identity (`jkt` = sha256 of the role ARN), and `up.sh --allow-instance-change` keeps the stack's role, so `pair-by-role` from a role with an ACTIVE key on a non-retired runner of the same name returns 200 with that runner's id and no invitation. A role whose runner was retired needs a new invitation from that runner's owner. A key for the role on another owner's runner (live, revoked or retired) is never erased, and a pending or revoked key on a live runner is never replaced: a revocation is undone by its owner, not by re-inviting. Each is the uniform 401.
- A machine running several runners pairs every runner in one call (see "Setting up the runners on a machine" in [runners.md](runners.md)). **A fleet member** joins with no invitation of its own: `pair-by-role` is `fleets.join` (the fleet's one passkey approval plus AWS's word that the instance is the fleet group's, [runner-fleets.md](runner-fleets.md)); its key is role + instance, so sign-in (`aws_iam_proof.verify_caller` → `known_key`) tells members apart.
- The runner signs its proof itself: `cloud_runner._bearer` (a runner with its own Unix user runs `canopy vault runner-session` with its software key); on a laptop `runner_token.py::RunnerCredential`. Both renew 10 minutes before expiry, retry a 401 once, and fall back to the PAT only while no approved key can get a token.

## The runner software

A runner is an installed package, never a checkout, and updates itself to what is deployed.

- **Laptop installs.** `/get-started` and the topology page offer the installers (`GET /api/harness/runner-releases/downloads`; a signed-in person gets a 302 to a short-lived presigned S3 URL). Each bundle carries its own CPython, Node.js and the ACP adapter; nothing is fetched at install. Build: `.github/workflows/runner-release.yml` and `runner/packaging/` (its README lists the signing secrets and testing paths). The upload needs `UploadRunnerReleasesOnly` on the deploy role (`deploy/aws/deploy_roles.py`, applied by hand).
- **The two installs share one runner**: the downloaded app and `install-runner.sh` use the same `runner.json`, device key and job labels; whichever installed last runs it, and switching never re-pairs. `~/.canopy/hold-updates` holds a box on what it runs, for both updaters.
- **Developer install**: `runner/canopy_runner/scripts/install-runner.sh` builds from a `git archive` of a ref into a tool venv no checkout can change; re-running restarts the daemon, not mid-turn.
- **Auto-update installs the DEPLOYED `expected_code_sha`, never `origin/main`**, and is read-only against the control plane (`canopy-runner update-check` → `current|stale|busy|unknown`, never a heartbeat). It defers while a turn is in flight (`~/.canopy/in-flight`), except a cloud daemon run by its supervisor, which HANDS OFF: the updater installs at once and SIGHUPs the supervisor, which swaps the daemon while every turn keeps running (only `pinned` turns, confined or on a sensitive-data box, still wait; `runner/ec2/README.md` § Turns survive an update). A heartbeat reporting a differing sha gets a `runner.update_available` frame that kicks the updater; the timer is the fallback. The downloaded install's updater (`canopy-runner self-update --if-stale`, `self_update.py`) checks the artifact's sha256 and, on macOS, the code signature's team before swapping. The canopy plugin + CLI is a second version a box runs, fixed by re-bootstrap: a box behind the canopy release gets `refresh_pending` on its heartbeat reply (`apps/harness/canopy_release.py`).
- **Code provenance.** `code_sha` is the last commit touching that runner kind's own source paths, not repo HEAD (both path lists are in `.github/workflows/deploy-labs.yml`). The server holds `RUNNER_CODE_SHA` / `RUNNER_CLOUD_CODE_SHA`; `RunnerOut.expected_code_sha` serves the one matching the row's `kind`, and `/supervisor` alerts only when both sides are non-empty and differ (empty = unknown).
- **Disk no runner owns.** A runner sweeps only its own scratch but its `disk` check measures the whole volume, so the cloud updater (root) also ages `/tmp` out, deletes the regenerable caches of the pre-runners user and records the largest of `/home/*` and `/tmp` for the `disk` check to name (`runner/ec2/update_runner.sh`, `cloud_runner._disk_largest`).

**The cloud runner** (`runner/ec2/cloud_runner.py`) polls claim and drains the queue, executes via `claude -p` or ACP, declares repos via `RUNNER_PROJECTS`, and runs the stream/backfill contract on a short clock. A cloud box learns of an agent only by bootstrapping, so registering one (or changing its repo) requests a refresh on the boxes that will take its turns (`apps/agents/setup.py::request_setup`); until that box posts the agent's bootstrap report, the setup checklist shows its runner step as waiting. A turn for an agent the box has no clone of bootstraps first (`cloud_runner._ensure_agent_clone`, once per `LAZY_BOOTSTRAP_RETRY`) rather than running in a bare scratch dir. `bootstrap_agents.sh` does the box's half and runs `canopy agent prepare --runner` per agent after the credential is staged; it is not `set -e`, so one agent's failure does not stop the rest.

### How the cloud runner drives a CLI (turn executors)

The CLI is *which* agent program runs a turn (`claude-code`, `codex`; `apps/harness/clis.py`); the **executor** is *how* the cloud runner drives it. Each executor is a `TurnExecutor` subclass in `cloud_runner.py`, registered in `_EXECUTORS` by its `RUNNER_EXECUTOR` value (runner.cfn.yaml `RunnerExecutor`, whose default is `acp`; a process with no value runs `cli`, `DEFAULT_EXECUTOR`), and `_executor()` is the only code that turns that setting into behaviour (a branch on the name fails `tests/test_turn_executors.py`). The interface and the contract of each method are on `TurnExecutor` and the comment block above it. Today: `cli` (`ClaudePrintExecutor`) and `acp` (`AcpExecutor`, which runs the turn as `claude -p` when canopy_acp did not import); both drive `claude-code`. A sensitive-data box runs only an executor whose `carries_settings` is true. The classes live in `cloud_runner.py` itself because the box runs that file alone (seeded whole, replaced whole by `update_runner.sh`).

What the claim says about the turn's CLI reaches it: a turn claimed for a CLI the box's executor does not drive is finished `failed` with `cli_mismatch` before anything runs (`_cli_refusal`; no `cli` = Claude Code), and the model its agent names (`cli_model`) is `--model` on `claude -p` (`_turn_model`) and `ANTHROPIC_MODEL` for the ACP adapter (`_model_env`). Shared by both executors as `claude-code`'s, not on the interface: the session store (`_resume_target_exists`, `_ship_transcript_rows`, `_TurnTail`), forks, the credential cascade and its probe, and reading a cap or sign-out from a turn's text. A second CLI brings its own of each.
