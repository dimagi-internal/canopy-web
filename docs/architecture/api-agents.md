# API: agents

Routes for an agent as an instance row: create, move, owner and admins, the access list and roles, read mode, skills, turn mode, runtime, A2A cards, agent runs, agent tasks, the state document and agent threads. Part of the [api surface](api-surface.md) topic; the index there lists every part.

## Agents (`apps/agents`) — first-class AI-agent workspace
An `Agent` is an instance row (its definition is the repo): status reports (syncs), skill catalog, packaged turns. **Tasks and projects are the workspace's** (`docs/architecture/work.md`): a task is named by its key (`DIM-142`) and assigned to a person or an agent; a project is addressed `<workspace>/<handle>`, led by a person and/or a lead agent, and worked on by member agents. The routes under `/api/agents/{slug}/` are that agent's view of them, kept so the fleet names work as it always has (`T12`, `P5`). Person-to-task moves go through one actions route; field changes are a plain PATCH. Roles and access: `docs/architecture/access.md`.
- `GET /api/agents/` list · `POST /api/agents/` upsert by slug (changing an existing agent's name, description, persona, email, google_account, avatar or runner_preference needs `agent_edit` on it; creating one needs an editor of the workspace; the definition fields stay the agent admins'; `google_account` — the agent's Google login when it is not its `email` — is written only when sent, "" clears it, 422 if not an address; a CREATE makes the caller the owner; an update never changes it; a create or a changed `repo_url` asks the cloud runners that will take its turns to re-run their bootstrap, `setup.request_setup`; a `workspace` other than the agent's current one is the full move below, not a pointer change) · `DELETE /api/agents/{slug}/` (editor/owner; removes everything hanging off it, and first closes its open chat sessions so their emdash tasks are deleted on the runner — an offline runner drains the close when it is back).
- `POST /api/agents/{slug}/move` `{workspace}` (`?dry_run=1` changes nothing) — moves the agent **with its history**, in one transaction or not at all (`apps/agents/move.py`): turns, chat sessions (+ participants outside the destination dropped), mail threads/messages, mail routes on a domain the destination may use, capability grants/leases, agent-scoped admission/retention rules, origin issues; the agent's own login joins the destination when the caller has `members.manage` there. People records and a person's grants stay (reported in `left_behind`); a route on a domain the destination cannot use is disabled. Returns `{agent, source, destination, dry_run, moved, tables: [{table, rows, how}], left_behind: [{table, rows, why}], stops_working: [{kind, detail}]}` — the dry run and the move share one code path. Writes an `agents.move` event in both workspaces. Agent admin + editor in the destination; 404 for a destination you are not in, 409 on a collision (nothing moved). CLI: `canopy agent move --slug <a> --to <ws> [--dry-run]`.
- Every agent item (list and detail) carries **`plugin`**: `{"repo": "owner/repo", "name": "<catalog name>"}`, named exactly as the caller's `canopy-agents` catalog names it (`apps/plugins/services.py::plugin_refs`), or `null` with no github.com repo. A plugin is code; an agent row is an instance (docs/architecture/plugin-marketplace.md).
- **Creating from the browser** (`apps/agents/creation.py`; editor in the target workspace). GitHub access is the person's own fine-grained token, the same credential agent turns use — no GitHub App install. `POST /api/agents/scaffold/check` {workspace, slug, repo, token} — reads only (POST to keep the token out of URLs): `ready` (empty, visible to the token; `login` = who it acts as), `update` (already this agent's scaffold — `.claude-plugin/plugin.json` names the slug — or only GitHub's starter files; `files_to_add` template files are missing), `adopt` (nothing missing), `name_mismatch` (another agent's repo; `suggested_slug`), `missing` (the token cannot see it), `not_empty` (not an agent repo), `no_token`; always returns `new_repo_url` and `token_url` (`delegations.token_form_url`). `POST /api/agents/scaffold` (201) — renders the `canopy-agent-factory` scaffold and pushes it with that token (empty repo: Contents API first commit, then one Git Data commit with file modes; `update`: one commit on top adding ONLY the missing template files — nothing already there is overwritten); stores nothing. Then the page registers via the upsert and lends the same token via `PUT /api/agents/{slug}/github`. Slugs `new`/`scaffold` are reserved.
- `GET /api/agents/{slug}/setup` (member) — the ordered checklist (`apps/agents/setup.py`): repo, GitHub identity (`delegations.readiness`), mailbox (`gog-token`), vault (`vault_health`: every declared secret stored and every machine let in), runner (routing order ∩ `runner_may_hold_agent` ∩ `runner_tenant_slugs`, online), job (a skill beyond the factory's own; `where: claude-code` with the command that starts the session), first finished turn. Each step reads the system's own check.
- `GET /api/agents/{slug}/` — detail with counts, `owner`, and the caller's `can_transfer_owner`, `is_admin`, `can_edit_agent` (`access.may_edit_agent`: holds `agent_edit` on this agent), `can_manage_admins`. `turn_count` / `latest_turn_at` read the harness turn queue (`latest_turn_at` = newest `started_at`, else `created_at`).
- `PUT /api/agents/{slug}/canopy-user` `{link: bool}` — the agent's canopy login is ALWAYS the account at its own email (`Agent.email`): `link: true` links it (none there → canopy creates it as the agent's login, which takes `members.manage`; an existing account nobody has signed in to interactively → linked; the caller's own signed-in account → after a passkey step-up, so a token is 403; anyone else's signed-in account → NOT linked, an `AgentLoginRequest` goes to that person, `canopy_user_request` on the answer); `link: false` unlinks. Agent admin, browser or token. 422 when the agent has no email. A new `Agent.email` on `POST /api/agents/` unlinks the old account and derives the link again.
- `GET /api/me/agent-login-requests/` · `POST …/{id}/accept` (browser only + passkey step-up; only the account's own person; 422 if closed, expired, or the asker is no longer an admin) · `POST …/{id}/decline` — requests to make YOUR account an agent's login.
- `POST /api/agents/{slug}/canopy-token` `{email?, label?}` (agent admin; 403 for a token-minted caller) → 201 `{raw, token_id, label, user_email, created_user}` — a PAT for the agent's OWN login that expires after `PAT_DEFAULT_TTL_DAYS` (180), shown once, creating the login when there is none (that takes agent admin **and** `members.manage` in the agent's workspace, else 403; 422 without a mailbox address; 409 if the address is already a canopy user). A linked login that has ever signed in interactively needs a workspace owner. Caller: `canopy agent vault`.
- `PUT /api/agents/{slug}/owner` — the agent's owner or a workspace owner transfers it to a member of its workspace (non-member 422); `{"user_id": null}` clears it (workspace owners only). The owner's GitHub grant is what History reads through.
- `GET /api/agents/{slug}/admins` (member) · `PUT|DELETE /api/agents/{slug}/admins/{user_id}` — admins = the owner, workspace owners (implicitly), and members granted by name (`AgentAdmin`; inert if the holder left the workspace). Grant/revoke: the agent's owner or a workspace owner only (403), target must be a member (422), the owner cannot be revoked (422).
- `GET /api/agents/{slug}/access` (member) — `{members, slack_enabled}`: one row per workspace member (owners of a parent workspace included): `workspace_role`, `agent_role` (the older three-word view: owner / admin / member, where member means neither), `basis` (why they are owner or agent admin), and what the rule says for them signed in: `role` (owner / admin / editor / read_write / read_only, null when the agent lets them in nowhere), `source` (`owner` | `admin` | `list:<line>`), `via` (the line in words), `access` (`full` / `confined` / `none`, the roster's wire word for refused; when confined, `profiles` lists the read-mode or host-site names it opens), `manual_only`, `may_request_auto`. People outside the workspace whom a line names are on the access list, not here. Computed with the predicates a turn uses (pinned by `tests/test_agent_access_roster.py`). UI: the roster under Settings → Roles → Access.
- **The access list** (`apps/agents/api_access_list.py`; [access-agent-roles-and-access-list.md § The access list](access-agent-roles-and-access-list.md#the-access-list)). `GET /api/agents/{slug}/access-list` (member) → `{inherit_workspace_defaults, lines, implicit, roles, can_edit}`: `lines` are the agent's own plus the workspace defaults it inherits (`scope` `agent` | `workspace`, `kind`, `who` in words, `role` or `host_site`, `manual_only`, `note`, `can_edit`); `host_sites: [{name, site}]` are the agent's host sites a line may open (`name` is the stored name a `host_site` line holds); `implicit` are the owner and agent admins, who hold their role with no line; `roles` is what each role can do. `POST /api/agents/{slug}/access-list` `{kind: person|workspace|domain|contact, role: read_only|read_write|editor (or host_site: <name>, with no role), user_id | email, workspace, at_least, include_below, domain, verified, manual_only, note}` → 201 the line (agent admin; 422 with the reason when the line is refused, 409 on a repeat of the same subject). `PATCH …/{line_id}` `{role?, manual_only?, note?}` and `DELETE …/{line_id}` → 204 act on the agent's OWN lines only (404 for an inherited one: change it on the workspace). `PUT /api/agents/{slug}/inherit-workspace-defaults` `{inherit}` → the list (agent admin). All four writes are settings changes (`access-list:<slug>`).
- **Agent roles** (`apps/agents/api_roles.py`; [access-agent-roles-and-access-list.md § Configurable roles](access-agent-roles-and-access-list.md#configurable-roles)). `GET /api/workspaces/{slug}/agent-roles` (member) → `{roles, fixed, can_edit, can_give_write}`: the roles visible to the workspace (its own and those above), each `{key, label, description, permissions, can, defined_on, builtin, contains_write, in_use, can_edit}`, and the fixed `owner`/`admin`. `POST` `{key, label, description, permissions}` → 201, `PATCH …/{key}` `{label?, description?, permissions?}`, `POST …/{key}/reset` (a built-in back to its defaults), `DELETE …/{key}?reassign_to=<key>` → 204: a workspace admin (`members.manage`), the workspace owner when the role before or after drives or changes the agent; every write a settings change (`agent-roles:<workspace>:<key>`) and a passkey step-up (a token only for a role that does not drive). 409 for a taken or clashing key, a built-in delete, or a role still in use; 422 for a permission outside `read`/`write`/`agent_edit`/`use:<site>` or an edit that would let an address-only line drive. The access-line `role` is a key from this list (`GET …/access-list` returns the roles visible to the agent, with `label`, `description`, `contains_write`).
- **A workspace's default lines** (same module): `GET /api/workspaces/{slug}/agent-defaults` (member) → `{lines, roles, can_edit, can_give_editor}`; `POST …/agent-defaults` (same body as a line) → 201 and `DELETE …/agent-defaults/{line_id}` → 204 need a workspace admin (`members.manage`), and a default giving `editor` the workspace owner. Settings changes (`agent-defaults:<workspace>`). UI: the Members page.
- `GET|PUT|DELETE /api/agents/{slug}/read-mode` and `GET /api/agents/{slug}/host-sites`, `PUT|DELETE …/host-sites/{site}` — the agent's two plain settings, both stored in one document, `Agent.interface` (`apps/agents/profile_settings.py`). Any member reads; the owner or an admin writes, browser or token. A PUT changes only the fields sent; `dry_run: true` checks without saving or auditing. A document these settings cannot hold (`profile_settings.document_problems`) is refused and left as it is. `GET /api/agents/{slug}/` carries both as `read_mode` and `host_sites`.
- The retired `interface` routes, `GET|PUT|DELETE /api/agents/{slug}/interface`, `POST …/interface/validate` and `PUT …/interface/capabilities/{name}/sensitive`, answer **410** to everyone, read and save nothing, and point at the routes above (`apps/agents/views.py`, a bare view in `config/urls.py`, so they are in neither OpenAPI nor the MCP tools). A host site's `sensitive` field needs no more than any other save (the agent's owner or an admin, browser or token); `apps/agents/published_profiles.py::parse` refuses a row that could leak, and every save is a `SettingChange` (`list_setting_changes`, target = the slug). Validation is strict (`parse`: unknown keys → 422; so are the retired `full:`, `editors:` and an entry's `callers:`, and `callers_default` other than `none`, each with a pointer to the access list; `version`, `callers_default: none` and an entry's `input` are accepted, ignored with a logged warning, and not written back). Read mode and a host site have no `role`: who may use them is the access list (a role line, or a `host_site` line). Each turn is resolved by `turn_context.resolve_turn_context` at enqueue and again at its claim (access-turn-context.md § Two moments), which stamps `Turn.capability`; a refusal is one code from `refusals.Code`, and the envelope's `access`, `granted_by`, `role` and `source` say why a turn has its access.
- `GET|POST /api/agents/{slug}/turns/` — list / package a turn: `task_ext_ids` advanced, `title`/`summary`, `work_product_urls`, optional transcript (uploaded to the sessions app; list returns `share_url` = `…/w/<workspace>/share/<token>`). Idempotent per `(agent, cli_session_id)`; `origin_ref` is merged into the row's own. POST attaches to the `harness.Turn` that dispatched the session, matched on `session_key` (`emdash_task_id` accepted as an alias); an unmatched session records a report-only turn.
- `GET|POST /api/agents/{slug}/syncs/` — status reports (Google-Doc syncs), upserted per `(period, source)`. `DELETE …/syncs/{sync_id}/` removes one filed under the wrong period.
- `GET|PUT /api/agents/{slug}/skills/` — list / replace the skill catalog (mirrors the repo); the PUT needs `agent_edit` on the agent (`@gate("agent-edit")`: 403 naming who can give you the editor role; non-member 404). Every catalog stays in step with the agent's runners: `apps/agents/skill_catalog.py` (every 5 min on `apps/common/ticks.py`) merges in the `<plugin>:<skill>` entries from the reachable runner that may hold the agent and installed its plugin last (`RunnerSlashCommands`, `plugin_updated_at`). New skills become rows with `source="runner"`, and skills no longer listed are removed. A published row (`source="published"`) keeps its note, `launchable`, link and args hint; its description follows the report unless the report's copy was cut at 300 characters. A published catalog changes only for a report whose install is dated after the publish; any other report can only set `internal`. A report at its 1000-entry limit removes nothing, and neither does one that would remove more than half of a catalog over 5 rows. `internal` means `user-invocable: false` in the skill's file: the row stays and counts, and the `/` menu leaves it out (`docs/architecture/chat-sessions.md` § Slash commands in the composer). No catalog after a day raises the `skill_catalog_empty` alert.
- `GET /api/agents/{slug}/skill-history/` (member) — skill history from the repo's git log (`skills/*/SKILL.md`) via `Agent.owner`'s GitHub grant. Syncs first when the last success is >1h old and no attempt was made in the last hour (in-flight debounced 90s); a sync failure serves stored history. Returns `credential_state` (`ok`/`no_repo`/`no_owner`/`owner_not_connected`/`repo_not_granted`), `owner_name`, `viewer_is_owner`, `viewer_can_sync`, `install_url`. `POST …/skill-history/sync` (editor+) forces one (never over an in-flight sync).
- `GET /api/agents/{slug}/skill-history/revisions` (member) — newest first with commit bodies; filters `skill` / `group` / `commit` (sha prefix) / `since` / `until`; 25 default, cap 300; bodies summarised to 700 chars; names `checked_by`/`checks` for a single skill. `GET …/skill-history/diff?sha=&skill=` — one commit's diff to one `SKILL.md`, live from GitHub, truncated to 20 KB; 422 on a malformed sha/skill.
- `GET /api/agents/{slug}/runtime` — Agent Runtime Registry: repo pointer, secret-reference names, agent CLIs (`clis`, `cli_models`), tenant.
- `PATCH /api/agents/{slug}/turn-mode` — `manual` (any editor) / `auto` (owner or admin). `PATCH …/slack` — under Slack. `PATCH …/clis` `{clis, cli_models?}` — owner or admin (a `DEFINITION_FIELDS` change, audited): the agent CLIs it runs on, preferred first (`claude-code`, `codex`; non-empty, no repeats), and a model per CLI; 422 for adding a CLI no runner serving the workspace has, or dropping one a schedule runs on; also settable on the upsert (`clis`, `cli_models`) and served on the detail and `GET …/runtime` → [runner-routing.md § Which CLI runs a turn](runner-routing.md#which-cli-runs-a-turn-appsharnessclispy). `PATCH …/repository` `{repo_url, repo_ref?}` — owner or admin (a `DEFINITION_FIELDS` change); any github.com spelling, stored `https://github.com/owner/repo`, 422 otherwise; audited; a changed repo asks its cloud boxes to re-bootstrap (`setup.request_setup`). The setup checklist's repository step links to it on Settings (`#repository`), never the create wizard.

## A2A Agent Cards (`apps/agents/api_a2a.py`, mounted at `/api/a2a`) — discovery only
Each agent's [A2A v1.0](https://a2a-protocol.org/latest/specification/) Agent Card, generated from its read mode and host sites (`apps/agents/agent_card.py`). A card grants nothing — turns are authorized at enqueue by `turn_context.resolve_turn_context`. Discovery comes from the access list: a public card exists only when an address-only line (a domain or a contact) reaches read mode or a host site (`_outsider_lines`); tags come from the lines that reach each profile, and a profile no line reaches is tagged `caller:admin`. `/api/a2a/` is public in the login middleware; each route self-enforces.
- `GET /api/a2a/agents/{slug}/.well-known/agent-card.json` — `auth=None`. Exists only when an address-only access-list line reaches read mode or a host site; every other case (nothing offered to outsiders, member-only, outsiders only via an editor line, no such agent) is the same 404. `skills[]` = what outsiders may open.
- `GET /api/a2a/agents/{slug}/extendedAgentCard` — session or PAT (a contact token → 401). Public skills plus what the caller may invoke (`published_profiles.offered_to`); 404 when that is nothing.
- **Paths:** one card per agent, base `{CANOPY_PUBLIC_BASE_URL}/api/a2a/agents/{slug}` (A2A's well-known URI is one card per origin, and canopy is many agents on one origin); no host-level card, no catalog.
- **Mapping:** `skills[].id` = the entry's stored name, `name` humanised, `description` (fallback `Ask <agent> (<name>).`), `tags` from the access-list lines that reach it (`caller:<member|contact>`, `domain:<d>`, `verified-sender`; public card tags outsider classes only; unlisted entry = `caller:admin`); Never emitted: `tools`, `bash`, `read_paths`, `entry`, `input` field names, the access list, the workspace. `securitySchemes`: `canopyPersonalAccessToken` (bearer PAT, extended card only — it invokes nothing), `canopyContactToken` (from `POST /api/auth/contact-token`, non-`:verified` contact skills under `/api/contact/`), `canopySession` (extended card only). `supportedInterfaces` are custom bindings by URI (canopy does not speak A2A messaging): `/api/contact/sessions`, `mailto:<agent mailbox>`. No MCP entry point: canopy's MCP server does not run agents — a member uses an agent by installing its plugin (`/get-started`), so a member-only skill carries no `securityRequirements`. `version` = `1.0.<interface_published_at epoch>`; `capabilities` = `{streaming: false, pushNotifications: false, extendedAgentCard: true}`; `provider` from `CANOPY_A2A_PROVIDER_{ORGANIZATION,URL}`.
- **Caching:** strong `ETag` + `If-None-Match` → 304. Public `Cache-Control: public, max-age=300`; extended `private, max-age=60`, `Vary: Authorization, Cookie`.
- **Unsigned:** cards carry no JWS `signatures[]`; canopy has no card-signing key.

## Agent runs (`apps/agent_runs`, mounted under `/api/agents`)
The unified run lifecycle (run → step → artifact → verdict/QA → decision → gate → fork) as a storage-agnostic read model behind a `RunStore` Protocol (DB adapter persists; Drive adapter reads ACE's YAML), backed by the Django-free `canopy_agent_runs` library (`packages/canopy_agent_runs`).
- `GET|POST /api/agents/{slug}/runs/` — list (paginated) / create.
- `GET /api/agents/{slug}/runs/{run_id}/` — full read model. `GET …/runs/{run_id}/steps/` — steps.
- `POST …/runs/{run_id}/steps/{step_key}/gate` — record a gate decision. `POST …/steps/{step_key}/verdict` — record a step verdict (QA/eval aggregate).
- `POST …/runs/{run_id}/fork` — fork at a step boundary.
- **Run documents** (`apps/agent_runs/documents.py`, mounted at `/api/agent-runs`): `GET /api/agent-runs/` (newest first across visible agents; `active=true` = still running, what a runner resumes; `repo_slug`), `POST /api/agent-runs/` (start or adopt), `GET /api/agent-runs/{ext_id}/`, `PUT /api/agent-runs/{ext_id}/state/`.

## An agent's state document (`apps/harness/api_agent_state.py`) and coaching facts (`apps/canopy_sessions/api_coaching.py`)
- `GET /api/agents/{slug}/state-document` → `{version, document, updated_at}` (`version: 0`, `document: null` when there is none). The agent's owner and admins; its own login only inside a running, unconfined turn that answers to nobody or to one of them (403 otherwise); anyone else 404. Rules: `docs/architecture/runners.md` § An agent's state document.
- `PUT /api/agents/{slug}/state-document` `{expected_version, document}` → `{version, updated_at}`. The agent's own login inside a running, unconfined turn of it; 409 with `current_version` when `expected_version` is stale; 413 above 1 MiB.
- `POST /api/coaching/facts/` `{kind, ref, person_id?, note_type?, reply?, finding_type?}` → `{recorded}`. The same login and turn; ids and closed words only (`docs/architecture/analytics.md`).

## Agent tasks (`apps/agent_tasks`, mounted at `/api/agent-tasks`) — call an agent inline, get a structured result
Framework tier. The contract, the completion rule and its two rails: [`agent-tasks.md`](agent-tasks.md). Anyone not listed gets a 404.
- `POST /api/agent-tasks/` `{agent, name, instructions?, input, output_schema, routing?, timeout_s?, parent?}` — create a task and queue ONE turn for the agent (`origin_ref.agent_task`). The gates of `POST /api/harness/turns/` (`agent.work`). 422 for an `output_schema` that is not a JSON Schema, 413 for `input` over 1 MiB. 201.
- `GET /api/agent-tasks/{id}?wait_s=0..20` — read (long-poll until the status changes): its creator, the agent's admins, the agent's own login. `input` only for the agent; the agent's read makes a queued task `running`. A task past its deadline fails here.
- `POST /api/agent-tasks/{id}/result` `{result}` — the agent's own login only, while queued/running; the ONLY way a task completes. 422 with `errors: [{path, message}]` (the task stays open), 409 once ended, 413 over 1 MiB.
- `POST /api/agent-tasks/{id}/cancel` — its creator or the agent's admins; cancels a still-queued turn too. Idempotent.

## Agent threads (`apps/threads`, mounted at `/api/threads`)
A bounded conversation between agents; messages are turns tagged `origin_ref = {kind: thread_message, thread, n, speaker}`, refused at enqueue on a closed/expired/out-of-budget thread, a non-participant, wrong speaker or out-of-order `n` (`apps/threads/guard.py`).
- `POST /api/threads/` — Open a thread among 2–6 distinct agents, moderated by one of the caller's agents (editor+ in its workspace, which becomes the thread's): `purpose`, `participants`, `kind`, `parent`, `context`, `max_messages`, `deadline_minutes`. Re-opening an OPEN thread with the same `parent` and agents returns it (200, else 201). 422 from inside a thread message (no nesting).
- `GET /api/threads/?parent_key=&parent_value=&agent=&status=&limit=` — Threads you can see, newest first (max 50), without messages.
- `GET /api/threads/{thread_id}` — One thread with its messages in order: each message's turn status and, where you may read the turn, its prompt and parsed reply.
- `POST /api/threads/{thread_id}/close` — Moderator ends it: `settled` (with `outcome`), `out_of_budget`, `timed_out` or `cancelled`. Only an open thread (409 otherwise); editor+.
