# API: an agent's credentials, Google and GitHub

Routes for an agent's credentials and their resolve proofs (AWS IAM, read alerts, zero-knowledge vault, PAT rotation), Google mint and delegation, sender trust, GitHub identity and Salesforce. Part of the [api surface](api-surface.md) topic; the index there lists every part.

- **Credentials** (owner or admin unless noted): `PUT /api/agents/{slug}/credentials` (write-only, non-clobbering upsert; returns masked status; from a BROWSER session it needs a passkey step-up — 403 `step_up_required` — while a PAT/MCP write does not) (the value is sealed to the agent's readers, `zks1`; nobody to seal to → 409 `zk_no_recipients`, nothing stored). There is no route that returns a stored value: a person reveals one in their browser with their own vault key · `DELETE …/credentials/{name}` · `GET …/credentials/status` (member; which declared refs are set, booleans) · `GET …/credentials/access` (whether THIS caller may resolve, as whom; session or bearer; non-member 404) · `GET …/credentials/resolve` (ciphertext the caller's own key opens: bearer only — a session is refused even for the owner — and only for a caller pairing a live runner this agent routes to, or an agent admin; otherwise 403 naming how to get access. `?refs=a,b` scopes it to those names (those that are stored); no `refs` = everything, unchanged. Credentials a person delegated to the agent (its GitHub token) never ride `values`: they come only in `delegated`, sealed to the machines that run it, and only to a `runner` read proved by one of them (`accounts.resolve_payload`) — never to an admin or a license holder. Besides the values it carries `mailbox` (`Agent.email`), `mailbox_backend` (`ses` | `google` | "") and `google_account` (`Agent.google_identity()`: `google_account`, else `mailbox` when that is a Google mailbox, else ""). Each ref handed out is logged as an `AgentCredentialRead` with caller, runner (`X-Canopy-Runner`, owned runners only) and `X-Canopy-Turn-Id`. `manage.py reencrypt_secrets [--apply]` re-wraps every other `*_enc` column under the current field key) · `GET …/readiness` (what each box reports it could actually materialize) · `POST …/bootstrap-report` (a box reports it; same gate as resolve).
- `POST /api/agents/{slug}/google/mint` (`start_google_mint`, owner or admin) — start connecting the agent's Google account; the sign-in is finished on one of its runners, so canopy-web never holds the token (`docs/architecture/vault.md` § Connect Google mailbox). 409 `no_mint_runner` when no runner that may hold the agent (and declares `google_mint`) is online. `GET /api/agents/{slug}/google/mint/{mint_id}` (`get_google_mint`) — its `status` (`requested` → `awaiting` with `authorize_url` for a top-level navigation → `completing` → `done`/`failed`) and `outcome`; never a code or token. Scopes are `google_oauth.scopes_for(agent)`: no `gmail.*` when the agent's mail is canopy-hosted on a verified domain and it has no Gmail address. `login_hint` defaults to the expected account (below), else `<slug>@dimagi-ai.com`. `GET /api/oauth/google/callback` — the fixed callback for every agent (agent, person and sign-in ride in signed state); it holds the code for the runner and returns to the agent's settings with `?google=pending&mint=<id>`. The runner's half: `GET /api/harness/runners/{id}/mint/claim` carries `google` (the step it owes; the code, consumed), `POST …/google-mint/{mint}/challenge {code_challenge}`, `POST …/google-mint/{mint}/result {value_zk, kv, account}` or `{error, detail}` — ciphertext only, refused when sealed to someone who may not read the agent; a consent from any account but the expected one (`google_oauth.expected_account`: `google_account` when set, else `agent.email` when that is a Google mailbox, case-insensitive) ends `wrong-account`, nothing stored.
- `POST /api/agents/{slug}/google/delegate {account, services}` (`start_google_delegation`, owner or admin) — connect MY OWN Google account (a personal Gmail) to the agent as a credential I delegate to it, through the same runner sign-in: `services` (gog names: `gmail` default, `calendar`, `drive`, `docs`, `sheets`) are all it asks Google for (`google_oauth.delegated_scopes`), the consent must come from `account`, and the runner seals the token (`zks1`) under `google-delegated-<account>` to the machines that may hold a credential of mine (`accounts.delegated_devices`) and my own vault key — never under the vault key; it posts `name` with the result, and one without it (an older CLI) ends `outdated-runner`. 403 `not_an_admin` for anyone not the agent's admin (a delegated entry is in force only while its person is, `accounts.serves`); 409 `no_mint_runner` when no runner with such a machine is online; 409 `entry_taken` when another person delegated that account. `GET /api/agents/{slug}/google/delegate/{mint_id}` (`get_google_delegation`) — my own sign-in's status, as `get_google_mint`. The callback returns to `/w/<ws>/agents/<slug>/connect/google?google=<status>&mint=<id>`. See [vault.md § Connect your own Google account](vault.md#connect-your-own-google-account-a-delegated-credential).
- `GET /api/agents/{slug}/sender-trust` · `PUT|DELETE …/sender-trust/{email}` — temporary (`days` 1–90) trust that ties a member's unaligned mail to their account, as long as it carries a passing DKIM signature and the address belongs to exactly one member; expired rules list with `active: false`; DELETE idempotent.
- `GET /api/agents/{slug}/github` — how the agent acts on GitHub (masked): whose identity (`lent_by_email`, `account_label` "GitHub · delegated by …"), what GitHub says about expiry, the last checks and who ran them (`checked_by`), whether it is a delegated credential in the vault (`in_vault`) and which machines can open it (`machines`, `waiting_machines`, and `eligible_machines` for a token the caller gave now — the cloud boxes that run it and the caller's own runners); `identity_for_repos` = repos whose agentless project turns run as this identity (`agents.RepoIdentity`, edited in Django admin); `can_lend` = whether the caller may delegate. `PUT …/github` (owner or admin; the caller's fine-grained PAT, checked against GitHub, then sealed to the machines that run the agent — refused with GitHub's reason, or 409 `no_machine_can_open`; from a browser behind a passkey step-up, a token may call it) · `POST …/github/check` (returns what the machines that open it last found; canopy-web cannot probe it) · `DELETE …/github` (withdraws the caller's own only). See [runner-credentials.md § The GitHub identity a turn gets](runner-credentials.md#the-github-identity-a-turn-gets).
- Salesforce for agents: a workspace vault holding `salesforce` (Eva's chrome-sales credential), attached to each agent that uses it; boxes stage it from the resolved values.

- **AWS IAM proof on resolve** (`apps/harness/aws_iam_proof.py`): instead of `DPoP`, header `X-Canopy-Aws-Proof` = base64 JSON `{method, url, headers, body}` of a SigV4-signed, unsent `POST https://sts.amazonaws.com/` `Action=GetCallerIdentity&Version=2011-06-15`. The signed headers must include `host`, `X-Canopy-Proof-Htu` (the canopy URL called; a query is ignored; normalized like DPoP's `htu`) and `X-Canopy-Proof-Iat` (unix seconds, ±120 s). Single-use (keyed on the signature). canopy-web sends it to the PINNED `https://sts.amazonaws.com/` (a client `url` naming anything else is refused unsent), canonicalizes the returned assumed-role ARN to its role, and accepts an ACTIVE `aws-iam` key for that role on a runner the agent routes to. `GetCallerIdentity` needs no IAM permission.
- **Read alerts** (`apps/agents/credentials/vault_alerts.py`): the agent's owner (else its admins) is emailed + pushed on a box read (`via` runner) with no `X-Canopy-Turn-Id`, more than `CANOPY_VAULT_READ_BURST_LIMIT` (50) resolves in 5 minutes, or a resolve refused for a bad/missing device proof; at most one per kind per agent per hour (repeats bump `occurrences` and append their context to `repeats`, capped at 20). Each alert keeps `context` — who asked, never a value: `X-Canopy-Client`, User-Agent, `X-Canopy-Parent-Session` / `X-Canopy-Claude-Session`, the caller's `X-Canopy-Proof-Missing` reason, and `turn` (what `X-Canopy-Turn-Id` names: agent, origin, status, runner, chat session, who started it — no prompt; `found: false` for an id that names no turn); the email lists it. `GET /api/agents/{slug}/credential-alerts` (agent admin).
- **Zero-knowledge vault** (`apps/agents/credentials/zk.py`; formats + vectors: `docs/vault/zk-v1/`, normative). **The agent vault's ONLY mode**: canopy-web stores no agent value it can decrypt (there is no custodial column). Every agent starts at kv 0 (no vault key yet) and stays zero-knowledge; there is no flag for it. Every `AgentCredential` holds `value_zk`: `zk1:` AES-GCM under the agent's vault key VK at version `kv`, or `zks1` sealed to each reader before VK exists; VK reaches each principal as an `AgentVaultWrap` (`device` → a device key's ECDH key, `member` → a person's `UserVaultKeyset`, one `recovery` per kv). canopy-web only shape-checks (alg, b64u lengths, `zk1:`) and never decrypts. `PUT …/credentials` (the CLI's plaintext import) and canopy-pat rotation SEAL the value to the agent's readers (`zks1`, no copy kept; 409 `zk_no_recipients` when there are none). All owner/admin, and from a browser session behind a passkey step-up (a token is let through: `_zk_admin`); errors are problem+json with an `error` code (`zk_invalid_shape`, `zk_invalid_target`, `zk_recovery_required`, `zk_caller_wrap_required`, `zk_values_incomplete`, `zk_rewrap_required`, `zk_kv_mismatch` 409, `zk_already_enabled` 409). Browser writes need a passkey step-up; a token may enable/values/wraps/rotate:
  - `GET /api/agents/{slug}/vault/zk[?values=true]` → `{agent, agent_id, enabled, kv, wraps: [{kind, kv, target, label, public_jwk, ecdh_public_jwk, ecdh_jkt, current, wrap, …}], pending: [{kind, target, public_jwk, ecdh_public_jwk, ecdh_jkt, runner_name, email, …}], rotation_recommended, values}`. `pending` = active device keys with an ECDH key on runners whose proof resolve accepts, and current agent admins with a keyset, holding no wrap at `kv`. `values` (name → `zk1:`) only with `?values=true`, each logged as a read (`via: zk-state`).
  - `POST …/vault/zk/enable` `{kv: 1, wraps: [{kind, target, wrap}], values: [{name, value_zk}]}` — atomic; at most one `recovery` — none needed when a member wrap goes to someone whose keyset carries their personal `recovery` seal — and a wrap the caller controls (their member wrap, or a device wrap on a runner they OWN — the CLI enabling as its device; the owner's member wrap can be granted later); `values` must cover every stored credential.
  - `PUT …/vault/zk/values` `{kv, values}` → `{kv, names}` (non-clobbering; stale kv → 409). `POST …/vault/zk/wraps` `{kv, wraps}` — grant device/member wraps (replaces that target's wrap; no recovery).
  - `POST …/vault/zk/rotate` `{new_kv: kv+1, wraps, values}` — replaces every wrap and value; every target that holds a wrap now and still qualifies must be re-wrapped; a recovery wrap on the same terms as enable.
  - **Give an agent a secret** (`apps/agents/credentials/secret_requests.py`, `zk_endorse.py`; spec `docs/superpowers/specs/2026-10-19-give-an-agent-a-secret-design.md`). No route here returns a value. `POST …/secret-requests` `{name, reason}` (the agent's own login or an admin; `name` must be declared, else 422 `not_declared`) opens a request bound to the chat named by `X-Canopy-Parent-Session` when that chat is the agent's own, and is refused in a contact's chat (409 `contact_chat`: a contact never sees a seal card and can't fill a secret, on purpose); its tool_result row carries `secret_request` and the chat shows a seal card. `GET …/secret-requests` → the agent's open, unexpired requests, newest first (admin only), shown on the agent's Settings → Security tab — the only place a request made outside its chats appears. `GET …/secret-requests/{id}` → status (`open|fulfilled|cancelled|expired`) and `has_value`. `PUT …/secret-requests/{id}/value` `{kv, value_zk}` takes `zks1` ONLY (422 `sealed_only`) at the current kv; an admin may fill or replace, a writer of the request's chat may fill a missing value only (409 `value_exists`), no agent login ever (403); browser + step-up. `GET …/vault/zk/recipients[?secret_request=id]` → `{agent_id, kv, recipients: [{kind, target, label, public_jwk, key_jkt}], endorsements: [{kind, target, key_jkt, by, by_email, by_jkt, by_public_jwk, sig}], declared, stored}` for an admin or whoever may answer that open request. `POST …/vault/zk/endorsements` `{endorsements: [{kind, target, key_jkt, by_jkt, sig}]}` — zk-v1 §7 signatures by the caller's OWN vault key over current recipients (422 `zk_not_your_key`, `zk_bad_signature`, `zk_invalid_target`); admin, browser + step-up. A writer seals only to recipients endorsed by a key it already trusts.
  - Resolve for a ZK agent: a device proof is REQUIRED (401 `device_proof_required` otherwise); 200 adds `{zk: true, kv, wrap, agent_id}` with `values` as `zk1:`/`zks1` ciphertexts (an agent holding nothing gets no values; `zk` is always `true`, kept for older clients, as is `enabled` on `GET …/vault/zk`); a proving device with no wrap at `kv` → 409 problem+json with members `{error: "zk_wrap_missing", kv, device_key}` and a `zk-wrap-missing` owner alert.
  - Device keys: `POST /api/runner-device-keys/` also takes `ecdh_public_jwk` (any kind, incl. `aws-iam`); rows carry `ecdh_jkt` (RFC 7638) + `ecdh_public_jwk`. A new/different ECDH key on an ACTIVE key sends it back to `pending` (rows then carry `reapproval: true`) and drops its wraps. Approve answers `zk_pending_agents` — ZK agents the approver administers that now wait on a grant for this key.
  - `GET /api/vault/setup` (self) → `{required, has_passkey, has_vault_key}`; `required` is a person at a browser with no vault key (never a token or token-minted session). The SPA's `VaultSetupGate` (`frontend/src/vault/VaultSetupGate.tsx`) answers it with a one-time passkey + vault key screen after sign-in, before any page except public link routes (`/invite/…`, the token viewers).
  - `GET|PUT /api/agents/{slug}/test-vault-key` `{enabled}` (agent admin; on: browser + passkey step-up; off: deletes the agent login's key and its conversation-key copies) — an agent login's test vault key, `docs/architecture/vault.md` § An agent login's test vault key.
  - `GET|PUT /api/vault/keyset` (`apps/passkeys/api_vault.py`, self) → `{user_id, prf_input, exists, public_jwk, seals, passkeys: [{credential_id, label, prf_enabled, sealed}]}`; GET is 404 `no_vault_keyset` until set up (the body still carries `user_id`, `prf_input`, `passkeys`). Seals are `prf`, `2skd` (passphrase + Secret Key, `i` 650000) or `recovery` — the person's ONE recovery code (§4c; at most one, never the only seal), which opens their key and so every agent they hold. PUT `{public_jwk, seals, replace}` needs a browser step-up (an agent login with its test vault key on: no step-up, one first key, passphrase seals only; any other login that is not a person: 403 `not_a_person`); each seal names one of the caller's passkeys; a different `public_jwk` is 409 `zk_keyset_exists` unless `replace` (which drops their member wraps). Deleting a passkey drops its seal; `Passkey.prf_enabled` records `clientExtensionResults.prf.enabled` from registration.
- **canopy-pat rotation** (`apps/agents/credentials/pat_rotation.py`): `GET|PATCH /api/agents/{slug}/pat-rotation` `{enabled, period_days: 1–365 (30), stored capped at 14 days short of the token's 180-day life}` (agent admin; turning on needs the agent's own login stored as `CANOPY_WEB_PAT` — the variable a runner writes it out as and the agent reads, never the old item name `canopy-pat`, which is not a variable name and is dropped — and a workspace owner once that login has signed in interactively); `POST /api/agents/{slug}/pat-rotation/rotate` rotates now (browser: passkey step-up). `POST /api/agents/{slug}/pat-rotation/own {reason}` (`rotate_own_pat`) is the same rotation triggered by the agent's OWN login when it thinks its token leaked — no admin needed, since it can only shorten the old token's life; the reason lands in the rotation row and the settings audit. A rotation mints a PAT for `Agent.user` with the PAT default lifetime, writes it to `CANOPY_WEB_PAT`, sets the old token's `expires_at` to now + 24 h and revokes it once that passes. Clock: a job on the off-request clock (`apps/common/ticks.py`, ASGI lifespan), every `CANOPY_PAT_ROTATION_TICK_S` (900); by hand: `manage.py rotate_canopy_pats [--dry-run]`.
