# API: an agent's credentials, Google and GitHub

The rules behind the routes for an agent's credentials and their resolve proofs, the zero-knowledge vault, Google mint and delegation, sender trust, GitHub identity and canopy-pat rotation. Part of the [api surface](api-surface.md) topic. Methods, paths, fields and status codes are in the routers and the OpenAPI schema (`/api/docs`); this page keeps what they do not make obvious.

Where to start reading (each router's module docstring names its neighbours): `apps/agents/api_credentials.py` (set, status, access, resolve, read log, alerts), `api_vault_zk.py`, `api_vault_members.py`, `api_secret_requests.py`, `api_sender_trust.py`, `api_github.py`, `api_pat_rotation.py`, `api_readiness.py`, `credentials/oauth_api.py` (Google), `apps/passkeys/api_vault.py` (a person's vault key), `apps/harness/api_device_keys.py`. Every route declares its gate with `@gate(...)`; formats of every ciphertext are `docs/vault/zk-v1/` (normative).

## Invariants
- **No route returns a stored agent value in plaintext to a browser.** A person reveals one in their own browser with their own vault key. The one route that hands out values is `GET /credentials/resolve`, and it is for machines. Pinned by `@gate(..., step_up=...)` on each route (`tests/test_every_route_declares_its_gate.py`).
- **The agent vault is zero-knowledge only.** `apps/agents/credentials/zk.py` shape-checks and stores ciphertext (`zk1:` under the vault key at version `kv`, or `zks1` sealed to each reader before a key exists); it never encrypts, decrypts or unwraps. There is no custodial column and no flag to turn it off. `PUT /credentials` (the CLI's plaintext import) and PAT rotation seal the value to the agent's readers; with nobody to seal to they refuse 409 `zk_no_recipients` and store nothing.
- **Step-up is for browsers only.** A browser write to credentials, the vault or a GitHub token needs a fresh passkey step-up (403 `step_up_required`); a token write does not (the CLI has no browser to ask) and is audited as a `SettingChange` like any other. `stepup.is_browser(request)` decides it per route. The vault writes admit `agent-admin` or `vault-admin` (`apps/agents/vault_gates.py::zk_admin`).
- **Vault ciphertext goes to vault members only.** `GET /vault/zk?values=true` refuses an agent admin who is no longer a member of its vault (403 `not_a_vault_member`) and logs each value as a read (`via: zk-state`): `api_vault_zk.py::get_agent_zk_state`.

## Resolve (`api_credentials.py::resolve_agent_credentials`, `credentials/credential_resolve.py`)
The route docstring states the full contract; the rules that must not be relaxed:
- **Bearer only.** A session is refused even for the owner, so a page cannot acquire the ability to render a secret. Besides that the caller must be one of three principals (`credential_access`): a runner pairing a live runner the agent routes to, an agent admin, or an active license holder naming their own open direct turn in `X-Canopy-Turn-Id`. A plain member or editor is refused and told which access to ask for.
- **Delegated credentials never ride `values`.** A token a person gave the agent (its GitHub token, `google-delegated-<account>`) comes only in `delegated`, sealed to the machines that run the agent, and only to a read proved by one of those machines (`accounts.resolve_payload`) - never to an admin or license holder. `credentials/access` reports them as `delegated_withheld`.
- **A device proof is required** (DPoP, or `X-Canopy-Aws-Proof` for an EC2 cloud runner, `apps/harness/aws_iam_proof.py`): 401 `device_proof_required` without one. A proving device with no wrap at the current `kv` gets 409 `zk_wrap_missing` and the owner an alert. `_credential_refusal` maps every `Refusal` to its problem.
- **Every ref handed out is logged** as an `AgentCredentialRead` (caller, runner, `X-Canopy-Turn-Id`) and can raise a read alert (`credentials/vault_alerts.py`: a box read with no turn id, a burst, a refused device proof; debounced to one per kind per agent per hour). Alert context says who asked, never a value.

## Zero-knowledge vault (`api_vault_zk.py`, `credentials/zk.py`)
- A wrap goes only to: an ACTIVE device key that has an ECDH key, on a runner the agent's resolve accepts, whose person is a member of the agent's vault; or a member of the agent's vault who has a `UserVaultKeyset`. Exactly one `recovery` wrap per `kv`, set only by enable and rotate. A write that leaves the caller unable to open the result is refused.
- Enable and rotate are atomic and must cover every stored credential. Rotate must re-wrap every target that holds a wrap now and still qualifies (422 `zk_rewrap_required`); a stale `kv` on values is 409 `zk_kv_mismatch`. Error codes: `credentials/zk.py::ZkError`, mapped by `route_refusals.zk_problem`.
- **A changed ECDH key waits for a person.** Registering a different ECDH key on a known device key clears its ECDH approval and drops the wraps to the old key; the signing key keeps its status, so the box keeps running agents that need no vault key but cannot read zero-knowledge agents until the new key is approved: `apps/harness/api_device_keys.py::set_ecdh`. Approve answers `zk_pending_agents`.
- **Give an agent a secret** (`api_secret_requests.py`, `credentials/secret_requests.py`, `zk_endorse.py`): no route returns a value. The value is sealed in a person's browser and arrives as `zks1` only (422 `sealed_only`) at the current `kv`. `name` must be declared (422 `not_declared`). The agent's own login can open a request but never answer one (403); an admin may fill or replace, a writer of the request's chat may fill a missing value only (409 `value_exists`). A request from a contact's chat is refused (409 `contact_chat`): a contact never sees a seal card. A sealer must verify each recipient's endorsement (a zk-v1 section 7 signature by the endorser's own vault key) against a key it already trusts before sealing: the recipient list is canopy-web's claim, the endorsements are not (`add_agent_zk_endorsements` takes only signatures by the caller's own key, 422 `zk_not_your_key`; a plain vault member may vouch only for their own machine).
- **A person's vault key** (`apps/passkeys/api_vault.py`): self only; writing needs a browser with a fresh step-up because the seals come from a passkey's PRF. A different `public_jwk` is 409 `zk_keyset_exists` unless `replace`, which drops their member wraps. The one `recovery` seal opens their key and so every agent they hold; it is never the only seal. `GET /api/vault/setup` says `required` only for a person at a browser with no vault key, never a token. The SPA gate is `frontend/src/vault/VaultSetupGate.tsx`.
- **A test vault key for an agent's own login** (`apps/agents/api.py::set_test_vault_key`, [vault.md](vault.md#an-agent-logins-test-vault-key)): on needs a browser step-up; off deletes the key and its conversation-key copies. Such a login is not a person (403 `not_a_person` elsewhere).

## Google (`credentials/oauth_api.py`, `credentials/google_mint.py`)
The sign-in finishes on one of the agent's runners, so canopy-web never holds a code or token: the status routes return a status and outcome only, and the runner posts ciphertext (refused when sealed to someone who may not read the agent). 409 `no_mint_runner` when no eligible runner is online - there is no fallback. A consent from any account other than the expected one (`google_oauth.expected_account`) ends `wrong-account` and stores nothing. The callback is one fixed path for every agent; agent, person and sign-in ride in signed state, and a state signed for a different user is refused (`google_callback`). Delegating your own account (`start_google_delegation`) needs agent-admin (403 `not_an_admin`: a delegated entry is in force only while its person is, `accounts.serves`), is sealed to the machines that may hold a credential of yours and to your own vault key (never the agent's), and is 409 `entry_taken` if another person delegated that account. See [vault.md](vault.md#connect-google-mailbox-the-token-is-made-on-a-runner) and [vault.md](vault.md#connect-your-own-google-account-a-delegated-credential).

## Sender trust and GitHub
- **Sender trust** (`api_sender_trust.py`): agent-admin to write, because it decides who an email is and so what the agent's full profile answers to. It ties a member's unaligned mail to their account for `days` only while the mail still carries a passing DKIM signature and the address belongs to exactly one member of the workspace.
- **GitHub** (`api_github.py`, `credentials/delegations.py`): the caller's own fine-grained token is checked against GitHub, then sealed to the machines that run the agent; nobody, the caller included, can read it back through canopy. canopy-web cannot probe it, so `check` returns what the machines last found. Delete withdraws only the caller's own delegation; a machine may keep a copy, so revoking at GitHub is the real recall. The identity a turn gets: [runner-credentials.md](runner-credentials.md#the-github-identity-a-turn-gets).

## canopy-pat rotation (`api_pat_rotation.py`, `credentials/pat_rotation.py`)
The credential rotated is `pat_rotation.CANOPY_PAT_REF` (`CANOPY_WEB_PAT`); route text that says `canopy-pat` means it. A rotation mints a token for `Agent.user`, writes it there, gives the old one 24 h, then revokes it. `period_days` is capped 14 days short of the token's life (`max_days`). `POST /pat-rotation/own` is the agent's own login only (403 otherwise) and needs no admin, because rotating can only shorten the old token's life; the reason lands in the rotation row and the settings audit. Turning rotation on is refused unless the agent has its own login and a stored `CANOPY_WEB_PAT` (`enable_refusal`). The clock is `apps/common/ticks.py`; by hand `manage.py rotate_canopy_pats [--dry-run]`.
