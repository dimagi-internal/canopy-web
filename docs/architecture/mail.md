# Workspace email domains (`apps/mail`)

A workspace admin brings their own domain; canopy-web runs its email through Amazon SES. **Agent addresses** (`ada@domain`) turn incoming mail into the agent's email turn and send as that address. **Every other address** is forwarded to a canopy user's login email (a catch-all route catches the rest). Setup is Settings → Email (`/w/:workspace/settings/email`); the operator steps are `docs/runbooks/mail-domain-onboarding.md`.

A superuser can **share** a domain with other workspaces (below), so one domain — dimagi.ai — serves as a sitewide address space instead of every workspace bringing its own.

Not here: human inboxes/IMAP/webmail, replying to forwarded mail *as* the domain, automatic DNS writes, bulk mail.

## Tier and removability

`apps/mail/` is a **product-tier** app: framework apps never import it (`tests/test_architecture_boundary.py`). It does not extend `apps/inbound` — `InboundMailbox` is Gmail-push routing and stays Gmail-only; SES routes are `MailRoute`, so `/runner-mailboxes` never lists them and no runner polls them with `gog`. Gate: the `perms.INTEGRATIONS` capability for domains and routes, `AGENT_WORK` (plus `access.decide` FULL on the agent) to send, reply or change a thread's state, and workspace membership to view threads.

## Model

- **`MailDomain`** — workspace FK, `name` (globally unique: SES identities are account-wide; a row still `pending` after `MAIL_PENDING_DOMAIN_TTL_DAYS` no longer holds it), `status` `pending` → `verified` → `suspended`, `receiving` (live MX check), `mail_from_subdomain` (`bounce`), `dkim_tokens`, `suspended_reason`, `daily_send_cap` (200). Routing is inert until `verified`; DKIM verifying is the proof of DNS control.
- **`MailDomainShare`** — a superuser's grant: `domain`, `workspace`, `daily_send_cap` (200). It covers the named workspace **and every workspace below it** (nearest grant wins, `domains.share_for`). Unique per (domain, workspace).
- **`MailRoute`** — `workspace` (the workspace that HOLDS the address: the domain's own, or one the domain is shared with; defaults to the domain's), `local_part` (`*` = catch-all; unique per domain), `kind` `agent` | `forward` | `drop`, `agent` FK, `forward_to` **User FK** (must be a workspace member), `enabled`. Exact local part beats `*`. The catch-all can forward or drop, never belong to an agent (422); an agent's own address is its non-catch-all route, the first by domain then local part. `canopy-forwarder` (the From of forwarded mail) cannot be routed. `dmarc` (the `rua` address of the DMARC record canopy asks for) is never taken by the catch-all — DMARC aggregate reports are dropped unless `dmarc@` has its own route.
- **`MailThread`** / **`MailMessage`** / **`MailAttachment`** — a thread has a public `uuid` (the `thread_id` agents and turns carry) and an `address` and `agent_slug` snapshotted from its route at creation (an agent's thread list filters on `agent_slug`, so it keeps threads whose route was removed). Its `route` is `SET_NULL`: removing a route or a domain stops the address receiving mail but keeps every thread and message (reads use `address`; a reply on a thread whose route is gone or disabled is 409 "this address no longer exists"). Messages dedupe on `message_id` per workspace + mailbox. An inbound message stores `reply_to` (its Reply-To addresses, at most 50); a reply with no `to` uses it only when every address is on the sender's domain or a subdomain (malformed and own-address entries dropped), else the sender — the thread detail shows the result as `default_reply_to`. It also stores `verdicts` (the SES receipt's spf/dkim/dmarc/spam/virus statuses, lowercase name → status; only agent mail is stored, so forwarded mail has none). Raw MIME for agent mail is copied to `kept/` in S3. Parsing strips NUL bytes from every stored field (Postgres text cannot hold them).
- **`MailForwardLog`** — one row per forwarded message (`forwarded` / `dropped` / an in-flight `sending` claim), metadata only; the body is never stored.
- **`MailEvent`** — one SES sending event; unique on the SNS envelope `MessageId` (`sns_message_id`) when set, so an SNS redelivery counts once while several notifications for one multi-recipient send (same SES message id) each count. Each recorded event prunes its domain's rows older than 8 days (the window plus a day).

Threading: an inbound message joins the thread whose messages' ids appear in its `In-Reply-To`/`References`, else starts one; replies set both headers.

## Shared domains

One domain, many workspaces. The domain's own workspace keeps everything domain-wide: DNS records, Re-check, Remove, the catch-all, the role addresses (`postmaster`, `abuse`, `hostmaster`, `webmaster`, `security`, `dmarc`), the domain-wide `daily_send_cap` and lifting a suspension. A workspace the domain is shared with sees it on its Email page as "Shared from <owner>" and only adds routes for **its own** agents and members.

- **Who:** sharing is `PUT/DELETE /api/mail/domains/{workspace}/{id}/shares` — `superuser` only (not a workspace setting: it lets one tenant hold addresses on another tenant's domain). The Email page shows the "Shared with" panel only when the domain answers `can_share`.
- **Addresses are first come, first served** across every workspace on the domain: a local part another workspace holds is 409 "that address is already taken", never replaced and never naming the holder.
- **Each workspace sees only its own addresses**, the owner included (`_domain_out` filters routes by workspace); threads, messages, attachments and forwards belong to the route's workspace.
- **Two caps on a send:** the domain-wide cap counts every workspace's sends; a shared workspace also has its grant's `daily_send_cap`, counted for that workspace alone. A bounce or complaint anywhere counts toward the one domain's reputation and a suspension stops every workspace on it — that is the cost of sharing, and why the per-workspace cap exists.
- **Revoking** a grant deletes no route, thread or message: the routes go inert (`domains.route_is_live`: inbound falls through to the owner's catch-all, a send is 409 "no longer shared") and re-sharing revives them.

## AWS side (`deploy/aws/canopy-mail.cfn.yaml`, stack `canopy-web-mail`, labs account, us-east-1)

Deployed by hand with a labs admin login (the deploy role holds no `ses:*`), from `main` after merge. Bucket `canopy-inbound-mail-<acct>` (`DeletionPolicy`/`UpdateReplacePolicy: Retain` — `kept/` is the only raw copy of agent mail): SES writes `incoming/` (expires after **7 days**); agent mail is copied to `kept/` (no expiry). Receipt rule set `canopy-inbound`, ONE rule `canopy-all`: no recipient filter, spam/virus scan on, TLS required, S3 action notifying SNS `canopy-inbound-mail` (object key only) → `POST /api/mail/ses/inbound/`. Configuration set `canopy-tenant-mail` (every tenant send) publishes send/delivery/bounce/complaint/reject to SNS `canopy-mail-events` → `POST /api/mail/ses/events/`. Both HTTPS subscriptions carry a custom `DeliveryPolicy` (100 retries, exponential backoff 20 s → 10 min) and default to `CanopyBaseUrl` `https://canopy.dimagi.com`. A policy on the shared task role creates/inspects/deletes identities and sends with a `ses:FromAddress` condition barring Dimagi addresses. That condition limits only this policy (IAM allows are additive and `canopy-ses-send` grants unconditioned sends), so it is defence in depth; the real guard is app-level — `agent_mail.send` and forward only ever send from a `MailDomain` address, and `apps/mail/ses.send_raw` always passes `MAIL_CONFIGURATION_SET` (not IAM-enforced). The rule set must be activated by hand (`aws ses set-active-receipt-rule-set`; it deactivates any other active set); `tests/test_mail_stack.py` pins the invariants.

Settings (env, from the stack Outputs via `canopy-web.cfn.yaml` parameters): `MAIL_ENABLED` (default **false**; adding a domain is 503, send/reply are 503, and inbound is acknowledged as `dropped:mail-off` when off), `MAIL_INBOUND_BUCKET`, `MAIL_INBOUND_TOPIC_ARN`, `MAIL_EVENTS_TOPIC_ARN`; also from env `MAIL_SES_REGION`, `MAIL_CONFIGURATION_SET`, `MAIL_SES_AUTHSERV_ID`, `MAIL_INBOUND_MX`, `MAIL_RESERVED_DOMAINS`, `MAIL_PENDING_DOMAIN_TTL_DAYS` (7). `MAIL_FORWARDER_LOCAL_PART` (`canopy-forwarder`) is a constant, not env.

## Flows

- **Add a domain:** uniqueness check (a holder still `pending` and older than `MAIL_PENDING_DOMAIN_TTL_DAYS`, in any workspace, is released first, under a row lock: SES is asked whether its identity verified — if so the row flips to `verified` and the add is 409; else the row and its routes are deleted conditionally and then its SES identity — canopy created it for that row; NotFound is fine, any other provider error keeps the row, 502; mail off 503; the release is folded into the adder's own audit row (`released_stale_claim`, never the holder's workspace or any detail of it) and the holder side is logged server-side only. If the add fails after the stale holder's SES identity was deleted, the rollback restores the holder row but its identity is gone; the next add sees NotFound and releases it cleanly. A fresh pending, verified or suspended holder → 409) → `CreateEmailIdentity` (Easy DKIM) + MAIL FROM `bounce.<domain>` → row `pending`. The page lists every DNS record with a live per-row check (server-side lookup, cached ~60 s). Status flips to `verified` when SES reports DKIM success, refreshed lazily on every domain read and by `manage.py mail_refresh` (no scheduler needed). MX is its own "Receiving" status and names the current MX provider so a working mailbox is not broken by accident.
- **Inbound:** the SNS signature is verified (cert and subscribe URLs must be `https://sns.<region>.amazonaws.com`, the region taken from our topic ARN; topic ARN ours) **before anything else is parsed**; a `SubscriptionConfirmation` fetches its URL once. A 4xx fetching the cert or subscribe URL is a bad message (404); a network error, timeout, TLS error or 5xx is transient (500, SNS retries) so a blip never drops real mail. A verified Notification whose Message is not a JSON object (SES's "Successfully validated SNS topic…") is acknowledged and logged at INFO, on both doors. Unknown or unverified domain, or a spam/virus FAIL verdict → drop and log, never forward or wake an agent. A subdomain resolves to its verified parent's routes. Route resolution: exact → `*` → drop. **Agent:** dedupe, copy to `kept/`, store (with the receipt verdicts), thread, enqueue the turn. A reply with no explicit `to` goes to the newest inbound message's `reply_to` (same-domain only), else its `from_addr`. **Forward:** re-send through SES from `"<Name> via <domain>" <canopy-forwarder@domain>` with `Reply-To` the original sender, to the user's login email; a destination on any canopy mail domain is dropped as `dropped:loop`. **Drop:** log only. Retries: only a transient failure (an SES/S3 client error, a DB connection error) answers 500 so SNS redelivers under the subscription's `DeliveryPolicy`; `MAIL_ENABLED` off answers 200 `dropped:mail-off`; any other error is acknowledged 200 as `error:<Type>` so a poisoned message cannot loop. Per-recipient dedupe makes a redelivery safe.
- **Replay:** `manage.py mail_replay <incoming-key> [--recipient ADDR …] [--dry-run]` re-handles a raw object still in `incoming/` (7 days) through the same code as a notification (`inbound.plan`/`deliver`). Recipients default to the To/Cc/Delivered-To addresses on one of our domains (a Bcc recipient must be named); keys outside `incoming/` or containing `..` are refused; the first `X-SES-Spam-Verdict`/`X-SES-Virus-Verdict` header (SES prepends its own; a sender's copy sits below) still drops a FAIL (those two are the only verdicts a replay records). A forward logged as dropped is retried only with `--reforward`, which clears that DROPPED claim first; a forwarded copy never re-sends. Dedupe makes it safe to repeat: a copy that already arrived reports `duplicate`. One `recipient: outcome` line each; a transient failure prints them, then exits non-zero.
- **Agent turn:** `harness.services.enqueue_turn` with origin `email`, key `email-<agent>-<thread uuid>-<message pk>`, prompt `/<agent>:turn --thread <uuid>`, `origin_ref.backend = "ses"`. Skipped (stored, no turn): the agent's own address as sender and automated mail (`Auto-Submitted` ≠ `no`, `Precedence: bulk|list|junk`, `List-Unsubscribe`). Sender grading uses the server-only `authserv_id` (`MAIL_SES_AUTHSERV_ID`, `amazonses.com`); runner-posted Gmail turns keep `INBOUND_EMAIL_AUTHSERV_ID`, so a runner can never choose its own trusted receiver. No runner reads the mailbox.
- **Reputation guard:** the events endpoint updates `delivery_status` and rolling counters; every event is recorded (sends are the denominator); a Bounce, Complaint or Reject triggers an evaluation, and so does the Send that brings the window to the minimum volume (earlier bounces start counting then). The sending domain is found by an exact match on the event's `mail.source`; an event matching no `MailDomain` is ignored. A domain is auto-suspended (sends refused; inbound still stored/forwarded) when, over 7 days with at least 50 sends, bounces exceed 4 % or complaints 0.08 %, or on a hard-bounce burst over 10 in an hour. The settings page shows the reason; an admin re-enables. Forwarded mail counts toward the forwarding domain. `agent_mail.send` holds a `select_for_update` lock on the domain row across the status/cap check, the SES call and the insert, so concurrent sends cannot overshoot `daily_send_cap` (no message row is written if SES refuses); sends use their own fail-fast SES client (5 s connect, 20 s read, 2 retries) because the lock is held across the call.

## Safety invariants

Forward destinations are User FKs only — no free-text destination exists, so the feature cannot be a relay. Tenant sends go through `canopy-tenant-mail` (set by `ses.send_raw`) and `agent_mail.send`/`forward` only ever use a `MailDomain` address; the IAM condition on Dimagi addresses is a backstop for its own policy only. HTML renders in an empty-sandbox iframe behind a no-network CSP, with any `<meta http-equiv="refresh">` stripped first (CSP does not stop navigation); attachments download via short-lived presigned URLs handed only to workspace members reading the thread. Removing a route or a domain (the domain also deletes its SES identity) keeps every thread and message; there is no thread delete. Every write route is in `route_gates` (domain/route writes are `SETTINGS`, audited via `audit.note_change`; send, reply, inbound and events are `NOT_SETTINGS`).
