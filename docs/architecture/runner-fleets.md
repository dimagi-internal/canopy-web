## Runner fleets (`apps/harness/fleets.py`)

Cloud capacity grows with a **fleet**: one EC2 Auto Scaling group of interchangeable cloud runners whose size canopy-web sets from the work waiting for it. The module docstring of `fleets.py` is the overview (how a member joins, the scaler's five steps, routing as the fleet); building one is `runner/ec2/fleet.sh` (README § Runner fleets). What an agent must not break:

- **One approval, then AWS vouches.** A fleet (`RunnerFleet`) is approved once, by its creator, from a browser behind a passkey; no token can approve it. After that an instance joins on its own at `pair-by-role` only when STS says it signs as `assumed-role/<the fleet's role>/<i-…>` and EC2 says that instance carries the reserved tag `aws:autoscaling:groupName = <the fleet's group>`. The role trusts only EC2, so the session name is an instance id EC2 set, and no caller can set an `aws:` tag. The fleet must be active and its owner must still have `agent.work` there. Any refusal is the uniform 401.
- **A member is its own runner** (name `<fleet>-<instance id>`, device key role + instance via `aws_iam_proof.member_jkt`, `machine_id` `<role>/<instance>`). One member cannot sign in as another and the role on its own signs in as nobody. A fleet's role is never one box's identity: an invitation, a fleet and a device-key enrollment each refuse a role another uses (`fleets.py`, `FleetRefused`).
- **One KMS key per fleet, so new members need no person.** Every member's ECDH key is the fleet's KMS key (`ecdh-kms.cfn.yaml`), which only the role can derive with. The first member is granted the credential set's vault key by its owner (once per fleet); after that canopy-web keeps the fleet's copy (`RunnerFleet.vault_wraps`) and hands it to each new member (`_give_wraps`). The copy is ciphertext bound to vault, key version and the ECDH key thumbprint, so it opens on any member and canopy-web opens none of it.
- **A member is routed as its fleet** (`fleets.sync_routing`, `RunnerFleet.routing`): agents' runner lists and workspaces' runner orders name runners, and a scaler-added member is a new runner. Route a fleet by routing any one member. A member whose instance left the group is retired with its rows deleted; the fleet's copy outlives every member.
- **A credential set is the fleet's one list** (below). `fleet.sh up --credential-set <name>` reads an existing set; otherwise the fleet gets a new one.
- **The scaler is `fleets.tick` on the off-request clock** (`RUNNER_SCALER_TICK_S`, 0 = off). Fail over runs BEFORE demand is measured, and a member that still answers is never moved off, because its handoff would still be packing. Shrink goes by one member per tick, never while anything waits, never below `min_members`; **the claim refuses a member whose `power` is not `on`** (`claim_next_turn`), which is what makes draining safe. A retired fleet is still ticked while it has members. Each size change is a `runner.fleet.scaled` fact.
- **Readers:** a member in the warm pool or coming up, not paused or signed out, of an active fleet, is `Runner.wakeable`: `turn_reach` counts it as a LIVE taker and the unclaimable report as reachable.
- **Keep `min_members` at least 1:** the Gmail doorbell and inbox pollers run on a box (every member polls; the server dedupes mail turns per thread; `api_runner_fleets.py`). Capacity per member is `MAX_CONCURRENT_TURNS` in `cloud_runner.py`; `fleet.sh` tells canopy-web the same number (`member_turns`).
- **Out of scope:** sensitive-data boxes and machines running several runners are single named boxes (`up.sh`). A fleet member is one runner for one workspace tree.

## Credential sets (`apps/harness/credential_sets.py`)

A **credential set** (`RunnerCredentialSet`) is one ordered list of Claude tokens and API keys that several cloud runners of one owner read as their own (`runners.list_owner`): every member of a fleet, and any other cloud runner of the owner that joins it. An edit from any of their Credentials tabs edits the set. Tokens and API keys only: a full login is refused (409), because its refresh token rotates and cannot be shared. Usage caps are per Claude account, so N runners on one token share one cap. The module docstring of `credential_sets.py` is the overview.

- **The list is shared across workspace trees; the values are not.** A vault never serves two isolation boundaries (`vault.md` § A runner's own vault), so a set keeps one vault per workspace tree (`RunnerCredentialSet.vaults`, `credential_sets.vault_in_tree`) and a runner on a set is served by that vault only. An entry with no value in a runner's tree is one that runner skips; its Credentials tab says how many it lacks.
- **Coming onto a set:** a fleet member joins as it pairs; `share` turns a runner's own list into a set (409 while the list holds a login); `join` makes a runner read a set (409 while it has entries of its own or is a fleet member; 422 `vault_crosses_isolation` when its tree's vault already serves runners of another boundary). Routes: `apps/harness/api_runner_credential_sets.py`. The set's vault then stops serving the runner's old copy of the key (`workspace_vaults.device_may_hold`).
- **One owner.** A set and every runner on it have the same owner. Only that person puts a runner on a set or changes the set's list (`api_runners._list_admin_or_404`, 403): a runner administrator administers one runner, and the list is every runner's on the set. They still read it.
- **Removing an entry** deletes its secret from every tree's vault of the set, unless a runner outside the set that a vault also serves still lists it.

## Runner readiness (the not-ready marker)

A failed turn writes `~/.canopy/not-ready` (`runner/canopy_runner/canopy_runner/readiness.py`, `mark_failed`); `readiness.compute` reports it on the heartbeat as `ready=False`, a not-ready runner is not `Runner.is_available`, and lower ranks in every cascade take its work. `mark_ok` clears it only after a turn executes, so the marker **expires after `MARKER_TTL_SECONDS`**: otherwise one transient failure exiles a box that keeps heartbeating ONLINE. Expiry is retry-with-backoff: a genuinely broken box fails its next turn and re-marks itself. The CDP probe gates independently (`compute`), so expiry cannot mask emdash being down.

**Signed out is the one not-ready note that stops claiming.** A laptop turn finishes at delivery, so without it a box with no Claude login would stay ready and answer every message with the CLI's "Not logged in". The hook listener reads the transcript tail on `Stop`/`Notification` (`canopy_transcript.signed_out`, the API-error record only, never agent text): on that record the box writes the marker with `canopy_transcript.SIGNED_OUT_NOTE`, raises `claude_auth_required` once (`hooks.report_signed_out`, mailed by `credential_notify`), and skips its claim; on the next real reply from any session on the box it clears it (`note_signed_in`). The server reads the note as `Runner.signed_out`: `claim_next_turn` refuses the box (above the pin), `turn_reach` returns `signed_out` for a turn only signed-out boxes could take, admission rules treat it as offline, and the session list carries `runner_signed_out` for `/ide`. Other not-ready notes (no Claude desktop CLI, which falls back to emdash) still claim.

## Why is my turn still queued?

A QUEUED turn explains itself, as `waiting` events on the turn (`GET /api/harness/turns/{id}/events`, or `canopy agent turns --slug <agent>`). `Runner.last_claim_poll_at` records when a runner last ASKED FOR WORK, distinct from its heartbeat (a laptop's daemon can heartbeat for hours while the app that takes turns is asleep); `claim._note_skips` records on the turn why a box passed it over; the `harness.note_waiting_turns` tick (`apps/harness/waiting.py`) writes one plain sentence per turn queued past `FIRST_NOTE_AFTER`. They are their own event kind so Slack and chat status reactions to `status` rows are not triggered.

**A restart does not stop a box taking work.** A box that has bootstrapped before (`~/.canopy-bootstrapped-at`) starts claiming within seconds of a restart and runs the bootstrap pass on a thread (`cloud_runner.start_bootstrap_beside_claims`); only a box's first pass comes before its claims, and `BOOTSTRAP_BESIDE_CLAIMS=0` puts the pass first again. Claims wait only while what a starting turn needs is being replaced (`setting_up`, the `setup` reason of `claim_gate`; `bootstrap_agents.sh` announces a CLI reinstall in `.canopy-setup-hold`). An agent's turns also wait while that agent is prepared, and a turn for an agent with no clone waits for the pass. The box reports `health.setting_up` while it holds its claims; a waiting turn says so (`Runner.setting_up`, read by `waiting.py`) and `TurnStatus.setting_up` makes the chat and Slack say the runner is restarting.
