# API surface

Every route canopy-web serves, and the rules a schema cannot express (gates, refusals, invariants).
The machine-readable schema is `/api/openapi.json` (Scalar at `/api/docs/`, Redoc at `/api/redoc/`); frontend types are generated from it into `frontend/src/api/generated.ts`.
All routes are Django Ninja (Pydantic v2) under `/api/` unless marked as a bare view; errors are RFC 7807 `application/problem+json`.
The canonical tenant URL is `/api/w/{ws}/…`: `apps/api/tenancy.py::WorkspaceResolveMiddleware` 404s a non-member, pins `request.workspace_slug`, strips the prefix and reroutes to the flat mount, so the schema stays single. Handlers read `getattr(request, "workspace_slug", None)` (truthy = pinned, `None` = unpinned). What an unpinned list or create covers: [roles.md § A read that names no workspace stays inside one organisation](roles.md#a-read-that-names-no-workspace-stays-inside-one-organisation).

### Errors
Every error is RFC 7807 `application/problem+json`: `{type, title, status, detail?, instance?, extras?}` plus any extension members at the top level.
- `title` is stable per `type`; the per-occurrence message is always `detail`, so a client shows `detail` and falls back to `title` (`frontend/src/api/problem.ts::problemMessage`).
- A bare `HttpError(status, msg)` in a route becomes `type: about:blank`, `title` = the status's reason phrase (`"Not Found"`, `"Forbidden"`…), `detail` = `msg` (`apps/api/api.py::_on_http_error`).
- `ProblemError(status, title, type_=TYPE_…, detail=, members=, headers=)` (`apps/api/errors.py`) sets a typed problem; `members` are top-level keys a client branches on (`error: "step_up_required"`, `error: "device_proof_required"`), `headers` adds response headers (`WWW-Authenticate`).
- Outside a Ninja route (middleware, bare views) build the body with `apps.api.errors.problem_response(status, *, type, title, detail, **members)` — never by hand: it JSON-escapes text taken from the request (the tenancy 404 names the URL's slug) and defaults `title` the same way.

### Auth + session (root)
- `GET /api/me/` — current user. `passkeys_here: false` on a session minted from a token (the Canopy Runner app's), on which every step-up and approval is refused: the SPA then hands each passkey moment to the browser (`frontend/src/auth/passkeyHere.ts`). `GET /api/health/` — health check (`auth=None`). The top-level `GET /health/` (also public) adds `runner_code_sha`, the laptop runner version this deployment ships, which a developer-install updater reads when canopy refuses its token (`runner/canopy_runner/canopy_runner/update.py`).
- `GET /api/csrf/` — CSRF token bootstrap (bare view). `GET /api/_auth_smoke/` — internal smoke check of session auth (returns the caller's email).
- `GET|PATCH /api/me/presence-preference/` — the user's presence-visibility opt-out (`docs/architecture/chat-sessions.md` § Viewer presence).
- `GET|PATCH /api/me/runner-app/` — `{opens_on: "supervisor"|"ide"}` (GET also returns `choices`, the pages offered, which the app's right-click menu → Opens on lists), the page the Canopy Runner desktop app opens on (`RunnerAppPreference`; default supervisor). The app loads the bare view `/runner-app/`, which 302s there — a new page is a new choice here, with no change on the box.
- `GET|PUT /api/me/canopy-projects/` — `{everything, projects}` (GET also returns `available`: the repos your own runners report, plus any you named), the repos canopy works in for you (`ProjectOptIn`; unset = none). A repo outside it is plain Claude Code: no repo turn routes there, no session, transcript or usage is mirrored from it. An agent's repo always counts. Audited setting → `docs/architecture/runners.md` § Opted-in projects.
- `GET /api/me/session-sharing/`, `PUT /api/me/session-sharing/{project_id}` `{shared}` — the projects in your workspaces whose repo you work in, and whether your laptop sessions in that repo are shared with the project's team (`ProjectSessionShare`; unset = not shared). On, the team (its owner and participants, never an agent login) reads, writes and may pull them; never a sensitive one. Audited setting → `docs/architecture/access.md` § Who can see a session.
- `GET|PATCH /api/me/session-workspace/` — the workspace NEW emdash sessions your runners discover are filed in when the emdash project is not an agent's (an agent's follows the agent). Must be a workspace you are editor+ in; blank clears (falls back to the runner's workspace); existing sessions stay put (move one with `POST /api/canopy-sessions/{id}/move`).
- `GET|POST /auth/cli/authorize/` — bare view (`apps/tokens/cli_authorize_views.py`). gh-style loopback: a signed-in browser mints a `PersonalToken` and 302s it to a local CLI callback (callback must be a safe loopback target). Pairs with `/canopy:canopy-web-pat-mint`.
- `GET /download/runner/<platform>` — bare view (`apps/harness/views.py::download_runner`): signed in → 302 to a 15-minute presigned URL for the deployed runner version's installer; signed out → sign in and back; unknown platform or nothing built → 404 (an HTML page saying so). See **Runner releases** below.
- `GET /auth/github/start/` · `GET /auth/github/callback/` — bare views, signed-in only: the per-user GitHub App connect flow (`apps/github_connect/github_app.py`). The callback path is registered on the GitHub App.
- `GET|POST /auth/connections/{provider}/{workspace}/start/` · `GET /auth/connections/{provider}/{workspace}/callback/` — bare views, signed-in only (`apps/connections/views.py`): the server-held OAuth connect flow through that workspace's app (`docs/architecture/vault.md` § OAuth connections are server-held). `start` takes `return_to` (a same-site path, else `/settings`) and `agent=<slug>` to connect for an agent (the agent must be in that workspace, else 404; caller must be an admin of it, else 403; asked again at the callback, since admin may be revoked in between). A person needs read on the workspace (else 404). An agent's start is a CSRF-checked **POST only** (a GET naming `agent` is 405) and passes the provider's agent parameters (Salesforce: `prompt=login consent`; Google: `select_account` and a `login_hint`), so the account attached is the one typed in, not the admin's browser session. A person's flow finishes only for the user who started it (`forbidden` otherwise); a callback whose workspace or provider differs from the parked flow is `bad_state`. The callback registered with the provider is `/auth/connections/<provider>/<workspace>/callback/` (shown in Settings). Both always land on `return_to` with `?connection=<provider>&status=connected|error[&reason=]`; reasons `not_configured` (no app in that workspace), `bad_state`, `forbidden`, `access_denied`, `insufficient_scope` (the grant lacks a scope the provider requires; nothing is stored), `wrong_account` (the signed-in account fails the app's rule; nothing is stored), `provider_error` (a provider that cannot be reached is also `provider_error`). An unknown provider, or an unknown `agent` slug on `start`, is 404.
- `POST /api/auth/contact-token` — `auth=None`; the credential is a connected site's **signed assertion** about its visitor (`apps/contacts/contact_api.py`, `assertions.py`). Arrival (`contacts.services.resolve_arrival`): an already-linked contact, or `email` + `email_verified: true` held verified by exactly one active canopy user who is a member of the site's workspace → a delegated USER token (`kind: "user"`, `DelegatedToken.assurance = host_signed`); otherwise a contact token (`kind: "contact"`). Never creates an account; membership is the whole gate. A signed `canopy_agent` claim (a page that chose its agent) must equal `agent_slug` (400 `agent_mismatch`) and be on the site's allow-list (403); the minted token (`bound_agent`) and the `HostGrant` it redeems (`agent`) then serve that one agent — `delegation.offered_for`, the contact routes' `_bound`, the chat socket, and `host_grants.grant_for` for the gateway and Views (`docs/architecture/embedding-a-canopy-agent.md` § 5c).
  - **Host grant at arrival** (contract: `sdk/python/README.md`): the body may carry `id_jag`, an ID-JAG the site signed for its own MCP server naming the same visitor. When the site has `host_issuer` + `host_mcp_resource`, canopy verifies it (site keys, `typ: oauth-id-jag+jwt`, `iss`=`aud`=issuer, `client_id`=canopy, `resource`, `sub` = the assertion's `sub`, ≤300s), discovers the token endpoint (RFC 8414, `issuer` checked), redeems it (jwt-bearer + `private_key_jwt` + DPoP + `resource`) and stores the DPoP-bound token Fernet-encrypted as a `HostGrant` keyed (site, visitor). A refusal never fails the arrival: the chat opens and an `Event` (`tokens.host_grants`) says why. Response `host_grant` says whether one was redeemed (never for a contact, who has no passkey to confirm it with; the grant is unusable until the person confirms it in the panel); if so the token lives 10 minutes so the widget re-mints about every 5. Every outbound fetch is https-only, refuses private addresses and follows no redirects (`apps/host_grants/outbound.py`).
- **MCP client sign-in (OAuth)** — bare views (`apps/oauth_server/mcp_oauth.py`): `POST /oauth/register` (RFC 7591; public PKCE clients only; rate-limited per IP; redirect URIs https, http-to-loopback, or a private-use scheme), `GET|POST /oauth/authorize` (consent page; needs a signed-in person and refuses a token-minted session; an unknown client or unregistered redirect is shown, never redirected to), and the `authorization_code` (PKCE S256 required) + `refresh_token` grants at `POST /oauth/token`. The access token is a `PersonalToken` tied to an `OAuthGrant`; lifetimes, rotation and reuse revocation: [mcp-surface.md § Auth model](mcp-surface.md#auth-model). `GET /api/tokens/connected-apps` lists the caller's grants plus the MCP address; `DELETE /api/tokens/connected-apps/{grant_id}` revokes one at once (no refresh).
- `GET /oauth/client.json` · `GET /oauth/jwks.json` — bare, public: canopy's OAuth CLIENT identity. The first is the Client ID Metadata Document whose URL IS canopy's `client_id`; the second the public CLIENT key (`use: sig`, RFC 7638 `kid`, EdDSA or ES256). The DPoP key is never published. 503 without `CANOPY_OAUTH_CLIENT_KEY` / `CANOPY_OAUTH_DPOP_KEY`. Neither key can assert a user (`apps/host_grants/client_identity.py`).
- **canopy-web as host of its own MCP** (`apps/host_grants/self_host.py`) — bare, public; the host half is off until `CANOPY_HOST_SIGNING_KEY` and the client keys are set: `POST /oauth/token` also serves the jwt-bearer grant (RFC 7523 + `private_key_jwt` + DPoP) for ONE client, canopy's own `client_id`, via the SDK's `GrantHandler`; `GET /oauth/host/jwks.json` (the HOST signing key, distinct from `/oauth/jwks.json`; what the `canopy-web` Connected site's JWKS URL names); `POST /oauth/probe` (live probe of the host half: a real ID-JAG for the dedicated probe user `CANOPY_HOST_PROBE_USERNAME`, for canopy's own client only, authenticated like the token endpoint; 404 while there is no probe user); `GET /.well-known/oauth-authorization-server[/…]` and `GET /.well-known/oauth-protected-resource[/…]` (RFC 8414 / 9728 for `{base}` and `{base}/api/mcp/`; always served, folding in the jwt-bearer grant only when the host half is configured). canopy's own redemption reaches these in-process (`self_host.loopback_*`, consulted by `outbound.py` and `jwks.py`); the gateway's MCP call is real HTTP to `{base}/api/mcp/`.

### Connections (`apps/connections`, mounted at `/api/connections`, `/api/agents`, `/api/me/connections`, `/api/workspaces`, `/api/harness`)
Server-held OAuth connections ([`vault.md`](vault.md) § OAuth connections are server-held). The browser legs are bare views, above. A connection is owned by one person or one agent and goes through one workspace's app; responses never carry a token or a client secret.
Every 409/502/503 below is problem+json with `error` set to the service layer's code, mapped in one place (`apps/connections/problems.py`): 409 `not_configured`, `not_connected`, `reconnect_required`, `ambiguous`, `insufficient_scope`, `wrong_account`, `app_locked`, `not_grantable`, `own_connection`; 400 `invalid_app`; 502 `provider_error`; 503 `provider_unavailable`.
- `GET /api/connections/` — Self. `{providers: [{name, title, configured, workspace, workspace_name}], connections: [...]}`: one row per (workspace the caller can read with the provider set up) — a provider set up in none still lists once with `workspace` empty and `configured` false — and the caller's own connections (each with `workspace`, `workspace_name`; `account_label`, `instance_url` — empty for a provider with a fixed API host —, `scopes` (what the provider granted), `needs_reconnect`, `usable` — false for one in a workspace the caller has left, which only disconnects —, `missing_scopes` (`[{scope, label}]` its app now asks for and the grant lacks: reconnect), `last_used_at`, `connected_by_email` — empty once that account is deleted). Never calls the provider.
- `GET /api/workspaces/{workspace}/connection-apps` — workspace `integrations` role. `{apps: [...]}`, one row per registered provider: set-up state, `client_id`, `has_secret` (never the secret; false when the stored one can no longer be decrypted), `options`, `scopes`, the provider's `option_fields` / `scope_choices` / `locked_options` (the options that, like `client_id`, cannot change while connections exist), `connection_count`, and the absolute `callback_url` to register. operationId `list_connection_apps`.
- `PUT /api/workspaces/{workspace}/connection-apps/{provider}` — `integrations` role, an audited setting, behind a passkey step-up from a browser. Creates or updates the app: `scopes` is replaced in full, `options` merged over the stored ones, a blank `client_secret` keeps the stored one (a new `client_id` needs its secret). 400 `invalid_app` (also a blank `client_secret` when the stored one cannot be decrypted); 422 a `client_id` over 255 or a `client_secret` over 4096 characters; 409 `app_locked` while connections exist and `client_id` or a locked option changes (the detail names which). Adding a scope leaves existing connections as they are: each lists it in `missing_scopes`. Not an MCP tool (it carries the secret). operationId `configure_connection_app`.
- `DELETE /api/workspaces/{workspace}/connection-apps/{provider}` — same gate. 204, also when none exists. Disconnects the app's connections first (revoking each; agents they were shared with lose them, recorded as `grant_revoked`). Not an MCP tool (it disconnects everyone's connections). operationId `remove_connection_app`. A workspace cannot be deleted while it has apps: `DELETE /api/workspaces/{slug}/` answers 409 saying to remove them first.
- `DELETE /api/connections/{id}` — Self, an audited setting; 204. Asks the provider to revoke. Someone else's id is 404, not 403.
- `GET /api/agents/{slug}/connections` — Agent admin. The agent's own connections (each with `shared_with`, the slugs it is granted to) plus ones granted to it (`granted_from` names the owner), each with `usable` (false once the owning agent is no longer in the connection's `workspace`: a connection made before a move, or shared by an agent that moved) and `missing_scopes`.
- `DELETE /api/agents/{slug}/connections/{id}` — Agent admin, an audited setting; from a browser behind a passkey step-up (a token is let through). 204; agents it was shared with lose it.
- `PUT|DELETE /api/agents/{slug}/connections/{id}/grants/{other_slug}` — share an agent's connection with another agent / stop sharing. Audited settings; a browser needs a passkey step-up, a token does not. `PUT` needs an admin of both agents (403 otherwise; 409 `error` `not_grantable` or `own_connection`); sharing again is a no-op. `DELETE` takes an admin of either agent — the grantee's admin even from another workspace, for a connection actually shared with their agent (404 otherwise). An unknown agent or a connection that is not the slug's is 404.
- `POST /api/me/connections/{provider}/token` — Self, kind `ephemeral-credential`. A fresh short-lived access token for the caller's own connection, for their CLI: `{access_token, instance_url, expires_at, account_label}`. A **plain personal access token over REST only**: a browser session, an MCP call, an OAuth-grant (connector) token and a conversation's caller token are all 403 `token_route_needs_pat`, so neither a stolen cookie nor a model holding the person's token can pull one; not an MCP tool. `?workspace=<slug>` picks the connection through that workspace's app; without it, connections through two workspaces' apps are `ambiguous`. A connection is usable only while the caller is a member of its workspace (else `not_connected`). `?refresh=true` forces a refresh even when the cached token looks fresh (after a 401 from the provider). 409 `not_connected`, `reconnect_required` or `ambiguous` (all three with `connect_url`, an absolute URL; `ambiguous` also lists `workspaces` and `accounts`) or `not_configured`; 502/503 as above; an unknown provider is 404. Each issue is logged as `connections.token_issued` with `to=cli` ([`vault.md`](vault.md) § Connection audit).
- `GET /api/harness/runners/{runner_id}/turns/{turn_id}/connections` — runner protocol (not an MCP tool), for a turn this runner is executing (else 404, and always for a caller's confined turn; 409 `no_agent`). `{providers: [...]}`: the provider keys the turn's AGENT has a connection for, its own or one granted to it, sorted — usually empty. The runner calls it once per turn and fetches a token only for these. No token.
- `POST /api/harness/runners/{runner_id}/turns/{turn_id}/connection-token` `{provider, min_life_seconds?, refresh?}` — Act-as, runner protocol (not an MCP tool), for a turn this runner is executing (else 404). The same token body, for the connection the turn's AGENT uses for `provider`: its own, else one granted to it — never the person's who started the turn. 404 also for a caller's (confined) turn, and when this runner may no longer hold the agent (asked again on every call). 409 `no_agent`, `not_connected`, `ambiguous`, `reconnect_required`, `not_configured`; 502/503 as above. An unknown `provider` is 404. `min_life_seconds` (0–3600, default 300) is how long the handed-out token must still live, else it is refreshed first (the cloud runner asks for 900, its re-stage margin; canopy-web caps it at half the lifetime the last token was issued with); `refresh: true` forces a refresh. Each issue is an Event `connections.token_issued` in the connection owner's workspace (`to=turn`, `agent`, `turn`, `runner`; one turn's repeat issues coalesce; never the token).

### Workspaces (`apps/workspaces`) — multi-tenancy
`Workspace` + members (`owner` / `admin` / `editor` / `viewer`) + email invites; workspaces nest (owners of a parent own the children). Gates use `apps/workspaces/permissions.py` (`docs/architecture/roles.md`).
- `POST /api/workspaces/` create · `GET /api/workspaces/` list mine · `GET /api/workspaces/{slug}/` (member) · `DELETE /api/workspaces/{slug}/` (owner; only an empty workspace — never one that still owns agents).
- `PUT /api/workspaces/{slug}/parent` — move in the tree (`parent: null` = root). Owner of both the moved workspace and the new parent; a cycle is 422. Someone who owns it only through its parent gets 409 making it a root, or moving it where a current owner would lose it.
- `GET /api/workspaces/{slug}/members/` (member) — includes parent-workspace owners with `inherited: true` (changed on the parent).
- `POST /api/workspaces/{slug}/members/` `{user_id, role}` → 201 `MemberOut` — add someone ALREADY in this workspace's tree, directly, no invite (admin or owner; a role you may grant, else 403). The person must be a member, directly or by inheritance, of a workspace the caller is in under the same root, else 404 — never an arbitrary user id; 409 if they already hold a direct row here (PATCH instead) (`services.add_tree_member`).
- `GET /api/workspaces/{slug}/member-tree` (member) — `{root, workspaces: [{slug, display_name, parent, depth, my_role, can_manage}], people: [{user_id, email, cells: {slug: {role, inherited, inherited_from}}}]}`: `slug` and the workspaces below it the caller is in (`services.subtree`), in tree order, and everyone in any of them from `services.effective_memberships` (a missing slug = not a member). The page `/w/:ws/settings/member-tree`.
- `PATCH|DELETE /api/workspaces/{slug}/members/{user_id}/` — change role / remove (admin or owner; an admin manages only roles strictly below its own). Role change is idempotent; demoting or removing the last owner is 400 (`services.is_last_owner`).
- `POST /api/workspaces/{slug}/invites/` (admin or owner) — emails the accept link through SES (`apps/common/email.py`); `email_status` (`sent` / `throttled` / `not_configured` / `failed`) says whether it went out, and the link in `token` works either way. Inviting an address with an outstanding invite returns that invite and re-sends, at most once a minute (its token is unchanged).
- `GET /api/workspaces/{slug}/invites/` (member) — `token` is filled only for owners.
- `POST /api/workspaces/{slug}/invites/{invite_id}/revoke` (admin or owner).
- `POST /api/workspaces/{slug}/invites/{invite_id}/reissue` (admin or owner) — new token + fresh 14-day expiry, emailed; the old link dies. Works on an expired invite; 410 on accepted/revoked; 429 if emailed under a minute ago (checked before rotating).
- `GET /api/workspaces/invites/{token}/preview` — `auth=None`, minimal disclosure (a dead token reveals only that it is dead). Drives `/invite/:token`. `POST /api/workspaces/invites/{token}/accept` — accept. An invite's address matches the signed-in email by `invites.mailbox_key`: case-insensitive, and a Gmail address under any dot spelling (Google signs a person in under the spelling the account was created with); never plus-addressing or other providers' dots.
- `GET /api/workspaces/invites/mine` (signed in) — your own live invites with their links, newest first; Home lists them. Listing joins nothing.
- **Access requests** (`docs/architecture/access.md` → "Getting into a workspace"; nothing joins automatically): `GET /api/workspaces/requestable` — workspaces whose server-only `access_request_domains` include the caller's email domain and they are not in, with their open request. `POST /api/workspaces/{slug}/access-requests` (`{note?}`) — emails every admin/owner; idempotent while pending (200); with `auto_approve_role` set it is approved at once; nonexistent and not-your-domain are the same 404; 409 if already a member. `GET …/access-requests[/{id}]` (admin or owner; `?status=`). `POST …/{id}/approve` (`{role}`: viewer/editor/admin, below your own unless owner → else 403) · `POST …/{id}/deny` (`{reason}`); both 409 once decided and email the requester. `PUT /api/workspaces/{slug}/access-settings` (owner) — `auto_approve_role` `""` / `viewer` / `editor`.
- `GET|PUT /api/workspaces/{slug}/runner-order` — the workspace's default runner order (index = rank): routes agentless repo turns, and is the default of every agent here, and every workspace below, with no order of its own (`harness.routing.inherited_orders`). Read: member. Write: admin or owner (`runners.route`); each runner must be able to serve this workspace, else 422 (as for unknown/retired). See `docs/architecture/runners.md`.
- `GET /api/workspaces/{slug}/runner-topology` — admin+ (`logs.read`), checked on every descendant too. This workspace and its descendants in tree order: agents, every `RunnerAssignment` row (default list + rules), and the runners named or living in the tree; `can_claim: false` on a route means the runner's owner is not in the agent's workspace, or the runner is directed-only (its row carries `directed: true`; an agent following an order that lists it names it in `follows.directed`). Computed (`apps/harness/topology.py`). UI: Settings → Topology (map + `/topology/runners`).
- `GET /api/workspaces/{slug}/health` — same gate. Every workspace in the tree (depth, shared vault + where it is inherited from) and every agent: owner, `can_fix` (`Agent.is_admin`), properties, `vault` (`vault_health`: per-ref stored/literal/local/missing, `machines_waiting`), `steps` (exactly `setup_steps`), `left`, sessions, projects and tasks; `runners` (the runner topology's rows, with `code_current` and `problems`); totals. `?setup=false` leaves `vault`, `steps`, `left` and the totals counted from them null; `GET …/health/setup?agents=a,b` (≤25, tree agents only) returns just those. `apps/agents/health.py`. UI: `/w/:ws/health`.
- `GET /api/workspaces/{slug}/analytics?days=30&tree=true` — same gate. Daily series, totals, per-agent, per-repository and per-person tables (one aggregation), no cost, over `Activity` + `TurnUsage` only (`apps/events/analytics.py`, `docs/architecture/analytics.md`). UI: `/w/:ws/analytics`.
- `GET /api/workspaces/{slug}/network?days=30&tree=true` — same gate. People, contacts and agents linked to the threads they wrote in (a chat, a bound Slack thread being one, or an email thread), each thread to its answering agent; a chat's title only where the session ACL lets the caller open it; at most `analytics.MAX_THREADS` threads, shared ones first (`analytics.network`, `docs/architecture/analytics.md` § Network). UI: `/w/:ws/network`.
- `GET /api/harness/runners/{id}/usage-scope` · `POST …/usage` (the runner) — the box's usage report: the repos it scans, and per Claude session per UTC day tokens, no content (`apps/events/usage.py`); a session canopy has no record of is dropped. canopy never asks a box for a session it was not sent.
- `PUT /api/harness/runners/{id}/slash-commands` (the runner) — the slash commands its sessions can run, `{commands: [{name, description, args_hint, source}]}`, replacing what was held; sent when the list changes (`canopy_runner/slash_commands.py`). Held on `Runner.slash_commands`, off `RunnerOut`.
- `GET /api/workspaces/{slug}/agent-topology` — same gate. For each ordered agent pair, what the first gets sending the second work with its own login: `access` full/confined/none, `basis` (owner, workspace-owner, admin, full-rule, no-interface, capabilities, nothing-offered, not-member, no-login), the capabilities when confined, `can_grant`/`can_revoke` for this caller; `full_people` per agent. Decided by the predicates a real turn uses. Grant via `PUT /api/agents/{slug}/admins/{user_id}` with the sender's login. UI: `/topology/agents`.
- `GET /api/workspaces/{slug}/retention` (member) · `GET …/retention/preview` (counts only, deletes nothing) · `POST …/retention/rules` · `PUT|DELETE …/retention/rules/{rule_id}` (`retention.manage`, admin+) — content retention rules incl. inherited ones; blank filters match anything, `keep_days` null = forever; 422 on a duplicate filter set or an agent outside the workspace. See [tenancy.md § Content retention](tenancy.md#content-retention-appsretention).
- `GET /api/workspaces/{slug}/admission-rules` (member) · `POST …` · `PATCH|DELETE …/admission-rules/{rule_id}` (`admission.manage`, admin+) — which turns this workspace refuses before they run, with fire counts. At least one condition per rule; an `allow` beats every `reject`; PATCH changes only the sent fields (incl. on/off); a deleted seeded default is not re-seeded. `PUT …/admission-settings` `{sender_notices_enabled}` (`admission.manage`) — whether a rule's automatic reply to a rejected sender is sent (off: recorded, not sent). See `docs/architecture/access.md` → "Admission rules".

Each row carries `live_probe` (`{at, ok, step, step_label, reason}`) and `traffic` (`{last_redeemed_at, last_site_call_at, refusals_24h}`).

The credential is `Authorization: Bearer <JWT>` signed by the site's own registered key (`assertions.keys_for_app`): `typ` `canopy-site-agents-request+jwt`, `iss` = `sub` = its Connected-site name (resolved by `embed_apps.resolve_site`: a signed `canopy_workspace` — the workspace slug — selects the tenant, or failing that a signed `canopy_agent`'s workspace; both must agree, else 409 `workspace_mismatch`; neither, between tenants sharing the name, 409 `ambiguous_issuer`), `aud` = the endpoint URL under canopy's identity or public base, ≤ 60 s, single-use `jti`. Refusals 401 (`unknown_issuer`, `bad_signature`, `replayed`, `wrong_audience`, `bad_typ`, …), rate-limited per client and per site. Answer `application/jose`: a compact JWS signed with canopy's client key (`typ` `canopy-site-agents+jwt`, `kid` in `/oauth/jwks.json`), payload `v`, `iss` (client_id), `aud` (site name), `iat`/`exp` (15 min), `version` (sha256 of the canonical `site`+`runner_flags`+`agents`), `site {name, tenant, settings_url}` (`settings_url` = the site's card on the Connected sites page, `…/settings/connected-apps#site-<id>`), `runner_flags [{flag, meaning}]`, `agents`: the site's `AppCredentialAgent`s in its own workspace, each with the capabilities naming the site in `sites:` (`handles_sensitive` = `data: sensitive`, `sensitive_set_by`/`sensitive_set_at` = the interface's last publisher, as `Canopy-Execution` states it), `runners {flags_available, ready_with}` (from `setup.runner_takers`, flags in force), `ready` (a capability for the site AND a runner ready now; no GitHub token is needed — a site turn is confined), `problems` (sentences naming where to fix it) and `problem_links` (`[{text, url}]`, the same sentences each with the URL that fixes it). Verified by `canopy_sdk.site_agents.fetch_site_agents`.
- `POST /api/sites/resources-updated` — **a connected site says some of its resources changed** (`apps/host_grants/api.py`, checks in `resources_updated.py`; `auth=None`, gate `host`, kind `action`; not an MCP tool). The credential is `Authorization: Bearer <JWT>` signed by the site's own registered key, resolved exactly as `GET /api/sites/agents`: `typ` `canopy-resources-updated+jwt`, `iss` = `sub` = the site's name, `aud` = this endpoint's URL, ≤ 60 s, single-use `jti`, and `uris` (1–50 resource URIs). The body is ignored. Every View subscribed (`…/apps/{tool_call_id}/subscribe`) to one of those URIs on THIS site gets the socket frame `app.resource_updated` — the URI and its call id, never data; each View re-reads as its viewer. Answer `{notified}`. Refusals 401 (`unknown_issuer`, `bad_signature`, `replayed`, `wrong_audience`, `bad_typ`, …), 400 (`malformed`), 429 (per client, per site). Built and sent by `canopy_sdk.resources.notify_updated`.
- `POST /api/sites/sign-offs` · `GET /api/sites/sign-offs/{id}` — **site sign-offs: a connected site asks a person to approve one action with their passkey** (`apps/host_grants/sign_offs_api.py`, rules in `sign_offs.py`, row `tokens.SiteSignOff`; `auth=None`, gate `host`, the ask kind `request`; spec `docs/superpowers/specs/2026-10-27-site-sign-offs-design.md`). Signed by the site's own key, resolved exactly as `GET /api/sites/agents`: `typ` `canopy-sign-off-request+jwt`, `aud` = the exact URL, ≤ 60 s, single-use `jti`; the ask carries `sign_off_request {subject, action {key, title, detail}, site_ref, return_url}`. `return_url` must be https on an origin the site registered (frame origins or JWKS URL), else 422 `bad_return_url`. Built and checked by `canopy_sdk.sign_offs`.
- `GET /api/sign-offs/{id}` · `POST /api/sign-offs/{id}/approve` · `POST /api/sign-offs/{id}/decline` — **the approver's side** (gate `sign-off-approver`, `sign_offs.may_approve`, asked again at every call; anyone else 404). Approve is a setting, needs a browser, a person and a passkey step-up (a token is 403), and answers the row plus `redirect_url` (the site's `return_url` with `?sign_off=<jws>&id=`); decline answers `redirect_url` with `?declined=`. A decided or expired request is 409 `closed`. Open requests are on their approvers' Home (`apps/host_grants/attention.py`).

The frame's delegated token, and only the frame of the site that asked (another site's frame, or a PAT, is 404/403); the person is `sign_offs.may_approve` as above. Approve is a WebAuthn assertion with one of the person's passkeys made in the frame (`begin` an ephemeral credential, slot per request and person; `finish` a setting), as the panel's act-as-you confirm: the token is the site's, the assertion over canopy's origin is the person's. Answers the row only, never the approval: the site reads that with `GET /api/sites/sign-offs/{id}`. 409 `closed` / `no_passkey`.
- `GET /api/workspaces/{slug}/connected-apps/{id}/needs` — what the site asks of agents (its signed `site.json`, read beside its `jwks.json` by `apps/host_grants/site_needs.py`: pinned/bounded fetch, verified with the site's keys, cached 10 min, last good shown `stale` for 24 h, else `available: false` + `reason`) and, per allowed agent, `{url, offered, sensitive_data, ready, can_handle_sensitive_data, why_not}` computed from the same `site_agents_content` the site reads — `sensitive_data` is whether the site lets the agent work with its sensitive data; `can_handle_sensitive_data` is `null` when it does not (nothing to meet, no reasons), else whether the agent meets the site's `sensitive_data.requires` and is ready, with `why_not: [{text, url}]` (no capability for the site says `data: sensitive`, no ready runner with the flag, or the agent's other problems, each with the canopy page that fixes it). `pages` (+ scopes) is the site's own description, shown for reference only — canopy neither enforces it nor tells an agent; `not_allowed` = agents the site names that this workspace does not allow on it. Gate `integrations`.
- `GET /api/workspaces/{slug}/connected-apps/discover?address=&app_id=` — **Fill from the site** (`apps/host_grants/api.py`, logic `site_needs.discover`; gate `own`, read-only). Finds the site's signed `site.json` from `address` (the document's URL, its JWKS URL, or just the site's address: `…/site.json`, `/.well-known/canopy-site.json`, `…/canopy/site.json`) or, with `app_id`, beside the site's keys / at its first origin; fetched fresh (pinned, https, public addresses, no redirects). Verified with the site's registered keys (`signed_by: registered_keys`) or the keys at the `jwks_url` the document declares (`published_keys`; `registered_keys_verify: false` when registered ones exist and do not verify it); `iss` must be the site's name for `app_id`. Returns `{url, tried, name, site: {origins, jwks_url, issuer, mcp_resource}, signed_by, registered_keys_verify, current, changes}` (`current`/`changes` for `app_id`). 422 with `unreachable`, `no_facts` (no `site` block: SDK < 0.16), `bad_signature`, `bad_issuer`, `keys_unreachable`, `malformed`, `no_address`. Never writes: the owner adopts the values through `POST`/`PATCH …/connected-apps` (audited).
- `POST /api/auth/contact-token` resolves the site the same way: the assertion's signed `canopy_workspace` selects the tenant (409 `workspace_mismatch` if `agent_slug` is not one of its agents; 400 `bad_workspace` for a malformed claim), else `agent_slug`'s workspace. The embed shell `/embed/chat` takes `?workspace=` beside `?agent=` (any refusal a 404).
- `POST /api/workspaces/{slug}/connected-apps/{id}/test` — **Test connection** (owner; another tenant's site 404s). From canopy's server, returns `{ok, checks: [{name, label, status: pass|fail|skip, detail}], live_probe, live_probe_ok}`: the JWKS (`check_jwks`: reachable, public-only, asymmetric, thumbprint `kid`; RSA only for an assertion-only site) and pasted PEM key types; for a host-grant site, RFC 8414 + 9728 discovery (`check_metadata`) and `check_client` (jwt-bearer with canopy's real client assertion + DPoP and an ID-JAG from a throwaway key: `invalid_grant` = host authenticated canopy, `invalid_client` = it does not accept canopy, 200 = it accepted a grant it never signed). Then the **live probe** (`apps/host_grants/live_probe.py`), folded into `ok`: the host's `canopy_probe_endpoint` signs a real ID-JAG for its probe principal; canopy redeems via `host_grants.redeem` and calls via `host_gateway` — the probe tool succeeds, an out-of-scope tool is refused by the host, and no proof / a stranger's proof / plain bearer are refused. No probe identity → `live_probe_ok: null`. All fetches via `outbound.py`.

### Personal Access Tokens (`apps/tokens`)
- `GET /api/tokens/` — my tokens (no raw values; OAuth-minted tokens omitted), each with `last_used_at` and `last_used_client` (the User-Agent of its last REST call or socket — a runner sends its host). Send `Authorization: Bearer <raw>`; `apps.tokens.middleware.BearerTokenAuthMiddleware` resolves it to `request.user`. Bootstrap: `uv run python manage.py create_token --email <email> --label "<label>" --create-user`.
- `GET /api/me/delegated-credentials/` — the credentials from my own accounts I delegated to agents: agent, provider and account, which machines can open each (only those), what the provider said, whether it is in force (I am still the agent's admin). Never the value. By person, not per organisation, like a token. `DELETE /api/me/delegated-credentials/{id}` — withdraw it from the agent's vault (mine only; audited as a setting). See [vault.md § Whose account an entry is](vault.md#whose-account-an-entry-is).
- `GET /api/me/host-grants/` — my live act-as-you permissions (host grants), one row per page (`host_grants.live_for`): site, agent, scope, until. By person, not per organisation: it is my own credential, like a token, and a site in a workspace I am not in can hold one for me. `DELETE /api/me/host-grants/{id}` — stop that page's permission at once (mine only; 404 otherwise; audited as a setting). `GET /api/me/host-grants/{id}` — one of my unexpired permissions, confirmed or still waiting. `POST /api/me/host-grants/{id}/confirm/begin` · `…/confirm/finish` — confirm a page's waiting permission in my browser, for a panel whose frame cannot use a passkey (the Runner app opens `/confirm/page-permission/<id>`): the same confirm as the panel's (`grants_api._confirm`), on my own browser session (a token or token-minted session → 403 `browser_session_required`; another person's grant → 404); the panel sees it on its next read. Mechanics: [embedding-internals.md § Act-as-you permissions](embedding-internals.md#act-as-you-permissions-host-grants-when-which-and-stop).
- `/api/me/act-as-requests/` — an agent acting as the person who started its turn, on canopy-web (`apps/harness/api_act_as.py`; [access.md § Acting as the person on canopy-web](access.md#acting-as-the-person-on-canopy-web-act-as-you-in-your-own-turn)). **The agent**, with its turn's own login (a session-scoped one on a laptop): `POST` `{reason (≤500), scope: read|write|either}` → 201 `{id, status: "pending", approve_url, expires_at}` (the request lapses at `expires_at`, 30 minutes, surviving the turn while its conversation is the person's; 403 saying why when the turn has no eligible asker or a stored token asks; 409 while one from this conversation, or this turn outside one, waits); `GET …/{id}` → `{id, status: pending|approved|declined|expired|stopped, scope (read|write once approved), expires_at (pending: the request's deadline; approved: the permission's end), …}` plus `token` in the FIRST agent read of a live approval only (hash stored; later reads omit it). The login that asked, or any later turn login of the same agent in the same conversation for the same person, reads it — 404 otherwise; `GET /api/me/act-as-requests/` with a turn login lists that agent's waiting and live requests in this conversation (no tokens); `POST …/{id}/stop`. **The person**: `GET /api/me/act-as-requests/` (waiting and live, with the reason), `GET …/{id}`, `POST …/{id}/approve/begin` + `…/approve/finish` `{credential, scope: read|write}` (a WebAuthn assertion begun for this request; browser only, every token refused; 409 when it is no longer pending), `POST …/{id}/decline` (browser only), `POST …/{id}/stop`. The `cact_` token then signs in as the person on REST and MCP for 30 minutes from the touch while the turn runs or its conversation is still the person's, `read` → GET routes only, never the routes `act_as.EXCLUDED_*` lists; every request is a call-log row (`acting_agent`, `act_as_grant`).
- `GET /api/tokens/github` — my GitHub App connection (never calls GitHub). `DELETE /api/tokens/github` — forget my grant (canopy's copy only; idempotent 204). `GET /api/tokens/github/installations` — live list of accounts/orgs the app is installed on (the create-agent owner picker); 409 when the grant is unusable (reconnect).

### Passkeys + step-up (`apps/passkeys`, mounted at `/api/passkeys`)
WebAuthn (py_webauthn) passkeys as a SECOND factor, never a sign-in. Every route touches only the caller's own passkeys; every ceremony needs a person at a browser (a token, MCP call or token-minted session gets 403 `browser_session_required`). RP id = the browser's host unless `PASSKEY_RP_ID`/`PASSKEY_ORIGINS` pin it.
- `GET /api/passkeys/` — my passkeys (label, created, last used, synced or device-bound). `DELETE /api/passkeys/{id}` — needs a fresh step-up.
- `POST /api/passkeys/register/begin` → `{options}` for `navigator.credentials.create()`; `POST …/register/finish {credential, label}` → 201. The FIRST passkey needs only a signed-in session (bootstrap); a second needs a step-up with one already held. Registration requires user verification and opens a step-up window.
- `GET /api/passkeys/step-up` — `{active, until, has_passkey, browser, window_seconds}`. `POST …/step-up/begin` → `{options}` for `navigator.credentials.get()` (409 `no_passkey` when none); `POST …/step-up/finish {credential}` verifies against one of the CALLER's passkeys and sets the session's step-up for 5 minutes.
- **The gate other routes use:** `apps.passkeys.stepup.require_recent_step_up(request)` → 403 problem+json with top-level `error: "step_up_required"`, `has_passkey`, `register_url`; the SPA's API client answers it with a passkey prompt and retries (`frontend/src/auth/stepUp.ts`). Each route that needs it says so, twice: it calls the gate after its own 404/403 checks, and its `@gate(..., step_up=True)` declares it. A route whose request or response carries a secret-named field (`SECRET_FIELDS` in `tests/test_every_route_declares_its_gate.py`) must declare `step_up=True` or `step_up="<why not>"` (runner protocol, a credential shown once to its creator, ciphertext only…), and CI checks the declaration against the view's code.

### Agents (`apps/agents`) — first-class AI-agent workspace
An `Agent` is an instance row (its definition is the repo): status reports (syncs), skill catalog, packaged turns. **Tasks and projects are the workspace's** (`docs/architecture/work.md`): a task is named by its key (`DIM-142`) and assigned to a person or an agent; a project is addressed `<workspace>/<handle>`, led by a person and/or a lead agent, and worked on by member agents. Person-to-task moves go through one actions route; field changes are a plain PATCH. Roles and access: `docs/architecture/access.md`.

- **Knowledge-base versions and sources** (`apps/agents/kb_api.py`, `kb_versions.py`; engine `canopy_kb.curate`). A KB is a version log of whole files (`KbVersion`: full | rollback; `delta` survives only on versions made before #1971). canopy-web never builds an index: the steward builds kb.sqlite on its own machine (`canopy_kb.curate`, `canopy kb push`) and publishes it whole (#1971: the in-process delta build ran the web task out of memory). Each version carries the curation state it was built from (`curation_sha`, a root in the steward's results store), and a refresh starts from the head version's: it decides on its own that nothing changed (nothing built, sent or saved), else applies the difference to the served file (`GET …/kb/file`), builds, and publishes the whole file, `…/kb/upload` then `…/kb/publish {key, sha256, base, curation, changes?}`, which records a FULL version made from version `base` (409 when another landed since: one refresh wins; `changes` counts content changes for the log). `GET …/kb/versions` (member) is the log; `POST …/kb/versions/{n}/rollback` serves version n's file and state again as a new ROLLBACK version (only the newest `KEEP_FILES` versions keep their file: `can_roll_back`). `GET …/kb/file` (member) is a 15-minute download of the served file (`canopy kb pull`). The `whats_new` tool reads the file's own history (`changes`: its builder records only documents whose content changed). ### A2A Agent Cards (`apps/agents/a2a_api.py`, mounted at `/api/a2a`) — discovery only
Each agent's [A2A v1.0](https://a2a-protocol.org/latest/specification/) Agent Card, generated from its declared interface (`apps/agents/agent_card.py`). A card grants nothing — turns are authorized at enqueue. `/api/a2a/` is public in the login middleware; each route self-enforces.
- `GET /api/a2a/agents/{slug}/.well-known/agent-card.json` — `auth=None`. Exists only for an agent offering a capability to a `contact` or `unknown` caller class; every other case (no interface, member-only, outsiders only via `full:`, no such agent) is the same 404. `skills[]` = the outsider capabilities.
- `GET /api/a2a/agents/{slug}/extendedAgentCard` — session or PAT (a contact token → 401). Public skills plus what the caller may invoke (`interface.offered_to`); 404 when that is nothing.
- **Paths:** one card per agent, base `{CANOPY_PUBLIC_BASE_URL}/api/a2a/agents/{slug}` (A2A's well-known URI is one card per origin, and canopy is many agents on one origin); no host-level card, no catalog.
- **Mapping:** `skills[].id` = capability name, `name` humanised, `description` (fallback `Ask <agent> (<name>).`), `tags` from caller classes (`caller:<member|contact|unknown>`, `domain:<d>`, `verified-sender`; public card tags outsider classes only; unlisted capability = `caller:admin`); Never emitted: `tools`, `bash`, `read_paths`, `entry`, `pages`, `input` field names, `full:` rules, the workspace. `securitySchemes`: `canopyPersonalAccessToken` (bearer PAT, extended card only — it invokes nothing), `canopyContactToken` (from `POST /api/auth/contact-token`, non-`:verified` contact skills under `/api/contact/`), `canopySession` (extended card only). `supportedInterfaces` are custom bindings by URI (canopy does not speak A2A messaging): `/api/contact/sessions`, `mailto:<agent mailbox>`. No MCP door: canopy's MCP server does not run agents — a member uses an agent by installing its plugin (`/get-started`), so a member-only skill carries no `securityRequirements`. `version` = `1.0.<interface_published_at epoch>`; `capabilities` = `{streaming: false, pushNotifications: false, extendedAgentCard: true}`; `provider` from `CANOPY_A2A_PROVIDER_{ORGANIZATION,URL}`.
- **Caching:** strong `ETag` + `If-None-Match` → 304. Public `Cache-Control: public, max-age=300`; extended `private, max-age=60`, `Vary: Authorization, Cookie`.
- **Unsigned:** cards carry no JWS `signatures[]`; canopy has no card-signing key.

### Harness (`apps/harness`, mounted at `/api/harness`) — runner registry + turn lifecycle
The agent-execution control plane: paired `Runner`s (laptop emdash daemons, cloud boxes) heartbeat and claim queued `Turn`s; a `Turn` is one unit of agent work with an append-only `TurnEvent` ledger. How a turn reaches a box — tenant gate, which agents a box may hold, the claim, `RunnerAssignment` lists and rules, the workspace default order, flags, schedules, the per-turn GitHub identity — is owned by [`runners.md`](runners.md); runner roles by [`access.md`](access.md) → "Runner roles". Spec: `docs/superpowers/specs/2026-07-05-agent-execution-control-plane-design.md`.

**Gates (three tiers, all 404 rather than 403).** *See* (`_runner_read_q`): runners homed in, or serving (`runner_tenant_slugs`, the claim gate), the caller's tenants, regardless of who paired them — so a turn can be pinned to any box claim would give it; a runner with no workspace is visible only to its owner. *Act as* (`_runner_or_404`): the runner's owner — everything that speaks FOR the box (heartbeat, claim, reports, its own credential fetch, its half of a mint). *Administer* (`_runner_admin_or_404`): the owner or a `RunnerAdmin` — credentials, browser sign-in, enrollments, flags, engine, refresh, starting drills. `RunnerOut.can_manage` / `can_administer` tell each caller which listed rows it may act on / administer. Retired runners 404 everywhere except `unretire`.

**Runner device keys** (Canopy Vault; `apps/harness/api_device_keys.py`, `apps/harness/device_keys.py`) — all runner-admin (owner or `RunnerAdmin`), 404 otherwise.
- `POST /api/runner-device-keys/` `{runner, public_jwk, kind: secure-enclave|tpm|software, label}` → `{id, jkt, status: "pending", approve_url}` (201; the same RFC 7638 `jkt` again → 200 with the existing row, whatever its status; a `jkt` on another runner → 409; a non-P-256 or private JWK → 422).
- An EC2 cloud runner registers its instance ROLE instead: `POST /api/runner-device-keys/` `{runner, kind: "aws-iam", role_arn, proof, label}` — `proof` is an `X-Canopy-Aws-Proof` value (below) whose htu is this URL; STS must answer with `role_arn` (422 otherwise). Stored as the canonical, path-free `arn:aws:iam::<acct>:role/<name>`, `jkt` = sha256 hex of it, `public_jwk` empty; approved and revoked like any key.
- `POST /api/runner-sessions/` `{runner}` — a box signs in as itself (`apps/harness/api_runner_sessions.py`, `auth=None`): an `X-Canopy-Aws-Proof` or `DPoP` proof for this URL from an ACTIVE device key of that runner → 201 `{access_token, expires_at, runner}`. The token (`crt_…`, `RunnerAccessToken`) lasts an hour, authenticates as the runner's owner, and opens only the runner protocol (`apps/harness/runner_auth.py`: its own `/api/harness/runners/<id>/…`, the owner's runner list, `/api/harness/turns…`, schedule list + fire, agent roster/detail/resolve reads, its agents' mailboxes (`/api/inbound/runner-mailboxes`, `POST /api/inbound/watch`), `/api/workspaces` GET, `/api/runner-device-keys`, `GET /api/harness/runner-releases/current`, `POST /api/events`, its own `ws/runner/<id>/`) — 403 elsewhere. It dies at once when the key is revoked, the runner retired or the owner deactivated. Every refusal is the same 401.
- `GET /api/runner-device-keys/?runner=<id>` — keys with status (no `runner` = every runner the caller administers); rows carry `role_arn` for `aws-iam`.
- `POST /api/runner-device-key-requests/` — `auth=None`: a runner whose token was revoked (within 30 days) proves a token of the runner's owner and the key being registered → a PENDING key and its `approve_url`; the owner is emailed and pushed the link. Every refusal is the same 401.
- `POST /api/runner-device-keys/{id}/approve` — `pending` → `active`; **browser session only** (a token is 403), behind a passkey step-up; a revoked key → 409.
- `POST /api/harness/runner-invitations/` `{name, workspace, role_arn, ecdh_public_jwk?}` — invite one new cloud box (what `runner/ec2/up.sh` calls). Non-member → 404, no `agent.work` there → 403, a name that is not a runner name or an ARN that is not an IAM role → 422. → 201 `{id, name, workspace, role_arn, status: "pending", approve_url, expires_at, runner_id: null, …}`; an hour long; your own live one for the same role and name is replaced (and anyone's expired one), but someone else's live one → 409, naming nobody (concurrent creates → 409 too). The creator is mailed and pushed `approve_url` (`/w/<ws>/runner-invitations/<id>`). Recorded as `runner.invited` activity.
- `GET /api/harness/runner-invitations/check?workspace=<slug>` — the create's gates without creating anything (404 not a member, 403 no `agent.work`) → `{workspace}`; `up.sh` asks it before any AWS write.
- `GET /api/harness/runner-invitations/{id}` — the creator only (else 404): `status` is `pending|approved|consumed|expired`, and `runner_id` once consumed.
- `POST /api/harness/runner-invitations/{id}/approve` — the creator only, **browser session + passkey step-up** (a token is 403); expired or used → 409; again → no-op. Recorded as `runner.invitation.approved`.
- `POST /api/harness/runners/pair-by-role` `{name, kind: "cloud", capabilities, host, proof, ecdh_public_jwk?, ecdh_store?}` — `auth=None`, public in `apps/common/middleware.py`: `proof` is an `X-Canopy-Aws-Proof` value for this URL. 201 `{status: "paired", runner_id}` (an approved invitation for that role and name: a new runner owned by its creator, in its workspace, with an ACTIVE aws-iam key); 200 `{status: "reattached", runner_id}` (that role's existing runner of that name); 202 `{status: "waiting"}` (not approved yet); every other case the same 401. Recorded as `runner.paired`. A role that is a **fleet's** joins instead (`fleets.join`): 201 `paired` for an instance EC2 says is pending/running in the fleet's group, named `<fleet>-<instance id>`, under an ACTIVE fleet; 200 `reattached` for that instance again; 202 `waiting` before the fleet's approval.
- **A machine running several runners** (`apps/harness/machine_pairing.py`): the invitation takes `runners: [{name, workspace, kind: "tree"|"agent", slug?, ecdh_public_jwk?}]` (each workspace passes the same gates; an agent's runner names an agent of its workspace; a name twice → 422) and returns them, each with its `runner_id` once paired. `pair-by-role` with `runners: [{name, public_jwk, ecdh_public_jwk?, ecdh_store?, capabilities, host}]` (`name` is then the box's): one runner per entry with an ACTIVE software key, in one transaction, under one approval → 201 `{status: "paired", runners: {name: runner_id}, device_keys: {name: key_id}}`; every entry already a live runner on this machine → 200 `reattached`, each key replaced in place (runner ids, bindings and wraps kept); a runner the invitation does not list, an invited runner the box did not bring, a creator without `agent.work` in any runner's workspace, a revoked runner key, a name live on another machine → the same 401, nothing made.
- **Laptop pairing by browser** (`apps/harness/api_runner_pairings.py`) — what a downloaded Canopy Runner does; no PAT at any point:
  - `POST /api/harness/runner-pairings/` `{public_jwk, kind: secure-enclave|tpm|software, ecdh_public_jwk?, ecdh_store?, hostname, account, platform: macos|windows|linux, has_emdash, emdash_cdp_live?, redirect_port: 1024–65535}` — `auth=None` (public in `apps/common/middleware.py`, POST only), with a `DPoP` proof for this URL by the key in `public_jwk`. → 201 `{id, user_code: "ABCD-EFGH", verify_url: "<CANOPY_PUBLIC_BASE_URL>/pair/<code>", expires_at (15 min), interval: 3}`; a key that is an ACTIVE key of a non-retired runner → 200 `{status: "reattached", runner_id, name, workspace, device_key_id}`, nothing made. One live pairing per key (a new one replaces it). A proof by another key, or a key canopy knows in any other state (pending, revoked, a retired runner's) → the same 401. A malformed body → 422.
  - `GET /api/harness/runner-pairings/{user_code}` — any signed-in person with the code (case and dash insensitive; unknown → 404): `{user_code, hostname, account, platform, kind, has_emdash, status: pending|approved|consumed|declined|expired, expires_at, suggested_name, workspaces: [{slug, name}], runner_id?}` — `workspaces` are the caller's with `agent.work`; `runner_id` only to the approver.
  - `POST /api/harness/runner-pairings/{user_code}/approve` `{workspace, name}` — **browser session + passkey step-up** (a token is 403); an agent's login → 403; not a member → 404, no `agent.work` there → 403; a name that is not a runner name → 422; a name the caller's own non-retired runner has → 409; used, declined or expired → 409. → `{status: "approved", redirect_url: "http://127.0.0.1:<port>/paired?pairing=<id>&secret=<raw>"}`. Not an MCP tool. `POST /api/harness/runners/{runner_id}/vault` — Administer tier (browser + step-up): the runner's own vault, made and attached (`docs/architecture/vault.md` § A runner's own vault). `PUT …/vault/values` — the box only, as resolve: `zk1:` values it sealed, for names on its list; each drops the stored copy. `POST …/vault/entries` — Administer tier: a token or API key whose value the browser seals into the vault (`{key, secret_name, vault_id, kv}`; 422 with no vault key).
- `PATCH /api/harness/runners/{runner_id}/credentials/{key}` (`{name}`; anything else, a `value` above all, is 422) · `DELETE …/credentials/{key}` · `PUT …/credentials/order` (`{keys}`) — Administer tier, settings. Rename one, remove any entry (422 for the last token or API key), or set the order (every key exactly once, else 422). A token or API key is added by signing it in or sealing it into the vault (`…/vault/entries`), never pasted here. The box uses the first that works; stepping onto an API key raises a coalesced `warn` event. Each returns the masked status. See `runners.md` § A cloud runner's Claude credentials.
- `POST /api/harness/runners/{runner_id}/logins` — Administer tier, settings. Add a full Claude login at the end of the list and start its sign-in. `DELETE …/logins/{key}` and `PUT …/logins/order` are the older names for the `credentials` routes.
- `GET /api/harness/runners/{runner_id}/credential` — Act-as. The list the box uses, with no value: `cascade` (every entry in order, a token's or key's `vault_secret` once a vault serving the runner holds it), `logins`, `vault_open`. No route takes a plaintext token or API key.
- `POST /api/harness/runners/{runner_id}/credential/swap` — Administer tier. Exchanges the first two tokens' places.
- `POST …/logins/report` (`{logins: [{key, signed_in, account}], adopt_default}`) — Act-as (the runner's half). Which listed logins the box holds and as whom; `adopt_default` adds a pre-existing default login at the front.
- `POST /api/harness/runners/{runner_id}/mint` (`{slot: box|token, login_key}`) · `GET …/mint` — Administer tier. Start (superseding any unfinished attempt) / read a browser sign-in: `box` signs in one of the box's logins (`login_key` "" = the default one), `token` makes a setup-token (`login_key` names the token to replace, "" adds one); 404 for an unknown key; `null` when none was ever started. canopy-web only relays — it never holds the PKCE verifier.
- `GET …/mint/claim` · `POST …/mint/url` · `POST …/mint/entry` · `POST …/mint/result` — Act-as (the runner's half). `claim` is polled and returns work only when the runner owes it; reading a code consumes it. `url` posts the URL a human must open. A `token` sign-in names its entry (`entry {vault_key}`), seals the token into the runner's vault, then reports `result {vault_key}` — done only if the vault holds it; with a `detail` it failed, and an entry made for it goes again. A token itself is never accepted (one sent fails the sign-in, unstored). A `box` sign-in reports `logged_in` + `account`, which marks that login signed in. 409 when no sign-in is in progress.
- `POST …/mint/code` — Administer tier. The human submits the single-use authorization code; 409 unless the runner is waiting for one, 422 if empty.
- `POST /api/harness/runners/{runner_id}/sign-in-request` — Act-as. The box started a device-code sign-in (AWS SSO) and pushes the approval link to the runner's owner. `reason` required (422). Returns `{sent, id}`: `sent` = devices reached (0 → fall back to another channel); `id` = the stored `SignInRequest`, kept until its code expires (~10 min) and shown on the owner's supervisor feed.
- `POST /api/harness/runners/{runner_id}/sign-in-requests/{request_id}/result` — Act-as. The box reports `outcome` (`approved` | `failed` | `expired`); clears the URL and takes it off the feed. First report wins.
- `GET /api/harness/sign-in-requests/mine` — Self. The caller's own open sign-in requests (runner, who, why, URL, expiry); expired rows are closed on read.
- `POST /api/harness/runners/{runner_id}/turns/{turn_id}/github-token` — Act-as, for a turn this runner is executing (else 404). The git identity of the GitHub token delegated to the turn's agent, and where it is: `delegated: "github-token"` and `agent` — the box opens it from its own resolve; no token (one still held the old way comes in `token`). 409 with the reason when none is delegated, its person is no longer an admin, or the turn is a caller's (confined) turn — no shared fallback. Re-checks that the box may still hold the agent. Each issue logged. See runners.md → "The GitHub identity a turn gets".
- `POST /api/harness/runners/{runner_id}/turns/{turn_id}/agent-token` — A canopy login as the turn's agent (`Agent.user`), for a turn this runner is executing (else 404); only with this runner's own runner token (a PAT, even its owner's, is 403). 409 with the reason for a direct turn, a confined (caller) turn, or an agent with no active login. Expires within 12 h; revoked when the turn stops executing on the runner. Each issue logged as a credential read. See runners.md → "The canopy login a turn gets".
- `GET /api/harness/runners/{runner_id}/turns/{turn_id}/attachments/{attachment_id}/content` — Act-as, for a turn this runner is executing. The bytes of any attachment already SENT in that turn's chat (earlier messages included; never another chat's, never an unsent draft), with the browser route's headers. Authorized by holding the turn, not by the box owner reading the chat — a teammate's chat is often invisible to the box's owner. Re-checks that the box may still hold the agent; every refusal is the same 404. In a sensitive conversation only a file THIS turn claimed, once: the bytes are deleted as they are served (`private_attachments.take_for_runner`), the name rides only in `Content-Disposition`, `Cache-Control: no-store`.
- `GET /api/harness/runners/{runner_id}/github-readiness` — Act-as. Per agent this runner serves: can it open a PR (a token held the old way is checked live against GitHub; a delegated one, by what the machines that open it last reported). Called at boot so a bad token is a red health check, not a mid-turn 403.
- `POST /api/harness/runners/{runner_id}/delegated-checks` — Runner. `{agent, name, checks, provider_expires_at, error}`: what this box found probing a credential delegated to an agent it runs (canopy-web cannot open one). A failed probe tells its person to replace it.
- `GET /api/harness/runners/{runner_id}/vault-keeper/slot-secrets` — Runner (a keeper). Pool-slot secrets sealed to one of this box's machines that a reader of the agent (a machine approved since, or a vault member) waits for, in the shape of `delegated`. `PUT …/vault-keeper/{slug}/slot-secrets/{capability}/{slot}/{key}` (`{value_zk, expect}`) stores the re-seal, refused for a recipient that is not one of the agent's readers, for dropping one that holds it, for a box with no copy, and when stale. capabilities.md §6.
- `PUT /api/harness/runners/{runner_id}/vault-keeper/{slug}/delegated/{name}` — Runner (a keeper). `{value_zk, expect}`: a delegated credential this box holds, re-sealed for a machine that was waiting (listed in `GET …/vault-keeper` → `delegated`). Refused for any recipient that is not a machine that runs the agent or its person, for dropping one that holds it, and when stale.
- `GET /api/harness/runners/{runner_id}/agents` — Act-as. The slugs of the agents this runner runs (`routing.agents_routed_to`: the claim's own static gates — enabled routing, enrollment, the hold check). The box's credential refresh prepares only these.

**Claiming and running turns** (act-as)
- `POST /api/harness/runners/{runner_id}/claim` (`?paused=<slug,slug>` = locally paused agents to skip) — Claim the next eligible queued turn; 204 when none. Returns `ClaimedTurnOut`: the `TurnOut` (with `cli`, the agent CLI the claim chose) plus `cli_model`, the turn's credentials (`claiming.issue_credentials`, shared with the WS claim) and `caller_context`, the caller envelope (who asked, `verified` for THIS message, relationship, contact profile). Only the claim carries it. The runner writes it to `~/.canopy/caller/<turn_id>.json` and passes `--caller <path>` to a slash-command prompt; a chat prompt is never touched. A turn with a `capability` (a confined caller's turn) goes only to a runner reporting sufficient `profiles` and `envelope` versions — not bypassable by a pin; one nothing can confine appears in `/turns/unclaimable` with that reason. Claim order: runners.md → "The claim".
- `POST /api/harness/runners/{runner_id}/resolve-session` — For (agent or project+workspace, thread_key): can this runner reuse an existing emdash session, or must it spawn fresh and rehydrate. A project session needs the owner's membership of the named workspace (404).
- `POST /api/harness/runners/{runner_id}/record-session` — Upsert the durable link and point its live hint at this runner/host; returns the fresh resolution. With `turn_id`, the server names the session from the turn (email subject, schedule name). 404 for a session that is not this agent's or not in the owner's tenant.
- `POST /api/harness/turns/{turn_id}/start` · `/finish` (`done|failed|cancelled`, optional `session_key`, `result_note`) — Reporting gate: the owner of the box that claimed the turn; on an unclaimed turn, the same tier as cancelling it. `start` 409s unless claimed/running; `finish` is idempotent on a terminal turn.
- `GET|POST /api/harness/turns/{turn_id}/events` — Read (content-read gate, `?after=<seq>`, max 500) / append (reporting gate; 422 on an unknown kind) the turn's event ledger.
- `POST|GET /api/harness/turns/{turn_id}/transcript` — The retained raw transcript (`TurnTranscript`, gzipped, beside the ledger). POST (reporting gate) appends raw `claude -p` JSONL lines, idempotent per `batch_id`; 422 over 1 MB per request; past 100 MB per turn the content is dropped with a marker and `truncated: true` (never a 4xx); appending after finish is allowed. GET (content-read gate) streams plain NDJSON; a turn with none is an empty 200.
- `GET /api/harness/turns/{turn_id}/messages` — The transcript parsed into readable messages (user, assistant, tool use/result), secrets scrubbed, bounded (`truncated`). Content-read gate.

**Sessions the runner reports** (act-as; chat semantics in [`chat-sessions.md`](chat-sessions.md), menus in [`blocked-agent-menus.md`](blocked-agent-menus.md))
- `POST /api/harness/runners/{runner_id}/sessions` — Wholesale report of the box's open emdash sessions (`sessions`, `archived: [<task name>]`, `complete`). Stamps each binding's `live_seen_at` (the liveness clock, read against `SESSION_LIVE_WINDOW`) and `reported_at` (what `/close` branches on). `archived` retires a session immediately; absence from a `complete` report retires it too. A report never clears `RunnerBinding.runner` (durable identity, not liveness). A NEW session is filed under its project's agent (among agents in the runner's tenant; a project naming an agent outside it is not filed and counts in the reply's `skipped`), else the owner's default session workspace (when it is in the runner's tenant), else the runner's workspace; existing sessions are never re-filed. 404 if the runner has no workspace.
- `GET /api/harness/runners/{runner_id}/streams` · `POST …/session-stream` — Every session this runner backs, with the held index range (`first_index`/`last_index`) and `live` (a viewer is attached); the runner ships transcript rows, which are persisted as `Message` rows whether or not anyone watches, and fanned out live only when `live`. User rows are persisted but not live-pushed.
- `GET /api/harness/runners/{runner_id}/backfills` · `POST …/session-backfill` — Sessions a client asked to rebuild; the runner ships the whole transcript in chunks and the server writes `Message` rows once. Only the chunk marked `final` clears the request. 404 for a session not bound to this runner. Both runner kinds implement it.
- `GET /api/harness/runners/{runner_id}/closes` — Sessions this runner was asked to close (`close_requested`) and has not, each with the failure the server already holds (`close_error`); drained on the poll tick so a lost WS frame costs one tick.
- `POST /api/harness/runners/{runner_id}/kept-conversations` — `{session_ids}` → `{open}`: which of the sensitive conversations a sensitive-data box keeps a Claude session for are still open (exist, not archived, and this runner claimed a confined turn in them). The box forgets every other; a confined conversation has no binding, so `/closes` never names it.
- `POST /api/harness/runners/{runner_id}/close-results` — `{results: [{session_key, project, ok, error}]}`: what became of the runner's close attempts, from every path (the phone's close drained on the poll tick, and the menu bar's `canopy-runner close-sessions`, including sessions it skipped for having no project). A failure is stored on the binding (`RunnerBinding.close_error`/`close_error_at`, served as `SessionOut.close_error`, shown in Supervisor as "Close failed: <reason>" with a Retry); a success, a new close request, or the task no longer being reported clears it. Matched on (this runner, project, task name).
- `GET /api/harness/runners/{runner_id}/handoffs` — What this runner owes as the SOURCE of a transfer: `capture` (pack the session's worktree; `transcript` = include the Claude transcript) or `close` (the target restored it, or a late snapshot is held). Drained on the poll tick above the pause gate. `POST …/handoffs/{id}/archive` (`{part, parts, data}` base64 chunks, in order, ≤ 24 MB in all) · `POST …/captured` (`{ok, manifest, error}`; the archive must match `manifest.sha256`) · `POST …/close-result` (`{ok, error}`; a failure stays due and raises the `transfer_left_open` alert) — source only. `GET …/handoffs/{id}/archive` (the tar.gz) · `POST …/restored` (`{report}`) — the transfer's target, or the box the session is on now. Anything else is 404.
- `GET /api/harness/runners/{runner_id}/menu-answers` · `POST …/menu-answer-result` — Answers a person gave to a blocked-agent menu that this runner has not pressed (`RunnerBinding.pending_answer`), and the runner's report of what became of one. Matched on `answer_id`: a result for a superseded answer does not clear the newer one (`{ok: false}`).
- `POST /api/harness/runners/{runner_id}/session-subagents` — `{session_id, subagents}`: the whole set of one held session's subagent summaries (`canopy_transcript.summarize_subagents`), sent by either runner when it changes. Sets `RunnerBinding.subagents` (unknown keys dropped, at most 50, `description`/`last` blanked for a sensitive session) and sends `session.subagents` only on a change; `{ok: false}` for a session this runner does not hold.
- `POST /api/harness/runners/{runner_id}/session-menu` — `{session_id, menu}`: a cloud runner's dialog for one chat session it holds (an ACP AskUserQuestion or permission prompt), or `menu: null` once it is answered or gone. Sets `RunnerBinding.pending_question` and sends the same `session.menu` frame and once-per-ask push as a laptop's session report; `{ok: false}` for a session this runner does not hold. A finished (or lease-swept) chat turn clears an `acp` menu its box left.
- `POST /api/harness/runners/{runner_id}/admission-notices` (`{mailboxes}`) · `POST …/admission-notices/{notice_id}` (`{outcome, detail}`) — Sender notices for refused turns that canopy-web could not send itself, leased to this runner to send from mailboxes it reads, and its report back (`apps/admission/runner_notices.py`; access.md → "Admission rules").
- `GET /api/harness/sessions` — Open emdash sessions across every live runner the caller can see, newest first (the supervisor's Open Sessions). A connected site sees only its own agents'.

**Turns**
- `POST /api/harness/turns/` — Enqueue a turn (idempotent per `idempotency_key`; 201 new, 200 existing. A key is unique per WORKSPACE (`Turn.idempotency_scope`, the target's workspace), never globally, so another workspace holding the same key neither blocks nor reveals anything — it cannot pre-claim a guessable key (`sched:<id>:<slot>`, `task-<pk>-<i>`) of yours. Within the workspace a key replays only to the target it was made for: same agent, chat session, or project; a key held by another turn there is 409 `conflict`, saying nothing about that turn. The returned turn passes the same content gate as `GET …/turns/{id}`). Exactly one of `agent_slug` / `project` (422). Agent turns need editor (`agent.work`) on the agent; project turns need `agent.work` in the workspace (pinned `/api/w/{ws}/…`, else the sole membership — several memberships → 422). `origin` is the source vocabulary and a routing input: `api` · `ace_web` · `email` · `slack` may be posted; `canopy_web_chat` and `canopy_scheduler` are set only by their in-repo producers; legacy spellings (`board`/`manual`/`drill` → `api`, `cron` → `canopy_scheduler`) are normalized. An `email` turn may be posted only by an admin of the agent (the runner that read its mailbox) — 403 otherwise; it names its own asker from `origin_ref`. Optional `runner_id` pins the turn: 422 for a runner the caller cannot see or a retired one; 403 when the box cannot hold the agent, when the caller may not pin it (agent admins may pin any holdable box, others only boxes they administer), or for a project turn when the box does not declare the repo. Access (`access.decide`) and a requested `turn_mode` are checked up front (403/422, `auto` for admins only). Optional `cli` runs it on that agent CLI: one the agent is set up for, Claude Code for a project turn, else 422. A rule on a source nothing emits is inert.
- `GET /api/harness/turns/` — List turns (`?agent=`, `?status=a,b`, `?huddle=` = `origin_ref.huddle`, `?parent_turn=`, `?limit=` ≤ 200, default 100), redacted per `turn_access`. Tenant + site gate in `visible_turns_qs`, shared with the huddles API.
- `GET /api/harness/turns/{turn_id}` — Get a turn (redacted per `turn_access`).
- Every turn read carries `canopy_session_id` + `canopy_session_url`: the canopy conversation it ran in (a chat turn's own session; for an agent/project turn, the one its runner's record-session made — `Turn.canopy_session`, first write wins; null while queued). That id is what `POST /api/canopy-sessions/{id}/send` takes, so a dispatcher holding only a turn id can follow up in the same conversation. Not `session_id`, the runner's own live-session name.
- `GET /api/harness/turns/{turn_id}/caller-context` — The caller envelope for one turn (same document as the claim's; MCP twin `who_is_asking`). Content-read gate (`turn_access.can_read_turn_content`).
- `POST /api/harness/turns/{turn_id}/cancel` — Cancel a QUEUED turn (finished CANCELLED); idempotent on a terminal turn, 409 once claimed. Gate: editor on the agent; for a session turn, write access to the chat; for a project turn, its initiator or `agent.work`.
- `GET /api/harness/turns/unclaimable` — Queued turns no online runner can claim, with the reason; composed from the same routing predicates as the claim. A caller in two tenant trees must pin one (422).

**Readiness drills**
- `POST /api/harness/runners/{runner_id}/drill` (`{agents?}`) — Administer tier. Fan out a read-only doctor/preflight turn per agent, pinned to this runner; default = every agent assigned to it or following it via a workspace order, disabled assignment rows included (drill before enabling). A caller who is not the runner's owner must be an admin of each agent: the default fan-out narrows to those (422 if none), and naming another in `agents` is a 403 naming it. The starter is the turn's accountable person.
- `GET /api/harness/runners/{runner_id}/drills` — Per-agent drill grid (outcome, summary, timestamps). Runner administrators, or a workspace `logs.read` holder in the runner's tenant; else 404.
- `POST /api/harness/drills/{drill_id}/report` (`{outcome: pass|fail, summary}`) — The drilled agent's callback, accepted with the run's signed report link (`?t=`), from the agent's own login (`Agent.user`), or from the runner's owner. A drill turn that finishes without a report is marked `fail`, even if the turn ended `DONE`.

**Auto-debug** (`apps/harness/auto_debug.py`, mounted at `/api/harness/failure-investigations`)
- `GET /api/harness/failure-investigations/` (`?status=open|held|debugger_failed|pending_deploy|resolved|escalated`) · `GET …/{id}` · `POST …/{id}/resolve` (`{note, fix_commit?, fix_committed_at?, pr?, merged?}`) · `POST …/{id}/hand-off` (`{ask, to?}`) — A turn that really ends `failed` immediately raises a `turn_failure` alert assigned to `CANOPY_AUTO_DEBUG_AGENT` (`ada`; silent) and enqueues a turn to it running `/ada:debug-failure --investigation <id>` with the evidence: the result note, the runner's diagnostic delivery events and its `landed` verdict, and a snapshot of the failing runner (code sha vs expected, engine, each Claude login's probe, pause) — never a field that can carry a person's words. One `FailureInvestigation` per fingerprint (normalized result note); repeats only count; never two debug turns for one fingerprint inside 30 minutes. A failing debug turn marks it `debugger_failed` and spawns nothing. `resolve` closes the alert silently, or — with a `fix_commit` some runner it hit does not run — leaves it `pending_deploy` until every such runner runs it (closed on the alert tick). `hand-off` gives it to a person (default the debugger's owner) with a one-line ask — the one notification — and the debugger's own `resolve` then gets 409. A recurrence after a fix never starts a debug turn: on a runner without the fix it only counts; otherwise it goes to a person. Fleet-wide caps (`CANOPY_AUTO_DEBUG_MAX_PER_HOUR`=3 / `_PER_DAY`=10, rolling) mark overflow `held` (+ a warn event); the next allowed debug turn carries every held/debugger_failed one. Skipped: drills, a human's stop or delivery collision, turns outside the debugger's workspace tree, `CANOPY_AUTO_DEBUG=false`, no such agent; lease-expired `lost` turns only with `CANOPY_AUTO_DEBUG_LOST`. Readable/resolvable by the workspace's `logs.read` holders, the debugger's admins and its own login; else 404. A list needs one tenant tree.

**Recurring turns** — the runner half of scheduling (canopy-web also fires every due slot itself, `apps/harness/schedule_clock.py`; a runner's fire of the same slot collapses onto that turn); the CRUD is `/api/agents/{slug}/schedules/` (Agents). Semantics (the `fire_after` anchor, idempotent slots, grace release, nags): runners.md → "Scheduled turns".
- `GET /api/harness/schedules/?runner_id=…` — The cron triggers this runner may fire, tenant-scoped from `runner.owner` (never `capabilities`), act-as; not gated on the runner being online.
- `POST /api/harness/schedules/{id}/fire?runner_id=…` (`{slot}`) — Report a due slot; the server materializes the turn (201). 404 for a schedule this runner may not fire; 409 for a one-off fired at a slot other than its instant, or for a trigger whose creator lost the right to it (the slot is consumed).

The server's schedule clock and the runner both evaluate crons with the Django-free `canopy_cron` library (`packages/canopy_cron`, which owns the `croniter>=6.0,<7.0` bound); the server's `preview` endpoint calls the same `next_slots()` / `due_slot()`, so the UI, the server and the runner agree on slots.

> **Deleting a user strands their runners.** `Runner.owner` is `SET_NULL`, and a NULL owner has no tenant: every claim and schedule route returns nothing for that box, which can only be retired and re-paired. Deactivate a departing user (`is_active=False`) instead if their runners should keep working.

How the runner software is installed, updated and versioned (`expected_code_sha`), and what the cloud runner does each tick: [`runners.md`](runners.md) → "The runner software".

### Direct use (`apps/harness/api_local.py`) — a person's private runner and its direct turns

What and why: [`access.md`](access.md) → "Direct use of an agent".

- `POST /api/private-runners/` (`{name, host}`) — Register one of YOUR machines (201; 200 when that name exists — idempotent, and it revives a retired one). `GET /api/private-runners/` — yours. `POST /api/private-runners/{id}/retire`. Only ever the caller's own rows.
- `POST /api/harness/local-turns/` (`{agent, private_runner, claude_session_id, cwd, turn_mode}`) — Open the direct turn for a Claude Code session on your private runner: a RUNNING `origin=local` turn, never claimed or routed, with you as its initiator. 404 for a non-member or someone else's private runner; 403 when `access.decide` does not give you the whole agent. `turn_mode: auto` is honoured only for an agent admin. Idempotent per Claude session while the turn is live (200); a session whose turn ended gets a new one (201). Returns `{turn_id, turn_mode, turn_mode_basis, url, envelope}` — the envelope a runner would have received at claim.
- `POST /api/harness/local-turns/{id}/renew` — Push its 8-hour lease out (the prompt hook calls it, throttled). Its initiator only.

- `GET /api/private-runners/used?workspace=<slug>` — The private runners direct turns on that workspace's agents ran on (whose, which agents, how many turns, last seen), for the runners page. Members only.

Any member. `POST /api/agents/{slug}/licenses/{user_id}/revoke` (`{note}`) and `…/approve` — agent admins; approve answers 409 unless the caller list gives the person the whole agent. Both are settings changes (audited).
- `/credentials/resolve` and `/credentials/access` take a third principal, `via: "license"`: an active license plus the caller's own running direct turn named in `X-Canopy-Turn-Id` (see the resolve route's own description).

### The HCP service (`apps/contacts/hcp_oauth_views.py`, `hcp_api.py`, `hcp_clients_api.py`) — OAuth for apps canopy does not operate

Issuer `<origin>/api/hcp`; design, flow and judgment calls in [`hcp-service.md`](hcp-service.md). Internal only (`HCP_SERVICE_AUDIENCE`). Errors on `/v1/` are `application/problem+json` with an HCP problem type; a mismatched `HCP-Version` header is refused.

- `GET|POST /api/hcp/oauth/authorize` — The two-act consent screen (bare view; signs the person in itself). Code + PKCE S256, exact redirect URI, scopes within the client's registration.
- `POST /api/hcp/oauth/token` — `authorization_code` (with `code_verifier`) or `refresh_token` (rotates; a replay revokes the grant). Form-encoded, public clients.
- `POST /api/hcp/oauth/revoke` — RFC 7009; revoking any of a grant's tokens revokes the grant.
- `GET /api/hcp/.well-known/oauth-authorization-server` (and `/.well-known/oauth-authorization-server/api/hcp`) — RFC 8414. `GET /api/hcp/.well-known/mcp-manifest` — Appendix B. `GET /.well-known/hcp-configuration` and `GET /api/hcp/.well-known/hcp-configuration` — Appendix C.
- **Data plane `/api/hcp/v1/…`** — auth is a canopy session/PAT or `Authorization: Bearer hcpat_…` (one person's grant; refused on every path outside `/api/hcp/v1/`, and on the person-only routes below). 120 requests a minute per client (429 + `Retry-After`). An agent names the turn it serves (`?turn=`) and gets only that turn's person, under its grant.
  - `POST /v1/preferences/search` (MCP `hcp_searchPreferences`) — recall entries relevant to a stated purpose; ≤ 20, by relevance, provenance redacted; audited.
  - `POST /v1/preferences/add` (MCP `hcp_addPreference`) — add an entry in a category the grant may write; `model-inferred` needs `confidence`; an inference contradicting a declared entry on the same dimension is quarantined. Idempotency-keyed.
  - `POST /v1/preferences` — the REST form (a full HCPEntry; `issuer-attested` allowed). Not an MCP tool.
  - `GET|PUT|DELETE /v1/preferences/{entry_id}` (MCP `hcp_getPreference` / `hcp_updatePreference` / `hcp_deletePreference`) — read (`purpose` required and logged; `version` is the person's only; a missing entry is 403 too), correct (new version, same id; the person updating a quarantined inference accepts it), forget (`hardDelete=true` is the person's only and removes every version).
  - `GET /v1/audit` (cursor-paged, filters) · `GET /v1/grants` · `DELETE /v1/grants/{grant_id}` · `GET /v1/export` — the person's own: audit log, grants (an agent sees only the grant it reads under), revoke (immediate, never rate-limited), export (`include=versions,audit`, `exclude=deleted`). Not MCP tools.
- `GET|POST /api/hcp-admin/clients` · `PATCH /api/hcp-admin/clients/{client_id}` — The client registry (`HcpClient`): register, change, disable (stops every token) or rotate the webhook secret (returned once). Narrowing `allowed_scopes` does not change existing grants. Superusers only; never MCP.

### People (`apps/contacts/people_api.py`, mounted at `/api/people`) — the fleet brain

What agents know about a person, per workspace. Rules in [`access.md`](access.md) → "What agents know about a person". "Person-only" below means 403 for an agent's login, a caller token or a system account.

- `GET|PUT /api/people/me/default-agent/` (`{agent}`) — The agent every embedded panel opens on for the caller, unless the page chose one (`PreferredAgent`); `PUT` takes a slug of an agent in one of their workspaces (else 404) or `""` to clear. `PUT` is person-only and audited.
- `GET /api/people/me/` — Everything held about the caller: `agent_memory: {record: {available, default, changed_at}, use: {…}}`, live facts in every workspace (with who learned each), the last 50 reads (`PersonAccess`). Any signed-in user, only their own.
- `PUT /api/people/me/agent-memory/` (`{record?: {available?, default?}, use?: {…}}`) — Canopy-level settings: whether each feature may be on at all, and whether it is on in a new session. `record` = agents may learn about me; `use` = agents may be told it. Off deletes nothing. Person-only; not an MCP tool. Audited (`agentRecord.*`, `agentUse.*`).
- `GET|PUT /api/people/me/sessions/{session_id}/agent-memory/` (`{record?, use?}` = `on|off|inherit`) — One of the caller's own sessions (`created_by`; else 404): per feature `{available, default, override, effective, granted, grant}`. Turning on an unavailable feature is 403; any other value 422. Person-only; not an MCP tool. Audited (`sessionRecord.*`, `sessionUse.*`).
- `POST /api/people/me/sessions/{session_id}/agent-grants/` — The person grants that session's agent `record` and/or `use`, for the session (`duration=session`, lapses with it or after `session_grant_hours`) or always (`duration=always`, until revoked). Only available features; granting one that is off by default turns it on for the session. Person-only; not an MCP tool.
- `GET|POST /api/people/me/memory-collections/` · `PUT|DELETE …/{collection_id}/` · `PUT /api/people/me/grants/{grant_id}/collection/` (`{collection_id|null, confirm_widening?}`) — Named sets of contexts (all of an org as it is when read, one workspace, or entries in no workspace) a person points an agent's grant at. A change that lets an agent reach more is 409 listing the grants in `confirm_widening` until re-sent with them; deleting a collection in use is 409. Person-only.
- `GET|POST /api/people/me/session-reviewers/` (`{agent}`) · `DELETE …/{agent_slug}/` — The agents the person lets review their sessions, read-only (`SessionReviewGrant`, the session ACL's leg 5 — tenancy.md § The chat-session ACL), the agents they could let in (of workspaces they are in, else 404), and `coach` — the agent `COACHING_AGENT_SLUG` names, when it is in a workspace they are in or may ask to join (`member`, `on`). Person-only (403 for an agent's login, a caller token or a system account). Audited (`sessionReviewer.granted` / `.revoked`); revoking is immediate.
- `GET /api/people/session-reviewers/granted-to-me/` — For an agent's own login: who let it review their sessions (`user_id`, `username`, `email`, `display_name`, `granted_at`); anyone else gets an empty list. One person's sessions: `GET /api/canopy-sessions/?of_user=<user_id>`.
- `GET /api/embed/sessions/{session_id}/agent-memory` — The same per-feature state for the widget to show, plus `manage_path`. Read-only, delegated-token only: the caller's own session with an agent the acting app offers, else 404. A site acting for its visitor cannot change their memory (the person routes refuse a delegated token); canopy's own widget, signed in by session cookie, uses those routes. Not an MCP tool.
- `/api/contact/hcp/…` — A CONTACT's own HCP, only on a site a superuser trusts for email (`AppCredential.asserts_verified_email`; keyed by `ContactToken.verified_email`). `POST /proof` mints a single-use frame proof, only to canopy's own frame (its HttpOnly + Partitioned `canopy_hcp_frame` cookie and `Sec-Fetch-Site: same-origin`); every other route spends one in `X-Canopy-Frame-Proof`, so the site holding the token can do none of it: `GET /state`, `POST /opt-in`, `POST /sessions/{id}/agent-grants` (session | always), `PUT /sessions/{id}/memory`, `PUT /policy`, `DELETE /grants/{id}`, `DELETE /entries/{id}`, `GET /export`. An address with a canopy account is refused. See hcp-service.md → "Contacts". Not MCP tools.
- `GET /api/people/lookup/?email=&workspace=` — The person an address names, only if a workspace the caller is a member of deals with them; else 404. Creates nothing.
- `GET /api/people/{id}/?workspace=<slug>` — The person and that workspace's live facts (corrections first). Members; the read is logged. 403 for an agent's login (agents recall through HCP).
- `POST /api/people/{id}/facts/` (`{workspace, kind, statement, basis, source_turn_id?, project_id?, instance_ref?, supersedes_id?, category?, dimension?, confidence?}`) → 201. `kind` ∈ role, project, instance, preference, correction, terminology (else 400); `source_turn_id`/`project_id` must belong to that workspace (400). Asserted by the agent when the caller is an agent's login, and then refused (403) unless the person lets agents learn about them in that turn; 403 on a zero-data-retention refusal.
- `POST /api/people/{id}/facts/{fid}/retract/` — The person, the asserter (user or the asserting agent's login), or an admin of the fact's workspace; else 404.
- `GET /api/people/{id}/conversations/?agent=<slug>&since=<iso>` — The turns that person started with that agent, newest first. The agent's own login (all of them) or its admins (only turns they can already read); 403 otherwise. Logged.
- `GET /api/people/{id}/projects/?workspace=<slug>` — Projects of that workspace's agents the person takes part in (`ProjectParticipant`), most recently active first. Same gate as `GET /api/people/{id}/`; logged.
- `GET /api/people/addresses/?workspace=<slug>` — Every member's contact details in one read (what an agent uses to find, e.g., each family member's work email): every human member of that workspace (not agents or system accounts) as `{person_id, user_id, email, display_name, may_edit, addresses}`; `may_edit` is true only on the caller's own row. Members only (else 404); a read is logged for each person whose addresses it returns.
- `GET /api/people/{id}/addresses/?workspace=<slug>` — More ways to reach a person (`PersonAddress`): their labelled emails and phones (`kind` email | phone, `label` work, personal …) beside the address that identifies them. They belong to the person's account, not a workspace; the workspace only proves the caller shares one with them. Same gate as `GET /api/people/{id}/` but an agent's login is allowed (declared by the person, not agent memory); logged. An address never joins or identifies anyone.
- `POST /api/people/me/addresses/` (`{kind, label, value}`) → 201 · `DELETE /api/people/me/addresses/{aid}/` → 204 — Only the person changes their own (not a workspace admin; an agent's login, a caller token or a system account is 403; someone else's row is 404). A bad kind, label or value is 400; the same kind and value again relabels it. The person sees every row in `GET /api/people/me/` (`addresses`).
- `GET /api/people/coverage/?workspace=<slug>&days=7` — Is the brain alive: per agent, human turns, how many carried a person block, facts recorded in-session, and `healthy` with its rule. Counts only; `days` 1–90. Workspace members; a non-member agent admin sees only their agents.

### Asks — a task that asks a person something
An ask is a property of a task, not a separate noun: `ask_kind` is `review` ("should I do this?") or `question` ("I need an answer"), with `ask_body` carrying its text (`origin_ref` is provenance, not identity). It is **open** until an action closes it: `approve` or `decline` on a review, `reply` (the answer) or `decline` on a question. No routes of its own — raised by `POST /api/agents/{slug}/tasks/`, answered by `POST /api/agents/{slug}/tasks/{ref}/actions` (Agents).

An ask is the dual of a `Turn` (work you do vs. work an agent does): an approved task's `on_approve` enqueues turns, or one turn written from the card when it has none (`Turn.raised_from_task`). `TurnSpec.target_agent=""` means the ask's own agent; set, it dispatches to another agent. Act + dispatch are one transaction: a bad `on_approve` spec is a 422 with the ask still open.

**Waiting on you is a filter.** `/supervisor` (`GET /api/me/tasks/?waiting=me`, every workspace you are in) and an agent's Tasks page (`?waiting=me`) render the same rows on the same card, actionable in place. Producers raise real asks: the schedule nag (`schedule_turns._raise_schedule_nag`; runners.md → "Scheduled turns"), run gates and task reviews (e.g. the fleet `task-tracker` skill). Any task row moving marks `task://` dirty (`apps/harness/signals.py`), so a page showing tasks re-reads.

### Attention (`apps/attention`, mounted at `/api/me/attention`) — what is waiting on you

- `GET /api/me/attention/` — a user-level view ([roles.md § A user-level view](roles.md#a-user-level-view-reads-each-organisation-on-its-own)): everything waiting on the caller in every organisation they are in, as `now` (activity in the last 3 days, `services.QUIET_AFTER`), `quiet` (older) and `hidden`, plus `running` — the caller's own sessions being worked right now (the feed's ownership rule `feed.held`; an agent's auto run counts), not asks, so never quiet or hidden — each newest first. Every item: `key` (`task:<agent>:<alias>` for a task with an agent alias, else `task:<key>`; `session:<id>`, `access:<id>`), `kind`, `state`, `reason`, `title`, `body`, `workspace`, `organisation`, `agent_slug`, `project`, `url`, `last_activity_at`, `actions`, `target`. **`state`** is what it asks of you, the one field a client branches on (`apps/attention/types.py`): `asking` (a dialog, review, question or join request), `your_move` (the agent finished, or a task is parked with you), `parked` (waiting behind a paused or offline runner — named in `reason`), `running`, `running_auto`; `reason` is display text. Each owning app supplies its own items by its own rule (`apps/<app>/attention.py`, registered by dotted path in `apps/attention/sources.py`): tasks by the board's `filter_tasks(waiting="me")`, chats by the feed's `feed.status` through the session list path, access requests by `members.manage`. Actions go to the existing routes (`act_on_task`).
- `POST /api/me/attention/hide` `{keys, days?}` — take things off the caller's own list and nothing more: no task is closed or decided, no chat is ended, nothing is sent and the agent is not told (`Hidden`). Each returns when its `last_activity_at` passes the hide, or after `days`. `DELETE /api/me/attention/hide/{key}` puts one back.

### Alerts (`apps/attention/alerts_api.py`, mounted at `/api/me/alerts`) — persisted things that need you

A user-level view like attention (read once per organisation, rows carry `organisation`). An alert is visible when its workspace is one the caller may read AND its source offers them an action (`visible_actions`; for `status=dismissed`, `offers_dismiss`); a row whose kind has no importable source is skipped. By id, anything not visible is a **404**, never a 403. Source modules and the lifecycle: `apps/attention/alerts.py`. The model, sources, screens and the rules that keep the list worth reading: [`alerts.md`](alerts.md).

- `GET /api/me/alerts/?scope=&status=open|dismissed` (`list_alerts`) — `AlertOut[]` (`id, kind, severity, title, body, url, workspace, organisation, scopes, status, first_seen_at, last_seen_at, occurrences, closed_by_email, closed_at, actions[{id,label,closes,href}], last_notify`), `blocking` then `action` then `setup`, newest first. `scope` keeps rows whose `scopes` contain it; a `workspace:<slug>` scope also keeps every alert whose workspace is that one or any below it (`wsvc.descendant_map`). `dismissed` = dismissed in the last 7 days that the caller could dismiss. `last_notify` is the latest `notified` event as a line ("A asked B at 14:02" / "Notified B at 14:02"), else "".
- `POST /api/me/alerts/{id}/act` `{action}` (`act_on_alert`) — runs an action still offered to the caller; for a link action (`href`) it only logs `acted` (no perform, no resolve) — the browser follows the link. **409** problem+json with `code: "action-not-offered"` when it is not (or no longer) offered.
- `POST /api/me/alerts/{id}/undismiss` (`undismiss_alert`) — anyone currently offered `dismiss`; **409** `action-not-offered` otherwise.
- `GET /api/me/alerts/{id}/history` (`alert_history`) — `AlertEventOut[]` (`at, kind, actor_email, action_id, payload`), oldest first; works for resolved alerts too (visible when the workspace is the caller's and the source offers them any action, whatever the status).

### User-level views (`/api/me/…`)

Each is a list below run once per organisation (`wsvc.each_organisation`) and re-sorted — [roles.md § A user-level view](roles.md#a-user-level-view-reads-each-organisation-on-its-own). `GET /api/me/sessions/` (`state`, `reply`, `q`, `limit`; the session list's order) — Supervisor's Feed, `/ide`, the chat home. `GET /api/me/tasks/` (the fleet task filters; `?waiting=me` is Supervisor's Waiting on you). `GET /api/me/agents/` (a `Page`, by name). `GET /api/me/projects/` (the projects you own; `?status=`, default active) — Home's side panel.

### Chat (`apps/canopy_sessions`) — multiplayer chat sessions (the live front-door)
A `Session` is a durable conversation with an agent (or, agentless, with a repo checkout), workspace-tenanted. A send enqueues a **session `Turn`**; a session-capable runner executes it and the reply comes back through the turn ledger and the transcript; `Message` rows are a projection. How a chat is recorded, its turn status, drafts/authorship, liveness and push are in `docs/architecture/chat-sessions.md`; blocked-agent dialogs in `docs/architecture/blocked-agent-menus.md`; the embedded widget and MCP Apps Views in `docs/architecture/embedding-internals.md`. WebSockets (`apps/realtime/routing.py`, `apps/canopy_sessions/routing.py`): `ws/canopy-sessions/{id}/` (connect snapshot, per-person drafts, presence, streamed reply — the `canopy-ui/chat` protocol), `ws/turns/{turn_id}/`, `ws/supervisor/` (`supervisor.sessions` frames), `ws/runner/{runner_id}/` (runner control channel), `ws/presence/`.
- **Access — one rule, `apps/canopy_sessions/access.py`**, asked by every door: [tenancy.md § The chat-session ACL](tenancy.md#the-chat-session-acl-ci-enforced). Pinned by `tests/test_session_acl.py`.
- `POST /api/canopy-sessions/` — Create (`agent_slug` XOR `project`, `title`, `metadata`, optional `runner_id` pinning the first turn, optional `parent`, optional `cli` — the agent CLI it runs on for life, one the agent is set up for, else 422 (`clis.refusal`)). A project chat's `runner_id` must be a box the caller administers (403 otherwise; `chat-sessions.md` → "Which box takes a chat's first turn"). Created in the current workspace; `/api/w/{ws}/canopy-sessions/` creates in that one. A delegated site may only open a chat with an agent it offers; `embed_app` is server-owned (taken from the token, never the body). `metadata` is an allowlist (`services.HOST_METADATA_KEYS`: `source`, `origin_key`, `opp_slug`, `opp_run_id`, `opp_step_skill`, `workflow_id`, `opportunity_id`, plus any key under `x_`, which canopy never reads); every other key — `fork` among them — is dropped. Under a site token that requires `sensitive_data`, someone without a vault key (or a contact) is refused 422 before anything is created: "a sensitive conversation needs a canopy account with a vault key; set yours up at …". Optional `conversation_key` `{conversation, public_jwk, wrap, recipient_jkt}`: a key pair canopy's own chat surfaces make in the browser, wrapped to the starter's current vault key (422 otherwise) — kept as the conversation's key, so if it is or becomes sensitive canopy-web never sees its private half.
- `GET /api/canopy-sessions/?state=active|archived|all&limit=` (≤ 500, no paging) — The sessions you can see: waiting on you first, then running, then most recent. Filters `q` (title/`session_key`), `repo`, `branch`, `pr`, `since`/`until`, `source`, `origin_key`, `embed_app`, `resource`, `page_path`, `session_key`, `runner` (id or name: every session on that box), `of_user` (one person's own sessions by user id — the chats they started and the runner sessions on their own boxes; narrows, grants nothing); `reply=true` stamps `feed_status`. "Active" is derived each read (rules: `chat-sessions.md` § Session liveness); rows carry `runner_online` and `runner_status` (the bound runner's `live_status`, null when unbound), `runner_id`, `runner_host` (the macOS login the session lives on) and `emdash_project` (the binding's project, else the repo or agent slug — what `/ide` groups by).
- `GET /api/canopy-sessions/search?cursor=&limit=&state=all&…` — Walk **every** session (the list caps at 500): `{sessions, next_cursor}`, keyset-paged on (last activity, id) desc; same filters as the list via one helper. Pass `until=<walk start>` to freeze the set.
- `GET /api/canopy-sessions/{id}` (`?full=true` for everything) — Session + transcript tail (`SESSION_TAIL_DEFAULT` = 60) + `menu`, `turn_status`, `my_role`, `can_move`, `sealed_key`. A SENSITIVE conversation's rows carry `sealed` (a `cc1:` envelope; `plaintext`/`content` are metadata) and `sealed_key` is `{conversation, public_jwk, wrap, recipient_jkt, current, keyset, index_offsets}` — your own wrap of its key (null if you were never given one; `current` false if your vault key changed since) and your keyset's public half and seals, for the browser to unlock and decrypt (`frontend/src/vault/sealedChat.ts`). Both are null for an ordinary conversation and for any reader `sensitivity.reads_content` refuses (MCP, a PAT, someone not in it). If no readable session has that id it is tried as a runner `session_key` (409 if it names several). `GET /{id}/messages` — scroll-back (`before=`).
- `GET /api/canopy-sessions/{id}/human-inputs?after=&limit=` — Only what people typed, oldest first: `{messages, next_cursor, source}`. Excludes agent output, tool rows, harness/system rows, prompts a program delivered (any turn that is not a chat send) and Claude Code's own user records (skill bodies, wake-ups, compaction, sidechains — decided by the transcript record's flags in `Message.content.record`). No durable rows yet → answered from the runner's tail (`source: "tail"`, unpaged).
- `GET /api/canopy-sessions/{id}/slash-commands` — What the composer's `/` menu offers: the agent's launchable skills (`<slug>:<name>`) first, then what the bound runner reported. Empty for someone who can read the session but not send to it (`apps/canopy_sessions/slash_commands.py`).
- `POST /api/canopy-sessions/{id}/send` — `text`, `client_id` (idempotency, ≤ 100 chars), optional `placement` (`"wait"` pins to the bound runner, a runner id re-pins), `origin` (postable sources only, e.g. `ace_web`), `parent`, `clear_prompt`. A site token's runner requirements (`sensitive_data`) are stamped on the session first. Clears the sender's draft.
- `POST /api/canopy-sessions/{id}/place` — Re-pin the session's oldest queued turn (`placement`, same shape as send); the chat banner's after-the-fact choice. For a project chat, a box you administer only (422 otherwise), as for send's `placement`.
- `POST /api/canopy-sessions/{id}/transfer` — Move a live session to another runner (`runner` id or name, `brief`, optional `cli` to continue on another agent CLI from a fresh session), history AND work included (`handoff`, rules: `chat-sessions.md` § A transfer carries the work). Onto a runner you administer (or between two runners with the same owner): `status: moved`; `turn_id` is empty while the source packs its worktree (at most 3 minutes) and `handoff` says how that is going. Onto someone else's: `status: pending` + `request_id` + `approvers`. 409 while the session is busy — a turn executing, or its runner (reachable, paused included) reporting the engine working, which is how a session typed into directly shows (`placement.busy_reason`) — stop and retry; also 409 while another request is pending.
- `POST /api/canopy-sessions/transfer-all` — `{from_runner, to_runner, brief?, session_ids?, dry_run?, cli?}`: every open session you can act in on `from_runner`, each transferred as above; `results[]` gives each one's `status` (`moved` | `pending` | `refused` + `error` | `would_move` on a dry run), `turn_id` and `handoff`. One that cannot move never stops the rest. Discovery alone: `GET /api/canopy-sessions/?runner=<name>`.
- `GET /api/canopy-sessions/{id}/handoffs` — Each transfer's work, newest first: `capture_status` (`pending` | `captured` | `failed` | `unreachable` | `timed_out` | `not_asked`) + `capture_note`, what was packed (`branch`, `head`, `local_commits`, staged/unstaged/untracked files, `skipped` with why), `restore_status` + `restore_report`, `close_status` (`pending` | `closed` | `kept` | …) + `close_error`.
- `POST /api/canopy-sessions/{id}/handoffs/{handoff_id}/restore` — Restore a snapshot that arrived after its transfer (a source that was asleep packs when it is back): a turn on the session's current runner restores it into a worktree with no uncommitted changes. 422 with no snapshot; 409 while a turn is queued or running.
- `POST /api/canopy-sessions/{id}/fork` — `{turn_index}`: a new session (returned) holding the conversation up to the end of that message's turn, on the same runner and in the same worktree (`parent_session` = the source). The runner cuts its transcript on the fork's first turn (`resolve-session` → `fork`; `worktree_of` names the directory a cloud runner runs every fork turn in). 422 unless the runner is a cloud runner or a laptop on the `claude-cli` runtime, or for a message from before a transfer; 409 when the cut falls in a turn still running.
- `GET /api/canopy-sessions/transfer-requests?status=pending|all` · `POST …/transfer-requests/{id}/approve|decline|cancel` — Transfer requests waiting on you (as an admin of the target runner) or that you made. Approve carries out the move (409 while a turn still executes; the request stays pending); decline takes a `note`; cancel is the requester's.
- `POST /api/canopy-sessions/{id}/move` — File the session in another workspace where you are editor+. Only the session's own person (creator of a web chat, owner of the runner an emdash session was discovered on); an agent's session cannot move (422). Participants not in the target are removed; a re-report never moves it back.
- `POST|GET /api/canopy-sessions/{id}/join-requests` · `POST …/join-requests/{request_id}/decline|cancel` — Asking to be added to a PRIVATE (sensitive) conversation you can see listed but are not in (`apps/canopy_sessions/join_requests.py`). `POST` (anyone the session ACL lets read it who is not one of its people; 409 for an ordinary conversation, one you are in, or one no member started) returns the open request if you already asked. `GET` is the open list for the conversation's own people, empty for anyone else; the same whole list rides the chat socket as `session.join_requests` on every change (ask, add, decline, withdraw), so an open chat shows it live. A request carries who asked and which conversation, never anything it said. Letting someone in is `POST …/participants` from the owner's browser (it wraps the key), which approves their request; `decline` is the owner's, `cancel` the asker's. A request is never a Home (`/api/me/attention/`) row: it is shown in the conversation. `SessionOut` carries `you_are_in_it` (null for an ordinary conversation) and `started_by_name`, and a sensitive row's `title`, `opening` and `last_reply` are always ""; `GET /{id}` adds `your_join_request`.
- `GET|POST /api/canopy-sessions/{id}/participants` · `DELETE …/participants/{user_id}` — Share a chat (the header's People control). Owner only (the creator; for an agent's own thread, its admins). The teammate must be in the chat's workspace; `role` `editor` (default) or `viewer`, re-adding changes it. Anyone may remove themselves; the owner cannot be removed. In a SENSITIVE conversation `POST` takes `wrap` `{alg: "ecdh-es", epk, n, ct, recipient_jkt}` — its key, wrapped in the adder's browser to the newcomer's vault key; required unless they already hold a current one (409 `wrap_required`), shape-checked and refused (422) unless `recipient_jkt` is their current vault key's thumbprint. Removing someone deletes their wrap. `GET …/participants/recipient?email=` → `{user_id, email, public_jwk, jkt}`, the key to wrap to (the owner, in the conversation — or anyone in it, for someone already in it; 409 `no_vault_key`); the browser wraps only to a key it trusts for them (pinned, or its fingerprint accepted now — `vault/trust.ts::trustPerson`). In a sensitive conversation each `ParticipantOut` carries `needs_key`: no copy of the key for their current vault key (given it before it became sensitive, or their vault key changed). `POST /{id}/key-copies` `{user_id, wrap}` — give someone already in it (its starter included) their copy: an editor or the owner in it (403 for a viewer) holding a current copy (409 otherwise), the target must be in it (404) and hold no copy for their current vault key (409 — a copy for an older key is provably stale and replaced; nobody overwrites a current one, the owner's included), the wrap is checked as above (422). A re-add or role change keeps a current copy whatever `wrap` says. `DELETE /{id}/key-copies/mine` — your own act: your copy does not open (broken, or wrapped to a key you lost), so drop it and be listed `needs_key` for a fresh one. Until they hold one the chat socket turns them away with `session.error` `needs_key`.
- `GET /api/canopy-sessions/my-vault-key` → `{user_id, public_jwk, jkt, keyset}` (self, 404 with none) — the key a browser wraps a new chat's key to; the embedded panel reads it with its own token. `keyset` (public half and seals, as `sealed_key.keyset`) only to the person's own browser on a chat surface (null for a token or a site's backend): a browser that has not opened the vault key before opens it from this and derives the public half itself before trusting the one named (`sealedChat.offerForNewChat`); a changed one stops the new chat. `GET|PUT /api/canopy-sessions/my-keys` (self, a chat surface) — before replacing a vault key: every sensitive conversation whose key you hold a copy of (`{session_id, conversation, public_jwk, wrap, recipient_jkt, agent_name, workspace, started_at}`, never its words); after, `{copies: [{session_id, wrap, recipient_jkt}]}` re-wrapped in the browser to the new key → `{stored}`. Only copies you hold, only to your current key (422, storing none).
- `POST /api/canopy-sessions/{id}/archive` · `/unarchive` — Retire / restore by hand. Idempotent, never destructive. Unarchive clears only the written half: a stale runner session stays out of `active` until reported again.
- `POST /api/canopy-sessions/{id}/close` — End a session for good. If a runner is currently reporting an emdash task for it (`RunnerBinding.reported_at` within the live window): cancel its turns, relay `runner.close_session` (the runner deletes the task; its next report retires the row), write nothing to the session — answers `closing: true`. Otherwise (cloud, never-bound web chat): cancel turns and archive. A refusal is a 200 `ok:false` with `reason` `unavailable` | `already_closed`; `unavailable` does not queue. Spec: `docs/superpowers/specs/2026-07-30-close-session-from-phone-design.md`.
- `POST /api/canopy-sessions/{id}/stop` — Stop the session: cancel its open turns, or, with none open, ask its runner to interrupt the agent. Returns `cancelled`, `interrupted`, `route`.
- `POST /api/canopy-sessions/{id}/reset` (`?dry_run=`) · `POST /api/canopy-sessions/reset` (`dry_run`, `prune_ghosts`) — Drop the derived `Message` rows and re-derive them from the runner's transcript. Refusal is a 200 `ok:false` + `reason` (`no_binding`, `runner_unreachable`). Bulk touches only sessions you may act in; `prune_ghosts` deletes runner-discovered sessions with no binding (never a human-started chat). `Turn`s and their ledger are never touched. Same service as the chat header button and `manage.py reset_chat_state`.
- `POST /api/canopy-sessions/{id}/answer-menu` — Answer a blocked agent's dialog: `option` (`null` = refuse/Escape), `selections` (one list per question for an AskUserQuestion), `texts`. Relayed to the runner; refusal is a 200 `ok:false` + `reason` (`unbound`, `unavailable`, …). Mechanics: `blocked-agent-menus.md`.
- `POST /api/canopy-sessions/{id}/attach` · `/detach` · `/backfill` — Register / unregister a live viewer (the bound runner tails and ships view-only rows while one is attached); ask the runner for full history.
- `POST /api/canopy-sessions/{id}/attachments` (201, multipart) · `GET /api/canopy-sessions/attachments/{id}/content` · `DELETE /api/canopy-sessions/attachments/{id}` — Composer attachments: uploaded unbound (the send binds it), type-allowlisted and size-capped (422), 503 when storage is unconfigured. In a sensitive conversation only its own people at a browser upload — canopy's chat page, or the panel's frame with its delegated token (`Sec-Fetch-Site: same-origin`), never a site's backend (422 otherwise; also 422 while it has no key), the row keeps a size bucket and type family under a key that names no file, and the plaintext content route serves it to nobody (tenancy.md § Sensitive conversations, *Files*). Content is gated on reading the session, served inline with `nosniff` + `CSP: sandbox`; a runner fetches through the turn it holds instead (harness `…/turns/{turn_id}/attachments/{id}/content`). Delete only while unsent (409 once sent).
- `POST /api/canopy-sessions/attachments/{id}/sealed` (204, multipart `sealed_name` + `file`) · `GET /api/canopy-sessions/attachments/{id}/sealed` · `GET /api/canopy-sessions/{id}/sealed-attachments` — A sensitive conversation's files, as its people keep them: the uploader's browser stores the name (`cf1:`) and bytes (`cfb1`) sealed to the conversation's key, once, before the send (422 when the envelopes are not this file's, 403 for anyone but the uploader, 409 twice or after the send); its people (`reads_content`) list them, with no name and each placed at the line it was sent with, and fetch the ciphertext. Everyone else: 404, or an empty list.
- `PUT /api/canopy-sessions/{id}/title` — `{title}` (owner/editor): rename it in canopy (the emdash task keeps its name). Whitespace collapses; blank clears, so it is named again like an untitled one. A typed title is never replaced by the runner's task name or autotitle (`harness.session_sync._title_is_derived`); publishes `session.title_updated`.
- `PUT /api/canopy-sessions/{id}/notify` — `{every_completion}`: push on every finished turn instead of once the chat goes quiet (served as `notify_every_completion`).
- `GET /api/canopy-sessions/{id}/secrets/recipients` · `POST|GET …/secrets` · `DELETE …/secrets/{name}` — Share a secret with one chat, sealed in the sharer's browser so canopy-web cannot read it (`docs/architecture/chat-sessions.md` § Secrets shared with a chat). `recipients` (a writer of the chat) → `{binding_id, kv, runner_id, runner_name, recipients: [{kind, target, label, public_jwk}], refusal, error}`: the bound runner's active, ECDH-approved device keys, or a sentence why there are none. `POST {name, value_zk}` takes `zks1` ONLY (plaintext `value` → 422 `sealed_only`), sealed to those keys (else 409 `stale_recipients`; no machine → 409 `no_runner` / `runner_has_no_ecdh_key`); `name` already env-var shaped (the seal binds it). The list returns names + expiry, never values; nothing is posted into the chat. A secret lives 30 min from sharing (re-sharing restarts it). Sharing from a browser needs a passkey step-up; a token is allowed.
- `GET /api/session-secrets/key` · `GET /api/session-secrets/key/{name}?sealed=true` — The agent half (`canopy secret list|exec`): present the chat's key in `X-Canopy-Chat-Key` (minted when a runner claims the chat's turn and handed only to that chat's session). No route takes a chat id, so a key reaches only its own chat's secrets. The value comes back sealed, `{name, value_zk, binding_id, kv}`, for the box to open with its ECDH key; without `sealed=true` (an older CLI) → 409 `update_canopy`. Bearer only; no/wrong/expired key → 404. Each read is a `session.secret.resolved` event. The same key scopes the MCP page tools to that chat's page.
- `GET /api/canopy-sessions/{id}/export` — The conversation as markdown (tool output shortened) to continue in your own Claude (`canopy runner export`). Creator only; refused (403) for an embedding site.
- `POST /api/canopy-sessions/slack/detach` — Disconnect a session from its Slack thread (see Slack below). Name it by `session_id`, `claude_session_id` or `emdash_task` (+ `emdash_project`; 409 if ambiguous). Owner/editor; idempotent (`status: not_bound`), or — for an agent's own login — by `turn_id`, its live turn (`access.own_turn_session`).
- `POST /api/canopy-sessions/slack/new-thread` — Move a conversation to a NEW thread in its own Slack channel (`start_new_slack_thread`): posts `summary` top-level, binds the session to it, tells the old thread where it went. Named like detach (`turn_id` for an agent's own live turn, else `session_id` / `claude_session_id` with owner/editor). 409 when unbound or a DM; 422 without a summary.
- **Page contract** (`docs/architecture/embedding-a-canopy-agent.md`): `PUT|GET /api/canopy-sessions/{id}/page-actions` (declare / list what the attached page can do; replaced wholesale; empty = no page attached) · `PUT|GET /{id}/page-state` (what the page shows; over the cap → 422 `too_large`) · `PUT /{id}/run-input` (AG-UI `RunAgentInput`: `tools` → actions, `state` → page state, other fields ignored) · `POST /{id}/page-actions/invoke` (blocks until the page answers; errors carry a `code`: `no_page`, `unknown_action`, `bad_arguments` (422), `timeout`, `refused` (409)) · `POST /{id}/page-actions/{action_id}/result` (the page reporting back).
- **MCP Apps Views** (`apps/canopy_sessions/app_views_api.py`, `apps/mcp_apps_host/mcp_apps_views.py`): `GET /api/canopy-sessions/{id}/apps/{tool_call_id}/resource` · `POST …/call` · `POST …/read` (same server only) · `PUT …/context` · `POST …/message` (starts a turn) · `POST …/subscribe` / `POST …/unsubscribe` (`{uri}`) — a rendered View's browser plumbing, run as the person looking at it. Not MCP tools; refuse a PAT. In a sensitive conversation `resource` returns `tool_input: {}` and, for its own people, `tool_input_sealed` (the call's `cc1:` envelope) with `tool_input_path` (`gateway` → the arguments are `input.arguments`, `direct` → `input`), which the browser decrypts and hands the View; its `tool_result` is the host's resource links alone — `{content: [resource_link…], structuredContent: null, _meta: {"canopy/withheld": true}, isError}` — or `null` when the call returned none (spec 2026-10-23-host-held-results). `read` refusals: 502 when the host did not answer, 403 when it refused (`host_refused: <its sentence>`). `subscribe` needs a View row and the viewer's own live grant (403 `no_grant`), a URI (422 `bad_uri`), at most 100 live per conversation (429); canopy holds it (`AppViewSubscription`, 24 h) and relays the host's signed notification (`POST /api/sites/resources-updated`, below) to the conversation's socket as `app.resource_updated` `{tool_call_id, uri}` (AG-UI CUSTOM `canopy.app.resource_updated`), which the page hands that View as `notifications/resources/updated`. `unsubscribe` is idempotent and needs only the session ACL.

Framework tier, generic over its target (`target_kind` + `target_ref` strings, never an FK). It has no pollers or connectors — an agent reads a channel and POSTs.

### Events (`apps/events`) — the fleet log of actions and errors
Framework tier, generic over its producer (`source` + `kind` strings). Where an operational fault lives when it belongs to no `Turn`. A log, not a queue: emits **no signal** (`tests/test_events_emits_nothing.py`); a turn sweeps it. `Event.workspace` is NOT NULL.
- `POST /api/events/` — Record (batch, atomic; editor+). Repeats of `(workspace, source, key)` coalesce onto one row (`count`, `last_seen_at`); a blank `key` never coalesces; a row with no `source` is dropped. The workspace is the pinned one, else — for a box posting with its runner token — `Runner.workspace`, else the caller's sole workspace (422 when there is none). A runner token's `claude_auth_required` / `claude_usage_exhausted` / `claude_credit_exhausted` / `claude_api_key_fallback` also mails and pushes the runner's approvers, once per (runner, alert) per UTC day (`apps/harness/credential_notify.py`) — except `claude_auth_required` (or `claude_credit_exhausted`) from a runner whose health reports a signed-out (or out-of-credit) `claude.probe.*` check, which reaches people as the `runner_credential` alert instead.
- `GET /api/events/?source=&kind=&level=&since_minutes=&limit=` — Admin+ (`logs.read`). `source`/`kind` are prefix matches; newest-touched first.
- Session lifecycle: every start, stop and change to who can see a session or where it is listed is one `session.*` event (`source` `canopy_sessions.lifecycle`) with ids, actor, turn and before/after only — `?kind=session.` reads a workspace's. Kinds and producers: `docs/architecture/chat-sessions.md` § A session's lifecycle is in the event log. `agent.canopy_token.issued` names the turn's conversation in `session` (blank only before an agent turn's runner records one) and `scope` (`turn`/`session`).
- `GET /api/events/setting-changes?operation=&target=&actor=&since_minutes=&limit=` — The settings audit trail (`SettingChange`, `docs/architecture/settings-audit.md`), newest first: changes in workspaces where you are admin+, plus your own. `operation` is a prefix, `target` a substring, `actor` an exact email; `limit` ≤ 500 (default 100).
- `GET /api/events/mcp-calls?tool=&failed=&since_minutes=&limit=` — The MCP audit log (`MCPAuditLog`), newest first: every call in workspaces where you are admin+, plus your own calls anywhere. `tool` is a prefix; `failed` keeps errors. A call made under an act-as-you permission on canopy (MCP or REST) names the person in `user_email` and the agent in `acting_agent`, with the grant id (`act_as_grant`).
- No mutation route. Retention: 30 days untouched (anchored on `last_seen_at`), pruned daily by the `events.prune` tick; `manage.py prune_events` by hand.

### Agent tasks (`apps/agent_tasks`, mounted at `/api/agent-tasks`) — call an agent inline, get a structured result
Framework tier. The contract, the completion rule and its two rails: [`agent-tasks.md`](agent-tasks.md). Anyone not listed gets a 404.
- `POST /api/agent-tasks/` `{agent, name, instructions?, input, output_schema, routing?, timeout_s?, parent?}` — create a task and queue ONE turn for the agent (`origin_ref.agent_task`). The gates of `POST /api/harness/turns/` (`agent.work`). 422 for an `output_schema` that is not a JSON Schema, 413 for `input` over 1 MiB. 201.
- `GET /api/agent-tasks/{id}?wait_s=0..20` — read (long-poll until the status changes): its creator, the agent's admins, the agent's own login. `input` only for the agent; the agent's read makes a queued task `running`. A task past its deadline fails here.
- `POST /api/agent-tasks/{id}/result` `{result}` — the agent's own login only, while queued/running; the ONLY way a task completes. 422 with `errors: [{path, message}]` (the task stays open), 409 once ended, 413 over 1 MiB.

### Inbound push (`apps/inbound`) — the doorbell
Framework tier. Gmail push turns new mail into a turn in seconds instead of on the runner's 300s poll.
- `POST /api/inbound/gmail/{workspace}/` — Gmail Pub/Sub push. `auth=None`, allowlisted in `apps/common/middleware.py`, self-enforcing on a Google-signed OIDC JWT checked against **that workspace's** `InboundPushConfig` (the tenant is in the path, so it is known before the body is decoded and one tenant's signer can never satisfy another's). Unverified → **404** (no enumeration); verified but not actionable → **200** (a 4xx makes Pub/Sub redeliver forever).
- `GET|PUT /api/inbound/config/{workspace}` — Audience, expected signer, watch topic; read member, write admin+ (`integrations`). Returns a server-computed `push_url`.
- `GET|POST /api/inbound/mailboxes/{workspace}` · `PATCH|DELETE /api/inbound/mailboxes/{workspace}/{id}` — Address → agent registry; writes admin+. An address is globally unique (409 if registered). `enabled=false` parks a mailbox on the poll.
- `GET /api/inbound/runner-mailboxes` — Every enabled mailbox the caller may read (address, agent, topic): the runner's mailbox probe keeps those it holds a token for, and its watch re-arm takes those with a topic.
- `POST /api/inbound/watch/` — Report a mailbox's Gmail watch expiry (editor+ in its workspace).

**A doorbell, not a reader.** A push carries `{emailAddress, historyId}` and no content: canopy resolves mailbox → agent → runners (via `harness.assignment_rows_for(..., ORIGIN_EMAIL, ...)`, the same rows the claim uses, so a strict `email` rule holds) and sends `runner.check_inbox` to every online assigned runner; the runner does its normal read. No mail credential is in the web app, and a forged doorbell causes at most an empty read. Enqueue is idempotent per `(thread, messageCount)`.

**The poll is the auditor.** Email turns record `origin_ref.discovered_by` (`push`/`poll`); a poll-found turn on a mailbox with a live watch writes `gmail.push.missed` at `error`. `gmail.push.unknown_mailbox`, `gmail.push.no_runner`, `gmail.watch.expiring`/`.expired` are logged too. Stamps are per mailbox.

**Watches.** The runner arms and re-arms each mailbox's Gmail watch (7-day expiry, re-armed 24h ahead) and reports the expiry; the GCP-project constraint, the two fleet clients and the grants: [gmail-push-provisioning.md](../runbooks/gmail-push-provisioning.md).

Configured only at `/w/:workspace/settings/inbound` (audience, signer, topic, mailboxes, watch health, generated `gcloud` commands); there are no deployment-global inbound settings.

### Slack (`apps/slack`) — the Slack front door
Framework tier. Any agent with Slack on can be reached by mention, DM, `/canopy <agent> …` or `/<agent> …`. A Slack thread becomes a `canopy_sessions.Session` and each message a `send_message(origin="slack", …)`. Design: `docs/superpowers/specs/2026-09-18-slack-front-door-design.md`; multi-tenant: `2026-09-22-slack-multi-tenant-design.md`.
- `POST /api/slack/events` · `POST /api/slack/commands` · `POST /api/slack/interactions` — Bare views, allowlisted, self-enforcing on the Slack signing secret (5-min replay window). A verified request always gets **200** (non-2xx makes Slack redeliver); refusals go back as ephemeral messages. Unconfigured (any setting empty or `PLACEHOLDER`) → **503**. Interactions: button/Submit presses on question posts (toggles ignored until Submit), Run-on-cloud, a closed thread's Start-a-new-session; needs Interactivity on with Request URL `…/api/slack/interactions`.
- `GET /auth/slack/install/?workspace=<slug>` → `GET /auth/slack/callback/` — OAuth install, owner of that workspace. One Slack can serve several canopy workspaces (`SlackWorkspaceLink`): connecting adds a link and refreshes the shared bot token. A message's tenant is what it is ABOUT (its thread's session, else the agent it names), never the Slack it arrived through.
- `GET /auth/slack/link/?token=…` — Link a Slack user to the signed-in canopy user, only when the Slack profile email equals the canopy email.
- `PATCH /api/agents/{slug}/slack` — `slack_enabled`, agent admin. Returns `command_status` (`synced` | `not_configured` | `error`) for the agent's `/<slug>` command.
- `GET /api/slack-config/{workspace}` (member) — The workspace's Slack connection. `reinstall: {needed, turns_on}` names, in plain words, what a reinstall would turn on when the install lacks a scope canopy asks for (granted scopes are recorded at install; an older install is asked once via `X-OAuth-Scopes`).
- `PUT|DELETE /api/slack-config/{workspace}/config-token` (owner) — Give / withdraw the Slack **app configuration token** (refresh half; rotated on receipt, stored encrypted, refreshed under a row lock) that lets canopy manage the app's slash commands by editing its manifest. 422 if Slack refuses it. Giving it from a browser needs a passkey step-up; a token does not.
- `POST /api/slack-config/{workspace}/sync` (admin+) — Reconcile slash commands now (also runs on every switch flip): adds `/canopy` and `/<slug>` per Slack-enabled agent across every linked tenant, removes only canopy's own commands, declares the app an agent (`features.agent_view`, agent scope and events — unless it is on the older `assistant_view`), writes the rest of the manifest back as exported. Also runs when Slack is (re)connected and canopy holds a configuration token. A slug over 32 chars is reported, not truncated.
- `PUT /api/slack-config/{workspace}/history` (admin+) — Whether `@canopy <agent> --history --min <n>|--msgs <n>|<time> <ask>` may hand the agent the channel's recent messages, and the longest window.
- `POST /api/slack-config/{workspace}/declare-agent` (owner) — Declare the Slack app an agent (manifest: `features.agent_view`, `assistant:write`, agent events) so Slack draws its own Working… indicator and Stop button. One-way: Slack cannot undo it. Every sync does this too; the endpoint remains for operators.
- `PUT /api/slack-config/{workspace}/channel-ingest` (owner) — `{enabled}`: whether this workspace's agents may ASK to read a whole channel (default off). Off also stops live reads.
- `POST /api/slack-config/{workspace}/channel-ingest/allowed` (admin or owner) — `{agent, channel (id or #name), follow, note}`: allow-lists ONE channel for ONE agent of this workspace, explicitly. When that agent asks for the channel, canopy reads it at once (approved by whoever added the entry) and posts a notice with Revoke in the channel instead of Approve / Decline. Works whether or not the switch above is on; a read-once entry refuses `follow`. Re-posting updates it. Listed in `GET /api/slack-config/{workspace}` as `channel_ingest.allowed`. The agent's own login can never add one.
- `DELETE /api/slack-config/{workspace}/channel-ingest/allowed/{allow_id}` (admin or owner) — removes the entry and revokes every pending or live read it allowed (transcripts deleted). Moving the agent to another workspace deletes its entries.
- `/api/slack-config/` is deliberately not under `/api/slack/`, which is allowlisted for Slack's anonymous signed webhooks. UI: `/w/:workspace/settings/slack`.

**Whole-channel reads for an agent** (`apps/slack/ingest.py`) — the permission is given in Slack, never through this API:
- `POST /api/slack-ingests/` (the agent's own login, or an agent admin) — `{agent, channel (id or #name), purpose, follow}`. Creates a `pending` ingest and posts ONE Approve / Decline message in the channel; reads nothing. An allow-listed channel is refused (409): it is read only when a person types `/<agent> read-channel <ask>` in it, which reads everything since the agent's last read there (`read_mark`) and sends it, with the ask, to the agent in that command's thread. 409 also if the workspace switch is off and the channel is not allow-listed, the agent has no login of its own, a pending/live ingest of that channel exists, or the bot is not in the channel.
- Approval happens on that post (`/api/slack/interactions`): only a channel member (`conversations.members`) who holds `integrations` in the agent's workspace, or the channel's creator — never the agent's own login. Any channel member may decline; a decline is final. Refused clicks are audited.
- `GET /api/slack-ingests/` · `GET /api/slack-ingests/{id}` (agent login, agent admin, workspace admin) — status `pending | reading | ready | declined | revoked | failed`, progress, error.
- `GET /api/slack-ingests/{id}/transcript[?after=<read_mark>]` (the agent's own login ONLY — not its owner) — the channel as Markdown, threads nested; partial while `reading`, whole when `ready`; 409 otherwise. With `after`, only the messages canopy stored since that read mark (a new reply to an old thread included, shown under its already-read parent), plus `total`, `mark` (to record next), `first_ts`/`last_ts`. The mark is a stored-row id, not a Slack ts, so a follow pass that stores an old thread's reply after newer messages is never skipped.
- `POST /api/slack-ingests/{id}/read-mark` `{mark}` (the agent's own login ONLY) — records how far the agent has read (`read_mark`, `read_at` on the ingest); never moves back or past what is stored. `canopy slack ingest transcript` reads `after=read_mark` by default and records the mark only after it has written the output.
- `POST /api/slack-ingests/{id}/revoke` (approver, agent login, agent admin, workspace admin; also the Revoke button on the post) — stops reads (incl. `follow`) and deletes the transcript; on a `pending` one, withdraws it.
- The read runs off-request (a job on `apps/common/ticks.py`, registered by `apps/slack/ingest_scheduler.py`, every `SLACK_INGEST_TICK_S`; `manage.py slack_ingest_tick` by hand): paginated, resumable, parked on Slack's `Retry-After`. Every request, decision, fetch batch, revoke and failure is a `slack.ingest_*` event in the workspace log.

**Who is asking.** A Slack user resolves to a member by an existing link, else by Slack profile email (exactly one active canopy account; never a guest, bot or deactivated user); the installer is linked at install. Anyone else is a `Contact` (`source="slack"`, keyed `<team>:<user>`, graded `slack`) and answered as one; their session has no `created_by`, so no member opens it. Only a blocked contact is refused. A member's session is private to the thread's starter; a member who joins the thread becomes a participant. A confined reply in someone else's thread forks to a thread of its own (`services._fork_confined`); `@canopy branch <ask>` splits a thread's conversation into a new one (`apps/slack/branch.py`). Every message not turned into a turn writes an `apps/events` row (`source="slack"`, `kind="slack.<status>"`).

**Replies and status.** Replies post into the thread (or DM) as the agent (`chat:write.customize`, falling back to the plain bot), converted to mrkdwn and split at 3500 chars, plus a note on a FAILED turn; exactly-once via `SlackRelayPost` (unique `turn, seq`), a failed post writes `slack.relay_failed` and is not retried. A plain reply in a thread canopy has a session for continues it (needs `message.channels`/`message.groups`; everything else is dropped unread). If that thread's agent session was **closed**, a reply that names no agent is never sent and never dropped silently: the first one gets ONE public notice in the thread (per closed session) with a **Start a new session with this thread's context** button, later ones a private pointer to it. The button (`services.restart_from_click`) starts a new session for the clicker in the same thread, seeded with the thread so far plus the latest turned-away message, judged like a message from them (principal, private conversation, access: none → nothing starts, confined in someone else's conversation → the separate-thread fork); one session per thread however many clicks, and the notice loses its button once used. A reply that names the agent asks it as before. An `@canopy` that starts a session partway through a thread hands the agent the thread so far once (`<slack-thread>`, capped by `SLACK_HISTORY_MESSAGE_CEILING`; logs `slack.thread_read`). Redelivery collapses via `client_id = slack:<channel>:<ts>`. A slash command's anchor post IS its status line (edited in place). Status rendering: `chat-sessions.md` § Turn status.

**Dialogs over Slack.** Each dialog that appears/changes posts once per question content (`SlackMenuPost`) as text plus Block Kit (a button per option for one pick-one question, else checkboxes/radios + Submit, plus Dismiss). Thread replies are parsed strictly (`2`, `1,3`, `2; 1`, `cancel`) and go through the same `answer_menu` as the phone; anything else while a parsed dialog is up is not sent. Button values name the session and question key and are re-checked against what is open now; answered posts become "Answered by @x: …". An option-less Notification marker is shown with a link and captures no replies.

**Sharing a session TO Slack** (`apps/slack/share.py`; `POST /api/canopy-sessions/slack/share`, MCP `share_session_to_slack`, `/canopy:share-to-slack`, the chat page's Share to Slack; the summary is always written by the session). **broadcast** posts once; **bind** gives the session the same `slack_*` metadata a Slack-born session has (refused without a resolvable session or when the agent's Slack is off). Re-sharing a bound session posts an update in its own thread. Turns before `slack_bound_at` are not relayed. A **repo session** bound this way accepts replies from workspace members only. When a bound session closes (archived in emdash, closed from canopy, or absent from two consecutive complete reports by its runner — `RunnerBinding.missed_reports`), its thread is told once and later replies get that answer. **Noise sweep**: `GET /api/canopy-sessions/noise` (MCP `audit_session_noise`) reports harness output stored as user messages in sessions you can read; `POST …/noise/purge` (MCP `purge_session_noise`) deletes them, dry run unless `apply`. **Detach** (`POST /api/canopy-sessions/slack/detach`, MCP `detach_session_from_slack`) moves the `slack_*` keys to `metadata.slack_detached`, stops both directions, posts one best-effort note and deletes nothing; re-attaching is a fresh bind. The three routes live in `apps/slack/session_api.py`, mounted at the session paths. Session payloads carry `slack` (the bound thread or null), from the reader Slack registers in `apps/canopy_sessions/channel_bindings.py` — canopy_sessions imports no Slack. **Agents and their own conversation:** an agent's own login cannot read a Slack thread a person started, but `access.own_turn_session` lets it act on the ONE conversation of a turn it is running, named by `turn_id`, while the turn is claimed/running/needs_human: update its thread (`share_session_to_slack` with `turn_id`), detach it, re-bind only in that conversation's own channel, or move it to a new thread there (`POST …/slack/new-thread`). The caller envelope's `conversation.slack` says where the conversation is (`apps/slack/location.py`, cached on the session, never fetched while building). Spec: `docs/superpowers/specs/2026-09-21-share-session-to-slack-design.md`.

### Storyboards (`apps/storyboards`) — the shareable arc
Product tier. `Storyboard → Act → Entry`; an entry names a narrative by slug and resolves to its current release at read time (`Entry.pinned_run_id` holds a known-good run while a narrative is redrafted). `slug` is unique per workspace.
- `GET|POST /api/storyboards/` — List (member) / create (editor+).
- `GET /api/storyboards/{slug}?ws=&t=` — `auth=None`, self-enforcing: member, or a matching `?t=`. A wrong token 404s (never 403). `ws` (the workspace in `/w/<ws>/storyboard/<slug>`) 404s a board elsewhere and disambiguates a slug two workspaces share; the narrative and feedback routes take it too.
- `PATCH /api/storyboards/{slug}` — Retitle / reorder / set capability / replace `brief` (editor+). Acts are replaced wholesale.
- **A board is the one link for a SET of demos.** Optional `brief` on create / patch / YAML import (`StoryboardBrief`, unknown keys 422): `audience`, `purpose` (the point to land), `data_disclosure`, `short_version {label, note, items: [{narrative_slug, cut_id?}]}`, `assumptions[]`, `divergences[{script, data, resolution}]`, `open_questions[]`. Each read entry carries `cuts[]` — a recorded narrative's cuts in running order (`apps/storyboards/cuts.py`): the pinned cut video (`video_url` withheld when this reader cannot stream it), `duration_sec`, `word_count` (counted from the narration), `scenes`, `anchor_id` (`cut:<id>`, what a per-cut note anchors to via `/feedback`), and `screen_notes` / `audience_note` / `provenance` / `poster_url` / `optional` from the version's `request_json.cuts[]` (provenance defaults to the scenes'). A declared cut with no video reads `recorded: false`. Entries also carry the version's own `assumptions` / `divergences` / `open_questions`.
- `POST /api/storyboards/{slug}/share` · `/rotate-token` — Mint the link if missing / re-mint it (kills every link sent). The link is `/w/<ws>/storyboard/<slug>?t=…`.
- `GET /api/storyboards/{slug}/narratives/{narrative_slug}` — The reviewer surface's read (current + previous narration). Same token gate; 404 if the narrative is not on the board.
- `POST /api/storyboards/{slug}/feedback` — Anonymous, capability-gated write. One grant per board: `read` < `comment` < `suggest` (insufficient → 403). `channel`/`target_kind` are server-set; a narrative not on the board → 404. Lives here, not in `apps/feedback`, because the product app owns the token; it calls the request-free `feedback.services.ingest`.
- **Feedback rounds** (`apps/storyboards/rounds.py`; session auth): `POST /api/storyboards/{slug}/rounds` (editor+) — open one: pins every narrative's current version and adopts the notes since the last round; 422 unless the board is linked to a project in its own workspace. `GET …/rounds/{number}` (members; a token holder 404s) — the round in full. `POST …/rounds/{number}/close` `{close_note?, picks?}` (editor+) — applies staged decision edits, then creates and approves ONE task on the board's project (one agent turn); a second close or an unpicked disagreement is 409. `POST …/rounds/{number}/consume` `{run_id}` (editor+, the agent's PAT) — refuses while any note is unanswered; opens round N+1. `DELETE …/notes/{note_id}` (editor+) — remove a note from the OPEN round (409 for one in a closed round).
- `POST /api/storyboards/{slug}/decisions/{key}/edit?t=` — `auth=None`, self-enforcing like the read: confirm / change / write in / undo one decision. Inside an open round every edit is staged (a link holder needs `suggest`, else 403); outside one only a member may (409), and a review-gate row needs editor+. 422 invalid, 409 conflict.
- `GET /api/storyboards/{slug}/notes` — Notes left on the board, members only (a share token never grants it). Never returns `author_email`; refuses a real board exactly like a missing one. `StoryboardOut.is_member` tells the page whether to fetch.
- Act identity is `Act.key` (from the title, or declared `key:` in YAML), never the row id — both write paths recreate acts. One derivation: `apps/storyboards/act_keys.py`.
- Authoring: `manage.py import_storyboard storyboard.yaml --workspace <slug>` — idempotent per `(workspace, slug)`, preserves the share token.

### Huddles (`apps/huddles`, mounted at `/api/huddles`) — derived, no storage
A huddle is agents syncing in rounds, led by one of them (canopy `huddle`; spec in `docs/superpowers/specs/2026-10-16-work-group-huddles-design.md`). Derived from the leader's anchor turn (`origin_ref.kind == "huddle"`, `cli_session_id = huddle:<id>`), round turns (`origin_ref = {kind: huddle_round, huddle, round, member, attempt}`), each member's fenced ```` ```huddle ```` JSON reply (round turn close-out, else a filed close-out, else its transcript), and board tasks whose `source_url` ends `/huddles/<id>`.
- `GET /api/huddles/?agent=&limit=50` — Huddles you can see, newest first; `agent` keeps those it led or joined. Each: type, team, leader, members, `rounds_dispatched`, `finished`, `outcome_count`.
- `GET /api/huddles/{huddle_id}` — A cell per (member, round), latest attempt only, plus `projects` (the proposed projects whose `source_url` is this huddle's page, each the same `ProposedProjectOut` card the project page serves), `tasks` (the tasks it proposed in its check-in's project, each a `ProposedTaskOut` card), `outputs` (loose tasks — huddles filed before proposed projects), `checkin` (`{id, name, project: {agent, ref, name, status, url, workspace}, channel_name, lead_email, run_id, read}` when the anchor's `origin_ref` carries a check-in run — `checkin_run`, or the older `run`/`group_run` — else null) and `deadline_at` (earliest round-1 dispatch + 90 min). Prompts, parsed blocks and the leader's `summary` only where `turn_access.can_read_turn_content` allows, else `content_hidden: true`. A block naming another huddle/round is ignored with `reply_error`. The shapes are a contract with `canopy huddle await/status/resume`.

### Project check-ins (`apps/huddles/checkins.py`, `checkins_api.py`) — spec `docs/superpowers/specs/2026-10-17-project-check-ins-design.md`
The PROJECT is the organizing unit; a check-in is a recurring meeting on it: `ProjectCheckin` (project, name unique per project, topic, lead, optional Slack channel, `agent_members` ⊇ `project.agent` (a project needs a lead agent to have a check-in), a 1:1 `AgentSchedule` on `project.agent`) and `CheckinRun` (`checkin` SET_NULL, `project`, a `participants` snapshot, `tasks_proposed`; `awaiting_confirm → reading → running → done`, or `skipped`/`expired`/`failed`). One agent → `format: solo`; more → `huddle`, led by the project's agent. **A check-in's channel is read only when its lead presses Confirm on the run's announcement in Slack** (`slack.ingest.start_group_read`, called only from that click); no route here can start a read (`tests/test_project_checkins.py::test_no_api_or_web_path_starts_a_read`). A check-in **without a channel** reads nothing: firing queues the agent's turn directly (no Slack post, no Confirm).
- `GET|POST /api/agents/{slug}/projects/{ref}/checkins/` · `GET|PATCH|DELETE …/checkins/{name}` · `POST …/checkins/{name}/run-now` (202). Reads: members. Writes: the project's `owner_user`, or a workspace owner/admin (`integrations`) — putting a NEW channel on the agent's read list is owner/admin only, and an agent's own login can't add one to its own list, but any writer reuses an entry already there (`added_allowance` false; never removed by the check-in). Save checks, refusing with a plain reason: the lead is a workspace member (and, with a channel, in it: `users.lookupByEmail` + paged `conversations.members`); `project.agent` may RUN every other agent (`topology.can_run`). Other agents become `checkin` participants, the lead a `manual` one. Delete keeps the runs. Run now announces (or, with no channel, queues the turn) — it never reads.
- `GET /api/agents/{slug}/projects/{ref}/checkin-runs` — the project's timeline, newest first, each run with `tasks` (what it proposed, live, with `spawned` projects) and `projects` (a pre-check-in huddle's proposed projects, by `huddle_id`). `GET /api/checkins/` — every check-in in your workspaces (navigation).
- **Firing.** `fire_schedule` / `run_schedule_now` on a check-in's schedule create the run (idempotent per slot; `read_since` fixed at announce: the check-in's last read end, or one cadence back), re-check lead and agents (a failure marks it `failed` + an Event, nothing posted), and with a channel post the announcement with Confirm/Skip; `POST /api/harness/schedules/{id}/fire` answers `202 {announced, run_id, status}`. Only the lead's click counts; 24 h unconfirmed → `expired` (`checkins.expire_due` on the channel-ingest loop). Confirm reads for `project.agent` with `pending_ask={"checkin_run": id}` (an older `group_run` key still lands); `deliver_read` cuts the transcript to `read_since`, skips canopy's own posts, stores the material, moves the read mark and queues the turn: prompt `<schedule prompt> --checkin-run <id>`, `origin_ref {kind: checkin_run, checkin, checkin_name, run, project, slot, schedule_id, schedule_name}`, key `checkin-run:<id>`, never late-slot-skipped.
- `GET /api/checkins/runs/{id}` (member, or the project agent's login; includes `material`) · `POST /api/checkins/runs/{id}/finished` `{huddle_id?, result_url, summary, tasks_proposed?, update?: {health, body}}` — the project's lead agent's own login only; `update` drafts the project's status update for a person to publish; 409 unless `running` (idempotent once `done`); `tasks_proposed` defaults to the tasks filed with this `run`. Posts ":white_check_mark: done — N proposed tasks: <link>" in the thread.
- `/api/huddle-groups/*` is gone (404); a run is read and finished only through `/api/checkins/runs/{id}`.
- **Outputs are proposed TASKS** (`apps/agents/proposals.py`): `POST /api/agents/{slug}/projects/{ref}/tasks/propose/` `{title, why, done_when, plan[], partners[], source_url, run?, new_evidence?}` → one `suggested` task (`origin_ref {kind: checkin_proposal, checkin, run, runs, huddle_id, done_when, proposed_at}`), its plan as child tasks, a linked task per partner; 201 created / 200 revised (same open title: backings go stale) / 409 declined before without `new_evidence`. Start/Decline are the task's own approve/decline, by the project's owner, the check-in's lead, or `projects.decide`; 14 days undecided → declined "not taken up". Backings: `GET|PUT|DELETE …/projects/{ref}/tasks/{task}/backings/…` (`me/`, `agents/{agent}/`) — `ProjectBacking` is on a project OR a task. `AgentProject.spawned_from` (a task): `projects/propose/ from_task: "<agent>/<ext_id>"`, or `PATCH …/projects/{ref}/ {spawned_from}`.

### Embedded widget (`apps/embedding/embed_api.py`, mounted at `/api/embed`)
The host-facing contract is `docs/architecture/embedding-a-canopy-agent.md`; internals in `embedding-internals.md`.
- `GET /api/embed/agents` — Agents the acting app may offer that the caller can also reach (app allowlist ∩ the viewer's memberships), each with its workspace, `default` (the one to open on: the bound agent, else the caller's preferred agent, else the site's default — each only if listed) and `preferred`.
- `PUT /api/embed/default-agent` (`{agent}`) — Make one of the agents this site offers the caller their preferred agent (`""` clears); another is 404. A person's account only. Audited.
- `GET /api/embed/self` — Whether canopy's own frontend should mount the widget at all.
- `POST /api/embed/token?page=` — canopy's own host-side token endpoint: a short-lived delegated token for the signed-in user (session-authenticated). For a `page` in `self_host.PAGE_SCOPES`, when the self site's `host_issuer`/`host_mcp_resource` name this deployment, canopy also signs and redeems an ID-JAG for that page's scopes — only when the body says `{"grant": true}`, which the panel sends once the person has sent from it (pages, scopes and tools: [embedding-a-canopy-agent.md §11](embedding-a-canopy-agent.md#canopy-web-as-a-host-of-its-own-mcp-agents-act-as-you-on-canopys-pages)); `host_grant` says whether it holds one, and the token points at it.
- `GET /api/embed/host-grant` · `DELETE /api/embed/host-grant` — the act-as-you permission (host grant) the panel's own token carries, `{grant: {id, site, agent, agent_name, scope, granted_at, expires_at, confirmed, requested, requested_reason} | null}` (unconfirmed while it waits for the passkey; `requested` once an agent's turn needed it — canopy pushes `host_grant.requested` to the panel then — with the agent's `requested_reason`), and the panel's Stop: revokes that page's whole permission (`host_grants.revoke`), audited as a setting. A contact holds none.
- `POST /api/embed/host-grant/confirm/begin` · `POST /api/embed/host-grant/confirm/finish` — confirm the waiting grant with one of the token's user's own passkeys (WebAuthn options, then `{credential}`); 404 with none waiting, 409 `no_passkey`, 400 on a failed assertion. Confirmed, it lasts 30 minutes from the touch (`host_grants.confirm`), audited as a setting. The panel's token is enough to ask; only the assertion, signed over canopy's origin, confirms.
- `POST /api/embed/ws-ticket` — Single-use, short-lived ticket to open a chat socket with (`?ticket=`), standing for the presented delegated token; fetch one per connection.
- `GET /api/embed/sessions/{session_id}/agent-memory` — Read-only agent-memory state for the widget (see People).

### Mail (`apps/mail`) — workspace email domains
Product tier, removable (`docs/architecture/mail.md`). With `MAIL_ENABLED` off only the add, send/reply and inbound paths refuse (add and send 503; inbound is acknowledged `dropped:mail-off`); reads, routes and removals still work.
- `GET /api/mail/domains/{workspace}` (member) · `POST …` (`integrations`) — A workspace's domains with DNS rows and status, plus list-level `can_manage` (`integrations` here); add one (409 if the name is already owned anywhere, unless the holder is still `pending` past `MAIL_PENDING_DOMAIN_TTL_DAYS` and SES confirms it never verified, which is released first).
- `POST /api/mail/domains/{workspace}/{domain_id}/refresh` (member) — Re-check DNS and SES verification now. When SES gave up verifying (DKIM or MAIL FROM `FAILED`) and those records check out in live DNS, it also restarts SES verification (at most every 10 min per domain, audited as a setting); `restart_note` says what it did. Every domain output carries `verification_error` (why SES stopped verifying, `""` otherwise).
- `PATCH /api/mail/domains/{workspace}/{domain_id}` (`integrations`) — `daily_send_cap`; `unsuspend: true` re-enables a suspended domain (saves only the fields it changes, so a concurrent auto-suspension is not undone). `DELETE …` removes the domain, its routes and its SES identity; threads and messages are kept.
- `PUT /api/mail/domains/{workspace}/{domain_id}/routes` (`integrations`) — Create or update a route by `local_part` (`*` = catch-all; kind `agent` | `forward` | `drop`; a forward goes only to a workspace member's login email; the catch-all cannot be `agent`, 422). `DELETE …/routes/{route_id}` — the address stops receiving mail; its threads and messages are kept.
- `PUT /api/mail/domains/{workspace}/{domain_id}/shares` (`superuser`) — `{workspace, daily_send_cap?}`: let that workspace and every workspace below it hold addresses on the domain (`{workspace}` is the domain's own; the caller need not be a member). `DELETE …/shares/{share_workspace}` stops it; the shared workspace's routes go inert, nothing is deleted. The list then includes shared domains for each covered workspace with `owned: false`, `owner_workspace`, no DNS records, only that workspace's routes, and its own `daily_send_cap`; `can_share` and `shares` are answered for superusers on an owned domain. A route on a shared domain is first come, first served (409 when another workspace holds it) and may not be the catch-all or a role address (422).
- `GET /api/mail/resolve?address=` · `?thread=<uuid>` (authenticated) — `{backend: "ses", workspace, agent, address}` only if the caller is a member of the address's (or the `MailThread`'s) workspace, else 404 (the canopy CLI then uses Gmail; a Gmail thread id is 404); neither param is 422. For a thread, `address` is the thread's own snapshot.
- `GET /api/mail/agents/{slug}/mailbox` (member) · `PUT …` `{address}` (owner or agent admin) — Where `Agent.email` lives (`kind` hosted | google | none, `live`, `route`), plus `addresses`: every address the agent has, `[{address, backend: "ses"|"gmail", primary}]` — its own (`primary`), its enabled agent routes, its Gmail push mailboxes, lowercase, each once; `used_bytes` (what the hosted address's mailbox holds, 0 otherwise) and `cap_bytes` (`MAIL_MAILBOX_CAP_BYTES`, past which its oldest mail is evicted — `docs/architecture/mail.md` § Mailbox cap). A second address is just another `kind: agent` route (`PUT …/routes` above). The PUT sets `Agent.email` and routes it at once when it is on a hosted domain and the caller has `integrations`.
- `GET /api/mail/threads/{workspace}?agent=&archived=` (member) · `GET …/{uuid}` — Threads and one thread's messages (attachments as short-lived presigned URLs — one over the per-message attachment limit has `kept: false` and no `url`; each message's SES `verdicts`); `counterpart` is the newest message's other party on both; `address` is the thread's own snapshot, `agent` is `""` once its route is gone. With `agent=`, `agent_address` is the agent's default From here: the route for `Agent.email`, else its first non-catch-all route by domain then local part.
- `POST /api/mail/threads/{workspace}/{uuid}/reply` · `POST /api/mail/send/{workspace}` (`agent.work`) — Reply in a thread (from the thread's route address) / start one (from `from_address` — one of the agent's enabled, live routes in this workspace, case-insensitive, else 422 "not one of this agent's addresses" — or by default from `agent_address`); enforces the domain's status and `daily_send_cap` (under a row lock); a reply with no `to` goes to the newest inbound message's Reply-To when it is on the sender's domain, else its sender (the thread detail's `default_reply_to`); also needs `access.decide` FULL on the agent. A reply on a thread whose route is gone or disabled is 409. `POST …/threads/{workspace}/{uuid}/state` (`agent.work`) — `{unread?, archived?}` (409 once the route is gone).
- `POST /api/mail/ses/inbound/` · `POST /api/mail/ses/events/` — SNS doors, `auth=None`, allowlisted in `apps/common/middleware.py`, self-enforcing: the SNS signature and topic ARN are verified before the body is read. A 4xx fetching the signing cert or SubscribeURL is 404; a network error, timeout, TLS error or 5xx is 500 so SNS retries. Inbound stores/forwards/drops (500 only for a transient failure SNS should retry); events update delivery status and the reputation guard, counting a redelivered event once. A verified Notification whose Message is not a JSON object is acknowledged 200 `{ignored}` and logged at INFO.
