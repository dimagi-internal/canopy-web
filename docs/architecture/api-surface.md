# API surface

Every route canopy-web serves, and the rules a schema cannot express (gates, refusals, invariants).
The machine-readable schema is `/api/openapi.json` (Scalar at `/api/docs/`, Redoc at `/api/redoc/`); frontend types are generated from it into `frontend/src/api/generated.ts`.
All routes are Django Ninja (Pydantic v2) under `/api/` unless marked as a bare view; errors are RFC 7807 `application/problem+json`.
The canonical tenant URL is `/api/w/{ws}/…`: `apps/api/tenancy.py::WorkspaceResolveMiddleware` 404s a non-member, pins `request.workspace_slug`, strips the prefix and reroutes to the flat mount, so the schema stays single. Handlers read `getattr(request, "workspace_slug", None)` (truthy = pinned, `None` = unpinned). What an unpinned list or create covers: [roles.md § A read that names no workspace stays inside one organisation](roles.md#a-read-that-names-no-workspace-stays-inside-one-organisation).

## Errors
Every error is RFC 7807 `application/problem+json`: `{type, title, status, detail?, instance?, extras?}` plus any extension members at the top level.
- `title` is stable per `type`; the per-occurrence message is always `detail`, so a client shows `detail` and falls back to `title` (`frontend/src/api/problem.ts::problemMessage`).
- A bare `HttpError(status, msg)` in a route becomes `type: about:blank`, `title` = the status's reason phrase (`"Not Found"`, `"Forbidden"`…), `detail` = `msg` (`apps/api/api.py::_on_http_error`).
- `ProblemError(status, title, type_=TYPE_…, detail=, members=, headers=)` (`apps/api/errors.py`) sets a typed problem; `members` are top-level keys a client branches on (`error: "step_up_required"`, `error: "device_proof_required"`), `headers` adds response headers (`WWW-Authenticate`).
- Outside a Ninja route (middleware, bare views) build the body with `apps.api.errors.problem_response(status, *, type, title, detail, **members)` — never by hand: it JSON-escapes text taken from the request (the tenancy 404 names the URL's slug) and defaults `title` the same way.
- **The schema says what a well-formed request is.** A rule JSON Schema can state goes in the schema: a length, a range, a `Literal`, a `pattern`. One it cannot — across fields, or against stored state — is declared on the route with `response={201: X, **refusals(422)}` (`apps/api/errors.py::refusals`) and said in its docstring; a declared refusal is documented as `application/problem+json`. The nightly contract fuzz (`tests/contract/`) accepts exactly the declared statuses as refusals of a schema-valid request.
- `apps/api/openapi_doc.py` corrects Ninja's document in one pass: every free-text request string gets a `pattern` excluding NUL (PostgreSQL refuses it in text and jsonb; the 400 "Value cannot be stored" handler answers it), and declared refusals are problem+json. Free-form JSON (`dict`, `Any`) cannot say that in JSON Schema, so `apps/api/nul_guard.py` (middleware) refuses a NUL anywhere in a JSON body under `/api/` — value or key, any depth — with that same 400, before any view runs; multipart and other bodies are not read. A `StrictModel` string with a minimum length is documented as already trimmed (`apps/common/schemas.py::strip_means_non_blank`), since it is stripped before it is measured.

## Auth + session (root)
- `GET /api/me/` — current user. `passkeys_here: false` on a session minted from a token (the Canopy Runner app's), on which every step-up and approval is refused: the SPA then hands each passkey moment to the browser (`frontend/src/auth/passkeyHere.ts`). `GET /api/health/` — health check (`auth=None`). The top-level `GET /health/` (also public) adds `runner_code_sha`, the laptop runner version this deployment ships, which a developer-install updater reads when canopy refuses its token (`runner/canopy_runner/canopy_runner/update.py`).
- `GET /api/csrf/` — CSRF token bootstrap (bare view). `GET /api/_auth_smoke/` — internal smoke check of session auth (returns the caller's email).
- `GET|PATCH /api/me/presence-preference/` — the user's presence-visibility opt-out (`docs/architecture/chat-sessions.md` § Viewer presence).
- `GET|PATCH /api/me/runner-app/` — `{opens_on: "supervisor"|"ide"}` (GET also returns `choices`, the pages offered, which the app's right-click menu → Opens on lists), the page the Canopy Runner desktop app opens on (`RunnerAppPreference`; default supervisor). The app loads the bare view `/runner-app/`, which 302s there — a new page is a new choice here, with no change on the box.
- `GET|PUT /api/me/canopy-projects/` — `{everything, projects}` (GET also returns `available`: the repos your own runners report, plus any you named), the repos canopy works in for you (`ProjectOptIn`; unset = none). A repo outside it is plain Claude Code: no repo turn routes there, no session, transcript or usage is mirrored from it. An agent's repo always counts. Audited setting → `docs/architecture/runners.md` § Opted-in projects.
- `GET /api/me/session-sharing/`, `PUT /api/me/session-sharing/{project_id}` `{shared}` — the projects in your workspaces whose repo you work in, and whether your laptop sessions in that repo are shared with the project's team (`ProjectSessionShare`; unset = not shared). On, the team (its owner and participants, never an agent login) reads, writes and may pull them; never a sensitive one. Audited setting → `docs/architecture/access-sessions-and-people.md` § Who can see a session.
- `GET|PATCH /api/me/session-workspace/` — the workspace NEW emdash sessions your runners discover are filed in when the emdash project is not an agent's (an agent's follows the agent). Must be a workspace you are editor+ in; blank clears (falls back to the runner's workspace); existing sessions stay put (move one with `POST /api/canopy-sessions/{id}/move`).
- `GET|POST /auth/cli/authorize/` — bare view (`apps/tokens/cli_authorize_views.py`). gh-style loopback: a signed-in browser mints a `PersonalToken` and 302s it to a local CLI callback (callback must be a safe loopback target). Pairs with `/canopy:canopy-web-pat-mint`.
- `GET /download/runner/<platform>` — bare view (`apps/harness/views.py::download_runner`): signed in → 302 to a 15-minute presigned URL for the deployed runner version's installer; signed out → sign in and back; unknown platform or nothing built → 404 (an HTML page saying so). See **Runner releases** below.
- `GET /auth/github/start/` · `GET /auth/github/callback/` — bare views, signed-in only: the per-user GitHub App connect flow (`apps/github_connect/github_app.py`). The callback path is registered on the GitHub App.
- `GET|POST /auth/connections/{provider}/{workspace}/start/` · `GET /auth/connections/{provider}/{workspace}/callback/` — bare views, signed-in only (`apps/connections/views.py`): the OAuth connect flow through that workspace's app (`docs/architecture/vault-connections.md` § OAuth connections are sealed to their owner). `start` takes `return_to` (a same-site path, else `/settings`), `temporary=1` with `for_agent=<slug>` for an access token alone (`vault.md` § Lending for an hour; no vault key, lands back on `return_to` with `status=ok`; `temporary_unsupported`, `bad_agent`), for a person's flow the limits `lend_minutes` (5-10080; anything else lands `bad_lend`) and `owner_turns_only=1` and `for_agent=<slug>` (ticks that agent on the share screen, granting nothing), and `agent=<slug>` to connect for an agent (the agent must be in that workspace, else 404; caller must be an admin of it, else 403; asked again at the callback, since admin may be revoked in between). A person needs read on the workspace (else 404). An agent's start is a CSRF-checked **POST only** (a GET naming `agent` is 405) and passes the provider's agent parameters (Salesforce: `prompt=login consent`; Google: `select_account` and a `login_hint`), so the account attached is the one typed in, not the admin's browser session. A person's flow finishes only for the user who started it (`forbidden` otherwise); a callback whose workspace or provider differs from the parked flow is `bad_state`. The callback registered with the provider is `/auth/connections/<provider>/<workspace>/callback/` (shown in Settings). Connecting needs the owner's vault key (the person's, or the connecting admin's for an agent): the token is sealed to it at the callback, and nothing readable is kept. A connect that succeeds lands on the success screen, `/w/<workspace>/connections/<id>/connected?return_to=<return_to>`, or, when it named limits or `for_agent` (that flow exists to be shared), straight on the share screen, `/w/<workspace>/connections/<id>/share?return_to=<return_to>`, plus `&agent=<for_agent>` when named; anything else lands on `return_to` with `?connection=<provider>&status=error&reason=`; reasons `not_configured` (no app in that workspace), `no_vault_key` (at start, with `setup=` naming where to set one up; nothing is begun), `bad_lend`, `bad_state`, `forbidden`, `access_denied`, `insufficient_scope` (the grant lacks a scope the provider requires; nothing is stored), `wrong_account` (the signed-in account fails the app's rule; nothing is stored), `provider_error` (a provider that cannot be reached is also `provider_error`). An unknown provider, or an unknown `agent` slug on `start`, is 404.
- `POST /api/auth/contact-token` — `auth=None`; the credential is a host site's **signed assertion** about its visitor (`apps/contacts/contact_api.py`, `assertions.py`). Arrival (`contacts.services.resolve_arrival`): an already-linked contact, or `email` + `email_verified: true` held verified by exactly one active canopy user who is a member of the site's workspace → a delegated USER token (`kind: "user"`, `DelegatedToken.assurance = host_signed`); otherwise a contact token (`kind: "contact"`). Never creates an account; membership is the whole gate. A signed `canopy_agent` claim (a page that chose its agent) must equal `agent_slug` (400 `agent_mismatch`) and be on the site's allow-list (403); the minted token (`bound_agent`) and the `HostGrant` it redeems (`agent`) then serve that one agent — `delegation.offered_for`, the contact routes' `_bound`, the chat socket, and `host_grants.grant_for` for the gateway and Views (`docs/architecture/embedding-advanced.md` § 5c).
  - **Host grant at arrival** (contract: `sdk/python/README.md`): the body may carry `id_jag`, an ID-JAG the site signed for its own MCP server naming the same visitor. When the site has `host_issuer` + `host_mcp_resource`, canopy verifies it (site keys, `typ: oauth-id-jag+jwt`, `iss`=`aud`=issuer, `client_id`=canopy, `resource`, `sub` = the assertion's `sub`, ≤300s), discovers the token endpoint (RFC 8414, `issuer` checked), redeems it (jwt-bearer + `private_key_jwt` + DPoP + `resource`) and stores the DPoP-bound token Fernet-encrypted as a `HostGrant` keyed (site, visitor). A refusal never fails the arrival: the chat opens and an `Event` (`tokens.host_grants`) says why. Response `host_grant` says whether one was redeemed (never for a contact, who has no passkey to confirm it with; the grant is unusable until the person confirms it in the panel); if so the token lives 10 minutes so the widget re-mints about every 5. Every outbound fetch is https-only, refuses private addresses and follows no redirects (`apps/host_grants/outbound.py`).
- **MCP client sign-in (OAuth)** — bare views (`apps/oauth_server/mcp_oauth.py`): `POST /oauth/register` (RFC 7591; public PKCE clients only; rate-limited per IP; redirect URIs https, http-to-loopback, or a private-use scheme), `GET|POST /oauth/authorize` (consent page; needs a signed-in person and refuses a token-minted session; an unknown client or unregistered redirect is shown, never redirected to), and the `authorization_code` (PKCE S256 required) + `refresh_token` grants at `POST /oauth/token`. The access token is a `PersonalToken` tied to an `OAuthGrant`; lifetimes, rotation and reuse revocation: [mcp-surface.md § Auth model](mcp-surface.md#auth-model). `GET /api/tokens/authorized-apps` lists the caller's grants plus the MCP address; `DELETE /api/tokens/authorized-apps/{grant_id}` revokes one at once (no refresh).
- `GET /oauth/client.json` · `GET /oauth/jwks.json` — bare, public: canopy's OAuth CLIENT identity. The first is the Client ID Metadata Document whose URL IS canopy's `client_id`; the second the public CLIENT key (`use: sig`, RFC 7638 `kid`, EdDSA or ES256). The DPoP key is never published. 503 without `CANOPY_OAUTH_CLIENT_KEY` / `CANOPY_OAUTH_DPOP_KEY`. Neither key can assert a user (`apps/host_grants/client_identity.py`).
- **canopy-web as host of its own MCP** (`apps/host_grants/self_host.py`) — bare, public; the host half is off until `CANOPY_HOST_SIGNING_KEY` and the client keys are set: `POST /oauth/token` also serves the jwt-bearer grant (RFC 7523 + `private_key_jwt` + DPoP) for ONE client, canopy's own `client_id`, via the SDK's `GrantHandler`; `GET /oauth/host/jwks.json` (the HOST signing key, distinct from `/oauth/jwks.json`; what the `canopy-web` host site's JWKS URL names); `POST /oauth/probe` (live probe of the host half: a real ID-JAG for the dedicated probe user `CANOPY_HOST_PROBE_USERNAME`, for canopy's own client only, authenticated like the token endpoint; 404 while there is no probe user); `GET /.well-known/oauth-authorization-server[/…]` and `GET /.well-known/oauth-protected-resource[/…]` (RFC 8414 / 9728 for `{base}` and `{base}/api/mcp/`; always served, folding in the jwt-bearer grant only when the host half is configured). canopy's own redemption reaches these in-process (`self_host.loopback_*`, consulted by `outbound.py` and `jwks.py`); the gateway's MCP call is real HTTP to `{base}/api/mcp/`.
