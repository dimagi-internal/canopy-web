# API surface

Every route canopy-web serves, and the rules a schema cannot express (gates, refusals, invariants).
The machine-readable schema is `/api/openapi.json` (Scalar at `/api/docs/`, Redoc at `/api/redoc/`); frontend types are generated from it into `frontend/src/api/generated.ts`.
All routes are Django Ninja (Pydantic v2) under `/api/` unless marked as a bare view; errors are RFC 7807 `application/problem+json`.
The canonical tenant URL is `/api/w/{ws}/…`: `apps/api/tenancy.py::WorkspaceResolveMiddleware` 404s a non-member, pins `request.workspace_slug`, strips the prefix and reroutes to the flat mount, so the schema stays single. Handlers read `getattr(request, "workspace_slug", None)` (truthy = pinned, `None` = unpinned). What an unpinned list or create covers: [roles.md § A read that names no workspace stays inside one organisation](roles.md#a-read-that-names-no-workspace-stays-inside-one-organisation).

### Errors
Every error is RFC 7807 `application/problem+json`: `{type, title, status, detail?, instance?, extras?}` plus any extension members at the top level.
- `title` is stable per `type`; the per-occurrence message is always `detail`, so a client shows `detail` and falls back to `title` (`frontend/src/api/problem.ts::problemMessage`).
- A bare `HttpError(status, msg)` in a route becomes `type: about:blank`, `title` = the status's reason phrase (`"Not Found"`, `"Forbidden"`…), `detail` = `msg` (`apps/api/api.py::_on_http_error`).
- `ProblemError(status, title, type_=TYPE_…, detail=, members=, headers=)` (`apps/api/errors.py`) sets a typed problem; `members` are top-level keys a client branches on (`error: "step_up_required"`, `error: "device_proof_required"`), `headers` adds response headers (`WWW-Authenticate`).
- Outside a Ninja route (middleware, bare views) build the body with `apps.api.errors.problem_response(status, *, type, title, detail, **members)` — never by hand: it JSON-escapes text taken from the request (the tenancy 404 names the URL's slug) and defaults `title` the same way.

### Auth + session (root)
- `GET /api/me/` — current user. `GET /api/health/` — health check (`auth=None`). The top-level `GET /health/` (also public) adds `runner_code_sha`, the laptop runner version this deployment ships, which a developer-install updater reads when canopy refuses its token (`runner/canopy_runner/canopy_runner/update.py`).
- `GET /api/csrf/` — CSRF token bootstrap (bare view). `GET /api/_auth_smoke/` — internal smoke check of session auth (returns the caller's email).
- `GET|PATCH /api/me/presence-preference/` — the user's presence-visibility opt-out (`docs/architecture/chat-sessions.md` § Viewer presence).
- `GET|PATCH /api/me/runner-app/` — `{opens_on: "supervisor"|"ide"}` (GET also returns `choices`, the pages offered, which the app's right-click menu → Opens on lists), the page the Canopy Runner desktop app opens on (`RunnerAppPreference`; default supervisor). The app loads the bare view `/runner-app/`, which 302s there — a new page is a new choice here, with no change on the box.
- `GET|PUT /api/me/canopy-projects/` — `{everything, projects}` (GET also returns `available`: the repos your own runners report, plus any you named), the repos canopy works in for you (`ProjectOptIn`; unset = none). A repo outside it is plain Claude Code: no repo turn routes there, no session, transcript or usage is mirrored from it. An agent's repo always counts. Audited setting → `docs/architecture/runners.md` § Opted-in projects.
- `GET|PATCH /api/me/session-workspace/` — the workspace NEW emdash sessions your runners discover are filed in when the emdash project is not an agent's (an agent's follows the agent). Must be a workspace you are editor+ in; blank clears (falls back to the runner's workspace); existing sessions stay put (move one with `POST /api/canopy-sessions/{id}/move`).
- `GET|POST /auth/cli/authorize/` — bare view (`apps/tokens/cli_authorize_views.py`). gh-style loopback: a signed-in browser mints a `PersonalToken` and 302s it to a local CLI callback (callback must be a safe loopback target). Pairs with `/canopy:canopy-web-pat-mint`.
- `GET /download/runner/<platform>` — bare view (`apps/harness/views.py::download_runner`): signed in → 302 to a 15-minute presigned URL for the deployed runner version's installer; signed out → sign in and back; unknown platform or nothing built → 404 (an HTML page saying so). See **Runner releases** below.
- `GET /auth/github/start/` · `GET /auth/github/callback/` — bare views, signed-in only: the per-user GitHub App connect flow (`apps/github_connect/github_app.py`). The callback path is registered on the GitHub App.
- `POST /api/auth/contact-token` — `auth=None`; the credential is a connected site's **signed assertion** about its visitor (`apps/contacts/contact_api.py`, `assertions.py`). Arrival (`contacts.services.resolve_arrival`): an already-linked contact, or `email` + `email_verified: true` held verified by exactly one active canopy user who is a member of the site's workspace → a delegated USER token (`kind: "user"`, `DelegatedToken.assurance = host_signed`); otherwise a contact token (`kind: "contact"`). Never creates an account; membership is the whole gate. A signed `canopy_agent` claim (a page that chose its agent) must equal `agent_slug` (400 `agent_mismatch`) and be on the site's allow-list (403); the minted token (`bound_agent`) and the `HostGrant` it redeems (`agent`) then serve that one agent — `delegation.offered_for`, the contact routes' `_bound`, the chat socket, and `host_grants.grant_for` for the gateway and Views (`docs/architecture/embedding-a-canopy-agent.md` § 5c).
  - **Host grant at arrival** (contract: `sdk/python/README.md`): the body may carry `id_jag`, an ID-JAG the site signed for its own MCP server naming the same visitor. When the site has `host_issuer` + `host_mcp_resource`, canopy verifies it (site keys, `typ: oauth-id-jag+jwt`, `iss`=`aud`=issuer, `client_id`=canopy, `resource`, `sub` = the assertion's `sub`, ≤300s), discovers the token endpoint (RFC 8414, `issuer` checked), redeems it (jwt-bearer + `private_key_jwt` + DPoP + `resource`) and stores the DPoP-bound token Fernet-encrypted as a `HostGrant` keyed (site, visitor). A refusal never fails the arrival: the chat opens and an `Event` (`tokens.host_grants`) says why. Response `host_grant` says whether one was redeemed; if so the token lives 5 minutes so the widget re-mints on that cadence. Every outbound fetch is https-only, refuses private addresses and follows no redirects (`apps/host_grants/outbound.py`).
- **MCP client sign-in (OAuth)** — bare views (`apps/oauth_server/mcp_oauth.py`): `POST /oauth/register` (RFC 7591; public PKCE clients only; rate-limited per IP; redirect URIs https, http-to-loopback, or a private-use scheme), `GET|POST /oauth/authorize` (consent page; needs a signed-in person and refuses a token-minted session; an unknown client or unregistered redirect is shown, never redirected to), and the `authorization_code` (PKCE S256 required) + `refresh_token` grants at `POST /oauth/token`. The access token is a `PersonalToken` tied to an `OAuthGrant`; lifetimes, rotation and reuse revocation: [mcp-surface.md § Auth model](mcp-surface.md#auth-model). `GET /api/tokens/connected-apps` lists the caller's grants plus the MCP address; `DELETE /api/tokens/connected-apps/{grant_id}` revokes one at once (no refresh).
- `GET /oauth/client.json` · `GET /oauth/jwks.json` — bare, public: canopy's OAuth CLIENT identity. The first is the Client ID Metadata Document whose URL IS canopy's `client_id`; the second the public CLIENT key (`use: sig`, RFC 7638 `kid`, EdDSA or ES256). The DPoP key is never published. 503 without `CANOPY_OAUTH_CLIENT_KEY` / `CANOPY_OAUTH_DPOP_KEY`. Neither key can assert a user (`apps/host_grants/client_identity.py`).
- **canopy-web as host of its own MCP** (`apps/host_grants/self_host.py`) — bare, public; the host half is off until `CANOPY_HOST_SIGNING_KEY` and the client keys are set: `POST /oauth/token` also serves the jwt-bearer grant (RFC 7523 + `private_key_jwt` + DPoP) for ONE client, canopy's own `client_id`, via the SDK's `GrantHandler`; `GET /oauth/host/jwks.json` (the HOST signing key, distinct from `/oauth/jwks.json`; what the `canopy-web` Connected site's JWKS URL names); `POST /oauth/probe` (live probe of the host half: a real ID-JAG for the dedicated probe user `CANOPY_HOST_PROBE_USERNAME`, for canopy's own client only, authenticated like the token endpoint; 404 while there is no probe user); `GET /.well-known/oauth-authorization-server[/…]` and `GET /.well-known/oauth-protected-resource[/…]` (RFC 8414 / 9728 for `{base}` and `{base}/api/mcp/`; always served, folding in the jwt-bearer grant only when the host half is configured). canopy's own redemption reaches these in-process (`self_host.loopback_*`, consulted by `outbound.py` and `jwks.py`); the gateway's MCP call is real HTTP to `{base}/api/mcp/`.

### Workspaces (`apps/workspaces`) — multi-tenancy
`Workspace` + members (`owner` / `admin` / `editor` / `viewer`) + email invites; workspaces nest (owners of a parent own the children). Gates use `apps/workspaces/permissions.py` (`docs/architecture/roles.md`).
- `POST /api/workspaces/` create · `GET /api/workspaces/` list mine · `GET /api/workspaces/{slug}/` (member) · `DELETE /api/workspaces/{slug}/` (owner; only an empty workspace — never one that still owns agents).
- `PUT /api/workspaces/{slug}/parent` — move in the tree (`parent: null` = root). Owner of both the moved workspace and the new parent; a cycle is 422. Someone who owns it only through its parent gets 409 making it a root, or moving it where a current owner would lose it.
- `GET /api/workspaces/{slug}/members/` (member) — includes parent-workspace owners with `inherited: true` (changed on the parent).
- `PATCH|DELETE /api/workspaces/{slug}/members/{user_id}/` — change role / remove (admin or owner; an admin manages only roles strictly below its own). Role change is idempotent; demoting or removing the last owner is 400 (`services.is_last_owner`).
- `GET|POST /api/workspaces/{slug}/system-accounts/` · `GET|PATCH|DELETE …/{account_id}/` · `POST …/{account_id}/senders/` · `DELETE …/senders/{sender_id}/` — members that can never sign in, standing in for automated senders (e.g. CloudWatch alarm mail): aligned mail from a bound address in THIS workspace whose subject matches makes agent turns as this account instead of as a contact. Read: member; write: admin or owner. Role editor (default) or viewer, never above. Delete drops its membership and bindings and its past turns lose their initiator — disable it to keep the name.
- `POST /api/workspaces/{slug}/invites/` (admin or owner) — emails the accept link through SES (`apps/common/email.py`); `email_status` (`sent` / `throttled` / `not_configured` / `failed`) says whether it went out, and the link in `token` works either way. Inviting an address with an outstanding invite returns that invite and re-sends, at most once a minute (its token is unchanged).
- `GET /api/workspaces/{slug}/invites/` (member) — `token` is filled only for owners.
- `POST /api/workspaces/{slug}/invites/{invite_id}/revoke` (admin or owner).
- `POST /api/workspaces/{slug}/invites/{invite_id}/reissue` (admin or owner) — new token + fresh 14-day expiry, emailed; the old link dies. Works on an expired invite; 410 on accepted/revoked; 429 if emailed under a minute ago (checked before rotating).
- `GET /api/workspaces/invites/{token}/preview` — `auth=None`, minimal disclosure (a dead token reveals only that it is dead). Drives `/invite/:token`. `POST /api/workspaces/invites/{token}/accept` — accept.
- **Access requests** (`docs/architecture/access.md` → "Getting into a workspace"; nothing joins automatically): `GET /api/workspaces/requestable` — workspaces whose server-only `access_request_domains` include the caller's email domain and they are not in, with their open request. `POST /api/workspaces/{slug}/access-requests` (`{note?}`) — emails every admin/owner; idempotent while pending (200); with `auto_approve_role` set it is approved at once; nonexistent and not-your-domain are the same 404; 409 if already a member. `GET …/access-requests[/{id}]` (admin or owner; `?status=`). `POST …/{id}/approve` (`{role}`: viewer/editor/admin, below your own unless owner → else 403) · `POST …/{id}/deny` (`{reason}`); both 409 once decided and email the requester. `PUT /api/workspaces/{slug}/access-settings` (owner) — `auto_approve_role` `""` / `viewer` / `editor`.
- `GET|PUT /api/workspaces/{slug}/shared-vault` (owner) — the TENANT level of the credential model: a 1Password vault name + service-account key, Fernet-encrypted and write-only (`SharedVaultOut.key_set`, never the value; a blank `service_key` is not written, so renaming the vault keeps the key). Holds what every agent here shares (the Google OAuth clients). The agent level is `GET|PUT /api/agents/{slug}/vault`; the two keys stay separate, and `/agents/{slug}/credentials/resolve` hands a box both, each read with its own key. UI: Settings → Secrets.
- `GET|PUT /api/workspaces/{slug}/runner-order` — the workspace's default runner order (index = rank): routes agentless repo turns, and is the default of every agent here, and every workspace below, with no order of its own (`harness.routing.inherited_orders`). Read: member. Write: admin or owner (`runners.route`); each runner must be able to serve this workspace, else 422 (as for unknown/retired). See `docs/architecture/runners.md`.
- `GET /api/workspaces/{slug}/runner-topology` — admin+ (`logs.read`), checked on every descendant too. This workspace and its descendants in tree order: agents, every `RunnerAssignment` row (default list + rules), and the runners named or living in the tree; `can_claim: false` on a route means the runner's owner is not in the agent's workspace, or the runner is directed-only (its row carries `directed: true`; an agent following an order that lists it names it in `follows.directed`). Computed (`apps/harness/topology.py`). UI: Settings → Topology (map + `/topology/runners`).
- `GET /api/workspaces/{slug}/health` — same gate. Every workspace in the tree (depth, shared vault + where it is inherited from) and every agent: owner, `can_fix` (`Agent.is_admin`), properties, `vault` (`vault_health`: per-ref stored/literal/local/1password/missing, `machines_waiting`), `steps` (exactly `setup_steps`), `left`, sessions, projects and tasks; `runners` (the runner topology's rows, with `code_current` and `problems`); totals. `apps/agents/health.py`. UI: `/w/:ws/health`.
- `GET /api/workspaces/{slug}/analytics?days=30&tree=true` — same gate. Daily series, totals, per-agent, per-repository and per-person tables (one aggregation), no cost, over `Activity` + `TurnUsage` only (`apps/events/analytics.py`, `docs/architecture/analytics.md`). UI: `/w/:ws/analytics`.
- `GET /api/workspaces/{slug}/network?days=30&tree=true` — same gate. People, contacts and agents linked to the threads they wrote in (a chat, a bound Slack thread being one, or an email thread), each thread to its answering agent; a chat's title only where the session ACL lets the caller open it; at most `analytics.MAX_THREADS` threads, shared ones first (`analytics.network`, `docs/architecture/analytics.md` § Network). UI: `/w/:ws/network`.
- `GET /api/harness/runners/{id}/usage-scope` · `POST …/usage` (the runner) — the box's usage report: the repos it scans, and per Claude session per UTC day tokens, no content (`apps/events/usage.py`). `POST …/usage-scan` · `GET|POST …/missing-sessions` (the runner's admins) — ask for a full rescan; list its local sessions canopy has no record of; send chosen ones up (filed by `session_home`, binding `claude:<uuid>`, backfill requested).
- `PUT /api/harness/runners/{id}/slash-commands` (the runner) — the slash commands its sessions can run, `{commands: [{name, description, args_hint, source}]}`, replacing what was held; sent when the list changes (`canopy_runner/slash_commands.py`). Held on `Runner.slash_commands`, off `RunnerOut`.
- `GET /api/workspaces/{slug}/agent-topology` — same gate. For each ordered agent pair, what the first gets sending the second work with its own login: `access` full/confined/none, `basis` (owner, workspace-owner, admin, full-rule, no-interface, capabilities, nothing-offered, not-member, no-login), the capabilities when confined, `can_grant`/`can_revoke` for this caller; `full_people` per agent. Decided by the predicates a real turn uses. Grant via `PUT /api/agents/{slug}/admins/{user_id}` with the sender's login. UI: `/topology/agents`.
- `GET /api/workspaces/{slug}/retention` (member) · `GET …/retention/preview` (counts only, deletes nothing) · `POST …/retention/rules` · `PUT|DELETE …/retention/rules/{rule_id}` (`retention.manage`, admin+) — content retention rules incl. inherited ones; blank filters match anything, `keep_days` null = forever; 422 on a duplicate filter set or an agent outside the workspace. See [tenancy.md § Content retention](tenancy.md#content-retention-appsretention).
- `GET /api/workspaces/{slug}/admission-rules` (member) · `POST …` · `PATCH|DELETE …/admission-rules/{rule_id}` (`admission.manage`, admin+) — which turns this workspace refuses before they run, with fire counts. At least one condition per rule; an `allow` beats every `reject`; PATCH changes only the sent fields (incl. on/off); a deleted seeded default is not re-seeded. `PUT …/admission-settings` `{sender_notices_enabled}` (`admission.manage`) — whether a rule's automatic reply to a rejected sender is sent (off: recorded, not sent). See `docs/architecture/access.md` → "Admission rules".
- **Connected sites** (`apps/embedding/connected_apps_api.py`, rules in `embed_apps.py`; owner): `GET|POST /api/workspaces/{slug}/connected-apps`, `PATCH|DELETE …/connected-apps/{id}`. Each row carries `live_probe` (`{at, ok, step, step_label, reason}`) and `traffic` (`{last_redeemed_at, last_site_call_at, refusals_24h}`).
- `GET /api/sites/agents` — **the site agents API** (`apps/host_grants/api.py`, content `site_agents.py`; `auth=None`, gate `host`). The credential is `Authorization: Bearer <JWT>` signed by the site's own registered key (`assertions.keys_for_app`): `typ` `canopy-site-agents-request+jwt`, `iss` = `sub` = its Connected-site name (resolved by `embed_apps.resolve_site`: a signed `canopy_workspace` — the workspace slug — selects the tenant, or failing that a signed `canopy_agent`'s workspace; both must agree, else 409 `workspace_mismatch`; neither, between tenants sharing the name, 409 `ambiguous_issuer`), `aud` = the endpoint URL under canopy's identity or public base, ≤ 60 s, single-use `jti`. Refusals 401 (`unknown_issuer`, `bad_signature`, `replayed`, `wrong_audience`, `bad_typ`, …), rate-limited per client and per site. Answer `application/jose`: a compact JWS signed with canopy's client key (`typ` `canopy-site-agents+jwt`, `kid` in `/oauth/jwks.json`), payload `v`, `iss` (client_id), `aud` (site name), `iat`/`exp` (15 min), `version` (sha256 of the canonical `site`+`runner_flags`+`agents`), `site {name, tenant, settings_url}` (`settings_url` = the site's card on the Connected sites page, `…/settings/connected-apps#site-<id>`), `runner_flags [{flag, meaning}]`, `agents`: the site's `AppCredentialAgent`s in its own workspace, each with the capabilities naming the site in `sites:` (`handles_sensitive` = `data: sensitive`, `sensitive_set_by`/`sensitive_set_at` = the interface's last publisher, as `Canopy-Execution` states it), `runners {flags_available, ready_with}` (from `setup.runner_takers`, flags in force), `ready` (a capability for the site AND a runner ready now; no GitHub token is needed — a site turn is confined), `problems` (sentences naming where to fix it) and `problem_links` (`[{text, url}]`, the same sentences each with the URL that fixes it). Verified by `canopy_sdk.site_agents.fetch_site_agents`.
- `GET /api/workspaces/{slug}/connected-apps/{id}/needs` — what the site asks of agents (its signed `site.json`, read beside its `jwks.json` by `apps/host_grants/site_needs.py`: pinned/bounded fetch, verified with the site's keys, cached 10 min, last good shown `stale` for 24 h, else `available: false` + `reason`) and, per allowed agent, `{offered, real_data, ready, meets_real_data, why_not}` computed from the same `site_agents_content` the site reads; `not_allowed` = agents the site names that this workspace does not allow on it. Gate `integrations`.
- `GET /api/workspaces/{slug}/connected-apps/discover?address=&app_id=` — **Fill from the site** (`apps/host_grants/api.py`, logic `site_needs.discover`; gate `own`, read-only). Finds the site's signed `site.json` from `address` (the document's URL, its JWKS URL, or just the site's address: `…/site.json`, `/.well-known/canopy-site.json`, `…/canopy/site.json`) or, with `app_id`, beside the site's keys / at its first origin; fetched fresh (pinned, https, public addresses, no redirects). Verified with the site's registered keys (`signed_by: registered_keys`) or the keys at the `jwks_url` the document declares (`published_keys`; `registered_keys_verify: false` when registered ones exist and do not verify it); `iss` must be the site's name for `app_id`. Returns `{url, tried, name, site: {origins, jwks_url, issuer, mcp_resource}, signed_by, registered_keys_verify, current, changes}` (`current`/`changes` for `app_id`). 422 with `unreachable`, `no_facts` (no `site` block: SDK < 0.16), `bad_signature`, `bad_issuer`, `keys_unreachable`, `malformed`, `no_address`. Never writes: the owner adopts the values through `POST`/`PATCH …/connected-apps` (audited).
- `POST /api/auth/contact-token` resolves the site the same way: the assertion's signed `canopy_workspace` selects the tenant (409 `workspace_mismatch` if `agent_slug` is not one of its agents; 400 `bad_workspace` for a malformed claim), else `agent_slug`'s workspace. The embed shell `/embed/chat` takes `?workspace=` beside `?agent=` (any refusal a 404).
- `POST /api/workspaces/{slug}/connected-apps/{id}/test` — **Test connection** (owner; another tenant's site 404s). From canopy's server, returns `{ok, checks: [{name, label, status: pass|fail|skip, detail}], live_probe, live_probe_ok}`: the JWKS (`check_jwks`: reachable, public-only, asymmetric, thumbprint `kid`; RSA only for an assertion-only site) and pasted PEM key types; for a host-grant site, RFC 8414 + 9728 discovery (`check_metadata`) and `check_client` (jwt-bearer with canopy's real client assertion + DPoP and an ID-JAG from a throwaway key: `invalid_grant` = host authenticated canopy, `invalid_client` = it does not accept canopy, 200 = it accepted a grant it never signed). Then the **live probe** (`apps/host_grants/live_probe.py`), folded into `ok`: the host's `canopy_probe_endpoint` signs a real ID-JAG for its probe principal; canopy redeems via `host_grants.redeem` and calls via `host_gateway` — the probe tool succeeds, an out-of-scope tool is refused by the host, and no proof / a stranger's proof / plain bearer are refused. No probe identity → `live_probe_ok: null`. All fetches via `outbound.py`.

### Personal Access Tokens (`apps/tokens`)
- `GET /api/tokens/` — my tokens (no raw values; OAuth-minted tokens omitted), each with `last_used_at` and `last_used_client` (the User-Agent of its last REST call or socket — a runner sends its host). A revoked token also stops any socket it opened: `RunnerConsumer` re-checks the credential on every frame (`apps/realtime/channels_auth.py::still_signed_in`) and closes 4001. `POST /api/tokens/` — mint (raw returned once). `DELETE /api/tokens/{id}/` — revoke (mine only; another user's 404s).
- Raw values are sha256-hashed at creation and never stored; a new one starts `cpat_` (older ones are 43 bare characters and still work — `tenancy.md` § Users). Send `Authorization: Bearer <raw>`; `apps.tokens.middleware.BearerTokenAuthMiddleware` resolves it to `request.user`. Bootstrap: `uv run python manage.py create_token --email <email> --label "<label>" --create-user`.
- `GET /api/tokens/github` — my GitHub App connection (never calls GitHub). `DELETE /api/tokens/github` — forget my grant (canopy's copy only; idempotent 204). `GET /api/tokens/github/installations` — live list of accounts/orgs the app is installed on (the create-agent owner picker); 409 when the grant is unusable (reconnect).

### Passkeys + step-up (`apps/passkeys`, mounted at `/api/passkeys`)
WebAuthn (py_webauthn) passkeys as a SECOND factor, never a sign-in. Every route touches only the caller's own passkeys; every ceremony needs a person at a browser (a token, MCP call or token-minted session gets 403 `browser_session_required`). RP id = the browser's host unless `PASSKEY_RP_ID`/`PASSKEY_ORIGINS` pin it.
- `GET /api/passkeys/` — my passkeys (label, created, last used, synced or device-bound). `DELETE /api/passkeys/{id}` — needs a fresh step-up.
- `POST /api/passkeys/register/begin` → `{options}` for `navigator.credentials.create()`; `POST …/register/finish {credential, label}` → 201. The FIRST passkey needs only a signed-in session (bootstrap); a second needs a step-up with one already held. Registration requires user verification and opens a step-up window.
- `GET /api/passkeys/step-up` — `{active, until, has_passkey, browser, window_seconds}`. `POST …/step-up/begin` → `{options}` for `navigator.credentials.get()` (409 `no_passkey` when none); `POST …/step-up/finish {credential}` verifies against one of the CALLER's passkeys and sets the session's step-up for 5 minutes.
- **The gate other routes use:** `apps.passkeys.stepup.require_recent_step_up(request)` → 403 problem+json with top-level `error: "step_up_required"`, `has_passkey`, `register_url`; the SPA's API client answers it with a passkey prompt and retries (`frontend/src/auth/stepUp.ts`). Each route that needs it says so.

### Walkthroughs (`apps/walkthroughs`)
- `GET /api/walkthroughs/` — list, scoped to the pinned workspace or all the caller's. Filters: `project` (repo `project_slug`), `agent_project` (`hal/P5`, `hal:P5` or id), `kind=html|video`, `mine=true`, `session`, `turn`.
- `POST /api/walkthroughs/` — upload (multipart): `file`, `kind`, optional `title`, `description`, `project_slug`, `visibility` (`private` | `link`; `link` mints a share token), `links`, `run_id`, `narrative_slug`, `role`, `narrative_review_id`, `session_id`, `turn_id`, `agent_project`. Optional `duration_sec` (the measured length; a malformed value is ignored). Over `WALKTHROUGH_MAX_UPLOAD_BYTES` → 413.
- `GET /api/walkthroughs/{wid}/` — `auth=None`. A `link` walkthrough needs `?t=<share_token>` for anonymous read; a missing/wrong token 404s like private. `is_owner` drives the toolbar; owners also get `share_url` (`…/w/<workspace>/walkthrough/<uuid>?t=<token>`).

- `DELETE /api/walkthroughs/{wid}/` (uploader or workspace owner) — deletes the Drive file and the row.
- `POST /api/walkthroughs/{wid}/rotate-token` (uploader or workspace owner) — re-mints the token, killing shared links.
- `GET /w/<workspace>/walkthrough/<id>/content` — bare streaming view (`apps/walkthroughs/streaming.py`), Range-aware. Session auth OR (`link` AND correct `?t=`). Another workspace's walkthrough 404s; registered `<str:wid>` so a malformed id 404s rather than hitting the SPA. Every `content_url` / `video_url` the API returns is this path.
- **No flat artifact addresses** — which prefixes 404 and why: [pages.md § Rules for every page](pages.md#rules-for-every-page). `tests/test_api_urls_are_workspace_scoped.py` fails on any artifact URL field not under `/w/<workspace>/`.

Spec: `docs/superpowers/specs/2026-07-13-walkthrough-share-token-revival-design.md`.

### Reviews (`apps/reviews`) — DDD narrative review surface
- `GET /api/reviews/` list (the `/ddd` dashboard) · `POST /api/reviews/` create (DDD orchestrator) · `DELETE /api/reviews/{rid}/`.
- `GET /api/reviews/{rid}/` — `auth=None`; detail / poll for resolution. A `link` review is readable by anyone with the URL (tokenless); private 404s. Carries `version_video` + `cut_videos`, each URL playable by THIS reader (a guest gets a public cut's token URL and none for a private one).
- `request_json` is stored verbatim; beyond the DDD fields the page renders these optional demo-framing keys when present: `title` (the narrative's name — also the storyboard card heading), `audience`, `purpose`, `data_disclosure`, `storyboard_url` + `storyboard_title` (the set it belongs to), `cuts[{id, title, screen_notes, audience_note, provenance, poster_url, duration_sec}]`, `assumptions[]`, `divergences[{script, data, resolution}]`, `open_questions[]`; and per narration item, `provenance`.
- `GET /api/reviews/{rid}/destination` — `auth=None`; where a review is read: `{url}` = the narrative's storyboard entry (board token only for a caller holding the review's own valid `?t=`; a member gets it tokenless), `null` for a findings review. May create the board. 404 to anyone else.
- A narrative review's gate is ALSO a decision row on its storyboard (`apps/storyboards/review_gate.py`): ruling it, or a round closing with it ruled, resolves the review server-side with `{decisions, edited_scenes, overall_feedback, build_order, resolved_via}`; a `submit` marks the row ruled in turn.
- `POST /api/reviews/{rid}/submit/` — approve/redraft + narration edits; requires a login (403 to an anonymous reader) and CSRF.
- `POST /api/reviews/{rid}/suggest/` — `auth=None`; suggested edits that never resolve the gate, appended for the owner (who is told). Caller: an external reviewer with the share token (`?t=`, no CSRF), or a member of the review's workspace saving edits without deciding (CSRF-checked). Unreadable → 404; neither → 403.
- **Run-child gates belong to no narrative.** `RUN_CHILD_GATES` (`apps/runs/ddd.py`; `product_findings`) hang off the run: `create_review` stores `narrative_slug=None`, `version=0`, and `/w/<ws>/review/:id` renders them standalone (the one review page left) (no DDD rail). `apps/runs/aggregate.py` may attach one to an existing narrative but never creates one, since the same gate is used outside DDD runs. `_NON_NARRATIVE_GATES` is a superset: `external_release` is not a version but may create its narrative.

Dry run by default (the plan is the undo record). Requires membership of both workspaces. Same service: `manage.py move_narrative_workspace --to <ws> --slug <slug> [--apply]`.

Bytes are on Drive under `narrative-sources/<id>/`, capped by `NARRATIVE_SOURCE_MAX_UPLOAD_BYTES` (150 MB). ### Agents (`apps/agents`) — first-class AI-agent workspace
An `Agent` is an instance row (its definition is the repo): status reports (syncs), skill catalog, packaged turns, and two nouns of work — **projects** (`P<N>`, work with an end) and **tasks** (`T<N>`, one step, optionally in a project). A project's `scope` is `agent` (the default: one agent's work) or `workspace`: owned by the workspace (`owner_workspace`), addressed `<workspace>/<handle>`, its `agent` the **steward** that keeps it current, and open to tasks from any agent in the workspace (a funder knowledge base many agents read). The DB is the source of truth; the board renders by who has the ball. Person-to-task moves go through one actions route; field changes are a plain PATCH. Roles and access: `docs/architecture/access.md`. Spec: `docs/superpowers/specs/2026-10-07-projects-and-tasks-design.md`.
- `GET /api/agents/` list · `POST /api/agents/` upsert by slug (`google_account` — the agent's Google login when it is not its `email` — is written only when sent, "" clears it, 422 if not an address; a CREATE makes the caller the owner; an update never changes it; a create or a changed `repo_url` asks the cloud runners that will take its turns to re-run their bootstrap, `setup.request_setup`; a `workspace` other than the agent's current one is the full move below, not a pointer change) · `DELETE /api/agents/{slug}/` (editor/owner; removes everything hanging off it, and first closes its open chat sessions so their emdash tasks are deleted on the runner — an offline runner drains the close when it is back).
- `POST /api/agents/{slug}/move` `{workspace}` (`?dry_run=1` changes nothing) — moves the agent **with its history**, in one transaction or not at all (`apps/agents/move.py`): turns, chat sessions (+ participants outside the destination dropped), mail threads/messages, mail routes on a domain the destination may use, capability grants/leases, agent-scoped admission/retention rules, origin issues; the agent's own login joins the destination when the caller has `members.manage` there. People records and a person's grants stay (reported in `left_behind`); a route on a domain the destination cannot use is disabled. Returns `{agent, source, destination, dry_run, moved, tables: [{table, rows, how}], left_behind: [{table, rows, why}], stops_working: [{kind, detail}]}` — the dry run and the move share one code path. Writes an `agents.move` event in both workspaces. Agent admin + editor in the destination; 404 for a destination you are not in, 409 on a collision (nothing moved). CLI: `canopy agent move --slug <a> --to <ws> [--dry-run]`.
- Every agent item (list and detail) carries **`op_vault`** — the instance's 1Password vault NAME (`Agent.op_vault`, `""` if unset; never the service-account token) — and **`plugin`**: `{"repo": "owner/repo", "name": "<catalog name>"}`, named exactly as the caller's `canopy-agents` catalog names it (`apps/plugins/services.py::plugin_refs`), or `null` with no github.com repo. A plugin is code; an agent row is an instance (docs/architecture/plugin-marketplace.md).
- **Creating from the browser** (`apps/agents/creation.py`; editor in the target workspace). GitHub access is the person's own fine-grained token, the same credential agent turns use — no GitHub App install. `POST /api/agents/scaffold/check` {workspace, slug, repo, token} — reads only (POST to keep the token out of URLs): `ready` (empty, visible to the token; `login` = who it acts as), `update` (already this agent's scaffold — `.claude-plugin/plugin.json` names the slug — or only GitHub's starter files; `files_to_add` template files are missing), `adopt` (nothing missing), `name_mismatch` (another agent's repo; `suggested_slug`), `missing` (the token cannot see it), `not_empty` (not an agent repo), `no_token`; always returns `new_repo_url` and `token_url` (`delegations.token_form_url`). `POST /api/agents/scaffold` (201) — renders the `canopy-agent-factory` scaffold and pushes it with that token (empty repo: Contents API first commit, then one Git Data commit with file modes; `update`: one commit on top adding ONLY the missing template files — nothing already there is overwritten); stores nothing. Then the page registers via the upsert and lends the same token via `PUT /api/agents/{slug}/github`. Slugs `new`/`scaffold` are reserved.
- `GET /api/agents/{slug}/setup` (member) — the ordered checklist (`apps/agents/setup.py`): repo, GitHub identity (`delegations.readiness`), mailbox (`gog-token`), vault (`vault_health`: a canopy-web agent needs every declared secret stored and every machine let in; a 1Password one its vault + key), runner (routing order ∩ `runner_may_hold_agent` ∩ `runner_tenant_slugs`, online), job (a skill beyond the factory's own; `where: claude-code` with the command that starts the session), first finished turn. Each step reads the system's own check.
- `GET /api/agents/{slug}/` — detail with counts, `owner`, and the caller's `can_transfer_owner`, `is_admin`, `can_manage_admins`. `turn_count` / `latest_turn_at` read the harness turn queue (`latest_turn_at` = newest `started_at`, else `created_at`).
- `PUT /api/agents/{slug}/canopy-user` — link the canopy user the agent's own token signs in as (`user_id: null` unlinks).
- `POST /api/agents/{slug}/canopy-token` `{email?, label?}` (agent admin; 403 for a token-minted caller) → 201 `{raw, token_id, label, user_email, created_user}` — a non-expiring PAT for the agent's OWN login, shown once, creating the login when there is none (that takes agent admin **and** `members.manage` in the agent's workspace, else 403; 422 without a mailbox address; 409 if the address is already a canopy user). A linked login that has ever signed in interactively needs a workspace owner. Caller: `canopy agent vault`.
- `PUT /api/agents/{slug}/owner` — the agent's owner or a workspace owner transfers it to a member of its workspace (non-member 422); `{"user_id": null}` clears it (workspace owners only). The owner's GitHub grant is what History reads through.
- `GET /api/agents/{slug}/admins` (member) · `PUT|DELETE /api/agents/{slug}/admins/{user_id}` — admins = the owner, workspace owners (implicitly), and members granted by name (`AgentAdmin`; inert if the holder left the workspace). Grant/revoke: the agent's owner or a workspace owner only (403), target must be a member (422), the owner cannot be revoked (422).
- `GET /api/agents/{slug}/access` (member) — one row per workspace member: `workspace_role`, `agent_role` (owner/admin/member), `basis`, `access` (`full` / `confined` to `capabilities` / `none`), and any `full_rule`; `outsiders` lists rules reaching contacts / unidentified callers; `interface_published: false` means only admins and workspace editors reach it. Computed with the predicates a turn uses (pinned by `tests/test_agent_access_roster.py`). UI: People roster on the agent's Settings.
- `GET|PUT|DELETE /api/agents/{slug}/interface` — the declared interface: what callers (anyone not an admin) may ask for; live state on canopy-web, never the repo (`canopy agent interface get|set`). PUT takes `source` (YAML, stored verbatim) or `interface` (mapping); strictly validated by `apps/agents/interface.py::parse` (unknown keys / caller classes / `callers_default` ≠ `none` → 422). Caller classes `member|contact|unknown`, optionally `@domain.tld` and `:verified`; a top-level `full:` list grants matching callers the whole profile. GET: member; PUT/DELETE: owner or admin. No interface = default deny for viewers, contacts and unidentified callers. `enqueue_turn` stamps `Turn.capability` from it (or writes the turn CANCELLED with the reason); the envelope's `granted_by` says why a turn has its access.
  A PUT whose interface marks a capability `data: sensitive` (it handles sensitive data) needs no more than any other save (the agent's owner or an admin, browser or token); removing `data: sensitive` and saving (or DELETE) turns it off. Like every interface save it is a `SettingChange` (`list_setting_changes`, target = the slug).
- `PUT /api/agents/{slug}/interface/capabilities/{name}/sensitive` `{handles_sensitive}` (owner or admin, browser or token) — the sensitive-data switch for one capability: writes or removes its `data: sensitive` line in the saved YAML (comments kept, `sensitive_data.with_sensitive`; a mapping-saved interface is edited as a mapping) and saves it through the same path as PUT `…/interface` — same `parse` (a capability that could leak is a 422 naming it), so the YAML and the switch never disagree. YAML laid out so a line edit cannot be proven exact (flow style, JSON) is a 422: edit the YAML. 404 for a capability the saved interface lacks. Audited as `set_capability_sensitive`, target `<slug> / <capability>`, change `sensitive_capabilities` before/after. UI: the Sensitive data column's Turn on / Turn off on Settings → Interface.
- `GET|POST /api/agents/{slug}/turns/` — list / package a turn: `task_ext_ids` advanced, `title`/`summary`, `work_product_urls`, optional transcript (uploaded to the sessions app; list returns `share_url` = `…/w/<workspace>/share/<token>`). Idempotent per `(agent, cli_session_id)`; `origin_ref` is merged into the row's own. POST attaches to the `harness.Turn` that dispatched the session, matched on `session_key` (`emdash_task_id` accepted as an alias); an unmatched session records a report-only turn.
- `GET|POST /api/agents/{slug}/syncs/` — status reports (Google-Doc syncs), upserted per `(period, source)`. `DELETE …/syncs/{sync_id}/` removes one filed under the wrong period.
- `GET|PUT /api/agents/{slug}/skills/` — list / replace the skill catalog (mirrors the repo).
- `GET /api/agents/{slug}/skill-history/` (member) — skill history from the repo's git log (`skills/*/SKILL.md`) via `Agent.owner`'s GitHub grant. Syncs first when the last success is >1h old and no attempt was made in the last hour (in-flight debounced 90s); a sync failure serves stored history. Returns `credential_state` (`ok`/`no_repo`/`no_owner`/`owner_not_connected`/`repo_not_granted`), `owner_name`, `viewer_is_owner`, `viewer_can_sync`, `install_url`. `POST …/skill-history/sync` (editor+) forces one (never over an in-flight sync).
- `GET /api/agents/{slug}/skill-history/revisions` (member) — newest first with commit bodies; filters `skill` / `group` / `commit` (sha prefix) / `since` / `until`; 25 default, cap 300; bodies summarised to 700 chars; names `checked_by`/`checks` for a single skill. `GET …/skill-history/diff?sha=&skill=` — one commit's diff to one `SKILL.md`, live from GitHub, truncated to 20 KB; 422 on a malformed sha/skill.
- `GET /api/agents/{slug}/runtime` — Agent Runtime Registry: repo pointer, secret-reference names, engine preference, tenant (`docs/superpowers/specs/2026-07-20-agent-runtime-registry-design.md`).
- `PATCH /api/agents/{slug}/turn-mode` — `manual` (any editor) / `auto` (owner or admin). `PATCH …/credential-source` — `1password` | `canopy-web` (owner or admin; not settable by the repo upsert). Moving to `canopy-web` makes the agent zero-knowledge: each stored custodial value is sealed (`zks1`) to its readers and the custodial copy wiped (`services.make_zero_knowledge`); nobody to seal to → 409 `zk_no_recipients`, nothing changes. `PATCH …/slack` — under Slack. `PATCH …/repository` `{repo_url, repo_ref?}` — owner or admin (a `DEFINITION_FIELDS` change); any github.com spelling, stored `https://github.com/owner/repo`, 422 otherwise; audited; a changed repo asks its cloud boxes to re-bootstrap (`setup.request_setup`). The setup checklist's repository step links to it on Settings (`#repository`), never the create wizard.
- **Credentials** (owner or admin unless noted): `PUT /api/agents/{slug}/credentials` (write-only, non-clobbering upsert; returns masked status; from a BROWSER session it needs a passkey step-up — 403 `step_up_required` — while a PAT/MCP write does not) · `POST …/credentials/{name}/reveal` (PLAINTEXT of one stored value: agent admin, browser session only, fresh passkey step-up; `Cache-Control: no-store`; each reveal is an `agent.credentials.revealed` event, written before the value is read and failing closed; a zero-knowledge value is never revealed — 409 `zk_enabled`, the server cannot decrypt it) · `DELETE …/credentials/{name}` · `GET …/credentials/status` (member; which declared refs are set, booleans) · `GET …/credentials/access` (which backend, and whether THIS caller may resolve, as whom; session or bearer; non-member 404) · `GET …/credentials/resolve` (PLAINTEXT: bearer only — a session is refused even for the owner — and only for a caller pairing a live runner this agent routes to, or an agent admin; otherwise 403 naming how to get access. `?refs=a,b` scopes it to those refs ∩ the agent's declared refs, and returns the secret extras `op_sa_token`/`shared_op_sa_token`/`github_token`/`salesforce_creds` only when named; no `refs` = everything, unchanged. Besides the values it carries `mailbox` (`Agent.email`), `mailbox_backend` (`ses` | `google` | "") and `google_account` (`Agent.google_identity()`: `google_account`, else `mailbox` when that is a Google mailbox, else ""). A `credential_source: canopy-web` agent never gets its `op_sa_token`. Each ref handed out is logged as an `AgentCredentialRead` with caller, runner (`X-Canopy-Runner`, owned runners only) and `X-Canopy-Turn-Id`. Values are Fernet, or `kms1:` envelopes when `VAULT_KMS_KEY_ID` is set — `apps/common/kms_envelope.py`; `manage.py reencrypt_secrets [--apply]` re-wraps every `*_enc` column under the current key) · `GET|PUT …/vault` (the agent's 1Password vault + service-account key, masked/write-only; scoped to one agent's vault) · `GET …/readiness` (what each box reports it could actually materialize) · `POST …/bootstrap-report` (a box reports it; same gate as resolve).
- `GET /api/agents/{slug}/google/authorize` — start the Google mint; returns the URL (not a 302) for a top-level navigation. Scopes are `google_oauth.scopes_for(agent)`: no `gmail.*` when the agent's mail is canopy-hosted on a verified domain and it has no Gmail address. `login_hint` defaults to the expected account (below), else `<slug>@dimagi-ai.com`. `GET /api/oauth/google/callback` — the fixed callback for every agent (the agent rides in signed state). It refuses a consent from any account but the expected one (`google_oauth.expected_account`: `google_account` when set, else `agent.email` when that is a Google mailbox), case-insensitive — `?google=wrong-account&account=<x>`, nothing stored; an agent with neither may use any account.
- `GET /api/agents/{slug}/sender-trust` · `PUT|DELETE …/sender-trust/{email}` — temporary (`days` 1–90) trust that ties a member's unaligned mail to their account, as long as it carries a passing DKIM signature and the address belongs to exactly one member; expired rules list with `active: false`; DELETE idempotent.
- `GET /api/agents/{slug}/github` — how the agent acts on GitHub (masked): whose identity, expiry, whether it can open a PR on the agent repo; `identity_for_repos` = repos whose agentless project turns borrow this identity (`agents.RepoIdentity`, edited in Django admin). `lent_by_email` = whose delegation is in force, `can_lend` = whether the caller may lend. `PUT …/github` (owner or admin; lends the caller's fine-grained PAT, verified before storing, else refused with the reason) · `POST …/github/check` · `DELETE …/github` (withdraws the caller's own delegation only). See [runners.md § The GitHub identity a turn gets](runners.md#the-github-identity-a-turn-gets).
- `GET|PUT|DELETE /api/agents/{slug}/salesforce` · `POST …/salesforce/check` — lend this agent another agent's Salesforce identity (owner of both; checked against Salesforce before storing).
- **Projects:** `GET|POST /api/agents/{slug}/projects/` (`?status=`) — the state behind each `Projects/<name>` Drive folder; numbered `P<N>` per agent, never reused; list carries `task_count`, `open_task_count`, `waiting_task_count`; `links` (`[{label, url}]`) are the recorded deliverables. `GET|PATCH …/projects/{ref}/` — fields, links, tasks (live first), `participants`, recent turns touching its tasks; closing (`status=done`) keeps the tasks.
- **Workspace projects** (`apps/agents/fleet_api.py`, `services.promote_project`/`set_steward`). `PATCH …/projects/{ref}/` `{handle, workspace?}` promotes an agent project, its agent as steward, into its agent's workspace or one below it (`workspace: "connect"` for a dimagi agent: an org's agent curating a division's resource; 422 above or across the tree; a different workspace needs the caller to be its editor, else 404) (one-way: 409 readdressing; 409 a taken handle; 422 a malformed one — `[a-z0-9-]`, 3-60). `GET /api/workspace-projects/` (member; `?status=`) lists them; `POST /api/workspace-projects/` `{name, handle, steward, workspace?, …}` creates one (the steward's write gate). A workspace project is readable by its workspace's members and by its steward's (the list includes both). `GET|PATCH /api/workspace-projects/{workspace}/{handle}/` — the same detail and patch as the agent route, by address (non-members 404); `{steward}` hands it to another agent of its workspace or one above it (both stewards' write gate; ext_id re-issued from the new steward's counter on a clash; 422 otherwise). A task names one in `project` by handle (the agent's workspace, then up its tree) or by address (also a workspace below the agent's) (`AgentTaskOut.project_address`). Every project row carries `scope`, `handle`, `steward_slug`, `address`, `url`, and `board_url` (its page on the agent's board, in the agent's workspace — where the address redirects; the detail's `board_readable` is false when the caller cannot open it, and the address then renders the project read-only in place). An agent that stewards one cannot be deleted or moved (409) until it is handed on: the project is the workspace's. **Its own MCP server** (`apps/mcp/projects.py`, `apps/agents/kb_store.py`, `packages/canopy_kb`): the steward's curator `POST …/{workspace}/{handle}/kb/upload` (a presigned S3 PUT, the bytes never pass through canopy; the steward's write gate) then `POST …/kb/publish {key, sha256}` (422 a key outside the project's prefix or an object that never arrived; 503 no bucket). Before publishing, `POST …/kb/originals {files: [{sha256, bytes, content_type}]}` (≤1000; the steward's write gate) answers a presigned PUT for each original file the project's store lacks, under `originals/<sha256>` with S3 checking the sha256 (`x-amz-checksum-sha256`); originals are never deleted, so a KB's superseded versions stay downloadable. The project then has `mcp_kind: "kb"` and `mcp_path` `/api/mcp/projects/{workspace}/{handle}/` — a Streamable-HTTP MCP server carrying ONLY that KB's tools (`canopy_kb.tools`: kb_info, search, entity, doc, read, grep, sql, get, whats_new, one per table…, and `original` — a 15-minute signed download of the file a document was read from, under its file name — when the KB keeps originals), answered from a per-instance copy cached by sha256. Same sign-in as `/api/mcp/` (personal token or OAuth; the `/api/mcp/` protected resource covers it as a path prefix); readable by members of the project's workspace or its steward's, and anyone else sees no tools. The project page shows the one-line install (`claude mcp add --transport http <handle> <url>`) and the connector URL. **The directory** — `GET /api/mcp-servers/` (member; the `list_mcp_servers` tool), page `/w/<ws>/mcp` (Projects ▸ MCP servers): every published, unarchived project server in the pinned workspace and the ones below it the caller belongs to (`read_scope`), each with its title, outcome, steward, publish date, size, URL and add command. Browsed and added by hand: nothing adds a project server to anyone's sessions. Every row is one the caller can call (the list spans owner and steward workspaces the same way the server's read check does). **Search** (`canopy_kb.research`, `apps/agents/kb_rerank.py`): research tools for an agent — `kb_info`, `search` (passages matching the words, all then any, plus documents whose catalog card matches; with `KB_RERANK_MODEL` set, a Vertex AI ranking API model orders the pool, the word order standing whenever it fails), `entity`, `doc`, `read`, `grep`, `sql`. No embeddings are involved. **Vectors are dormant** (`apps/agents/kb_vectors.py`, `canopy_kb.vectors`, `KbPassage`): with `KB_VECTORS` off (the default and production) search passes none, a publish starts no sync and `manage.py kb_embed` refuses. Kept so a corpus that needs search by meaning can have it back with one setting: when on, a publish syncs passage vectors (gemini-embedding-001, `halfvec(3072)`, HNSW, at most `KB_SYNC_MAX_EMBED` per publish; `kb_embed <ws>/<handle>` for the rest) and `search` adds the nearest passages to the pool the reranker orders.
- **Knowledge-base versions, deltas and sources** (`apps/agents/kb_api.py`, `kb_versions.py`, `kb_index.py`, `kb_drive.py`; engine `canopy_kb.records` / `canopy_kb.apply`). A KB is a version log (`KbVersion`: full | delta | rollback; pending → building → ready | failed). A publish names a STATE — each document record's and corpus part's sha256 (`{docs: {item_id: sha}, parts: {manifest|aliases|table:<name>: sha}}`). `POST …/kb/plan {state}` (the steward's write gate; changes nothing) answers what changed since the head and what to send: `unchanged` (send nothing, no version), `full_required` (the head carries no state: publish the whole file once, `…/kb/publish {key, sha256, state}`, which records a FULL version), else `upload_docs`/`upload_parts`. `POST …/kb/blobs {blobs: [{sha256, gz_sha256, bytes}]}` (≤1000) answers presigned PUTs under `records/<sha256>` for what the store lacks (S3 checks the gzip's sha256; the index job checks the content's). `POST …/kb/versions {state, base, uploaded_bytes}` commits a pending DELTA (409 the head moved or a version is building — plan again; 422 a record not uploaded, or a Drive document not approved for indexing; `created: false` for an unchanged state). The index job (`kb_index`: a thread the off-request clock kicks, `agents.kb_index`) applies the delta to the base's kb.sqlite with `canopy_kb.apply` — the same writer a full build uses, so the result is the full build of that content — stores it and points the project at it only if the project still serves the base; a failure leaves the published version serving and the version `failed` with its error. `GET …/kb/versions` (member) is the log; `POST …/kb/versions/{n}/rollback` serves version n's file again as a new ROLLBACK version (only the newest `KEEP_FILES` versions keep their file: `can_roll_back`). `GET …/kb/file` (member) is a 15-minute download of the served file (`canopy kb pull`). The `whats_new` tool reads the log (`KbChange`: what each version added, changed and removed). `PUT …/kb/settings {drive_replica}` (setting): off by default; on, each new version's kb.sqlite.gz is also written into the project's Drive folder with canopy-web's service account. **Sources** (`KbSource`): `GET|POST …/kb/sources` (`web`, or `drive_folders` with `config.folders`). A Drive source's steward posts a METADATA listing (`POST …/kb/sources/{id}/inventory`, never contents); canopy-web flags likely-sensitive names (`canopy_kb.sensitive.name_flags`), skips files shared more narrowly than their folder, keeps each decision across refreshes, queues files that appear under an approved folder ("new since approval") unless the folder auto-approves, and marks files gone from Drive. Only the project's owner (`owner_user`) decides: `GET …/kb/review`, `POST …/kb/review/approvals {source, files: [{file_id, decision?, auto_approve?, release_hold?}]}` (a folder's decision reaches what it holds; an excluded file stays excluded), `POST …/kb/readers {add, remove}` (who beside owner and steward may query a Drive KB — not every workspace member, unlike a KB of public material; the MCP server and the directory apply the same rule). The steward reads only `GET …/kb/sources/{id}/files?readable=true`, and holds an approved spreadsheet whose headers look like personal data (`POST …/kb/sources/{id}/files/{file_id}/hold {headers}`) until the owner releases it. Page: `/w/<ws>/projects/<handle>/kb`.

### A2A Agent Cards (`apps/agents/a2a_api.py`, mounted at `/api/a2a`) — discovery only
Each agent's [A2A v1.0](https://a2a-protocol.org/latest/specification/) Agent Card, generated from its declared interface (`apps/agents/agent_card.py`). A card grants nothing — turns are authorized at enqueue. `/api/a2a/` is public in the login middleware; each route self-enforces.
- `GET /api/a2a/agents/{slug}/.well-known/agent-card.json` — `auth=None`. Exists only for an agent offering a capability to a `contact` or `unknown` caller class; every other case (no interface, member-only, outsiders only via `full:`, no such agent) is the same 404. `skills[]` = the outsider capabilities.
- `GET /api/a2a/agents/{slug}/extendedAgentCard` — session or PAT (a contact token → 401). Public skills plus what the caller may invoke (`interface.offered_to`); 404 when that is nothing.
- **Paths:** one card per agent, base `{CANOPY_PUBLIC_BASE_URL}/api/a2a/agents/{slug}` (A2A's well-known URI is one card per origin, and canopy is many agents on one origin); no host-level card, no catalog.
- **Mapping:** `skills[].id` = capability name, `name` humanised, `description` (fallback `Ask <agent> (<name>).`), `tags` from caller classes (`caller:<member|contact|unknown>`, `domain:<d>`, `verified-sender`; public card tags outsider classes only; unlisted capability = `caller:admin`); Never emitted: `tools`, `bash`, `read_paths`, `entry`, `pages`, `input` field names, `full:` rules, the workspace. `securitySchemes`: `canopyPersonalAccessToken` (bearer PAT, extended card only — it invokes nothing), `canopyContactToken` (from `POST /api/auth/contact-token`, non-`:verified` contact skills under `/api/contact/`), `canopySession` (extended card only). `supportedInterfaces` are custom bindings by URI (canopy does not speak A2A messaging): `/api/contact/sessions`, `mailto:<agent mailbox>`. No MCP door: canopy's MCP server does not run agents — a member uses an agent by installing its plugin (`/get-started`), so a member-only skill carries no `securityRequirements`. `version` = `1.0.<interface_published_at epoch>`; `capabilities` = `{streaming: false, pushNotifications: false, extendedAgentCard: true}`; `provider` from `CANOPY_A2A_PROVIDER_{ORGANIZATION,URL}`.
- **Caching:** strong `ETag` + `If-None-Match` → 304. Public `Cache-Control: public, max-age=300`; extended `private, max-age=60`, `Vary: Authorization, Cookie`.
- **Unsigned:** cards carry no JWS `signatures[]`; canopy has no card-signing key.

### Harness (`apps/harness`, mounted at `/api/harness`) — runner registry + turn lifecycle
The agent-execution control plane: paired `Runner`s (laptop emdash daemons, cloud boxes) heartbeat and claim queued `Turn`s; a `Turn` is one unit of agent work with an append-only `TurnEvent` ledger. How a turn reaches a box — tenant gate, which agents a box may hold, the claim, `RunnerAssignment` lists and rules, the workspace default order, flags, schedules, the per-turn GitHub identity — is owned by [`runners.md`](runners.md); runner roles by [`access.md`](access.md) → "Runner roles". Spec: `docs/superpowers/specs/2026-07-05-agent-execution-control-plane-design.md`.

**Gates (three tiers, all 404 rather than 403).** *See* (`_runner_read_q`): runners homed in, or serving (`runner_tenant_slugs`, the claim gate), the caller's tenants, regardless of who paired them — so a turn can be pinned to any box claim would give it; a runner with no workspace is visible only to its owner. *Act as* (`_runner_or_404`): the runner's owner — everything that speaks FOR the box (heartbeat, claim, reports, its own credential fetch, its half of a mint). *Administer* (`_runner_admin_or_404`): the owner or a `RunnerAdmin` — credentials, browser sign-in, enrollments, flags, engine, refresh, starting drills. `RunnerOut.can_manage` / `can_administer` tell each caller which listed rows it may act on / administer. Retired runners 404 everywhere except `unretire`.

**Runner device keys** (Canopy Vault; `apps/harness/api_device_keys.py`, `apps/harness/device_keys.py`) — all runner-admin (owner or `RunnerAdmin`), 404 otherwise.
- `POST /api/runner-device-keys/` `{runner, public_jwk, kind: secure-enclave|tpm|software, label}` → `{id, jkt, status: "pending", approve_url}` (201; the same RFC 7638 `jkt` again → 200 with the existing row, whatever its status; a `jkt` on another runner → 409; a non-P-256 or private JWK → 422).
- An EC2 cloud runner registers its instance ROLE instead: `POST /api/runner-device-keys/` `{runner, kind: "aws-iam", role_arn, proof, label}` — `proof` is an `X-Canopy-Aws-Proof` value (below) whose htu is this URL; STS must answer with `role_arn` (422 otherwise). Stored as the canonical, path-free `arn:aws:iam::<acct>:role/<name>`, `jkt` = sha256 hex of it, `public_jwk` empty; approved and revoked like any key.
- `POST /api/runner-sessions/` `{runner}` — a box signs in as itself (`apps/harness/api_runner_sessions.py`, `auth=None`): an `X-Canopy-Aws-Proof` or `DPoP` proof for this URL from an ACTIVE device key of that runner → 201 `{access_token, expires_at, runner}`. The token (`crt_…`, `RunnerAccessToken`) lasts an hour, authenticates as the runner's owner, and opens only the runner protocol (`apps/harness/runner_auth.py`: its own `/api/harness/runners/<id>/…`, the owner's runner list, `/api/harness/turns…`, schedule list + fire, agent roster/detail/resolve reads, its agents' mailboxes (`/api/inbound/runner-mailboxes`, `POST /api/inbound/watch`), `/api/workspaces` GET, `/api/runner-device-keys`, `GET /api/harness/runner-releases/current`, `POST /api/events`, its own `ws/runner/<id>/`) — 403 elsewhere. - `POST /api/runner-device-key-requests/` — `auth=None`: a runner whose token was revoked (within 30 days) proves a token of the runner's owner and the key being registered → a PENDING key and its `approve_url`; the owner is emailed and pushed the link. Every refusal is the same 401.

- `POST /api/harness/runner-invitations/` `{name, workspace, role_arn, ecdh_public_jwk?}` — invite one new cloud box (what `runner/ec2/up.sh` calls). Non-member → 404, no `agent.work` there → 403, a name that is not a runner name or an ARN that is not an IAM role → 422. → 201 `{id, name, workspace, role_arn, status: "pending", approve_url, expires_at, runner_id: null, …}`; an hour long; your own live one for the same role and name is replaced (and anyone's expired one), but someone else's live one → 409, naming nobody (concurrent creates → 409 too). - `POST /api/harness/runner-invitations/{id}/approve` — the creator only, **browser session + passkey step-up** (a token is 403); expired or used → 409; again → no-op. Recorded as `runner.invitation.approved`.
- `POST /api/harness/runners/pair-by-role` `{name, kind: "cloud", capabilities, host, proof, ecdh_public_jwk?, ecdh_store?}` — `auth=None`, public in `apps/common/middleware.py`: `proof` is an `X-Canopy-Aws-Proof` value for this URL. 201 `{status: "paired", runner_id}` (an approved invitation for that role and name: a new runner owned by its creator, in its workspace, with an ACTIVE aws-iam key); 200 `{status: "reattached", runner_id}` (that role's existing runner of that name); 202 `{status: "waiting"}` (not approved yet); every other case the same 401. - **A box of isolation units** (`apps/harness/unit_pairing.py`): the invitation takes `units: [{name, workspace, kind: "tree"|"agent", slug?, ecdh_public_jwk?}]` (each workspace passes the same gates; an agent unit names an agent of its workspace; a name twice → 422) and returns them, each with its `runner_id` once paired. `pair-by-role` with `units: [{name, public_jwk, ecdh_public_jwk?, ecdh_store?, capabilities, host}]` (`name` is then the box's): one runner per unit with an ACTIVE software key, in one transaction, under one approval → 201 `{status: "paired", units: {name: runner_id}, device_keys: {name: key_id}}`; every unit already a live runner on this machine → 200 `reattached`, each key replaced in place (runner ids, bindings and wraps kept); a unit the invitation does not list, an invited unit the box did not bring, a creator without `agent.work` in any unit's workspace, a revoked unit key, a name live on another machine → the same 401, nothing made.

**Runners**
- `POST /api/harness/runners/` — Pair a runner; `owner` = the caller. Refused (403) for an agent's login — a runner is owned by a person (grant the agent admin instead). `workspace` optional: a non-member gets 404; omitted with zero or several memberships → 422 naming the fix. The box is enrolled only in the workspace it paired into. `profiles`/`envelope`/`midturn` in `capabilities` are dropped (they are reported, never declared).
- `GET /api/harness/runners/` — The fleet the caller can see (newest heartbeat first, max 50), each row stamped `can_manage`/`can_administer`. A connected site acting for a visitor sees only runners serving its own agents.
- `GET|POST /api/harness/runners/{runner_id}/workspaces` · `DELETE …/workspaces/{workspace}` — Which workspaces the box serves (`RunnerEnrollment`). It claims a workspace's work (agent turns, repo turns, unbound chats, schedules) only where it is enrolled — there or in any workspace above it, including divisions created later — AND its owner holds `agent.work` there; separate roots stay separate (`routing.runner_tenant_slugs`, see runners.md). Row: `serving` (both hold), `covers` (served workspaces below it). Administer tier. POST is idempotent; 422 when the box's OWNER is not an editor there, or when a cloud runner would span two roots (a cloud runner serves one tree); 404 when the CALLER is not a member. An administrator lists only workspaces they are themselves in. DELETE does nothing effective while a workspace above is still enrolled; a held turn runs to completion. Joining a workspace never enrolls existing boxes; leaving one drops their enrollments. Session discovery (`POST …/sessions`) is not routed by enrollment.
- `GET|POST /api/harness/runners/{runner_id}/admins` · `DELETE …/admins/{user_id}` — Runner administrators. GET: administer tier. Grant/revoke: owner only (grantees cannot mint more admins); 404 for an unknown email, 422 when the grantee is not a member of the runner's workspace.
- `POST /api/harness/runners/{runner_id}/heartbeat` — Act-as. Status, `active_turn_ids`, `degraded`/`note`, `ready`/`ready_note`, `host`, code provenance (`code_branch`, `code_version`, `code_sha`, `code_committed_at`), and reported capabilities: `projects` (the repos the box can drive — emdash's `projects` table on a laptop, `RUNNER_PROJECTS` on a cloud box), `profiles`/`envelope`/`midturn` (versions of confinement, caller-envelope and mid-turn support), `mailboxes_readable`, and an optional `health` block (`{checks: [{name, status: ok|warn|fail, detail}], checked_at, bootstrapped_at}`). **Absent ≠ empty:** an omitted `projects` or `health` leaves the stored value alone; `projects: []` means "none". A runner that cannot read emdash must omit `projects`. Provenance fields are assigned unconditionally (an omitted one clears), so each runner builds its payload in one place. Served back on `RunnerOut` as `health_checks` (map keyed by check name; `null` = never reported, i.e. unknown), `health_received_at`, `health_bootstrapped_at`, `refresh_pending`, `expected_code_sha`. The WS heartbeat carries the same block; its `heartbeat.ack` returns `refresh_pending`.
- `PATCH /api/harness/runners/{runner_id}` — Replace `capabilities` (act-as). 422 on `projects`, `profiles`, `envelope` or `midturn` (reported by the runner); those are preserved across a write that omits them. `capabilities` is a routing hint, never a boundary.
- `POST /api/harness/runners/{runner_id}/refresh` — Administer tier. Asks the box to re-run its bootstrap (canopy plugin + CLI, Claude Code, each agent's provisioning) and restart at its next idle moment. Durable (`Runner.refresh_requested_at`), read by the box off its heartbeat reply as `refresh_pending`; discharged only when the box reports a `bootstrapped_at` newer than the request. The cloud runner also refreshes itself when its last bootstrap is over 24h old, and never restarts itself twice within 30 minutes. A laptop runner has no bootstrap: it updates its plugin marketplaces, this account's plugins and the canopy CLI in place, without restarting, and reports one `refresh` health check (`runner/canopy_runner/canopy_runner/refresh.py`, at most once per 30 minutes).
- `PUT /api/harness/runners/{runner_id}/flags` — Administer tier. Replace the attestations the owner vouches for (today `sensitive_data`: a sensitive-data runner — a ZDR API key for Claude, a locked harness, egress limited to an allowlist, nothing kept after a turn); each records who declared it and changes are logged as events. Unverifiable by canopy; checked against a host's `canopy_runner_requirements` at claim, placement and `site_call`. 422 on an unknown flag. See runners.md → "Runner flags and host requirements" and `docs/superpowers/specs/2026-09-30-zdr-runners-design.md`.
- `PUT /api/harness/runners/{runner_id}/egress` `{locked, allow}` — Administer tier, an audited setting. The runner's egress lock (`apps/harness/egress.py`): locked, its units reach the network only through the box's proxy, to canopy-web, the model, GitHub and `allow` (hostnames; `.example.com` = every subdomain; 422 otherwise). A sensitive-data box (`runner_requirements.is_sensitive_data_box`) cannot be unlocked (422), and adding a host to one needs a browser passkey step-up (a token gets 403); anything else from any client, MCP included. `RunnerOut` carries `egress_locked`, `egress_allow`, `egress_forced`. See `runner/ec2/README.md` § Egress lock.
- `POST /api/harness/runners/box-egress` `{proof}` — `auth=None`: root on a cloud box proves its instance role (`aws_iam_proof`, bound to this URL) and reads every live runner on that machine (`Runner.machine_id`) with its effective lock (`locked` is true for a sensitive-data box whatever is set) and `allow`. One uniform 401 for a bad proof (`apps/harness/api_box_egress.py`).
- `PUT /api/harness/runners/{runner_id}/engine` — Administer tier. The runtime a LAPTOP runner opens new sessions in (`emdash` | `claude-desktop` | `claude-cli`); read off the next heartbeat, running sessions stay put. 422 for an unknown runtime or a cloud runner.
- `POST /api/harness/runners/{runner_id}/pause` · `/unpause` — Act-as, idempotent. Park a box without decommissioning it; `pause` takes `note` and optional `until` (a scheduled unpause — what a runner sends on a Claude usage cap; a past `until` is a no-op, it never shortens a scheduled unpause nor attaches one to an open-ended operator pause, and a pause without `until` cancels any scheduled unpause). `Runner.paused` mirrors the box's local `~/.canopy/PAUSED` sentinel (reported as an edge). Enforced server-side (`live_status` = `PAUSED`), so it binds any runner binary; outranks a pin; stops STARTING work, never finishing it. Records who paused (`paused_by_email` on `RunnerOut`); an open-ended pause puts the queued turns only that box could take to the workspace's reach admission rules (`access.md`). Unpause clears the flag and `paused_by` only — liveness comes from the next heartbeat. UI: `/supervisor` → Runners → `RunnerDetail`.
- `POST /api/harness/runners/{runner_id}/retire` — Act-as. Decommission: status `RETIRED`, and the runner is removed from every `RunnerAssignment` and every `WorkspaceRunnerOrder` (each logged as `runner.route_dropped`). Returns `{runner, dropped_routes}`. Prefer `pause` to park a box.
- `POST /api/harness/runners/{runner_id}/unretire` — Bring a retired runner back keeping its id (bindings, sessions, credentials survive); restores `DISCONNECTED`, never `ONLINE`. Does NOT restore the routes `retire` dropped — re-add them. The only route that reaches a retired runner. Idempotent.
- `GET /api/harness/fleet-hold` · `POST /api/harness/fleet-hold` (`{note}`) · `POST /api/harness/fleet-hold/release` — The fleet-wide sibling of pause (`FleetHold`): while held no runner starts anything; turns keep enqueuing and wait QUEUED; running turns finish. GET: anyone signed in (`can_hold`, `can_release`, `queued`). Hold: a superuser or a named holder (`CANOPY_FLEET_HOLDERS`), idempotent (refreshes the note). Release: superuser only; wakes every workspace's runners. 403 otherwise.

**Claiming and running turns** (act-as)
- `POST /api/harness/runners/{runner_id}/claim` (`?paused=<slug,slug>` = locally paused agents to skip) — Claim the next eligible queued turn; 204 when none. Returns `ClaimedTurnOut`: the `TurnOut` plus the turn's credentials (`claiming.issue_credentials`, shared with the WS claim) and `caller_context`, the caller envelope (who asked, `verified` for THIS message, relationship, contact profile). Only the claim carries it. The runner writes it to `~/.canopy/caller/<turn_id>.json` and passes `--caller <path>` to a slash-command prompt; a chat prompt is never touched. A turn with a `capability` (a confined caller's turn) goes only to a runner reporting sufficient `profiles` and `envelope` versions — not bypassable by a pin; one nothing can confine appears in `/turns/unclaimable` with that reason. Claim order: runners.md → "The claim".
- `POST /api/harness/runners/{runner_id}/resolve-session` — For (agent or project+workspace, thread_key): can this runner reuse an existing emdash session, or must it spawn fresh and rehydrate. A project session needs the owner's membership of the named workspace (404).
- `POST /api/harness/runners/{runner_id}/record-session` — Upsert the durable link and point its live hint at this runner/host; returns the fresh resolution. With `turn_id`, the server names the session from the turn (email subject, schedule name). 404 for a session that is not this agent's or not in the owner's tenant.
- `POST /api/harness/turns/{turn_id}/start` · `/finish` (`done|failed|cancelled`, optional `session_key`, `result_note`) — Reporting gate: the owner of the box that claimed the turn; on an unclaimed turn, the same tier as cancelling it. `start` 409s unless claimed/running; `finish` is idempotent on a terminal turn.
- `GET|POST /api/harness/turns/{turn_id}/events` — Read (content-read gate, `?after=<seq>`, max 500) / append (reporting gate; 422 on an unknown kind) the turn's event ledger.
- `POST|GET /api/harness/turns/{turn_id}/transcript` — The retained raw transcript (`TurnTranscript`, gzipped, beside the ledger). POST (reporting gate) appends raw `claude -p` JSONL lines, idempotent per `batch_id`; 422 over 1 MB per request; past 100 MB per turn the content is dropped with a marker and `truncated: true` (never a 4xx); appending after finish is allowed. GET (content-read gate) streams plain NDJSON; a turn with none is an empty 200.
- `GET /api/harness/turns/{turn_id}/messages` — The transcript parsed into readable messages (user, assistant, tool use/result), secrets scrubbed, bounded (`truncated`). Content-read gate.

**Sessions the runner reports** (act-as; chat semantics in [`chat-sessions.md`](chat-sessions.md), menus in [`blocked-agent-menus.md`](blocked-agent-menus.md))
- `POST /api/harness/runners/{runner_id}/sessions` — Wholesale report of the box's open emdash sessions (`sessions`, `archived: [<task name>]`, `complete`). Stamps each binding's `live_seen_at` (the liveness clock, read against `SESSION_LIVE_WINDOW`) and `reported_at` (what `/close` branches on). `archived` retires a session immediately; absence from a `complete` report retires it too. A report never clears `RunnerBinding.runner` (durable identity, not liveness). A NEW session is filed under its project's agent (among agents in the runner's tenant; a project naming an agent outside it is not filed and counts in the reply's `skipped`), else the owner's default session workspace (when it is in the runner's tenant), else the runner's workspace; existing sessions are never re-filed. 404 if the runner has no workspace.
- `GET /api/harness/runners/{runner_id}/streams` · `POST …/session-stream` — Every session this runner backs, with the held index range (`first_index`/`last_index`) and `live` (a viewer is attached); the runner ships transcript rows, which are persisted as `Message` rows whether or not anyone watches, and fanned out live only when `live`. User rows are persisted but not live-pushed.
- `GET /api/harness/runners/{runner_id}/backfills` · `POST …/session-backfill` — Sessions a client asked to rebuild; the runner ships the whole transcript in chunks and the server writes `Message` rows once. Only the chunk marked `final` clears the request. 404 for a session not bound to this runner. Both runner kinds implement it.
- `GET /api/harness/runners/{runner_id}/closes` — Sessions this runner was asked to close (`close_requested`) and has not, each with the failure the server already holds (`close_error`); drained on the poll tick so a lost WS frame costs one tick.
- `POST /api/harness/runners/{runner_id}/close-results` — `{results: [{session_key, project, ok, error}]}`: what became of the runner's close attempts, from every path (the phone's close drained on the poll tick, and the menu bar's `canopy-runner close-sessions`, including sessions it skipped for having no project). A failure is stored on the binding (`RunnerBinding.close_error`/`close_error_at`, served as `SessionOut.close_error`, shown in Supervisor as "Close failed: <reason>" with a Retry); a success, a new close request, or the task no longer being reported clears it. Matched on (this runner, project, task name).
- `GET /api/harness/runners/{runner_id}/menu-answers` · `POST …/menu-answer-result` — Answers a person gave to a blocked-agent menu that this runner has not pressed (`RunnerBinding.pending_answer`), and the runner's report of what became of one. Matched on `answer_id`: a result for a superseded answer does not clear the newer one (`{ok: false}`).
- `POST /api/harness/runners/{runner_id}/session-menu` — `{session_id, menu}`: a cloud runner's dialog for one chat session it holds (an ACP AskUserQuestion or permission prompt), or `menu: null` once it is answered or gone. Sets `RunnerBinding.pending_question` and sends the same `session.menu` frame and once-per-ask push as a laptop's session report; `{ok: false}` for a session this runner does not hold. A finished (or lease-swept) chat turn clears an `acp` menu its box left.
- `POST /api/harness/runners/{runner_id}/admission-notices` (`{mailboxes}`) · `POST …/admission-notices/{notice_id}` (`{outcome, detail}`) — Sender notices for refused turns that canopy-web could not send itself, leased to this runner to send from mailboxes it reads, and its report back (`apps/admission/runner_notices.py`; access.md → "Admission rules").
- `GET /api/harness/sessions` — Open emdash sessions across every live runner the caller can see, newest first (the supervisor's Open Sessions). A connected site sees only its own agents'.

**Turns**
- `POST /api/harness/turns/` — Enqueue a turn (idempotent per `idempotency_key`; 201 new, 200 existing. A key is unique per WORKSPACE (`Turn.idempotency_scope`, the target's workspace), never globally, so another workspace holding the same key neither blocks nor reveals anything — it cannot pre-claim a guessable key (`sched:<id>:<slot>`, `task-<pk>-<i>`) of yours. Within the workspace a key replays only to the target it was made for: same agent, chat session, or project; a key held by another turn there is 409 `conflict`, saying nothing about that turn. The returned turn passes the same content gate as `GET …/turns/{id}`). Exactly one of `agent_slug` / `project` (422). Agent turns need editor (`agent.work`) on the agent; project turns need `agent.work` in the workspace (pinned `/api/w/{ws}/…`, else the sole membership — several memberships → 422). `origin` is the source vocabulary and a routing input: `api` · `ace_web` · `email` · `slack` may be posted; `canopy_web_chat` and `canopy_scheduler` are set only by their in-repo producers; legacy spellings (`board`/`manual`/`drill` → `api`, `cron` → `canopy_scheduler`) are normalized. An `email` turn may be posted only by an admin of the agent (the runner that read its mailbox) — 403 otherwise; it names its own asker from `origin_ref`. Optional `runner_id` pins the turn: 422 for a runner the caller cannot see or a retired one; 403 when the box cannot hold the agent, when the caller may not pin it (agent admins may pin any holdable box, others only boxes they administer), or for a project turn when the box does not declare the repo. Access (`access.decide`) and a requested `turn_mode` are checked up front (403/422, `auto` for admins only). A rule on a source nothing emits is inert.
- `GET /api/harness/turns/` — List turns (`?agent=`, `?status=a,b`, `?huddle=` = `origin_ref.huddle`, `?parent_turn=`, `?limit=` ≤ 200, default 100), redacted per `turn_access`. Tenant + site gate in `visible_turns_qs`, shared with the huddles API.
- `GET /api/harness/turns/{turn_id}` — Get a turn (redacted per `turn_access`).
- `GET /api/harness/turns/{turn_id}/caller-context` — The caller envelope for one turn (same document as the claim's; MCP twin `who_is_asking`). Content-read gate (`turn_access.can_read_turn_content`).
- `POST /api/harness/turns/{turn_id}/cancel` — Cancel a QUEUED turn (finished CANCELLED); idempotent on a terminal turn, 409 once claimed. Gate: editor on the agent; for a session turn, write access to the chat; for a project turn, its initiator or `agent.work`.
- `GET /api/harness/turns/unclaimable` — Queued turns no online runner can claim, with the reason; composed from the same routing predicates as the claim. A caller in two tenant trees must pin one (422).

**Readiness drills**
- `POST /api/harness/runners/{runner_id}/drill` (`{agents?}`) — Administer tier. Fan out a read-only doctor/preflight turn per agent, pinned to this runner; default = every agent assigned to it or following it via a workspace order, disabled assignment rows included (drill before enabling). A caller who is not the runner's owner must be an admin of each agent: the default fan-out narrows to those (422 if none), and naming another in `agents` is a 403 naming it. The starter is the turn's accountable person.
- `GET /api/harness/runners/{runner_id}/drills` — Per-agent drill grid (outcome, summary, timestamps). Runner administrators, or a workspace `logs.read` holder in the runner's tenant; else 404.
- `POST /api/harness/drills/{drill_id}/report` (`{outcome: pass|fail, summary}`) — The drilled agent's callback, accepted with the run's signed report link (`?t=`), from the agent's own login (`Agent.user`), or from the runner's owner. A drill turn that finishes without a report is marked `fail`, even if the turn ended `DONE`.

**Auto-debug** (`apps/harness/auto_debug.py`, mounted at `/api/harness/failure-investigations`)
- `GET /api/harness/failure-investigations/` (`?status=open|held|debugger_failed|resolved|escalated`) · `GET …/{id}` · `POST …/{id}/resolve` (`{note}`) — A turn that really ends `failed` immediately enqueues a turn to `CANOPY_AUTO_DEBUG_AGENT` (`ada`) running `/ada:debug-failure --investigation <id>` with the evidence. One `FailureInvestigation` per fingerprint (normalized result note); repeats only count. A failing debug turn marks it `debugger_failed` and spawns nothing. A fingerprint that recurs after `resolve` gets one escalation turn, then only counts. Fleet-wide caps (`CANOPY_AUTO_DEBUG_MAX_PER_HOUR`=3 / `_PER_DAY`=10, rolling) mark overflow `held` (+ a warn event); the next allowed debug turn carries every held/debugger_failed one. Skipped: drills, a human's stop or delivery collision, turns outside the debugger's workspace tree, `CANOPY_AUTO_DEBUG=false`, no such agent; lease-expired `lost` turns only with `CANOPY_AUTO_DEBUG_LOST`. Readable/resolvable by the workspace's `logs.read` holders, the debugger's admins and its own login; else 404. A list needs one tenant tree.

**Recurring turns** — the runner half of scheduling (canopy-web also fires every due slot itself, `apps/harness/schedule_clock.py`; a runner's fire of the same slot collapses onto that turn); the CRUD is `/api/agents/{slug}/schedules/` (Agents). Semantics (the `fire_after` anchor, idempotent slots, grace release, nags): runners.md → "Scheduled turns".
- `GET /api/harness/schedules/?runner_id=…` — The schedules this runner may fire, tenant-scoped from `runner.owner` (never `capabilities`), act-as; not gated on the runner being online.
- `POST /api/harness/schedules/{id}/fire?runner_id=…` (`{slot}`) — Report a due slot; the server materializes the turn (201). 404 for a schedule this runner may not fire; 409 for a one-off fired at a slot other than its instant.

The server's schedule clock and the runner both evaluate crons with the Django-free `canopy_cron` library (`packages/canopy_cron`, which owns the `croniter>=6.0,<7.0` bound); the server's `preview` endpoint calls the same `next_slots()` / `due_slot()`, so the UI, the server and the runner agree on slots.

> **Deleting a user strands their runners.** `Runner.owner` is `SET_NULL`, and a NULL owner has no tenant: every claim and schedule route returns nothing for that box, which can only be retired and re-paired. Deactivate a departing user (`is_active=False`) instead if their runners should keep working.

How the runner software is installed, updated and versioned (`expected_code_sha`), and what the cloud runner does each tick: [`runners.md`](runners.md) → "The runner software".

### The HCP service (`apps/contacts/hcp_oauth_views.py`, `hcp_api.py`, `hcp_clients_api.py`) — OAuth for apps canopy does not operate

Issuer `<origin>/api/hcp`; design, flow and judgment calls in [`hcp-service.md`](hcp-service.md). Internal only (`HCP_SERVICE_AUDIENCE`). Errors on `/v1/` are `application/problem+json` with an HCP problem type; a mismatched `HCP-Version` header is refused.

- `GET|POST /api/hcp/oauth/authorize` — The two-act consent screen (bare view; signs the person in itself). Code + PKCE S256, exact redirect URI, scopes within the client's registration.
- `POST /api/hcp/oauth/token` — `authorization_code` (with `code_verifier`) or `refresh_token` (rotates; a replay revokes the grant). Form-encoded, public clients.
- `POST /api/hcp/oauth/revoke` — RFC 7009; revoking any of a grant's tokens revokes the grant.
- `GET /api/hcp/.well-known/oauth-authorization-server` (and `/.well-known/oauth-authorization-server/api/hcp`) — RFC 8414. `GET /api/hcp/.well-known/mcp-manifest` — Appendix B. `GET /.well-known/hcp-configuration` and `GET /api/hcp/.well-known/hcp-configuration` — Appendix C.
- **Data plane `/api/hcp/v1/…`** — auth is a canopy session/PAT or `Authorization: Bearer hcpat_…` (one person's grant; refused on every path outside `/api/hcp/v1/`, and on the person-only routes below). 120 requests a minute per client (429 + `Retry-After`). An agent names the turn it serves (`?turn=`) and gets only that turn's person, under its grant.
  - `POST /v1/preferences/search` (MCP `hcp_searchPreferences`) — recall entries relevant to a stated purpose; ≤ 20, by relevance, provenance redacted; audited.
  - `POST /v1/preferences/add` (MCP `hcp_addPreference`) — add an entry in a category the grant may write; `model-inferred` needs `confidence`; an inference contradicting a declared entry on the same dimension is quarantined. Idempotency-keyed.
  - `POST /v1/preferences` — the REST form (a full HCPEntry; `issuer-attested` allowed). Not an MCP tool.
  - `GET|PUT|DELETE /v1/preferences/{entry_id}` (MCP `hcp_getPreference` / `hcp_updatePreference` / `hcp_deletePreference`) — read (`purpose` required and logged; `version` is the person's only; a missing entry is 403 too), correct (new version, same id; the person updating a quarantined inference accepts it), forget (`hardDelete=true` is the person's only and removes every version).
  - `GET /v1/audit` (cursor-paged, filters) · `GET /v1/grants` · `DELETE /v1/grants/{grant_id}` · `GET /v1/export` — the person's own: audit log, grants (an agent sees only the grant it reads under), revoke (immediate, never rate-limited), export (`include=versions,audit`, `exclude=deleted`). Not MCP tools.
- `GET|POST /api/hcp-admin/clients` · `PATCH /api/hcp-admin/clients/{client_id}` — The client registry (`HcpClient`): register, change, disable (stops every token) or rotate the webhook secret (returned once). Narrowing `allowed_scopes` does not change existing grants. Superusers only; never MCP.

What agents know about a person, per workspace. Rules in [`access.md`](access.md) → "What agents know about a person". "Person-only" below means 403 for an agent's login, a caller token or a system account.

- `GET /api/people/me/` — Everything held about the caller: `agent_memory: {record: {available, default, changed_at}, use: {…}}`, live facts in every workspace (with who learned each), the last 50 reads (`PersonAccess`). Any signed-in user, only their own.
- `PUT /api/people/me/agent-memory/` (`{record?: {available?, default?}, use?: {…}}`) — Canopy-level settings: whether each feature may be on at all, and whether it is on in a new session. `record` = agents may learn about me; `use` = agents may be told it. Off deletes nothing. Person-only; not an MCP tool. Audited (`agentRecord.*`, `agentUse.*`).
- `GET|PUT /api/people/me/sessions/{session_id}/agent-memory/` (`{record?, use?}` = `on|off|inherit`) — One of the caller's own sessions (`created_by`; else 404): per feature `{available, default, override, effective, granted, grant}`. Turning on an unavailable feature is 403; any other value 422. Person-only; not an MCP tool. Audited (`sessionRecord.*`, `sessionUse.*`).
- `POST /api/people/me/sessions/{session_id}/agent-grants/` — The person grants that session's agent `record` and/or `use`, for the session (`duration=session`, lapses with it or after `session_grant_hours`) or always (`duration=always`, until revoked). Only available features; granting one that is off by default turns it on for the session. Person-only; not an MCP tool.
- `GET|POST /api/people/me/memory-collections/` · `PUT|DELETE …/{collection_id}/` · `PUT /api/people/me/grants/{grant_id}/collection/` (`{collection_id|null, confirm_widening?}`) — Named sets of contexts (all of an org as it is when read, one workspace, or entries in no workspace) a person points an agent's grant at. ### Asks — a task that asks a person something
An ask is a property of a task, not a separate noun: `ask_kind` is `review` ("should I do this?") or `question` ("I need an answer"), with `ask_body` carrying its text (`origin_ref` is provenance, not identity). It is **open** until an action closes it: `approve` or `decline` on a review, `reply` (the answer) or `decline` on a question. No routes of its own — raised by `POST /api/agents/{slug}/tasks/`, answered by `POST /api/agents/{slug}/tasks/{ref}/actions` (Agents).

An ask is the dual of a `Turn` (work you do vs. work an agent does): an approved task's `on_approve` enqueues turns, or one turn written from the card when it has none (`Turn.raised_from_task`). `TurnSpec.target_agent=""` means the ask's own agent; set, it dispatches to another agent. Act + dispatch are one transaction: a bad `on_approve` spec is a 422 with the ask still open.

**Waiting on you is a filter.** `/supervisor` (`GET /api/me/tasks/?waiting=me`, every workspace you are in) and an agent's Tasks page (`?waiting=me`) render the same rows on the same card, actionable in place. Producers raise real asks: the schedule nag (`schedule_turns._raise_schedule_nag`; runners.md → "Scheduled turns"), run gates and task reviews (e.g. the fleet `task-tracker` skill). Any task row moving marks `task://` dirty (`apps/harness/signals.py`), so a page showing tasks re-reads.

### Attention (`apps/attention`, mounted at `/api/me/attention`) — what is waiting on you

- `GET /api/me/attention/` — a user-level view ([roles.md § A user-level view](roles.md#a-user-level-view-reads-each-organisation-on-its-own)): everything waiting on the caller in every organisation they are in, as `now` (activity in the last 3 days, `services.QUIET_AFTER`), `quiet` (older) and `hidden`, plus `running` — the caller's own sessions being worked right now (the feed's ownership rule `feed.held`; an agent's auto run counts), not asks, so never quiet or hidden — each newest first. Every item: `key` (`task:<agent>:<ref>`, `session:<id>`, `access:<id>`), `kind`, `state`, `reason`, `title`, `body`, `workspace`, `organisation`, `agent_slug`, `project`, `url`, `last_activity_at`, `actions`, `target`. **`state`** is what it asks of you, the one field a client branches on (`apps/attention/types.py`): `asking` (a dialog, review, question or join request), `your_move` (the agent finished, or a task is parked with you), `parked` (waiting behind a paused or offline runner — named in `reason`), `running`, `running_auto`; `reason` is display text. Each owning app supplies its own items by its own rule (`apps/<app>/attention.py`, registered by dotted path in `apps/attention/sources.py`): tasks by the board's `filter_tasks(waiting="me")`, chats by the feed's `feed.status` through the session list path, access requests by `members.manage`. Actions go to the existing routes (`act_on_task`).
- `POST /api/me/attention/hide` `{keys, days?}` — take things off the caller's own list and nothing more: no task is closed or decided, no chat is ended, nothing is sent and the agent is not told (`Hidden`). Each returns when its `last_activity_at` passes the hide, or after `days`. `DELETE /api/me/attention/hide/{key}` puts one back.

### Alerts (`apps/attention/alerts_api.py`, mounted at `/api/me/alerts`) — persisted things that need you

A user-level view like attention (read once per organisation, rows carry `organisation`). An alert is visible when its workspace is one the caller may read AND its source offers them an action (`visible_actions`; for `status=dismissed`, `offers_dismiss`); a row whose kind has no importable source is skipped. By id, anything not visible is a **404**, never a 403. Source modules and the lifecycle: `apps/attention/alerts.py`. The model, sources, screens and the rules that keep the list worth reading: [`alerts.md`](alerts.md).

- `GET /api/me/alerts/?scope=&status=open|dismissed` (`list_alerts`) — `AlertOut[]` (`id, kind, severity, title, body, url, workspace, organisation, scopes, status, first_seen_at, last_seen_at, occurrences, closed_by_email, closed_at, actions[{id,label,closes,href}], last_notify`), `blocking` then `action` then `setup`, newest first. `scope` keeps rows whose `scopes` contain it; a `workspace:<slug>` scope also keeps every alert whose workspace is that one or any below it (`wsvc.descendant_map`). `dismissed` = dismissed in the last 7 days that the caller could dismiss. `last_notify` is the latest `notified` event as a line ("A asked B at 14:02" / "Notified B at 14:02"), else "".
- `POST /api/me/alerts/{id}/act` `{action}` (`act_on_alert`) — runs an action still offered to the caller; for a link action (`href`) it only logs `acted` (no perform, no resolve) — the browser follows the link. **409** problem+json with `code: "action-not-offered"` when it is not (or no longer) offered.
- `POST /api/me/alerts/{id}/undismiss` (`undismiss_alert`) — anyone currently offered `dismiss`; **409** `action-not-offered` otherwise.
- `GET /api/me/alerts/{id}/history` (`alert_history`) — `AlertEventOut[]` (`at, kind, actor_email, action_id, payload`), oldest first; works for resolved alerts too (visible when the workspace is the caller's and the source offers them any action, whatever the status).

### Chat (`apps/canopy_sessions`) — multiplayer chat sessions (the live front-door)
A `Session` is a durable conversation with an agent (or, agentless, with a repo checkout), workspace-tenanted. A send enqueues a **session `Turn`**; a session-capable runner executes it and the reply comes back through the turn ledger and the transcript; `Message` rows are a projection. How a chat is recorded, its turn status, drafts/authorship, liveness and push are in `docs/architecture/chat-sessions.md`; blocked-agent dialogs in `docs/architecture/blocked-agent-menus.md`; the embedded widget and MCP Apps Views in `docs/architecture/embedding-internals.md`. WebSockets (`apps/realtime/routing.py`, `apps/canopy_sessions/routing.py`): `ws/canopy-sessions/{id}/` (connect snapshot, per-person drafts, presence, streamed reply — the `canopy-ui/chat` protocol), `ws/turns/{turn_id}/`, `ws/supervisor/` (`supervisor.sessions` frames), `ws/runner/{runner_id}/` (runner control channel), `ws/presence/`.
- **Access — one rule, `apps/canopy_sessions/access.py`**, asked by every door: [tenancy.md § The chat-session ACL](tenancy.md#the-chat-session-acl-ci-enforced). Pinned by `tests/test_session_acl.py`.
- `POST /api/canopy-sessions/` — Create (`agent_slug` XOR `project`, `title`, `metadata`, optional `runner_id` pinning the first turn, optional `parent`). A project chat's `runner_id` must be a box the caller administers (403 otherwise; `chat-sessions.md` → "Which box takes a chat's first turn"). Created in the current workspace; `/api/w/{ws}/canopy-sessions/` creates in that one. A delegated site may only open a chat with an agent it offers; `embed_app` is server-owned (taken from the token, never the body).
- `GET /api/canopy-sessions/?state=active|archived|all&limit=` (≤ 500, no paging) — The sessions you can see: waiting on you first, then running, then most recent. Filters `q` (title/`session_key`), `repo`, `branch`, `pr`, `since`/`until`, `source`, `origin_key`, `embed_app`, `resource`, `page_path`, `session_key`; `reply=true` stamps `feed_status`. "Active" is derived each read (rules: `chat-sessions.md` § Session liveness); rows carry `runner_online` and `runner_status` (the bound runner's `live_status`, null when unbound), `runner_id`, `runner_host` (the macOS login the session lives on) and `emdash_project` (the binding's project, else the repo or agent slug — what `/ide` groups by).
- `GET /api/canopy-sessions/search?cursor=&limit=&state=all&…` — Walk **every** session (the list caps at 500): `{sessions, next_cursor}`, keyset-paged on (last activity, id) desc; same filters as the list via one helper. Pass `until=<walk start>` to freeze the set.
- `GET /api/canopy-sessions/{id}` (`?full=true` for everything) — Session + transcript tail (`SESSION_TAIL_DEFAULT` = 60) + `menu`, `turn_status`, `my_role`, `can_move`. If no readable session has that id it is tried as a runner `session_key` (409 if it names several). `GET /{id}/messages` — scroll-back (`before=`).
- `GET /api/canopy-sessions/{id}/human-inputs?after=&limit=` — Only what people typed, oldest first: `{messages, next_cursor, source}`. Excludes agent output, tool rows, harness/system rows, prompts a program delivered (any turn that is not a chat send) and Claude Code's own user records (skill bodies, wake-ups, compaction, sidechains — decided by the transcript record's flags in `Message.content.record`). No durable rows yet → answered from the runner's tail (`source: "tail"`, unpaged).
- `GET /api/canopy-sessions/{id}/slash-commands` — What the composer's `/` menu offers: the agent's launchable skills (`<slug>:<name>`) first, then what the bound runner reported. Empty for someone who can read the session but not send to it (`apps/canopy_sessions/slash_commands.py`).
- `POST /api/canopy-sessions/{id}/send` — `text`, `client_id` (idempotency, ≤ 100 chars), optional `placement` (`"wait"` pins to the bound runner, a runner id re-pins), `origin` (postable sources only, e.g. `ace_web`), `parent`, `clear_prompt`. A site token's runner requirements (`sensitive_data`) are stamped on the session first. Clears the sender's draft.
- `POST /api/canopy-sessions/{id}/place` — Re-pin the session's oldest queued turn (`placement`, same shape as send); the chat banner's after-the-fact choice. For a project chat, a box you administer only (422 otherwise), as for send's `placement`.
- `POST /api/canopy-sessions/{id}/transfer` — Move a live session to another runner (`runner` id or name, `brief`), history included. Onto a runner you administer (or between two runners with the same owner): `status: moved`. Onto someone else's: `status: pending` + `request_id` + `approvers`. 409 while a turn executes (stop and retry) or another request is pending.
- `POST /api/canopy-sessions/{id}/fork` — `{turn_index}`: a new session (returned) holding the conversation up to the end of that message's turn, on the same runner and in the same worktree (`parent_session` = the source). The runner cuts its transcript on the fork's first turn (`resolve-session` → `fork`; `worktree_of` names the directory a cloud runner runs every fork turn in). 422 unless the runner is a cloud runner or a laptop on the `claude-cli` runtime, or for a message from before a transfer; 409 when the cut falls in a turn still running.
- `GET /api/canopy-sessions/transfer-requests?status=pending|all` · `POST …/transfer-requests/{id}/approve|decline|cancel` — Transfer requests waiting on you (as an admin of the target runner) or that you made. Approve carries out the move (409 while a turn still executes; the request stays pending); decline takes a `note`; cancel is the requester's.
- `POST /api/canopy-sessions/{id}/move` — File the session in another workspace where you are editor+. Only the session's own person (creator of a web chat, owner of the runner an emdash session was discovered on); an agent's session cannot move (422). Participants not in the target are removed; a re-report never moves it back.
- `GET|POST /api/canopy-sessions/{id}/participants` · `DELETE …/participants/{user_id}` — Share a chat (the header's People control). Owner only (the creator; for an agent's own thread, its admins). The teammate must be in the chat's workspace; `role` `editor` (default) or `viewer`, re-adding changes it. Anyone may remove themselves; the owner cannot be removed.
- `POST /api/canopy-sessions/{id}/archive` · `/unarchive` — Retire / restore by hand. Idempotent, never destructive. Unarchive clears only the written half: a stale runner session stays out of `active` until reported again.
- `POST /api/canopy-sessions/{id}/close` — End a session for good. If a runner is currently reporting an emdash task for it (`RunnerBinding.reported_at` within the live window): cancel its turns, relay `runner.close_session` (the runner deletes the task; its next report retires the row), write nothing to the session — answers `closing: true`. Otherwise (cloud, never-bound web chat): cancel turns and archive. A refusal is a 200 `ok:false` with `reason` `unavailable` | `already_closed`; `unavailable` does not queue. Spec: `docs/superpowers/specs/2026-07-30-close-session-from-phone-design.md`.
- `POST /api/canopy-sessions/{id}/stop` — Stop the session: cancel its open turns, or, with none open, ask its runner to interrupt the agent. Returns `cancelled`, `interrupted`, `route`.
- `POST /api/canopy-sessions/{id}/reset` (`?dry_run=`) · `POST /api/canopy-sessions/reset` (`dry_run`, `prune_ghosts`) — Drop the derived `Message` rows and re-derive them from the runner's transcript. Refusal is a 200 `ok:false` + `reason` (`no_binding`, `runner_unreachable`). Bulk touches only sessions you may act in; `prune_ghosts` deletes runner-discovered sessions with no binding (never a human-started chat). `Turn`s and their ledger are never touched. Same service as the chat header button and `manage.py reset_chat_state`.
- `POST /api/canopy-sessions/{id}/answer-menu` — Answer a blocked agent's dialog: `option` (`null` = refuse/Escape), `selections` (one list per question for an AskUserQuestion), `texts`. Relayed to the runner; refusal is a 200 `ok:false` + `reason` (`unbound`, `unavailable`, …). Mechanics: `blocked-agent-menus.md`.
- `POST /api/canopy-sessions/{id}/attach` · `/detach` · `/backfill` — Register / unregister a live viewer (the bound runner tails and ships view-only rows while one is attached); ask the runner for full history.
- `POST /api/canopy-sessions/{id}/attachments` (201, multipart) · `GET /api/canopy-sessions/attachments/{id}/content` · `DELETE /api/canopy-sessions/attachments/{id}` — Composer attachments: uploaded unbound (the send binds it), type-allowlisted and size-capped (422), 503 when storage is unconfigured. Content is gated on reading the session, served inline with `nosniff` + `CSP: sandbox`; a runner fetches through the turn it holds instead (harness `…/turns/{turn_id}/attachments/{id}/content`). Delete only while unsent (409 once sent).
- `PUT /api/canopy-sessions/{id}/title` — `{title}` (owner/editor): rename it in canopy (the emdash task keeps its name). Whitespace collapses; blank clears, so it is named again like an untitled one. A typed title is never replaced by the runner's task name or autotitle (`harness.session_sync._title_is_derived`); publishes `session.title_updated`.
- `PUT /api/canopy-sessions/{id}/notify` — `{every_completion}`: push on every finished turn instead of once the chat goes quiet (served as `notify_every_completion`).
- `POST|GET /api/canopy-sessions/{id}/secrets` · `DELETE …/secrets/{name}` — Share a secret with one chat (write-only; list returns names + expiry, never values); nothing is posted into the chat. A secret lives 30 min from sharing (re-sharing restarts it).
- `GET /api/session-secrets/key` · `GET /api/session-secrets/key/{name}` — The agent half (`canopy secret list|exec`): present the chat's key in `X-Canopy-Chat-Key` (minted when a runner claims the chat's turn and handed only to that chat's session). No route takes a chat id, so a key reaches only its own chat's secrets. Bearer only; no/wrong/expired key → 404. Each read is a `session.secret.resolved` event. The same key scopes the MCP page tools to that chat's page.
- `GET /api/canopy-sessions/{id}/export` — The conversation as markdown (tool output shortened) to continue in your own Claude (`canopy runner export`). Creator only; refused (403) for an embedding site.
- `POST /api/canopy-sessions/slack/detach` — Disconnect a session from its Slack thread (see Slack below). Name it by `session_id`, `claude_session_id` or `emdash_task` (+ `emdash_project`; 409 if ambiguous). Owner/editor; idempotent (`status: not_bound`), or — for an agent's own login — by `turn_id`, its live turn (`access.own_turn_session`).
- `POST /api/canopy-sessions/slack/new-thread` — Move a conversation to a NEW thread in its own Slack channel (`start_new_slack_thread`): posts `summary` top-level, binds the session to it, tells the old thread where it went. Named like detach (`turn_id` for an agent's own live turn, else `session_id` / `claude_session_id` with owner/editor). 409 when unbound or a DM; 422 without a summary.
- **Page contract** (`docs/architecture/embedding-a-canopy-agent.md`): `PUT|GET /api/canopy-sessions/{id}/page-actions` (declare / list what the attached page can do; replaced wholesale; empty = no page attached) · `PUT|GET /{id}/page-state` (what the page shows; over the cap → 422 `too_large`) · `PUT /{id}/run-input` (AG-UI `RunAgentInput`: `tools` → actions, `state` → page state, other fields ignored) · `POST /{id}/page-actions/invoke` (blocks until the page answers; errors carry a `code`: `no_page`, `unknown_action`, `bad_arguments` (422), `timeout`, `refused` (409)) · `POST /{id}/page-actions/{action_id}/result` (the page reporting back).
- **MCP Apps Views** (`apps/canopy_sessions/app_views_api.py`, `apps/mcp_apps_host/mcp_apps_views.py`): `GET /api/canopy-sessions/{id}/apps/{tool_call_id}/resource` · `POST …/call` · `POST …/read` (same server only) · `PUT …/context` · `POST …/message` (starts a turn) — a rendered View's browser plumbing, run as the person looking at it. Not MCP tools; refuse a PAT.

How a runner drives a chat turn (the bridge, transcript rows, ordinals, hooks): [`chat-sessions.md`](chat-sessions.md) → "How the runner drives a chat".

### Feedback (`apps/feedback`) — what someone said, from any channel
Framework tier, generic over its target (`target_kind` + `target_ref` strings, never an FK). Feedback is input to a judgement, not work: the app emits **no signal** (no ask, push or timeline event; `tests/test_feedback_emits_nothing.py`). It has no pollers or connectors — an agent reads a channel and POSTs.
- `POST /api/feedback/` — Ingest (batch, atomic; editor+). Idempotent per `(channel, source_ref)` (partial unique index excluding blanks). `submitted_by` is the caller, never the external author.
- `GET /api/feedback/?target_kind=&target_ref=&state=&channel=` — The pool, in your workspaces.
- `POST /api/feedback/{id}/resolve` — Record a disposition (editor in its workspace). The only mutation.

### Events (`apps/events`) — the fleet log of actions and errors
Framework tier, generic over its producer (`source` + `kind` strings). Where an operational fault lives when it belongs to no `Turn`. A log, not a queue: emits **no signal** (`tests/test_events_emits_nothing.py`); a turn sweeps it. `Event.workspace` is NOT NULL.
- `POST /api/events/` — Record (batch, atomic; editor+). Repeats of `(workspace, source, key)` coalesce onto one row (`count`, `last_seen_at`); a blank `key` never coalesces; a row with no `source` is dropped. The workspace is the pinned one, else — for a box posting with its runner token — `Runner.workspace`, else the caller's sole workspace (422 when there is none). A runner token's `claude_auth_required` / `claude_usage_exhausted` / `claude_api_key_fallback` also mails and pushes the runner's approvers, once per (runner, alert) per UTC day (`apps/harness/credential_notify.py`) — except `claude_auth_required` from a runner whose health reports a signed-out `claude.probe.*` check, which reaches people as the `runner_credential` alert instead.
- `GET /api/events/?source=&kind=&level=&since_minutes=&limit=` — Admin+ (`logs.read`). `source`/`kind` are prefix matches; newest-touched first.
- `GET /api/events/setting-changes?operation=&target=&actor=&since_minutes=&limit=` — The settings audit trail (`SettingChange`, `docs/architecture/settings-audit.md`), newest first: changes in workspaces where you are admin+, plus your own. `operation` is a prefix, `target` a substring, `actor` an exact email; `limit` ≤ 500 (default 100).
- `GET /api/events/mcp-calls?tool=&failed=&since_minutes=&limit=` — The MCP audit log (`MCPAuditLog`), newest first: every call in workspaces where you are admin+, plus your own calls anywhere. `tool` is a prefix; `failed` keeps errors.
- No mutation route. Retention: `manage.py prune_events --older-than-days 30` (anchored on `last_seen_at`).

### Inbound push (`apps/inbound`) — the doorbell
Framework tier. Gmail push turns new mail into a turn in seconds instead of on the runner's 300s poll.
- `POST /api/inbound/gmail/{workspace}/` — Gmail Pub/Sub push. `auth=None`, allowlisted in `apps/common/middleware.py`, self-enforcing on a Google-signed OIDC JWT checked against **that workspace's** `InboundPushConfig` (the tenant is in the path, so it is known before the body is decoded and one tenant's signer can never satisfy another's). Unverified → **404** (no enumeration); verified but not actionable → **200** (a 4xx makes Pub/Sub redeliver forever).
- `GET|PUT /api/inbound/config/{workspace}` — Audience, expected signer, watch topic; read member, write admin+ (`integrations`). Returns a server-computed `push_url`.
- `GET|POST /api/inbound/mailboxes/{workspace}` · `PATCH|DELETE /api/inbound/mailboxes/{workspace}/{id}` — Address → agent registry; writes admin+. An address is globally unique (409 if registered). `enabled=false` parks a mailbox on the poll.
- `GET /api/inbound/runner-mailboxes` — Every enabled mailbox the caller may read (address, agent, topic): the runner's mailbox probe keeps those it holds a token for, and its watch re-arm takes those with a topic.
- `POST /api/inbound/watch/` — Report a mailbox's Gmail watch expiry (editor+ in its workspace).

**A doorbell, not a reader.** A push carries `{emailAddress, historyId}` and no content: canopy resolves mailbox → agent → runners (via `harness.assignment_rows_for(..., ORIGIN_EMAIL, ...)`, the same rows the claim uses, so a strict `email` rule holds) and sends `runner.check_inbox` to every online assigned runner; the runner does its normal read. No mail credential is in the web app, and a forged doorbell causes at most an empty read. Enqueue is idempotent per `(thread, messageCount)`.

**The poll is the auditor.** Email turns record `origin_ref.discovered_by` (`push`/`poll`); a poll-found turn on a mailbox with a live watch writes `gmail.push.missed` at `error`. `gmail.push.unknown_mailbox`, `gmail.push.no_runner`, `gmail.watch.expiring`/`.expired` are logged too. Stamps are per mailbox.

**Watches.** The runner arms and re-arms each mailbox's Gmail watch (7-day expiry, re-armed 24h ahead) and reports the expiry; the GCP-project constraint, the two fleet clients and the grants: [gmail-push-provisioning.md](../runbooks/gmail-push-provisioning.md).

Configured only at `/w/:workspace/settings/inbound` (audience, signer, topic, mailboxes, watch health, generated `gcloud` commands); there are no deployment-global inbound settings.

### Slack (`apps/slack`) — the Slack front door
Framework tier. Any agent with Slack on can be reached by mention, DM, `/canopy <agent> …` or `/<agent> …`. A Slack thread becomes a `canopy_sessions.Session` and each message a `send_message(origin="slack", …)`. Design: `docs/superpowers/specs/2026-09-18-slack-front-door-design.md`; multi-tenant: `2026-09-22-slack-multi-tenant-design.md`.
- `POST /api/slack/events` · `POST /api/slack/commands` · `POST /api/slack/interactions` — Bare views, allowlisted, self-enforcing on the Slack signing secret (5-min replay window). A verified request always gets **200** (non-2xx makes Slack redeliver); refusals go back as ephemeral messages. Unconfigured (any setting empty or `PLACEHOLDER`) → **503**. Interactions: button/Submit presses on question posts (toggles ignored until Submit); needs Interactivity on with Request URL `…/api/slack/interactions`.
- `GET /auth/slack/install/?workspace=<slug>` → `GET /auth/slack/callback/` — OAuth install, owner of that workspace. One Slack can serve several canopy workspaces (`SlackWorkspaceLink`): connecting adds a link and refreshes the shared bot token. A message's tenant is what it is ABOUT (its thread's session, else the agent it names), never the Slack it arrived through.
- `GET /auth/slack/link/?token=…` — Link a Slack user to the signed-in canopy user, only when the Slack profile email equals the canopy email.
- `PATCH /api/agents/{slug}/slack` — `slack_enabled`, agent admin. Returns `command_status` (`synced` | `not_configured` | `error`) for the agent's `/<slug>` command.
- `GET /api/slack-config/{workspace}` (member) — The workspace's Slack connection. `reinstall: {needed, turns_on}` names, in plain words, what a reinstall would turn on when the install lacks a scope canopy asks for (granted scopes are recorded at install; an older install is asked once via `X-OAuth-Scopes`).
- `PUT|DELETE /api/slack-config/{workspace}/config-token` (owner) — Give / withdraw the Slack **app configuration token** (refresh half; rotated on receipt, stored encrypted, refreshed under a row lock) that lets canopy manage the app's slash commands by editing its manifest. 422 if Slack refuses it.
- `POST /api/slack-config/{workspace}/sync` (admin+) — Reconcile slash commands now (also runs on every switch flip): adds `/canopy` and `/<slug>` per Slack-enabled agent across every linked tenant, removes only canopy's own commands, declares the app an agent (`features.agent_view`, agent scope and events — unless it is on the older `assistant_view`), writes the rest of the manifest back as exported. Also runs when Slack is (re)connected and canopy holds a configuration token. A slug over 32 chars is reported, not truncated.
- `PUT /api/slack-config/{workspace}/history` (admin+) — Whether `@canopy <agent> --history --min <n>|--msgs <n>|<time> <ask>` may hand the agent the channel's recent messages, and the longest window.
- `POST /api/slack-config/{workspace}/declare-agent` (owner) — Declare the Slack app an agent (manifest: `features.agent_view`, `assistant:write`, agent events) so Slack draws its own Working… indicator and Stop button. One-way: Slack cannot undo it. Every sync does this too; the endpoint remains for operators.
- `PUT /api/slack-config/{workspace}/channel-ingest` (owner) — `{enabled}`: whether this workspace's agents may ASK to read a whole channel (default off). Off also stops live reads.
- `POST /api/slack-config/{workspace}/channel-ingest/allowed` (admin or owner) — `{agent, channel (id or #name), follow, note}`: allow-lists ONE channel for ONE agent of this workspace, explicitly. When that agent asks for the channel, canopy reads it at once (approved by whoever added the entry) and posts a notice with Revoke in the channel instead of Approve / Decline. Works whether or not the switch above is on; a read-once entry refuses `follow`. Re-posting updates it. Listed in `GET /api/slack-config/{workspace}` as `channel_ingest.allowed`. The agent's own login can never add one.
- `DELETE /api/slack-config/{workspace}/channel-ingest/allowed/{allow_id}` (admin or owner) — removes the entry and revokes every pending or live read it allowed (transcripts deleted). Moving the agent to another workspace deletes its entries.
- `/api/slack-config/` is deliberately not under `/api/slack/`, which is allowlisted for Slack's anonymous signed webhooks. UI: `/w/:workspace/settings/slack`.

**Whole-channel reads for an agent** (`apps/slack/ingest.py`) — the permission is given in Slack, never through this API:
- `POST /api/slack-ingests/` (the agent's own login, or an agent admin) — `{agent, channel (id or #name), purpose, follow}`. Creates a `pending` ingest and posts ONE Approve / Decline message in the channel; reads nothing. An allow-listed channel is refused (409): it is read only when a person types `/<agent> read-channel <ask>` in it, which reads everything since the agent's last read there (`read_mark`) and sends it, with the ask, to the agent in that command's thread. 409 also if the workspace switch is off and the channel is not allow-listed, the agent has no login of its own, a pending/live ingest of that channel exists, or the bot is not in the channel.
- Approval happens on that post (`/api/slack/interactions`): only a channel member (`conversations.members`) who holds `integrations` in the agent's workspace, or the channel's creator — never the agent's own login. Any channel member may decline; a decline is final. Refused clicks are audited.
- `GET /api/slack-ingests/` · `GET /api/slack-ingests/{id}` (agent login, agent admin, workspace admin) — status `pending | reading | ready | declined | revoked | failed`, progress, error.
- `GET /api/slack-ingests/{id}/transcript[?after=<read_mark>]` (the agent's own login ONLY — not its owner) — the channel as Markdown, threads nested; partial while `reading`, whole when `ready`; 409 otherwise. With `after`, only the messages canopy stored since that read mark (a new reply to an old thread included, shown under its already-read parent), plus `total`, `mark` (to record next), `first_ts`/`last_ts`. The mark is a stored-row id, not a Slack ts, so a follow pass that stores an old thread's reply after newer messages is never skipped.
- `POST /api/slack-ingests/{id}/read-mark` `{mark}` (the agent's own login ONLY) — records how far the agent has read (`read_mark`, `read_at` on the ingest); never moves back or past what is stored. `canopy slack ingest transcript` reads `after=read_mark` by default and records the mark only after it has written the output.
- `POST /api/slack-ingests/{id}/revoke` (approver, agent login, agent admin, workspace admin; also the Revoke button on the post) — stops reads (incl. `follow`) and deletes the transcript; on a `pending` one, withdraws it.
- The read runs off-request (a job on `apps/common/ticks.py`, registered by `apps/slack/ingest_scheduler.py`, every `SLACK_INGEST_TICK_S`; `manage.py slack_ingest_tick` by hand): paginated, resumable, parked on Slack's `Retry-After`. Every request, decision, fetch batch, revoke and failure is a `slack.ingest_*` event in the workspace log.

**Who is asking.** A Slack user resolves to a member by an existing link, else by Slack profile email (exactly one active canopy account; never a guest, bot or deactivated user); the installer is linked at install. Anyone else is a `Contact` (`source="slack"`, keyed `<team>:<user>`, graded `slack`) and answered as one; their session has no `created_by`, so no member opens it. Only a blocked contact is refused. A member's session is private to the thread's starter; a member who joins the thread becomes a participant. A confined reply in someone else's thread forks to a thread of its own (`services._fork_confined`); `@canopy branch <ask>` splits a thread's conversation into a new one (`apps/slack/branch.py`). Every message not turned into a turn writes an `apps/events` row (`source="slack"`, `kind="slack.<status>"`).

**Replies and status.** Replies post into the thread (or DM) as the agent (`chat:write.customize`, falling back to the plain bot), converted to mrkdwn and split at 3500 chars, plus a note on a FAILED turn; exactly-once via `SlackRelayPost` (unique `turn, seq`), a failed post writes `slack.relay_failed` and is not retried. A plain reply in a thread canopy has a session for continues it (needs `message.channels`/`message.groups`; everything else is dropped unread). An `@canopy` that starts a session partway through a thread hands the agent the thread so far once (`<slack-thread>`, capped by `SLACK_HISTORY_MESSAGE_CEILING`; logs `slack.thread_read`). Redelivery collapses via `client_id = slack:<channel>:<ts>`. A slash command's anchor post IS its status line (edited in place). Status rendering: `chat-sessions.md` § Turn status.

**Dialogs over Slack.** Each dialog that appears/changes posts once per question content (`SlackMenuPost`) as text plus Block Kit (a button per option for one pick-one question, else checkboxes/radios + Submit, plus Dismiss). Thread replies are parsed strictly (`2`, `1,3`, `2; 1`, `cancel`) and go through the same `answer_menu` as the phone; anything else while a parsed dialog is up is not sent. Button values name the session and question key and are re-checked against what is open now; answered posts become "Answered by @x: …". An option-less Notification marker is shown with a link and captures no replies.

**Sharing a session TO Slack** (`apps/slack/share.py`; `POST /api/canopy-sessions/slack/share`, MCP `share_session_to_slack`, `/canopy:share-to-slack`, the chat page's Share to Slack; the summary is always written by the session). **broadcast** posts once; **bind** gives the session the same `slack_*` metadata a Slack-born session has (refused without a resolvable session or when the agent's Slack is off). Re-sharing a bound session posts an update in its own thread. Turns before `slack_bound_at` are not relayed. A **repo session** bound this way accepts replies from workspace members only. When a bound session closes (archived in emdash, closed from canopy, or absent from two consecutive complete reports by its runner — `RunnerBinding.missed_reports`), its thread is told once and later replies get that answer. **Noise sweep**: `GET /api/canopy-sessions/noise` (MCP `audit_session_noise`) reports harness output stored as user messages in sessions you can read; `POST …/noise/purge` (MCP `purge_session_noise`) deletes them, dry run unless `apply`. **Detach** (`POST /api/canopy-sessions/slack/detach`, MCP `detach_session_from_slack`) moves the `slack_*` keys to `metadata.slack_detached`, stops both directions, posts one best-effort note and deletes nothing; re-attaching is a fresh bind. The three routes live in `apps/slack/session_api.py`, mounted at the session paths. Session payloads carry `slack` (the bound thread or null), from the reader Slack registers in `apps/canopy_sessions/channel_bindings.py` — canopy_sessions imports no Slack. **Agents and their own conversation:** an agent's own login cannot read a Slack thread a person started, but `access.own_turn_session` lets it act on the ONE conversation of a turn it is running, named by `turn_id`, while the turn is claimed/running/needs_human: update its thread (`share_session_to_slack` with `turn_id`), detach it, re-bind only in that conversation's own channel, or move it to a new thread there (`POST …/slack/new-thread`). The caller envelope's `conversation.slack` says where the conversation is (`apps/slack/location.py`, cached on the session, never fetched while building). Spec: `docs/superpowers/specs/2026-09-21-share-session-to-slack-design.md`.

### Storyboards (`apps/storyboards`) — the shareable arc
Product tier. `Storyboard → Act → Entry`; an entry names a narrative by slug and resolves to its current release at read time (`Entry.pinned_run_id` holds a known-good run while a narrative is redrafted). `slug` is unique per workspace.
- `GET|POST /api/storyboards/` — List (member) / create (editor+).
- `GET /api/storyboards/{slug}?ws=&t=` — `auth=None`, self-enforcing: member, or a matching `?t=`. A wrong token 404s (never 403). `ws` (the workspace in `/w/<ws>/storyboard/<slug>`) 404s a board elsewhere and disambiguates a slug two workspaces share; the narrative and feedback routes take it too.
- `PATCH /api/storyboards/{slug}` — Retitle / reorder / set capability / replace `brief` (editor+). Acts are replaced wholesale.
- **A board is the one link for a SET of demos.** Optional `brief` on create / patch / YAML import (`StoryboardBrief`, unknown keys 422): `audience`, `purpose` (the point to land), `data_disclosure`, `short_version {label, note, items: [{narrative_slug, cut_id?}]}`, `assumptions[]`, `divergences[{script, data, resolution}]`, `open_questions[]`. Each read entry carries `cuts[]` — a recorded narrative's cuts in running order (`apps/storyboards/cuts.py`): the pinned cut video (`video_url` withheld when this reader cannot stream it), `duration_sec`, `word_count` (counted from the narration), `scenes`, `anchor_id` (`cut:<id>`, what a per-cut note anchors to via `/feedback`), and `screen_notes` / `audience_note` / `provenance` / `poster_url` / `optional` from the version's `request_json.cuts[]` (provenance defaults to the scenes'). A declared cut with no video reads `recorded: false`. Entries also carry the version's own `assumptions` / `divergences` / `open_questions`.
- `POST /api/storyboards/{slug}/share` · `/rotate-token` — Mint the link if missing / re-mint it (kills every link sent). The link is `/w/<ws>/storyboard/<slug>?t=…`.
- `GET /api/storyboards/{slug}/narratives/{narrative_slug}` — The reviewer surface's read (current + previous narration). Same token gate; 404 if the narrative is not on the board.
- `POST /api/storyboards/{slug}/feedback` — Anonymous, capability-gated write. One grant per board: `read` < `comment` < `suggest` (insufficient → 403). `channel`/`target_kind` are server-set; a narrative not on the board → 404. Lives here, not in `apps/feedback`, because the product app owns the token; it calls the request-free `feedback.services.ingest`.
- **Feedback rounds** (`apps/storyboards/rounds.py`; session auth): `POST /api/storyboards/{slug}/rounds` (editor+) — open one: pins every narrative's current version and adopts the notes since the last round; 422 unless the board is linked to a project in its own workspace. `GET …/rounds/{number}` (members; a token holder 404s) — the round in full. `POST …/rounds/{number}/close` `{close_note?, picks?}` (editor+) — applies staged decision edits, then creates and approves ONE task on the board's project (one agent turn); a second close or an unpicked disagreement is 409. `POST …/rounds/{number}/consume` `{run_id}` (editor+, the agent's PAT) — refuses while any note is unanswered; opens round N+1. `DELETE …/notes/{note_id}` (editor+) — remove a note from the OPEN round (409 for one in a closed round).
- `POST /api/storyboards/{slug}/decisions/{key}/edit?t=` — `auth=None`, self-enforcing like the read: confirm / change / write in / undo one decision. Inside an open round every edit is staged (a link holder needs `suggest`, else 403); outside one only a member may (409), and a review-gate row needs editor+. 422 invalid, 409 conflict.
- `GET /api/storyboards/{slug}/notes` — Notes left on the board, members only (a share token never grants it). Never returns `author_email`; refuses a real board exactly like a missing one. `StoryboardOut.is_member` tells the page whether to fetch.
- Act identity is `Act.key` (from the title, or declared `key:` in YAML), never the row id — both write paths recreate acts. One derivation: `apps/storyboards/act_keys.py`.
- Authoring: `manage.py import_storyboard storyboard.yaml --workspace <slug>` — idempotent per `(workspace, slug)`, preserves the share token.

### Huddles (`apps/huddles`, mounted at `/api/huddles`) — derived, no storage
A huddle is agents syncing in rounds, led by one of them (canopy `huddle`; spec in canopy `docs/superpowers/specs/2026-10-06-huddle-design.md`). Derived from the leader's anchor turn (`origin_ref.kind == "huddle"`, `cli_session_id = huddle:<id>`), round turns (`origin_ref = {kind: huddle_round, huddle, round, member, attempt}`), each member's fenced ```` ```huddle ```` JSON reply (round turn close-out, else a filed close-out, else its transcript), and board tasks whose `source_url` ends `/huddles/<id>`.
- `GET /api/huddles/?agent=&limit=50` — Huddles you can see, newest first; `agent` keeps those it led or joined. Each: type, team, leader, members, `rounds_dispatched`, `finished`, `outcome_count`.
- `GET /api/huddles/{huddle_id}` — A cell per (member, round), latest attempt only, plus `projects` (the proposed projects whose `source_url` is this huddle's page, each the same `ProposedProjectOut` card the project page serves), `tasks` (the tasks it proposed in its check-in's project, each a `ProposedTaskOut` card), `outputs` (loose tasks — huddles filed before proposed projects), `checkin` (`{id, name, project: {agent, ref, name, status, url, workspace}, channel_name, lead_email, run_id, read}` when the anchor's `origin_ref` carries a check-in run — `checkin_run`, or the older `run`/`group_run` — else null) and `deadline_at` (earliest round-1 dispatch + 90 min). Prompts, parsed blocks and the leader's `summary` only where `turn_access.can_read_turn_content` allows, else `content_hidden: true`. A block naming another huddle/round is ignored with `reply_error`. The shapes are a contract with `canopy huddle await/status/resume`.

### Project check-ins (`apps/huddles/checkins.py`, `checkins_api.py`) — spec `docs/superpowers/specs/2026-10-17-project-check-ins-design.md`
The PROJECT is the organizing unit; a check-in is a recurring meeting on it: `ProjectCheckin` (project, name unique per project, topic, lead, optional Slack channel, agents ⊇ `project.agent`, a 1:1 `AgentSchedule` on `project.agent`) and `CheckinRun` (`checkin` SET_NULL, `project`, a `participants` snapshot, `tasks_proposed`; `awaiting_confirm → reading → running → done`, or `skipped`/`expired`/`failed`). One agent → `format: solo`; more → `huddle`, led by the project's agent. **A check-in's channel is read only when its lead presses Confirm on the run's announcement in Slack** (`slack.ingest.start_group_read`, called only from that click); no route here can start a read (`tests/test_project_checkins.py::test_no_api_or_web_path_starts_a_read`). A check-in **without a channel** reads nothing: firing queues the agent's turn directly (no Slack post, no Confirm).
- `GET|POST /api/agents/{slug}/projects/{ref}/checkins/` · `GET|PATCH|DELETE …/checkins/{name}` · `POST …/checkins/{name}/run-now` (202). Reads: members. Writes: the project's `owner_user`, or a workspace owner/admin (`integrations`) — putting a NEW channel on the agent's read list is owner/admin only, and an agent's own login can't add one to its own list, but any writer reuses an entry already there (`added_allowance` false; never removed by the check-in). Save checks, refusing with a plain reason: the lead is a workspace member (and, with a channel, in it: `users.lookupByEmail` + paged `conversations.members`); `project.agent` may RUN every other agent (`topology.can_run`). Other agents become `checkin` participants, the lead a `manual` one. Delete keeps the runs. Run now announces (or, with no channel, queues the turn) — it never reads.
- `GET /api/agents/{slug}/projects/{ref}/checkin-runs` — the project's timeline, newest first, each run with `tasks` (what it proposed, live, with `spawned` projects) and `projects` (a pre-check-in huddle's proposed projects, by `huddle_id`). `GET /api/checkins/` — every check-in in your workspaces (navigation).
- **Firing.** `fire_schedule` / `run_schedule_now` on a check-in's schedule create the run (idempotent per slot; `read_since` fixed at announce: the check-in's last read end, or one cadence back), re-check lead and agents (a failure marks it `failed` + an Event, nothing posted), and with a channel post the announcement with Confirm/Skip; `POST /api/harness/schedules/{id}/fire` answers `202 {announced, run_id, status}`. Only the lead's click counts; 24 h unconfirmed → `expired` (`checkins.expire_due` on the channel-ingest loop). Confirm reads for `project.agent` with `pending_ask={"checkin_run": id}` (an older `group_run` key still lands); `deliver_read` cuts the transcript to `read_since`, skips canopy's own posts, stores the material, moves the read mark and queues the turn: prompt `<schedule prompt> --checkin-run <id>`, `origin_ref {kind: checkin_run, checkin, checkin_name, run, project, slot, schedule_id, schedule_name}`, key `checkin-run:<id>`, never late-slot-skipped.
- `GET /api/checkins/runs/{id}` (member, or the project agent's login; includes `material`) · `POST /api/checkins/runs/{id}/finished` `{huddle_id?, result_url, summary, tasks_proposed?}` — the project agent's own login only; 409 unless `running` (idempotent once `done`); `tasks_proposed` defaults to the tasks filed with this `run`. Posts ":white_check_mark: done — N proposed tasks: <link>" in the thread.
- `/api/huddle-groups/*` is gone (404); a run is read and finished only through `/api/checkins/runs/{id}`.
- **Outputs are proposed TASKS** (`apps/agents/proposals.py`): `POST /api/agents/{slug}/projects/{ref}/tasks/propose/` `{title, why, done_when, plan[], partners[], source_url, run?, new_evidence?}` → one `suggested` task (`origin_ref {kind: checkin_proposal, checkin, run, runs, huddle_id, done_when, proposed_at}`), its plan as child tasks, a linked task per partner; 201 created / 200 revised (same open title: backings go stale) / 409 declined before without `new_evidence`. Start/Decline are the task's own approve/decline, by the project's owner, the check-in's lead, or `projects.decide`; 14 days undecided → declined "not taken up". Backings: `GET|PUT|DELETE …/projects/{ref}/tasks/{task}/backings/…` (`me/`, `agents/{agent}/`) — `ProjectBacking` is on a project OR a task. `AgentProject.spawned_from` (a task): `projects/propose/ from_task: "<agent>/<ext_id>"`, or `PATCH …/projects/{ref}/ {spawned_from}`.

### Mail (`apps/mail`) — workspace email domains
Product tier, removable (`docs/architecture/mail.md`). With `MAIL_ENABLED` off only the add, send/reply and inbound paths refuse (add and send 503; inbound is acknowledged `dropped:mail-off`); reads, routes and removals still work.
- `GET /api/mail/domains/{workspace}` (member) · `POST …` (`integrations`) — A workspace's domains with DNS rows and status, plus list-level `can_manage` (`integrations` here); add one (409 if the name is already owned anywhere, unless the holder is still `pending` past `MAIL_PENDING_DOMAIN_TTL_DAYS` and SES confirms it never verified, which is released first).
- `POST /api/mail/domains/{workspace}/{domain_id}/refresh` (member) — Re-check DNS and SES verification now. When SES gave up verifying (DKIM or MAIL FROM `FAILED`) and those records check out in live DNS, it also restarts SES verification (at most every 10 min per domain, audited as a setting); `restart_note` says what it did. Every domain output carries `verification_error` (why SES stopped verifying, `""` otherwise).
- `PATCH /api/mail/domains/{workspace}/{domain_id}` (`integrations`) — `daily_send_cap`; `unsuspend: true` re-enables a suspended domain (saves only the fields it changes, so a concurrent auto-suspension is not undone). `DELETE …` removes the domain, its routes and its SES identity; threads and messages are kept.
- `PUT /api/mail/domains/{workspace}/{domain_id}/routes` (`integrations`) — Create or update a route by `local_part` (`*` = catch-all; kind `agent` | `forward` | `drop`; a forward goes only to a workspace member's login email; the catch-all cannot be `agent`, 422). `DELETE …/routes/{route_id}` — the address stops receiving mail; its threads and messages are kept.
- `PUT /api/mail/domains/{workspace}/{domain_id}/shares` (`superuser`) — `{workspace, daily_send_cap?}`: let that workspace and every workspace below it hold addresses on the domain (`{workspace}` is the domain's own; the caller need not be a member). `DELETE …/shares/{share_workspace}` stops it; the shared workspace's routes go inert, nothing is deleted. The list then includes shared domains for each covered workspace with `owned: false`, `owner_workspace`, no DNS records, only that workspace's routes, and its own `daily_send_cap`; `can_share` and `shares` are answered for superusers on an owned domain. A route on a shared domain is first come, first served (409 when another workspace holds it) and may not be the catch-all or a role address (422).
- `GET /api/mail/resolve?address=` · `?thread=<uuid>` (authenticated) — `{backend: "ses", workspace, agent, address}` only if the caller is a member of the address's (or the `MailThread`'s) workspace, else 404 (the canopy CLI then uses Gmail; a Gmail thread id is 404); neither param is 422. For a thread, `address` is the thread's own snapshot.
- `GET /api/mail/agents/{slug}/mailbox` (member) · `PUT …` `{address}` (owner or agent admin) — Where `Agent.email` lives (`kind` hosted | google | none, `live`, `route`), plus `addresses`: every address the agent has, `[{address, backend: "ses"|"gmail", primary}]` — its own (`primary`), its enabled agent routes, its Gmail push mailboxes, lowercase, each once. A second address is just another `kind: agent` route (`PUT …/routes` above). The PUT sets `Agent.email` and routes it at once when it is on a hosted domain and the caller has `integrations`.
- `GET /api/mail/threads/{workspace}?agent=&archived=` (member) · `GET …/{uuid}` — Threads and one thread's messages (attachments as short-lived presigned URLs; each message's SES `verdicts`); `counterpart` is the newest message's other party on both; `address` is the thread's own snapshot, `agent` is `""` once its route is gone. With `agent=`, `agent_address` is the agent's default From here: the route for `Agent.email`, else its first non-catch-all route by domain then local part.
- `POST /api/mail/threads/{workspace}/{uuid}/reply` · `POST /api/mail/send/{workspace}` (`agent.work`) — Reply in a thread (from the thread's route address) / start one (from `from_address` — one of the agent's enabled, live routes in this workspace, case-insensitive, else 422 "not one of this agent's addresses" — or by default from `agent_address`); enforces the domain's status and `daily_send_cap` (under a row lock); a reply with no `to` goes to the newest inbound message's Reply-To when it is on the sender's domain, else its sender (the thread detail's `default_reply_to`); also needs `access.decide` FULL on the agent. A reply on a thread whose route is gone or disabled is 409. `POST …/threads/{workspace}/{uuid}/state` (`agent.work`) — `{unread?, archived?}` (409 once the route is gone).
- `POST /api/mail/ses/inbound/` · `POST /api/mail/ses/events/` — SNS doors, `auth=None`, allowlisted in `apps/common/middleware.py`, self-enforcing: the SNS signature and topic ARN are verified before the body is read. A 4xx fetching the signing cert or SubscribeURL is 404; a network error, timeout, TLS error or 5xx is 500 so SNS retries. Inbound stores/forwards/drops (500 only for a transient failure SNS should retry); events update delivery status and the reputation guard, counting a redelivered event once. A verified Notification whose Message is not a JSON object is acknowledged 200 `{ignored}` and logged at INFO.
