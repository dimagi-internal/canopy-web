# API: chat sessions and shared sessions

The rules behind the routes for multiplayer chat sessions (the live entry point) and shared Claude Code transcripts. Part of the [api surface](api-surface.md) topic. Methods, paths, fields and status codes are in the routers (every route declares its gate with `@gate(...)`, its docstring is the OpenAPI description) and the OpenAPI schema (`/api/docs`); this page keeps what they do not make obvious.

## Chat (`apps/canopy_sessions`)
A `Session` is a durable conversation with an agent (or, agentless, with a repo checkout), workspace-tenanted. A send enqueues a session `Turn`; a session-capable runner executes it; `Message` rows are a projection. Start reading at `apps/canopy_sessions/api.py` (the one router and its helpers; the route modules `api_read`, `api_lifecycle`, `api_transfer`, `api_people`, `api_attachments`, `api_secrets`, `secrets_api`, `api_page`, `app_views_api`, `lineage_api` import it, and import order decides which literal path wins over `/{session_id}`), `apps/slack/session_api.py` (the `/slack/*` routes), `routing.py` for WebSockets. How a chat is recorded, turn status, drafts, liveness and push: [chat-sessions.md](chat-sessions.md); blocked-agent dialogs: [blocked-agent-menus.md](blocked-agent-menus.md); the embedded widget: [embedding-internals.md](embedding-internals.md).

### Access
One rule, `apps/canopy_sessions/access.py`, asked by every entry point: [tenancy-session-access-and-retention.md § The chat-session ACL](tenancy-session-access-and-retention.md#the-chat-session-acl-ci-enforced), pinned by `tests/test_session_acl.py`. A non-member gets 404, not 403 (`api.py::_session_or_404`). Reads declare `@gate("session-acl")`; writes add `kind="conversation"` and resolve the session with `write=True`.

### Create (`api_lifecycle.py::create_session`)
- `agent_slug` XOR `project` (422 for both). A delegated site may open a chat only with an agent it offers and never an agentless one (404).
- `metadata` is an allowlist: `services.host_metadata` keeps `HOST_METADATA_KEYS` and `x_*` keys and drops everything else, `fork` included. `embed_app` and a site's runner requirements are server-owned: taken from the delegated token, never the body.
- Under a site token that requires `sensitive_data`, someone with no vault key is refused 422 before anything exists (`conversation_keys.check_holder`), and the CLI must be one of `clis.SENSITIVE_CLIS`. A `cli` the agent is not set up for is 422 (`clis.refusal`). An optional `conversation_key` is a key pair made in the starter's browser and wrapped to their current vault key (422 otherwise): if the conversation is or becomes sensitive, canopy-web never sees the private half.
- `runner_id` pins the first turn only if `placement.may_place` allows it (403 otherwise): for an agent chat its admins or whoever administers that box, for a project chat only the box's administrator. The same rule gates `send`'s and `place`'s `placement`. Which box takes a first turn: [chat-sessions.md § Which box takes a chat's first turn](chat-sessions.md#which-box-takes-a-chats-first-turn).

### Reading
- The list is capped (`limit` <= 500, no paging) and ordered waiting-on-you, running, most recent; `GET /search` walks every session by keyset cursor (`until` freezes the set). "Active" is derived on every read, never stored ([chat-sessions.md § Session liveness is polled](chat-sessions.md#session-liveness-is-polled)). `of_user` only narrows the sessions you can already see; it grants nothing.
- `GET /{id}` falls back to the runner `session_key` when no readable session has that id (409 if it names several). A sensitive conversation's rows carry `sealed` envelopes and `sealed_key` (your own wrap of its key plus your keyset, for the browser to open: `frontend/src/vault/sealedChat.ts`); both are null for any reader `sensitivity.reads_content` refuses (MCP, a PAT, someone not in it).
- `GET /{id}/context` and `/turns/{turn_id}/context` hold no prompt, transcript, person block or credential value. In a sensitive conversation only its own people on its chat surfaces get `turn_context` (everyone else `withheld`); a turn's record follows `turn_access.can_read_turn_log` ([access-turn-context.md § Seeing it](access-turn-context.md)).
- `GET /asked-review/messages` is for a turn in a review chat, with its caller token only; it takes no session id and is 404 when the ask was withdrawn or expired, the session is sensitive or content-deleted, or the request is anything else (`api_read.py::read_asked_session`).
- `GET /{id}/export` is the starter's only, 403 for an embedding site and for a sensitive conversation (`api_read.py::export_session`).
- `GET /{id}/human-inputs` excludes everything a person did not type (agent output, harness rows, program-delivered prompts, Claude Code's own user records); `transcript_read.human_inputs` has the rules.

### Deleting your own session's content (`DELETE /{id}/content`)
The person whose session it is, as themselves, and nobody else: an agent's login, a turn's token, a site token and every admin get 403 (`access.owns_words`, `acting_person.refusal`). 409 while a turn works or it is moving, a fork holds a copy, or anyone else is or was in it. It does not reach copies canopy does not hold. Rules and what survives: [tenancy-session-access-and-retention.md § Deleting your own session's content](tenancy-session-access-and-retention.md#deleting-your-own-sessions-content); `api_lifecycle.py::delete_session_content`.

### Sensitive (private) conversations
Defined in [tenancy-sensitive-conversations.md](tenancy-sensitive-conversations.md); the route-level rules:
- A sensitive session's `title`, `opening` and `last_reply` are always "" in rows (`session_row.py`), and setting a title is 422 (`set_session_title`); it is listed but its words are not.
- Forking one is the owner's act (403 `NOT_OWNER_FORK`), because the fork carries the key, its people's wraps and the agent's memory.
- Attachments: only its own people at a browser upload (canopy's chat page, or the panel's frame with its delegated token), never a site's backend, a token or MCP (422 `ATTACHMENTS_NOT_HERE`; also 422 while it has no key). The people's copy is sealed in the uploader's browser to the conversation's key (`POST /attachments/{id}/sealed`: once, by the uploader, before the send); the plaintext copy the agent fetches is held only until its turn fetches it or ends, under a key naming no file, and the plaintext content route serves it to nobody (`api_attachments.py`, `private_attachments`).
- Participants (`api_people.py`): `POST /api/canopy-sessions/{id}/participants` takes a `wrap` of the conversation's key to the newcomer's vault key, required unless they already hold a current one (409 `wrap_required`), checked against their current vault-key thumbprint (422). A role change keeps a current copy whatever `wrap` says. `GET /participants/recipient` is the key to wrap to (409 `no_vault_key`). `POST /api/canopy-sessions/{id}/key-copies` repairs someone already in it: an editor or the owner holding a current copy, to a person with no copy for their current vault key (409 otherwise; nobody overwrites a current copy). `DELETE /api/canopy-sessions/{id}/key-copies/mine` sets aside your own copy that will not open. Removing someone deletes their wrap but does not rotate the key (they may have kept what they read). The owner cannot be removed; anyone may remove themselves.
- Join requests (`join_requests.py`): anyone who can see a private conversation listed and is not in it may ask (409 for an ordinary conversation or one they are in; 429 within the hour after a declined or withdrawn ask); the open list is for its own people only. A request never carries anything said. Adding the person settles their request.
- `my-vault-key` and `my-keys` are self only. `my-keys` is for a chat surface and replaces copies only with ones wrapped to your current key.

### Participants and sharing
`POST /api/canopy-sessions/{id}/participants` is for the chat's owner, or the owner of the agent it is with when they are in it (`access.can_add_people`); the agent's owner may add someone new but cannot change an existing person's role (409). The teammate must already be in the chat's workspace. Role is `editor` or `viewer`.

### Lifecycle
- `archive`/`unarchive` are idempotent and never destructive. Archive cancels queued and running turns and marks `Session.HAND_ARCHIVED_KEY`, so a laptop's report does not revive it; unarchive clears only that written half, a stale runner session stays out of `active` until reported again. A send into an archived session unarchives it (`control.py`).
- `close` ends a session: relayed to the runner when one reports a task for it, else cancel and archive. `reset` drops the derived `Message` rows and re-derives them from the runner's transcript; `Turn`s and their ledger are never touched; bulk reset deletes runner-discovered sessions with no binding only under `prune_ghosts`, never a human-started chat, and only sessions you may act in. For `close`, `reset` and `answer-menu` a refusal is a 200 with `ok:false` and a `reason`, not a 4xx, because the dialog or runner state goes stale between render and click.
- `fork` needs a cloud runner or a laptop on the `claude-cli` runtime and a message from after the last transfer (422), and is 409 when the cut falls in a running turn (`placement.fork_session`).
- `move` files the session in another workspace where you are editor or better; only the session's own person (creator of a web chat, owner of the runner a session was discovered on); an agent's session cannot move (422). Participants not in the target are removed; a re-report never moves it back (`filing.move`).
- A typed title is never replaced by the runner's task name or autotitle (`harness.session_sync._title_is_derived`).

### Transfer (`api_transfer.py`, rules in [chat-sessions-recording-and-transfer.md § A transfer carries the work](chat-sessions-recording-and-transfer.md#a-transfer-carries-the-work))
- Whose box decides: onto a runner you administer, or between two runners with the same owner, the move happens now (`status: moved`); onto someone else's it becomes a request an administrator of the target must approve (`status: pending`), because it spends their machine and subscription. Approval is re-checked at decision time.
- 409 (not 422) while a turn executes or the runner reports the engine working (`placement.busy_reason`), or another request is pending; stop the session and retry. Approving while a turn executes is also 409 and the request stays pending.
- `transfer-all` moves each session as its own transfer; one that cannot move is reported `refused` and never stops the rest. Only sessions you may move (`access.may_move`).
- `place` re-pins the oldest queued turn only; it does not move the binding or the work (use `transfer`). `handoffs/{id}/restore` restores a late snapshot only into a worktree with no uncommitted changes; 409 while a turn is queued or running.

### Secrets shared with a chat (`api_secrets.py`, `secrets_api.py`)
Sealed in the sharer's browser to the bound runner's approved ECDH device keys; canopy-web takes `zks1` only (plaintext `value` is 422 `sealed_only`; stale recipients 409 `stale_recipients`) and cannot open it. A secret lives 30 minutes from sharing (`secrets.TTL`). Sharing from a browser needs a passkey step-up; a token is allowed. The agent half is bearer-only and keyed by `X-Canopy-Chat-Key` (minted when a runner claims the chat's turn): no route takes a chat id, so a key reaches only its own chat's secrets; a CLI that does not ask for `sealed=true` gets 409 `update_canopy`; no or a wrong key is 404. The same key scopes the MCP page tools to that chat's page (`mcp/chat_scope.py`). Full mechanics: [chat-sessions-recording-and-transfer.md § Secrets shared with a chat](chat-sessions-recording-and-transfer.md#secrets-shared-with-a-chat-sealed-to-the-machine-running-it).

### Page contract and MCP Apps Views
- Page contract (`api_page.py`, [embedding-a-canopy-agent.md](embedding-a-canopy-agent.md)): actions and state are replaced wholesale and empty means no page attached; a state over the server cap is 422 `too_large`; `page-actions/invoke` blocks until the page answers and fails with `no_page`, `unknown_action`, `bad_arguments` (422), `timeout` or `refused` (409) (`page_actions.py`).
- Views (`app_views_api.py`, `apps/mcp_apps_host/mcp_apps_views.py`): a rendered View's browser plumbing, run as the person looking at it. Every route is excluded from MCP and refuses a PAT (`browser_only`), so the model can never reach an app-only call. `call`, `context`, `message` need a write role plus the viewer's own host grant; `read` and `subscribe` need the viewer's own grant and `may_read` (403 `no_grant` otherwise). In a sensitive conversation `resource` returns `tool_input: {}` plus the sealed `tool_input_sealed`, and its `tool_result` is the host's resource links alone. A subscription is held by canopy for 24 h, at most 100 per conversation (429); the host's signed `POST /api/sites/resources-updated` reaches the View as `app.resource_updated`, a URI and never data.

### Slack and lineage
`apps/slack/session_api.py`: an agent's own login may act only on the conversation of a turn it is running (`turn_id`, `access.own_turn_session`), while that turn is in flight; a person needs owner or editor access. `slack/offline` takes the work offline with THAT turn's person, never one the agent names; 403 for a private conversation. `POST /lineage/report-back` (`lineage_api.py`): a child session reports into a turn in its parent asked by the child's person; 409 without a parent or with a closed one, 403 when that person cannot write in the parent.

## Sessions (`apps/session_sharing`) - shared Claude Code transcripts
Token-shared transcripts (`/canopy:share-session`) at `/api/sessions` and `/api/share`; start at `apps/session_sharing/api.py`. Shared sessions and arcs carry their own rotatable `share_token`, separate from walkthrough/review visibility. Sharing needs editor (`content.write`) in the workspace it lands in (`_share_workspace`). Owner-only management and `rotate-token` (kills the old `/w/<ws>/share/<token>` link). `GET /api/share/{token}?ws=` is the one public (`auth=None`) read, exempted in `LoginRequiredMiddleware`; a `ws` that does not match the share's workspace is 404 (`_at`).
