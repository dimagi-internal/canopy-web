# API: people, contacts, attention and engagement

Rules that cross the routes for people and contacts, the HCP service, asks, attention and alerts, user-level views, huddles, engagement and project check-ins. Part of the [api surface](api-surface.md) topic. Method, path, fields and status codes are the handler signatures and docstrings in the router files named below, and `/api/openapi.json`; this page keeps only what those do not say.

## The HCP service (`apps/contacts/hcp_oauth_views.py`, `hcp_api.py`, `hcp_clients_api.py`, `hcp_oauth.py`) — OAuth for apps canopy does not operate
Design, flow and judgment calls: [`hcp-service.md`](hcp-service.md). The module docstrings of `hcp_api.py` (whose instance, who is asking) and `hcp_oauth.py` (tokens, reach, switches) state the rules.
- An `hcpat_` access token is verified by the bearer middleware and opens `/api/hcp/v1/` and nothing else (`apps/tokens/middleware.py`); the person-only routes (audit, grants, export; `hcp_api.py::_person_principal`) refuse it, an agent's login and a caller token alike, and are not MCP tools; `hardDelete` is the person's only. Rate limit per client: `hcp_oauth.RATE_LIMIT_PER_MINUTE`.
- An agent reaches only the person who STARTED the turn it names (`?turn=`), under the client's grant; a missing entry and an unauthorized one are the same 403.
- The person's own switches bound every client (`hcp.require`); the service is internal only (`settings.HCP_SERVICE_AUDIENCE`, read in `hcp_oauth.py` and nowhere else).
- The client registry `/api/hcp-admin/clients` is superusers only and never MCP: an agent registering an app that then asks people for context is the escalation ruled out. The webhook secret is returned once.

## People (`apps/contacts/people_api.py`, mounted at `/api/people`) — the fleet brain
The module docstring states the rules (all applied in `apps/contacts/people.py`): facts are per workspace and a person a workspace does not deal with (`people.known_in`) is 404 there, so a guessed id or address confirms nothing across tenants; the subject sees everything (`GET /me/`); every read is logged (`PersonAccess`); conversations are the one read of turn content, for the agent that had them. Fuller rules: [`access-sessions-and-people.md`](access-sessions-and-people.md) § What agents know about a person.
- **"Person-only" is `people_api.py::_the_person_themself`**: an agent's login, a caller token (a session speaking for a turn) or a non-human account gets 403, and the memory switches, grants, collections, addresses and session-review routes all use it. The one `/me` read a caller token also reaches is `list_my_session_reviewers` (the agent asking "has my asker enrolled?"), narrowed to that agent. The embed read `apps/embedding/embed_api.py::embed_session_memory` is delegated-token read-only: a site acting for its visitor may show what applies, never change it.
- **An agent never bulk-reads a person.** `get_person` is 403 for an agent's login ("Agents recall through HCP": `hcp_searchPreferences` for the turn it serves). `list_person_addresses` allows an agent because the person declared those addresses; `list_person_conversations` is the agent's own login or its admins, and an admin gets only turns `turn_access.can_read_turn_content` already shows them.
- **Facts** (`add_person_fact`): `kind` is a closed set; `source_turn_id` and `project_id` must belong to that workspace (a personal project is refused: a fact is read beyond a personal project's readers); an agent's login is refused 403 unless the person lets agents learn about them in that turn (`hcp.may_record`), and a zero-data-retention refusal is 403. Retract (`retract_person_fact`) is the subject, the asserter or an admin of the fact's workspace; anyone else gets 404.
- **Session review**: `SessionReviewGrant` is the session ACL's leg 5 ([`tenancy-session-access-and-retention.md`](tenancy-session-access-and-retention.md) § The chat-session ACL); `SessionReviewAsk` (one session, 7 days, withdrawable at once) is in [`access-sessions-and-people.md`](access-sessions-and-people.md) § Asking a coach to review one session. `list_session_granters` answers only for an agent's own login (`viewers.viewing_agent`: never a caller token or an HCP client) and is empty for anyone else.
- **Memory page viewers** (`apps/contacts/viewers.py`): an agent's own login the person named may read their memory page read-only; every other caller gets 404 so an id confirms nothing.
- **Contacts' own HCP** (`/api/contact/hcp/…`, `contact_hcp_api.py`): only on a site a superuser trusts for email (`AppCredential.asserts_verified_email`). Every route needs a single-use FRAME PROOF minted only to canopy's own frame (HttpOnly, partitioned cookie plus `Sec-Fetch-Site: same-origin`), so the site that minted the contact token cannot act with the token alone. An address that belongs to a canopy account is refused. [`hcp-service.md`](hcp-service.md) § Contacts.

## Asks — a task that asks a person something
An ask is a property of a task, not a noun (`AgentTask.ask_kind` `review|question`, `ask_body`, `ask_closed_at` in `apps/agents/models/work.py`). It has no routes of its own: raised through the task routes, answered by `api_board.py::act_on_task`.
- **Open until an action closes it.** Approving or answering a closed ask is 409.
- **Act and dispatch are one transaction** (`services/task_actions.py::act`): a bad `on_approve` spec is a 422 and the ask stays open and retryable, because committing first would close an ask whose work never ran. The row is re-read under a lock so two tabs cannot dispatch twice.
- **Waiting on you is a filter** (`?waiting=me` on the task list; `/supervisor` and an agent's Tasks page render the same rows). Producers raise real asks (`harness/schedule_turns.py::_raise_schedule_nag`, run gates, task reviews). Any task row moving marks `task://` dirty (`apps/agents/signals.py`), so a page showing tasks re-reads.

## Attention (`apps/attention`, mounted at `/api/me/attention`) and alerts (`alerts_api.py`, `/api/me/alerts`)
Both are user-level views: read once per organisation (`wsvc.each_organisation`) and labelled with `organisation` ([`roles.md`](roles.md#a-user-level-view-reads-each-organisation-on-its-own)).
- **Attention items come from the app that owns the thing**: `apps/<app>/attention.py::items`, registered by dotted path in `apps/attention/sources.py::REGISTRY` (a source that raises is logged and skipped, one broken subsystem never blanks Home). Each applies its own rule: tasks by the board's `filter_tasks(waiting="me")`, chats by the session ACL, access requests by `members.manage`. Clients branch on `state` (`apps/attention/types.py::STATES`); `reason` is display text. `running` is never quiet or hidden.
- **Hiding takes things off the caller's own list and nothing more** (`hide_attention`): no task is decided, no chat ended, nothing sent, the agent is not told.
- **Alerts: a row you may not see is a 404 by id, never a 403** (`alerts_api.py::_visible`): the alert's workspace must be one the caller is in AND its source must offer them an action (for a dismissed one, `dismiss`). History (`_history_visible`) is the audit trail and outlives the alert. `act_on_alert` re-checks the offer on every call (409 `action-not-offered`; 409 `action-failed` when the handler refused, nothing changed); a link action only records that it was followed. Model, sources and lifecycle: [`alerts.md`](alerts.md).

## User-level views (`/api/me/…`)
`/api/me/sessions/`, `/tasks/`, `/agents/`, `/projects/` run their list once per organisation and re-sort ([`roles.md`](roles.md#a-user-level-view-reads-each-organisation-on-its-own)). The order and filters are those of the list each wraps.

## Huddles (`apps/huddles/api.py`, `/api/huddles`) — derived, no storage
`apps/huddles/services.py` (module docstring) says what a huddle is: derived from a leader's anchor turn, its round turns (`origin_ref.kind`), each member's fenced `huddle` reply and the board tasks whose `source_url` is the huddle page. Every read goes through the caller's visible-turn queryset, and a cell's prompt and reply only where `turn_access.can_read_turn_content` allows (the `turn-content` gate); a caller who may only see THAT a round ran gets its status and nothing else. The response shapes are a contract with the canopy CLI (`canopy huddle await/status/resume`; see `schemas.py`), so change them with the CLI.

## Engagement (`apps/agents/api_engagement.py`, `/api/engagement`) — what people do
One append-only `EngagementEvent` table written only through `apps/agents/engagement.py::record`: an unknown `kind` or `surface` raises (a typo fails its test), any other failure is logged and swallowed so telemetry never fails the act it records. The view beacon counts once per person, per object, per UTC day and is 404 for anything the caller cannot see; agent logins are excluded from the summary's unique people.

## Project check-ins (`apps/huddles/checkins.py`, `checkins_api.py`)
The module docstrings state the run's life (announce, click, `deliver_read`, finish) and the routes' roles.
- **A check-in's Slack channel is read only when its lead presses Confirm on the announcement** (`slack.ingest.start_group_read`, called only from that click); no route here can start a read (`tests/test_project_checkins.py::test_no_api_or_web_path_starts_a_read`). A check-in without a channel reads nothing: firing queues the agent's turn directly. `run-now` announces (or queues); it never reads. Unconfirmed runs expire after `checkins.EXPIRE_AFTER`.
- **Writes** are the project's owner or a workspace owner/admin (`checkins.may_write`); members read. Putting a NEW channel on an agent's read list is owner/admin only (`INTEGRATIONS`), and the agent's own login cannot add one to its own list; any writer reuses an entry already there, and delete releases only an entry the check-in itself added (`added_allowance`). Save refuses with a plain reason when the lead is not a workspace member (nor in the channel) or the project's agent may not run every other agent (`topology.can_run`). A personal project has no check-ins.
- **`POST /api/checkins/runs/{id}/finished` is the project agent's own login only** (`_finish`: 403 otherwise; 409 unless `running`); `update` only drafts the project's status update for a person to publish.
- **Outputs are proposed TASKS** (`apps/agents/proposals.py`, module docstring): a `suggested` task with `origin_ref.kind == "checkin_proposal"`, its plan as child tasks, a linked task per partner. Start and Decline are the task's own approve and decline; a backing (`ProjectBacking`) is a signal, never a gate. Re-proposing an open title revises it; one declined before needs `new_evidence`.

## Contacts (`apps/contacts/api.py`, `/api/contacts`) and the contact surface (`contact_api.py`, `/api/contact/`)
- **Contacts**: people a workspace knows who are not members; recording one grants nothing. There is deliberately no create route (contacts arrive by writing to canopy: `services.record_inbound_sender`). `patch_contact` needs `content.write`, and another tenant's id is 404 before 403 so existence never leaks.
- **`/api/contact/` is the whole of what a contact token can reach, and the prefix is the security boundary.** A contact token sets no `request.user`, so `LoginRequiredMiddleware` refuses every path except the allowlisted prefixes, and `/api/contact/` is the only one a contact can satisfy. A surface becomes reachable by a contact by being moved here deliberately. `tests/test_contact_surface_is_bounded.py` fails the build if that stops being true. The token is minted at `POST /api/auth/contact-token` from a site's signed assertion.
