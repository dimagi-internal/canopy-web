# Runbook: connecting a system to canopy

What setting up a connected system actually involves, what is self-serve, and —
the part worth writing down — **which state lives only in the production
database** because somebody typed it once.

The host-facing guide is
[`docs/architecture/embedding-a-canopy-agent.md`](../architecture/embedding-a-canopy-agent.md);
this is the operator's side.

---

## 1. The short version

Connecting a **new** system is entirely self-serve, in the UI, by a workspace
owner. There is no shell step and no secret to hand over:

1. The host generates a keypair, keeps the private half, and publishes the
   public half as a JWKS at a URL of its own.
2. A workspace owner opens **`/w/<workspace>/settings/connected-apps`** and
   registers the site: name, site URLs, which of this workspace's agents it may
   offer, and that JWKS URL.
3. The host adds one backend endpoint (mint a visitor token) and one script
   tag.

That is it. Canopy holds only a public key, fetched from the host, so nothing
has to be copied and a rotation on the host's side needs no change here.

**A second workspace** registers the site itself, the same way, with the same
JWKS URL. Registrations are per workspace — there is no shared row and no
custodian (2026-09-24) — so the host must then **name the agent** when it mints
a visitor token (`agent_slug`) and in `canopy.init` (`agent`). A name alone is
ambiguous once two workspaces hold it, and canopy refuses rather than guesses.

## 2. What is already set up (2026-09-24)

| Thing | Where it lives | Reproducible? |
| --- | --- | --- |
| ace-web signs assertions | `CANOPY_SIGNING_KEY`, from Secrets Manager `ace-web/canopy-signing-key` | Wiring is in `deploy/aws/ace-web.cfn.yaml`; **the key value was generated by hand** |
| ace-web publishes its keys | `GET /ace/api/canopy/jwks`, derived from that key | Yes — code |
| canopy trusts ace-web | the `ace-web` **Connected site** row: workspace `connect`, `jwks_url` set, **no** pasted keys, agent `ace`, `resolvable_domains` `dimagi.com` / `dimagi-ai.com` / `dimagi-associate.com` | **No — hand-made prod state** |
| canopy can vouch to a host | `ONBEHALF_SIGNING_KEY`, secret created by CFN | Container is in CFN; **value is deliberately `PLACEHOLDER`**, so the feature is off |
| ACE's declared interface | live state on canopy-web (agent → Overview → Callers) | **No — hand-made prod state** |

### The gap, stated plainly

Three rows above are **typed-once production state that exists in no file**:
the Connected site row, the signing key's value, and ACE's published interface.
Rebuild the database and they are gone; nothing in CI would notice. This is the
same shape as the hand-made IAM grants `CLAUDE.md` complains about under
Deployment — recorded here so it is at least *known*, not so it is fine.

Reproducing them is §4.

## 3. What an operator may still need to do

**Nothing, for ace-web.** It is live and was verified end to end: canopy holds
no key for it, fetches its JWKS, and resolved a real assertion to a canopy user.

Everything below is a "when X happens" step, not a pending task.

### The host rotates its signing key

Nothing to do in canopy. The host publishes the new key beside the old, switches
what it signs with, and drops the old one later; canopy follows by `kid`,
refetching the moment it sees one it does not know.

On ace-web specifically, keep the outgoing public half in
`CANOPY_RETIRED_PUBLIC_KEYS` (pipe-separated PEMs) until canopy's caches age
out — otherwise assertions already in flight fail for the few minutes between
the switch and the refetch.

### The host's JWKS URL goes down

Canopy keeps the last good copy for 24 hours and only refuses when it has never
had one. An ace-web outage therefore does not stop canopy vouching for its
people; a *permanently* broken URL eventually does.

### Turning on on-behalf-of (canopy vouching to a host)

Two steps, in this order, and only when a host is ready to verify:

```bash
# 1. a real key in place of the PLACEHOLDER CFN creates
openssl genpkey -algorithm ed25519 -out /tmp/onbehalf.pem
AWS_PROFILE=labs aws secretsmanager put-secret-value \
    --secret-id canopy-web/onbehalf-signing-key \
    --secret-string "file:///tmp/onbehalf.pem"
# 2. restart the service so the container picks it up, then confirm:
curl -s https://labs.connect.dimagi.com/canopy/api/tokens/on-behalf-of/jwks
# {"keys":[{...}]} rather than {"keys":[]}
```

Until a host verifies those assertions this changes nothing — see §8a of the
embedding guide for why the agent still uses its own credentials.

## 4. Reproducing the hand-made state

ECS Exec is **disabled** on both services, so the way into a running
deployment's database is a one-off task on the live task definition:

```bash
TD=$(AWS_PROFILE=labs aws ecs describe-services --cluster labs-jj-cluster \
      --services labs-jj-canopy-web --query 'services[0].taskDefinition' \
      --output text | sed 's|.*/||')
cat > /tmp/setup.py <<'PY'
from apps.tokens.models import AppCredential, AppCredentialAgent
from apps.agents.models import Agent
from apps.workspaces.models import Workspace

app, _ = AppCredential.objects.get_or_create(
    name="ace-web", workspace=Workspace.objects.get(slug="connect"), revoked_at=None)
app.jwks_url = "https://labs.connect.dimagi.com/ace/api/canopy/jwks"
app.public_keys = []          # the URL is the key source; nothing is pasted
app.save()
app.resolvable_domains = ["dimagi.com", "dimagi-ai.com", "dimagi-associate.com"]
app.save()
AppCredentialAgent.objects.get_or_create(app=app, agent=Agent.objects.get(slug="ace"))
print("ok", app.jwks_url, app.resolvable_domains)
PY
python3 -c "import json;print(json.dumps({'containerOverrides':[{'name':'canopy-web',\
'command':['python','manage.py','shell','-c',open('/tmp/setup.py').read()]}]}))" > /tmp/ov.json
AWS_PROFILE=labs aws ecs run-task --cluster labs-jj-cluster --task-definition "$TD" \
  --launch-type FARGATE --overrides file:///tmp/ov.json \
  --network-configuration 'awsvpcConfiguration={subnets=[subnet-06646effb09be2f42,subnet-08a18eb47b48aff54],securityGroups=[sg-0666a5ed512c97d9d],assignPublicIp=ENABLED}'
# read the output from the task's log stream in /ecs/labs-jj-canopy-web
```

Everything that script does is also doable from the Connected sites page. It is
written down because the ace-web row **predates that page** and carries a
`resolvable_domains` list wider than the page will grant (the page bounds a
domain to the setting owner's own; this row was set by an operator for three).

## 5. Checking it actually works

The only check worth trusting drives the real deployment. From ace-web's
worktree, with its private key:

```python
# signs as the site, exactly as ace-web does, and asks canopy who that person is
jwt.encode({"iss": "ace-web", "sub": email,
            "aud": "https://labs.connect.dimagi.com/canopy",   # canopy's public URL
            "iat": now, "exp": now + 60, "jti": str(uuid.uuid4()),
            "email": email, "email_verified": True},
           private_key_pem, algorithm="EdDSA", headers={"kid": thumbprint})
# POST it to https://labs.connect.dimagi.com/canopy/api/auth/contact-token
```

* `200` with `"kind": "user"` — the person has a canopy account at a resolvable
  domain and arrived as themselves.
* `200` with `"kind": "contact"` — correct for anyone else; no account is ever
  created.
* `401 wrong_audience` — `aud` must be canopy's public base URL.
* `401 keys_unreachable` — canopy could not read the host's JWKS, and had no
  cached copy. Check the URL is https, public, and serves `{"keys": [...]}`.

Passing this with **no pasted key registered** is the thing that proves the
JWKS path is live rather than merely configured.
